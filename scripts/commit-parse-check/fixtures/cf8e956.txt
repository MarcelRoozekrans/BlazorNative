* docs(planning): design phase 13.1 -- type the lengths

Phase-scope design spec for M13's second phase. Three decisions were taken with
the owner and each is recorded with the evidence behind it rather than as a
preference:

Two types, not four. BnLength and BnAutoLength close the auto axis; the negative
axis stays shell-side where YogaLayout.length(negative =) already enforces it.
Four types would double a public surface that freezes at 1.0 to catch a rare
value-in-the-wrong-place rather than a typo class. Recorded as a deliberate
limitation: Width="-8" still compiles.

BnLength? / BnAutoLength?, nullable, null means unset. This is #178/#181 applied
before the fact -- default(BnLength) is a real zero-point length and
default(BnAutoLength) reads as `auto`, either of which would be a struct's
zero-value silently meaning something the author never chose. Nullable closes
both, keeps the null-reset path (and its existing pins) untouched, and makes the
migration mechanical.

BnList<TItem> stays allowlisted, and the reason is upgraded from "deferred to
13.1" to settled: its Height is BnListWindow.Compute's divisor and must be a
point value, which BnAutoLength cannot promise. Its Width is typed here.

Two things were measured rather than assumed. A throwaway Razor probe proved the
DoD's core claim -- 12px, 50%, auto, abc and "100 px" are all compile errors with
no analyzer needed -- and corrected the design while doing it: Razor emits 12.5 as
a double, and double->float is narrowing, so an implicit double operator is
required or every decimal literal fails CS1503. Migration cost was counted across
the repo: 44 numeric literals compile unchanged, 76 @-bound sites change type, and
exactly one literal percentage exists.

The spec also names a gap the phase must close: DefaultStructTrapSweepTests sweeps
Core, Runtime and Device but not Components -- the assembly this phase adds two
public structs to.

* docs(planning): impact analysis for phase 13.1 -- type the lengths

Change Interface refactor, 50 affected files, 7 risks, Medium. The analysis is
mostly a map, but three findings change how the phase must be built.

The three emission mechanisms 13.0 left behind are NOT equally exposed by typing,
and treating them alike is the easy way to get this wrong. Mechanism A (7
hand-written emitters) formats explicitly at the call site. Mechanism C (the
wrappers) is safe for a non-obvious reason: AddComponentParameter forwards a
COMPONENT parameter, so the value stays typed and no culture is ever consulted.
Mechanism B is the dangerous one -- ItemAttributes is a dictionary whose values
land on an ELEMENT and are stringified by the renderer, so a boxed BnLength on a
comma-decimal machine puts "1,5" on the wire and both shells reject it. That risk
does not exist today; this phase creates it. The splat must carry formatted
strings, never structs, and a comma-decimal-culture pin holds it.

The zero-warning pack bar is the release's own validate job -- the gate that made
v0.9.0 an orphan tag. New public types without complete XML docs raise CS1591 and
fail it. 13.0 additionally broke the site build with <see cref> to protected
members under onBrokenAnchors: 'throw'. Both are now written risks with the same
mitigation: full docs, <c> not <see cref>, verified by a clean pack AND npm run
build.

Groups 3-5 deliberately leave the tree non-compiling: the bases and every emitter
must change together, and markup cannot migrate until the types exist. Group 6 is
the first full-suite checkpoint after Group 2, and the order says so out loud
rather than letting someone discover it mid-phase.

Also recorded: five cross-cutting decisions are embedded here because
decision-tracker degraded -- no longterm-memory MCP in this session and no
.squad/decisions.md -- so the plan documents are their only home.

Ten TDD tasks, 61 steps, built from the impact analysis's eight execution groups.

* refactor(samples,tests): migrate markup to the typed length surface

The first fully-compiling tree since Task 3, and the phase's first real
test run. Two migration classes, not one.

MARKUP (6 sample pages). Every page held an `internal const int <N>Dp`
plus a `private static readonly string <N>` that stringified it only to
satisfy the old `string?` parameters. The typed surface makes the
stringifier dead weight, so the alias is deleted and the constant bound
directly -- 24 fields, 72 lines net. The template's `Padding="16"` is an
int literal and needed no edit; verified by compiling BnStarterPage.razor
against BlazorNative.Components rather than by inspection.

DICTIONARIES (~60 sites). Through ParameterView / AddComponentParameter
the value is `object`, so the boxed type must be EXACTLY the parameter's
type. A `string` compiles and throws at first render -- and so does a
raw `float`: the implicit operators are compile-time only and do not
exist at unbox time. That second class was the entire content of the
first red run (5 failures, all `Padding = 16f`, one of them commented
"typed (7.1)"), and it reached beyond the solution into ConsumerSmoke
and into BnCameraDemo.cs, a hand-written BuildRenderTree the build
could never flag.

Semantic, not mechanical, where the value carries meaning:
`Basis = "auto"` -> BnAutoLength.Auto (not zero, which collapses the
node); `MaxWidth = "50%"` -> BnLength.Percent(50) (not 50 points); and
ItemSurfaceDropHost's cycle array keeps its `null` as BnAutoLength?[],
because that null is the unset state the drop/restore test exists for.

No wire value moves. No expectation was adjusted to make a test pass --
verified mechanically: not one lower-case wire-table line is added or
removed anywhere in the diff. No shell file, frame table or
wire-vocabulary entry is touched.

.NET suite: 1049 passed / 0 skipped / 0 failed (27 + 136 + 886). The
ci.yml gate still reads 1032 and is Task 9's to rebase.

* test(components): pin that every length parameter is DECLARED nullable

Spec 3.3 spends a page arguing that a length parameter must be BnLength? /
BnAutoLength? and never bare -- default(BnLength) is a real zero-POINT length
and default(BnAutoLength) reads as `auto`, so a parameter nobody assigned means

value re-centres the node.

bare BnAutoLength left the whole suite green. That is the safety-claims-without-

* refactor(components): drop the hand-lifted ternary on BnList.Width

`Width="@(Width is { } w ? (BnAutoLength?)w : null)"` spelled out by hand what
the language already does: C# lifts the user-defined BnLength -> BnAutoLength
conversion to its nullable form, so BnLength? -> BnAutoLength? is implicit and
maps null to null. `Width="@Width"` compiles and means the same thing --
compiled, not reasoned about, and covered by BnListDemoTests asserting
width="300" on the viewport node.

The comment left behind records the second finding: the neighbouring
(BnAutoLength?) casts are not REQUIRED either -- a user-defined implicit
conversion may be followed by a standard one, so float -> BnAutoLength? chains --
which was also compiled rather than assumed, after the first draft of this
comment claimed the opposite. They stay as a legibility choice at the bare-float
and arithmetic sites; Width's ternary was different in kind, because it read as
a null-check that mattered and did not.

* docs(planning): record the phase 13.1 conclusion

Written after the device lanes came back, not before. android-instrumented
(32422529858) and ios (32422532073) are both green on the branch, and no shell,
frame-table or wire-vocabulary file appears in the diff -- that pair is the
acceptance condition, and a green tick alone is not.

The conclusion records four things the plan got wrong, because they are worth
remembering rather than tidying away:

A pin that would have passed while checking nothing.
LayoutSurfaceSequenceBandTests had no sample-value arm for the new types, so 12 of
22 parameters would have been left unset -- and an unset element attribute never
reaches the frame array. The band pin would have stopped checking over half the
surface while reporting PASS.

The nullability invariant was pinned by a test that could not fail. Asserting
default(BnAutoLength?) is null is a C# language axiom; the actual invariant --
every length parameter is DECLARED nullable -- was guarded by nothing, and a bare
BnAutoLength would have left the suite green. The replacement sweeps by reflection
and is mutation-proven.

A boxed float is a landmine, not just a boxed string: the implicit operators are
compile-time only, so `= 16f` in a ParameterView dictionary compiles and throws at
first render. Nine files were affected; one carried a comment asserting it was fine.

And samples/ConsumerSmoke/SmokeRoot.cs is not a solution member, so no build in
the repo would have flagged its break -- it would have surfaced inside
consumer-smoke.ps1, the release pipeline's own validate job.

Section 8 records one substitution in the open rather than ticking a DoD box
silently: the milestone asked for a compile-failure test, and what shipped is a
mutation-proven reflection guard on the mechanism. A Roslyn test would compile C#,
not Razor markup, so it would restate that guard more expensively rather than
testing what the DoD line describes.
