**Goal:** An iOS `show` completes `Granted` once its request is handed to `UNUserNotificationCenter`, as Android's does after `nm.notify`, so a SpringBoard presentation stall (#444) can no longer delay it or red the iOS lane.

**Architecture:**
- `BnNotifications.runAction` completes a `show` right after it calls `add`. `add`'s completion keeps its #444 trace and routes an error to `BnRuntime.shared?.onError`, or `BnLog.error` with no runtime. It never completes twice.
- `schedule` is unchanged: it completes in `add`'s completion, `Granted` or `Error`.
- A static seam, `BnNotifications.addForTest`, replaces only the call to the center, so the error route and the schedule rule are pinned without a real `add` failure.
- A held-presentation pin uses the real center with a test delegate that holds `willPresent`, the technique of run 40624968569.

**Tech Stack:** Swift 5, XCTest on the iOS simulator (`src/BlazorNative.Apple/BnHostTests`), GitHub Actions `ios.yml` on macOS. **Swift does not compile on the Linux host:** every Swift build, test and red runs on `ios.yml`.

**Spec:** `docs/superpowers/specs/2026-11-14-phase-18.10-design.md`. Read it in full before your task. The owner approved it on 2026-11-14.

## Review Focus

1. **A test delegate or a hold left behind** poisons later tests: a held `willPresent` never released stalls every later show. The held-presentation pin releases the hold and sets `UNUserNotificationCenter.current().delegate = nil` in a `defer` and in `tearDown`, and `resetForTest` clears `addForTest`.
2. **The hold does not engage** (the test delegate never gets `willPresent`), so the held pin passes on today's code too. Its hold anchor asserts the delegate received `willPresent` for the request's identifier while `add` was still uncompleted; red `18.10-R2` makes the hold a no-op.
3. **A second completion on `show`:** the late error path calls `complete` too, delivering `Error` after `Granted`. The late-error pin asserts exactly one captured status; red `18.10-R4`.
4. **The seam leaks into production behaviour:** `addForTest` set in one test and not cleared runs a fake center in the next. `resetForTest` clears it, and `setUp` calls `resetForTest`.
5. **A late completion after `resetForTest`** for a show whose handler is gone: the error route must not touch freed state. The completion captures nothing but the request and identifier strings, logs, and never calls `complete`.
