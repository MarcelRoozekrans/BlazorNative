# Phase 18.3 Secure-storage per-key ordering Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Tick each box in this file as you finish its step, and commit the ticks with the step's work.** The complete-phase gate fails on unticked boxes.

**Goal:** A secure-storage request on a key never runs ahead of an earlier same-key request that is waiting on a biometric prompt, on Android and iOS. Other keys keep flowing (#506).

**Architecture:** Each shell keeps its one serial queue and adds a per-key hold to it.
- A prompt request takes the hold for its key before it arms the gate.
- Same-key requests that start while the key is held are parked in that key's FIFO.
- When the prompt answers, the after-auth task releases the hold and drains the FIFO inline, stopping at a request that takes a new hold.
- On iOS, the gate's answer hops onto `workQueue`.
- If Task 1 shows Android can lose a prompt's answer when its Activity is destroyed, the bridge denies its pending prompts on that destroy.

**Tech Stack:** Kotlin, `androidx.biometric:biometric:1.1.0`, AndroidKeyStore, instrumented JUnit4 on the AVD lane. Swift, Keychain, LocalAuthentication, XCTest on the simulator lane.

**Spec:** `docs/superpowers/specs/2026-10-31-phase-18.3-design.md`. Read it in full before your task. Its sections 1–6 are the rules this plan implements.

## Review Focus

1. **Two prompt requests in a row on one key** (auth set, then auth set, or getWithAuth, then getWithAuth). The second must take the hold when it drains, and a third request must stay parked behind it. Pins 1c and 5b.
2. **A late or duplicate gate answer.** It must not release a hold another request now owns. Pin 4a.
3. **A throw between taking the hold and arming the gate,** or in Android's main-thread prompt setup. The key must not stay held forever. Pin 2b.
4. **Same-key work that arrives while a drain runs.** It must queue behind the drain and keep begin order. Covered by construction: the drain is one executor task. Pin 1c's FIFO order checks it.
5. **A request on another key while a key is held,** including a non-prompt `getWithAuth` of a plain item. It must complete without waiting. Pins 2 and 6.
