**Goal:** `AShellCallBegunOnAnotherThread_DoesNotMarkTheDispatch_SoAFaultAfterItIsRc2` no longer depends on the thread pool inside its 1 s dispatch bound, and a pin holds that.

**Architecture:**
- The cause: the probe handler `pool-begin-then-throw` blocks the dispatch's synchronous part on `Task.Run(...).Wait()`. xunit 2.9 runs test bodies on the pool, so on a 4-vCPU runner the queued item can wait more than 1 s for an injected thread. The spec gives the evidence.
- The fix: the handler begins its call on a dedicated `Thread`, started with `Start` so the `ExecutionContext` and the flowing dispatch scope still flow, and joins it.
- A new pin runs the probe with every pool worker held, and asserts that it returns within the bound.
- Test code and counts only. No product file changes.

**Tech Stack:** C#/.NET 10 and 11, xUnit 2.9 (`tests/BlazorNative.Runtime.Tests`), GitHub Actions `ci.yml` on `windows-latest`.

**Spec:** `docs/superpowers/specs/2026-11-14-phase-18.9-design.md`. Read it in full before your task. The owner approved it on 2026-11-14.

## Review Focus

1. **The pin holds the pool, and something in the probe or `TearDown` needs the pool,** so the pin hangs or overruns for a reason other than the handler. `TearDown` used `Task.WaitAll` over `ContinueWith`, which needs the pool; final-review fix: its waits now wait on each task directly, need no pool thread, and throw a `TimeoutException` when one runs out its budget. The hold is disposed before `TearDown`, and on an overrun it goes through `DispatchProbe`'s `release`. Task 1's green run, with the fix in place, shows the probe itself needs no pool.
2. **A thread that does not flow the context,** for example `UnsafeStart`, or `ExecutionContext.SuppressFlow` around the start. That leaves rc 2 for the wrong reason, because no scope arrived. Task 2's flow anchor covers it, and so does red `18.9-R2`.
3. **The pin's hold does not hold,** so it passes without testing anything. Its anchor is `PoolHold.EveryWorkerHeld(ProbeWindow)`, and red `18.9-R5` makes the hold a no-op.
4. **The hold stalls facts in other collections.** The pin lives in the `pool-starvation` collection, which runs alone after the parallel collections. Check with a full-suite run, Task 3 Step 3.
5. **The begin raises on the dedicated thread,** so the join returns before the call began and the begin anchor still passes. The thread body records the begin's thread only after `CheckGeolocationPermissionAsync()` has returned its task. Any exception on the thread is captured and asserted null in the fact.
