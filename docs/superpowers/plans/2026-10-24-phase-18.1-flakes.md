# Phase 18.1 — CI flakes at their cause Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix #564, #551, #453, #407 and #444 at their causes. Pin each fix, and raise no bound.

**Architecture:** Five tasks, one per flake, each test-first. The investigation record holds the evidence and the reproductions.

**Tech Stack:** C#/xUnit, Swift/XCTest, Kotlin Android instrumented tests, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-24-phase-18.1-design.md`

**Evidence:** `docs/plans/2026-10-24-phase-18.1-investigation.md`

## Global Constraints

- **Raise no bound.** No timeout or bound may be raised, and no test may be retried to make it pass.
- **Test-first.** Write each pin first and watch it red for the right reason. A flake's pin must force its race deterministically where the design names a way to.
- **Grading.** Pins are graded against `docs/pin-standard.md`, "Grading a pin: sites and reds". Each site needs a fresh red with its message quoted in the record `docs/plans/2026-10-24-phase-18.1-record.md`, and its register cell is written in this phase.
- **Mirrors.** The template copies of any shell file stay byte-identical where the mirror guard requires.
- **ABI.** No change to the ABI: the 80-byte struct and the 10 exports stay as they are.
- **Lanes.**
  - Dispatch one run at a time.
  - Wait with `gh run watch --exit-status` in the foreground.
  - Check `headSha` and attempt 1.
  - Use scratch refs named `scratch/18.1-<id>`, and delete each one after its run.
- **Stubs.** Kill stub processes only with a `ps | grep '[x]'` pattern. Never use `pkill -f`.
- **Commits:**
  - `fix(18.1):`, `test(18.1):`, `ci(18.1):` or `docs(18.1):`.
  - No nested parentheses and no session URL.
  - No closing keywords, except the final PR body's deliberate `Closes` lines.
  - No Claude signature: no `Co-Authored-By` trailer and no "Generated with Claude Code" line, by owner rule of 2026-10-25.
  - Run the parse check.

## Review Focus

- A fix that is really a raised bound or a retry.
- A pin whose red depends on timing luck rather than a forced race.
- `BnLog`'s sink changing format, level or privacy behaviour, or losing lines silently.
- The iOS warm-up blocking boot, or racing the first biometric call.
- #444 "fixed" without a found cause.

### Task 2: #564, a non-blocking `BnLog` sink and the probe's teardown

- [ ] **Step 1: Write the three pins first.** These are design §1's sink pin, drop-count pin and leak-isolation pin. Watch each red against current code.
- [ ] **Step 2: Implement the sink and the teardown.**
  - The sink is a bounded queue with one drain thread. When the queue is full it drops and counts; the next write reports the count, and the queue drains at exit.
  - Make `DispatchProbe`'s teardown run on every exit path.
- [ ] **Step 3: Reproduce and record.** Run the investigation's `squeeze.sh` reproduction (appendix A) against the fixed code; it must stay green. Then run the full suite. Record mutations that red each pin's sites.
- [ ] **Step 4: Commit** as `fix(18.1): BnLog never blocks its caller on a full stderr pipe`.

### Task 3: #551, process waits kept off the thread pool

- [ ] **Step 1: Write the two pins first.** Both come from design §2:
  - `RunBounded` called on a pool thread fails, naming the rule.
  - A pool-starvation reproduction: with every pool thread held on a gate, the positive control still gets its frame, or the test names pool starvation.

  Watch each red.
- [ ] **Step 2: Implement.** Move `RunBounded`'s waits off the pool, make the reference fixtures `IAsyncLifetime`, and make `GeneratorRunTests` use `LongRunning`.
- [ ] **Step 3: Run and record.** Do 20 local runs of the affected classes, logging the pool delay. Run the full suite. Record each site's red.
- [ ] **Step 4: Commit** as `fix(18.1): blocking process waits stay off the test thread pool`.

### Task 4: #453, the iOS `LAContext` warm-up and a pre-booted simulator

- [ ] **Step 1: Write the ordering pin first.** Through `contextFactoryForTest`, it shows the warm-up runs at boot, before the first biometric request.
- [ ] **Step 2: Warm the context and pre-boot the simulator.**
  - Warm one `LAContext` at shell boot, without blocking boot, in both copies. The boot tests wait for it as a named step.
  - `ios.yml` boots the simulator and waits for it before `xcodebuild test`.
- [ ] **Step 3: Prove it on the lane.** Run the iOS lane on a fresh boot at least 10 times, with iterations if the lane supports them. Record each run's id and `headSha`.
- [ ] **Step 4: Commit** as `fix(18.1): the iOS shell warms LAContext at boot` and `ci(18.1): boot the simulator before xcodebuild test`.

### Task 5: #407, settle the emulator and name a recreation

- [ ] **Step 1: Write the pin first.** During the camera test's poll, force `scenario.recreate()`. The poll must fail naming the recreation.
- [ ] **Step 2: Implement.**
  - `android-instrumented.yml` waits for the emulator's package updates to settle before `connectedAndroidTest`.
  - The camera test's poll names a recreation.
- [ ] **Step 3: Verify, record and commit.**
  - Get a lane run that shows the settle step working, with logcat checked.
  - Record the pin's red.
  - Commit `fix(18.1): the camera test names a recreation, and the emulator settles first`.

### Task 6: #444, diagnose then fix

- [ ] **Step 1: Instrument the show test.** Add everything in design §5:
  - the captured statuses in the failure message;
  - timestamps on `add` and on its completion;
  - a 5 s daemon probe;
  - the simulator's UserNotifications log, collected on failure;
  - a unique request id.

  Commit it as `test(18.1): …`.
- [ ] **Step 2: Reproduce it.** Loop the suite with `-test-iterations 30` on a fresh simulator, through a scratch ref. Record the diagnostics.
- [ ] **Step 3: If it reproduced:** find the cause, fix it there, and pin the fix test-first.
- [ ] **Step 4: If 30 iterations never reproduce it:** stop and report. The controller asks the owner.
