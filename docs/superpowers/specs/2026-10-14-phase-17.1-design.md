# Phase 17.1 Design — `Fault attribution`

**Date:** 2026-10-14
**Phase:** `17.1`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M17 — Close the Dispatch Lane's Debt](../../planning/MILESTONE.md)
**Issues:** #464, the defect; #494, the 16.7 pin partials, in the same test files.

## Goal

A fault that a dispatch's **own code** raises belongs to that dispatch. A **render** fault belongs
to the batch that renders it, which is the window: see "What does not change". Take dispatch A, whose continuation runs
inline inside dispatch B's synchronous part, because app code completed a `TaskCompletionSource`
without `RunContinuationsAsynchronously`. If that continuation faults:
- the fault is **A's**, a late FaultNotice under **A's** handler id;
- B is not charged with it, and B's own synchronous fault is still reported, rc 2.

A call A's continuation begins never marks B. The 16.7 pin partials in #494 are proven, rewritten
or fixed in the same files.

## Approach

**The two code points #464 names, both in `src/BlazorNative.Renderer/NativeRenderer.cs`.** Inside
B's window, the execution context of A's inline continuation still carries A's scope in
`s_flowingScope`. That is what tells the two apart.

1. **Capture, `HandleException`.** The window, `_currentScope`, keeps a fault unless the flowing
   scope is a **different dispatch scope** owned by this renderer:
   - **flowing is the window's own scope, or null:** captured into the window, as today. *Owner
     decision, 2026-10-14:* code that flows no dispatch is the window's, so nothing that is B's
     today becomes unreported.
   - **flowing is another scope, not `Done`:** the fault is that dispatch's late fault, recorded
     through the existing `LateFault` path. It is logged with `LateFaultLogLabel` and becomes its
     pending Task's fault, then its FaultNotice under its own handler id.
   - **flowing is another scope that is `Done`:** the no-window path, the same as a late fault
     after `Done` today: logged, and thrown in strict mode. **Never the window's.** *Owner decision,
     2026-10-14.*
   - A parameter-binding fault keeps its #164 handling: it is never moved by this rule.
2. **Mark, `NoteShellCallBegun`.** It marks `t_syncScope` only when the flowing scope is that same
   scope. A call begun by another dispatch's continuation, inline in this synchronous part, does
   not mark this dispatch. The thread-bound condition stays. Both conditions are needed:
   - thread-bound alone mis-marks the inline continuation, which is #464;
   - flowing alone mis-marks `Task.Run` work, the 16.7 record's M4.

**What does not change.**
- **`RunAfterDispatch`**, owner decision 2026-10-14. Work that A's continuation queues inside B's
  window still runs when B's window closes, and a fault in it lands on B. It is disclosed in the
  DOES NOT COVER block, and filed if it is worth fixing.
- **A re-render that A's continuation queues**, owner decision 2026-10-14. When A's continuation
  calls `StateHasChanged` inside B's window, Blazor renders that component in B's batch, under B's
  scope, so a render fault from it lands on B. Render faults belong to the batch that renders them,
  which is consistent with the synchronous-part contract. Attributing per render would mean tracking
  which dispatch queued each render. This is disclosed in the DOES NOT COVER block and **filed as
  its own issue in this phase**.
- **A flowing scope owned by another renderer** is treated as no flow: the window's. *Builder's
  call.*
- The ordered mark, the cancellation behaviour, and every 16.7 fact that is not about #464.

**The rc change, BREAKING.** In #464's scenario, B used to return rc 0, with a FaultNotice carrying
A's message under B's id, and B's own fault was lost. Now B returns its own rc, 2 if B faulted and
0 if not, and A's FaultNotice carries A's id. This ships as `fix(17.1)!` with a `BREAKING CHANGE:`
footer, as 16.7 did:
- the three rc-contract copies gain one sentence: the window owns only its own flow and code that
  flows none. `RcContractCopiesTests` keeps them identical;
- the contract's wording otherwise holds.

## Tests

- **#464, two facts, red first on current code:**
  1. **A's fault is A's.** A awaits an app-made TCS without `RunContinuationsAsynchronously`.
     B's handler completes it, and A's continuation throws. Assert:
     - B's rc is 0, from B's own clean synchronous part;
     - one FaultNotice, carrying A's handler id and A's message;
     - an anchor, that A's continuation really ran inside B's window.
  2. **B's own fault survives.** The same setup, but B also throws after completing the TCS.
     Assert B's rc is 2, and A's notice still carries A's id.
- **#464, variants:**
  - **the mark:** A's continuation begins a host call inside B's window, and B then faults. B is
    rc 2, unmarked;
  - **the null-flow rule:** a continuation with no dispatch flow, inline in B, is B's;
  - **the Done rule:** A has finished, and its continuation fault inside B's window is not B's. The
    fault must be raised by A's own code, not by a re-render, because a re-render is the window's
    under the rule above. *Builder's call:* the scenario is a Blazor-observed Task that A started
    and that outlives A, such as a child's `OnInitializedAsync` begun in A's synchronous part,
    which faults inline in B after A is `Done`. If that scenario cannot be built, the fact is
    replaced by a named partial.
- **Guards that must stay green:** all 16.7 facts, including the sibling-order fact and the
  thread-bound `AShellCallBegunOnAnotherThread_…`; `DispatchWindowScopeTests`; the mount guards.
- **Mutations per pin, anchors included,** recorded in the record. 16.7's M4 is re-run as a
  vacuity contrast: flowing-only marking must red the `Task.Run` fact.
- **JVM anchor reds** for `answeredInsideBegin` and `completeRc` need the Windows native library.
  They run through a throwaway draft PR, as in 16.8, with the scratch branch deleted afterwards.
  *Builder's call.*
- **Lanes:**
  - the full .NET suite;
  - the JVM, on CI;
  - both device lanes on the PR head, `headSha` checked. The XCTest and instrumented FaultNotice
    suites must stay green: the shells only route notices, and their contract is unchanged.

## Open Questions

None. Owner decisions, 2026-10-14:
- #464 goes to the flowing scope;
- code with no dispatch flow is the window's;
- a `Done` owner takes the no-window path;
- `RunAfterDispatch` is left and disclosed;
- a re-render A queues is the window's, disclosed and filed.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The inline continuation's execution context is not A's in some path, for example an awaiter that suppresses flow | That path's fault stays B's, and the fix is partial | Fact 1's anchor asserts the flowing scope seen in `HandleException` is A's; a path with suppressed flow falls to the null-flow rule, B's, and is disclosed |
| A child component's render inside B carries no flowing scope | The child-begin fact reds under the new mark condition | The child renders inside B's synchronous part, under B's execution context; the new child-begin fact guards it. If it reds, the mark condition is wrong, so stop and re-design |
| The rc change surprises an app | A different rc in #464's scenario only | A BREAKING note in the changelog; the scenario needs app code the runtime never runs itself |
| Anchor mutations prove nothing, because they break the scenario rather than the anchor | Vacuous anchor reds | Each anchor mutation removes the anchor's premise, and the record shows the anchor's own message in the red, not a later assertion's |
