# Phase 17.4 Design — `Fault-path parity`

**Date:** 2026-10-16
**Phase:** `17.4`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M17 — Close the Dispatch Lane's Debt](../../planning/MILESTONE.md)
**Issues:** #426 and #435.

## Goal

Two things are fixed:

- **#426.** An Android Release build no longer writes the app's text into logcat. That covers an exception message, a stack trace, a route, or anything else that did not come from a constant. iOS has always kept that text out of its logs.
- **#435.** The slow-handler warning names the app's own handler behind every forwarding control, not the `BlazorNative.Components` wrapper.

## What iOS actually does, measured

The milestone left this to the design: measure what iOS redacts, and when, before deciding where Android's redaction lives.

- **What iOS redacts.** `BnLog.swift` applies one rule: a message is `.redacted` unless its text is a compile-time constant, plus at most the framework version. Four call sites pass `.safe`: three constants, and `BnBiometrics`' OSStatus number. Everything else is written as `.private`. That includes:
  - the default `onError` (`BnRuntime.swift`: `BnLog.error(…, "\(msg): \(err)")`);
  - every line the stderr pump forwards from .NET (`BnStderrPump.sink` → `BnLog.write`, default `.redacted`).
- **When iOS redacts.** In **every** build configuration. `.private` text is shown only when a debugger is attached, which is how Xcode runs an app. Nothing about it is tied to Debug or Release.
- **Where it lives.** In the **library**: `BnLog` and the pump, not the app template.

**Android today**, by contrast:
- `BnStderrLogcatPump.toLogcat` writes every .NET line verbatim with `Log.println`. That includes .NET's own `BnLog.Error("Exports", "… faulted after its first await", fault)`, with the exception's message and **stack trace**.
- `MainActivity`'s `onError` is a plain `Log.e(tag, msg, t)`. The FaultNotice text reaches it through `BridgeRegistrar.deliverFaultNotice`.
- Warnings and errors elsewhere in the shell go straight to `Log.w` and `Log.e`. Only `BnShellLog.info`, `debug` and `verbose` are gated, and that gating is by level, not by privacy.

So #426's literal scope, the FaultNotice message alone, would leave the same message one logcat line earlier. **Owner decision, 2026-10-16: mirror iOS fully.**

## Approach

### #426 — Android redacts like iOS

1. **One privacy rule, in the library.**
   - `BnShellLog` gains `warn` and `error`, so all five levels go through one seam.
   - Every call takes a privacy argument whose default is `REDACTED`. `SAFE` is an explicit opt-in, allowed **only on a string literal with no `$` template**. A `const val` interpolated into a message, a node id or a return code makes the line `REDACTED`, as iOS redacts node ids. The drift pin enforces the literal rule mechanically. *Builder's call.*
   - **Level gating is unchanged.** `warn` and `error` stay ungated, as `BnShellLog`'s header and `AndroidLogDriftTests` require. "Mirror iOS" is about redaction, not gating. *Builder's call.*
   - A redacted message is written as `<private>`. The level, the tag and the category stay readable.
   - A throwable's message and stack are dropped with the text. **Its class name is dropped too**: iOS writes the whole interpolation as `.private`. A `SAFE` line keeps its text, but its throwable is still redacted unless the app is debuggable: a stack trace can name app classes. *Builder's call.*
2. **The reveal switch is "the app is debuggable".**
   - `MainActivity.onCreate` sets `BnShellLog` to reveal when `ApplicationInfo.FLAG_DEBUGGABLE` is set. It is set once, **before the stderr pump is installed**, so a debug build shows .NET's earliest boot lines too. *Builder's call.*
   - Debug builds show everything, as before. Release builds show `<private>`.
   - **Why not "debugger attached", iOS's literal condition:** Android Studio's Run does not attach a debugger, Xcode's does. "Debuggable" is the condition under which an Android developer would actually see the text. *Builder's call, recorded as a ruling.*
3. **The pump redacts each forwarded .NET line by the same rule.** No .NET line is a shell-side constant, so every one is `REDACTED`, as on iOS. The pump's priority mapping and category tag are unchanged.
4. **Every Android shell log site goes through `BnShellLog`.** That is 58 `android.util.Log` sites in `androidMain`, measured 2026-10-16:

   | File | Sites |
   |---|---|
   | `WidgetMapper` | 45 |
   | `MainActivity` | 7 |
   | `BnStderrLogcatPump` | 3 |
   | `YogaLayout` | 2 |
   | `BnShellLog` itself | 1 |

   - The pump's own failure reports go through `BnShellLog` too. `BnShellLog` writes with `android.util.Log` directly, never through stderr, so they still work when `dup2` fails.
   - The template's copies change the same way, kept byte-identical or within their existing allowances.
   - The `onError` lambda in `MainActivity` becomes `BnShellLog.error(tag, msg, t)`.
4b. **The shared JVM code's `System.err` writes are in scope too,** because ART sends `System.err` to logcat under the tag `System.err`. The sites:
   - `ShellBridge.kt`'s two completer reports;
   - `NativeFrameAdapter.kt`;
   - `BlazorNativeRuntime`'s default `onError`.

   `src/main` cannot reference `android.util.Log`, so it gets one injectable diagnostics sink. Its default is `System.err`, for the JVM, and the Android shell points it at `BnShellLog` at boot. *Builder's call.*
5. **The .NET side does not change.** .NET keeps writing full text to stderr, and each shell decides what its system log shows. That is iOS's model too. No ABI or wire change.

### #435 — a forwarding hook names the app's handler

1. **The hook, in `BlazorNative.Core`.**
   - An `internal` interface: `IForwardsUiEvent`, with `Delegate? ForwardedHandler(string eventName, Delegate attached)`. *Revised 2026-10-16 in execution:* the renderer passes the delegate it recorded, and a wrapper returns the app's delegate only when `attached` equals its own forwarding method. A second handler on the same wrapper, such as BnModal's content-box tap, gets null whether or not it is static.
   - `Core` grants `InternalsVisibleTo` to `BlazorNative.Components` and `BlazorNative.Renderer`, so the hook adds nothing to any public or `PublicAPI` surface. The milestone's risk row asks for exactly this.
2. **The wrappers implement it.** `BnInput`, `BnCheckbox`, `BnPicker`, `BnSlider`, `BnSwitch` and `BnModal` return the app's delegate behind the event they forward.
   - The delegate is read from the app's `EventCallback` with `[UnsafeAccessor]`. That reaches Blazor's internal `Delegate` field and is NativeAOT-safe: no reflection, no trimming risk.
   - `BnModal`'s dismiss is a non-generic `EventCallback`. The others are `EventCallback<T>`.
   - A wrapper whose app callback is empty returns null, and the key falls back as it does today.
3. **The renderer consults the hook.**
   - `HandlerCallSite.Resolve` keys a dispatch by its handler's method. When that method belongs to framework code, `Resolve` first asks whether the handler's `Target` implements the hook.
   - If it returns the app's delegate, that delegate is resolved instead, by the same owner rule, so an app method names itself.
   - Resolution stays lazy, at warn time, so the hot path allocates nothing.
4. **`@bind-Value` names the page that binds it.** *Revised 2026-10-16 in execution: measured Razor output.*
   - The design assumed a bound wrapper forwards Blazor's framework binder lambda, and planned a fallback key on the parent page with a narrowed known limit. The Razor output says otherwise.
   - Under the .NET 10 Razor compiler, `@bind-Value` and `@bind-Value:after` pass the wrapper a lambda the compiler declares on the page, one per call site. `CreateInferredBindSetter` returns its callback unchanged. `:get`/`:set` passes the app's `:set` method.
   - So the delegate the hook returns is app code, and the same owner rule applies. The warning names the page's lambda, `Page.<BuildRenderTree>b__N_M`, which names the page. Two bound inputs on one page get two warnings.
   - There is no fallback key and no parent-type map. Blazor's framework binder, `EventCallback.Factory.CreateBinder`, serves an element `@bind`. It never reaches a wrapper's typed callback, and the existing call-site key covers it.
5. **The KnownLimit pin is flipped**, as its doc says: two `BnInput`s with different slow handlers give two warnings, each naming the app's method.

- **Docs:** the website's logging and threading pages, `docs/pin-standard.md`, the record, and the counts.

## Tests

- **#426, the rule, on the JVM** (`testDebugUnitTest`). The redaction function and `BnShellLog`'s rendering are pure Kotlin:
  - not revealed: `REDACTED` text and a throwable become `<private>`, and `SAFE` text stays;
  - revealed: everything stays;
  - the pump's record mapping redacts a forwarded line.
  - **Anchor:** the unredacted path still produces the original text, so `<private>` is not a constant.
- **#426, on a device.** The instrumented APK is debuggable, so a device test can only pin the revealed half. A test pins it: a FaultNotice's message reaches `onError`'s log line in a debuggable build. The redacted half is pinned on the JVM, and the reveal switch's wiring is pinned by a source assertion in the drift test below.
- **The twin pin**, in the .NET suite's drift family, beside `BnLogFormatDriftTests`. It reads both shells' sources and holds them together:
  - Swift's `BnLog.write` defaults to `.redacted`, and its pump sink uses that default;
  - Kotlin's `BnShellLog` defaults to `REDACTED`, its pump sink redacts, and `MainActivity` sets the reveal switch from `FLAG_DEBUGGABLE` only;
  - **no `android.util.Log` call remains in `androidMain` outside `BnShellLog`, and no `System.err` write remains in `src/main` outside the diagnostics sink's default;**
  - **every `SAFE` argument is a string literal with no `$`.**
  - Mutating any one of these reds it, and a mutation reds each of its branches (pin-standard Rule 7).
- **#435, in .NET:**
  - the KnownLimit test flipped to `TwoBnInputs_WithDifferentSlowHandlers_GetTwoWarnings_NamingTheAppsHandlers`;
  - one fact per other wrapper, `BnCheckbox`, `BnPicker`, `BnSlider`, `BnSwitch` and `BnModal`, each red first;
  - a control: a wrapper with no app callback still keys by the wrapper call site;
  - `@bind-Value`, from real `.razor` fixtures: plain, with a slow `:after`, and `:get`/`:set`. Two bound inputs on two pages give two warnings, each naming its page, and two on one page give two distinct warnings naming the page. Two plain-bound inputs on one page give two warnings naming the page, and a `:get`/`:set` input's warning names the app's `:set` method. None names `BnInput`. *Revised 2026-10-16 in execution: measured Razor output;*
  - **anchor:** the `[UnsafeAccessor]` read returns the app's delegate, so a renamed Blazor field reds loudly instead of silently falling back.
- **Mutations:** the hook not consulted; the accessor returning null; `SAFE` as the default; the reveal switch always on; the pump not redacting.
- **Lanes:** .NET, JVM, Android and iOS on the PR head, with `headSha` compared.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Release logcat loses the .NET diagnostics developers read from a release build today | A field bug is harder to read from a release device | It is iOS's behaviour already, and the owner's decision. A debuggable build shows everything. The website's logging page says so |
| `[UnsafeAccessor]` on Blazor's internal `Delegate` field breaks on a Blazor upgrade | The hook silently stops naming the app's handler | The anchor fact reds when the accessor fails, so an upgrade cannot pass silently |
| `[UnsafeAccessor]` on a field of a generic struct needs .NET 9 or later | It does not compile, or throws at run time | The repo targets net10.0, and the plan's first task proves it on `EventCallback<string>` before anything builds on it |
| Converting 62 log sites misses one, or marks app text `SAFE` | Text leaks, or a constant is hidden | The drift test fails on any raw `Log.*` call left. Each `SAFE` is reviewed against the rule in the final review |
| Template copies drift during the conversion | `TemplateDriftTests` reds | Edit both copies in the same step and run the drift tests locally each time |
