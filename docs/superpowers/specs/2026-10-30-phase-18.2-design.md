# Phase 18.2 Design — Fault attribution for queued work (#500)

**Date:** 2026-10-30
**Phase:** `18.2`
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Approved:** by the owner, 2026-10-30, including the five calls listed under "Calls made in this design".

## Goal

A fault in a re-render or a `RunAfterDispatch` action that dispatch A queued while its continuation
ran inside dispatch B's window is A's: a late FaultNotice under A's handler id, and B keeps its own rc.
This is the owner decision of 2026-10-24 and the M18 DoD item for #500.

## Background: how it works today

- Dispatch A awaits a `TaskCompletionSource` that the app made without
  `RunContinuationsAsynchronously`. B's handler completes it, so A's continuation runs inline inside
  B's synchronous part, on the render thread, while B's `DispatchScope` is `_currentScope`.
- 17.1 (#464) already attributes a fault **A's own code** raises there. The continuation's execution
  context flows A's scope (`s_flowingScope`), and `HandleException` sends the fault to A's `LateFault`.
- Two paths still charge B, and `FaultNoticeTests`' 17.1 DOES NOT COVER block discloses both:
  1. **The re-render.** A's continuation calls `StateHasChanged`, or ComponentBase's own re-render
     runs after A's handler task completes (`CallStateHasChangedOnAsyncCompletion`). B's batch is in
     progress, so Blazor only enqueues the render. It renders later in B's batch, under B's execution
     context, so `HandleException` sees B's flow and captures the fault in B's window: rc 2 for B,
     or a FaultNotice under B's id.
  2. **`RunAfterDispatch`.** A's continuation queues an action, a navigation for example. It goes into
     `_currentScope`, which is B's, and `DrainPostDispatchActions` charges its fault to `B.Fault`.
- **The Done trap.** In the inline case, A's handler task finishes inside the same inline segment,
  so `AwaitWholeHandler` marks A `Done` before B's batch renders A's re-render and before B drains
  A's action. Attributing to a `Done` scope takes 17.1's "finished dispatch" path, which only logs.
  Tagging alone therefore cannot produce the FaultNotice the DoD asks for. A's completion must also
  wait for its tagged work to settle.
- Blazor 10.0.14 offers no hook on the render queue. `AddToRenderQueue`, `ProcessRenderQueue` and
  `RenderInExistingBatch` are internal and non-virtual. Two internals exist and are used here, as the
  owner chose on 2026-10-30:
  - `ComponentBase._hasPendingQueuedRender`, a private bool on a public type. `StateHasChanged` sets
    it when it enqueues; the render fragment clears it as the render starts.
  - `Renderer.Log.RenderingComponent(componentId, type)`, which Blazor calls at Debug level before
    every queued component render, through the `ILogger` from the renderer's own
    `NativeRendererLoggerFactory`.

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| **Flags + render log** | Two Blazor internals, a private bool on a public type and a Debug log call. Both can be drift-checked. It covers ComponentBase components only, and costs nothing unless a tag is outstanding. | **Chosen by the owner, 2026-10-30.** |
| Read the render queue | Exact for any `IComponent`, but it binds through `UnsafeAccessorType` to `Queue<RenderQueueEntry>`, an internal generic struct. That is harder to drift-check and riskier under NativeAOT trimming, and it still needs a "who is rendering now" signal. | Rejected. |
| Reschedule A's continuation out of B's window | Removes the inline case at its root. But every yield-based fix for #455 failed in 16.7, deadlocking a blocked render thread or breaking synchronous mount, and the owner decided on attribution. | Dropped. |

## Approach

**1. `RunAfterDispatch` carries its queuer.** When `RunAfterDispatch` queues into the open window
`_currentScope` (B), it reads `s_flowingScope.Value`. When that is another dispatch's scope of the
same renderer (A, not B), the queued entry is tagged with A, and A's outstanding count goes up by
one (see 3). `DrainPostDispatchActions` routes a tagged action's fault to A: `A.LateFault`
(first wins, logged with `LateFaultLogLabel`) while A is not `Done`, otherwise
`FinishedDispatchFaultLogLabel`, never `B.Fault`. An untagged action keeps today's behaviour.
The nested-dispatch move of queued actions to the outer scope keeps the tags. The action still
runs with today's flow, outside any scope. Its own batches' non-strict render faults stay on the
log-only path, as they do for B's own actions. That is the existing honest boundary, unchanged.

**2. A re-render carries its queuer.**
- **Segment detection.** `s_flowingScope` becomes an `AsyncLocal` with a value-changed callback.
  The callback acts only on a renderer's render thread while that renderer has an open window. When
  the flow switches **to** another dispatch A of the same renderer, finished or not, it records which live
  ComponentBase components already have `_hasPendingQueuedRender` set. When the flow switches
  **away from** A, it diffs: every component whose flag went false→true in between was dirtied by A.
  It is tagged with A, and, while A is not `Done`, A's outstanding count goes up. The renderer keeps the live component
  instances it already sees in `CreateComponentState`, next to `_componentTypes`.
- **Who is rendering.** The renderer's logger for Blazor's `Renderer` category answers
  `IsEnabled(Debug)` true while this renderer has an outstanding tag, and otherwise defers to
  `BnLog` as today. On the `RenderingComponent` event it records the component id as "rendering now".
  It reads the id from the structured state's `ComponentId` entry. A tag is **used up** by its
  component's first `RenderingComponent`: that render is the one A queued, and the tag becomes
  "rendering now, for A". A later render of the same component in the batch, for example because
  B's render gave it new parameters, finds no tag and is B's. "Rendering now" lasts until the next
  `RenderingComponent` or until `UpdateDisplayAsync` starts, since the batch's renders are done by then.
- **Attribution.** In `HandleException`, inside B's window, a fault while "rendering now, for A" is
  A's, never the window's. While A is not `Done`, it goes to `A.LateFault`, logged with
  `LateFaultLogLabel`. Once A is `Done` (a fire-and-forget continuation of a finished A), it is
  logged with `FinishedDispatchFaultLogLabel`, matching 17.1's rule for a finished dispatch's own
  code and the `RunAfterDispatch` rule. Inside that render this covers a synchronous fault in a
  child's `SetParametersAsync`, and a `Dispose` fault in a component that A's render removed, since
  Blazor disposes it before the next render starts. Anything else stays the window's.

**3. A's completion waits for its tagged work.** `DispatchScope` gains an outstanding count and a
settle signal. `AwaitWholeHandler`, after the handler's Task completes, first **flushes the segment
diff explicitly**. It does not rely on the change callback having fired before it reads the count;
today that holds only because `AwaitWholeHandler` is called after `DispatchSyncPart` restored the
flow, and moving that call would silently reopen the Done trap. Then it awaits, never blocks on, the
count reaching zero, marks `Done`, and throws `LateFault` if any. The settle signal is a
`TaskCompletionSource` with `RunContinuationsAsynchronously`, so A's completion never runs inline
inside B's `finally`; a blocking wait would deadlock, because the settle runs on the same render
thread. The window that holds A's tagged work settles
it at its close in `DispatchSyncPart`'s `finally`. By then Blazor has processed the batch, because
`DispatchEventAsync` renders the queue before it returns, and the drain has run. Every tag the window
holds is released, rendered or not: a component disposed before it rendered just releases. The wait
never spans more than B's synchronous part, which the render thread is already running.

**4. Drift guards.** The `_hasPendingQueuedRender` field joins `BlazorInterop`'s load-time
`VerifyAccessors`, which throws `BlazorVersionMismatchException`, by owner decision of 2026-10-30.
That is the house pattern. `VerifyVersion` checks only major.minor, so this field check is the real
guard against a 10.0.x patch. It also means the change callback can never read a missing field. An
exception inside an `AsyncLocal` change callback calls `Environment.FailFast`, so the callback must
not throw for any reason: its body is field reads only. The `RenderingComponent` event is a log call
and cannot be checked at load. It is pinned by a test that renders a component with a tag
outstanding and asserts the logger saw its id. If Blazor drops the event, attribution falls back to
the window, which is today's behaviour, and CI reds on the dependency bump.

## Tests

Pins, on the real `HostSession`/export path that the 17.1 facts already use, each with an anchor that
A's continuation ran inside B's window:

1. **Re-render, explicit.** A's continuation calls `StateHasChanged`, and its next render throws. A gets a
   late FaultNotice under A's handler id; B returns rc 0 and sends no notice.
2. **Re-render, Blazor's after-handler render.** The same, through ComponentBase's own re-render when
   A's handler completes. This is the common case, and it pins the Done trap.
3. **`RunAfterDispatch`.** A's continuation queues an action that throws. A gets a late FaultNotice; B
   keeps rc 0.
4. **B keeps its own fault.** B's own handler fault, with A's tagged render also faulting. B gets rc 2
   with its own exception, and A gets its notice. Neither is swapped.
5. **Untagged work stays the window's.** A render B queues itself still faults B. So does a second
   render of a component A tagged, once B's render re-dirtied it: the tag is used up by the first.
   The tag rule does not over-reach.
6. **Drift.** The `RenderingComponent` capture sees the rendered component id. The accessor's
   load-time check holds.

Each pin gets mutation proof under `docs/pin-standard.md` "Grading a pin: sites and reds". Every
labelled anchor and every name clause gets a fresh subject red that quotes its message. Examples:
drop the segment tag, drop the rendering-now rule, mark `Done` without waiting, drain without the tag.
The record checks staleness against each red's own commit. The full .NET suite stays green against
the 1387 baseline plus the new facts. The device lanes need no new pin: this is renderer-only, with
no wire or shell change.

## Calls made in this design (the builder's, for the owner to check)

- **A tag is used up by its first render** (builder check, 2026-10-30), so a second render B causes
  in the same batch is B's.
- **A finished A's re-render is tagged too, and its fault is log-only**, like 17.1's finished-dispatch
  rule and the `RunAfterDispatch` rule. Before this phase that fault was B's rc 2.
- **A disposal caused by A's tagged render is A's**, like a child's synchronous `SetParametersAsync`
  fault.
- **The diff is flushed explicitly before the count is read, and the settle completes
  asynchronously** (builder check, 2026-10-30).

- **ComponentBase only.** A custom `IComponent` that A re-renders inside B's window stays B's.
  This is disclosed in DOES NOT COVER.
- **A component B had already dirtied** before A's segment and A dirtied again renders once, in B's
  batch, and is B's. Nothing observable separates them. Disclosed.
- **A child re-render that A's tagged render enqueues** is not tagged; it is B's. Only a synchronous
  fault during the tagged render itself is A's. Disclosed.
- **Frame delivery of the mixed batch** (`UpdateDisplayAsync` faults) stays B's: batch-level, as today.
- **Inline segments outside a dispatch window**, such as during a mount or a host-event arm, are out
  of scope. There, A's `StateHasChanged` renders immediately under A's flow and is already A's
  through 17.1, unless a non-dispatch batch is in progress. Disclosed.

## Open Questions

- None blocking. The approach was chosen on 2026-10-30.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| An `AsyncLocal` change callback runs on every execution-context switch where the value differs, process-wide | Overhead on handler continuations | The callback returns at once off the render thread, or with no open window; measure the suite's run time before and after |
| A wait before `Done` never settles | A's pending Task hangs, and the shell never gets A's outcome | Settle in the window's `finally`, release every tag the window holds, and pin a disposed-before-render case |
| Blazor renames `_hasPendingQueuedRender` or drops `RenderingComponent` | Startup throws for the field; attribution reverts to the window for the event | The field joins `VerifyAccessors`; the drift pin reds on the bump |
| Re-entrancy: a callback fires during the diff itself | A corrupted snapshot | The diff reads fields only, with no awaits and no app code; guard with a render-thread-only reentrancy flag |
