# Phase 14.2 Design — Safe-Area Insets to .NET

**Date:** 2026-09-21
**Phase:** 14.2
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [14 — Twin Divergence, Closed Mechanically](2026-09-21-milestone-14-design.md)
**Closes:** [#338](https://github.com/MarcelRoozekrans/BlazorNative/issues/338)
**Depends on:** phase 14.0 — the inset event needs a generated host-event name, and hand-adding a
sixth name to a pinned vocabulary is the thing M14 exists to stop.

## Goal

Give app authors a `BnSafeArea` component that keeps content clear of notches, status bars, camera
cutouts and home indicators on **both** shells — and make it visible in every code snippet a user
would copy, so the correct thing is the thing they see first.

## The defect

On an iPhone 17 Pro Max, the top ~50pt is Dynamic Island and **the system takes touches there**.
`BnCameraDemo` opens a bare `div`, so layout starts at `y=0` and its `Take Photo` button lands at
**(220, 15)** — drawn correctly, entirely untappable. No highlight, no error, no TCC prompt; the
echo stays at `"ready"`. All four capability pages are affected. `BnDemo` escapes only incidentally,
because `BnThemedPanel Padding="16"` plus a title push its buttons clear.

The shell does no safe-area handling at all: `HostViewController.viewDidLayoutSubviews` solves the
Yoga tree against `view.bounds.size`, and
`grep -rn "safeArea|layoutMargins" src/BlazorNative.Apple/` returns only comments and tests.
**Android is identical** — `grep -rn "WindowInsets|fitsSystemWindows|systemBars"` over the Jni
shell returns **zero**. Both shells agree perfectly and are identically wrong; Android simply lacks
a Dynamic Island to turn it into a dead button.

`BnHostTests` drives the view hierarchy programmatically and asserts frame **tables** — it never
issues a real touch. A control that is perfectly laid out but physically unreachable passes every
assertion, and frame parity passes too, **because the frames are correct**.

## How other frameworks solve this

Researched against current documentation rather than recollection.

| Framework | Automatic? | Mechanism |
|---|---|---|
| **SwiftUI** | **yes** — opt *out* with `.ignoresSafeArea()` | built into layout |
| **Flutter** | no — opt-in | `SafeArea` widget; all four sides by default, disable per side |
| **React Native** | no — opt-in | `SafeAreaProvider` + `SafeAreaView` / `useSafeAreaInsets` |
| **.NET MAUI** | no — opt-in, **iOS only** | `Page.SetUseSafeArea(...)` platform-specific |
| **Jetpack Compose** | no — opt-in | `Modifier.windowInsetsPadding(...)` |

*(Flutter, React Native and MAUI verified against current docs; SwiftUI and Compose from general
knowledge and marked as such.)*

**Four of five are opt-in**, and they succeed because `SafeArea` appears in every tutorial, every
snippet and every starter template. Flutter's docs say outright: *"it's generally recommended to
wrap the body of a `Scaffold` in `SafeArea` as a good place to start."*

**MAUI is the instructive one.** Its own design document states: *"at the moment, we only support
Safe Area on iOS. We should support it on Android, but we haven't done that yet."* That is exactly
BlazorNative's gap, left open by the closest comparable framework. Shipping both shells puts this
repo ahead of it.

## Decisions

1. **Opt-in, following the de-facto standard.** Not automatic root application. An automatic root
   inset was considered and rejected: it is the *shell-insets-its-own-root* design the milestone
   already rejected wearing a component's clothes, it forces every page to be inset whether it wants
   to be or not, and it would re-baseline all four declared frame tables. The ecosystem's answer to
   "opt-in is easy to forget" is **visibility**, not automation — see decision 2.
2. **Present in every snippet a user would copy.** The `dotnet new` template's starter page, all
   four capability demo pages, and every documentation example that shows a page. This is the
   mechanism Flutter and React Native actually rely on, and it is what makes opt-in safe in
   practice. A correct default that is invisible teaches nobody; a correct example teaches everyone
   who copies it.
3. **Nested instances must not double-pad.** Flutter's `SafeArea` rewrites the inset data its
   children see, so only the outermost one pads. Without this, wrapping a page and then wrapping a
   section inside it applies the inset twice. This is the detail most likely to be got wrong.
4. **Per-edge modes follow React Native:** each edge is `off`, `additive` (default) or `maximum`.
   `maximum` means *"my own padding, or the inset, whichever is larger"* — the case authors
   otherwise hand-write as `Math.max(insets.bottom, 16)`, visible in RN's own docs.
5. **Padding only; no `margin` mode.** RN offers both. YAGNI: padding solves #338, and adding a
   mode later is non-breaking while removing one is not.
6. **The three layout/scroll/image demo pages stay unwrapped.** They demonstrate layout primitives
   and carry the cross-shell parity contract. Wrapping them would change what they teach and
   re-baseline the tables for no benefit — the pages that caused #338 have no frame tables at all.
7. **First frame renders at zero insets and re-renders when they arrive.** Both shells boot and
   mount in `viewDidLoad` / `onCreate`, *before* the first layout pass, so neither can report an
   inset at mount. React Native accepts the same delay — its docs say *"insets are not updated
   synchronously, so expect a slight delay."* Recorded as a known limitation with a known fix shape,
   not as permanent: RN's `initialWindowMetrics` supplies synchronously-available initial insets at
   native-module init, which suggests our shells could too. **Out of scope here.**

## Architecture

### The wire

`safeAreaChanged` joins `src/wire-vocabulary.json` tagged **`reserved`**, so 14.0's generator emits
it into both shells' `BnHostEvent` enums and neither shell can spell it by hand. The name follows
the `themeChanged` shape phase 13.5 proposed.

The payload is flat JSON — `{"top":"47","right":"0","bottom":"34","left":"0"}` — matching the
established shape for structured host data, which `host_call_complete` already uses. `navigate`
carries a bare string, but four numbers need keys. Values are in each platform's layout units,
which is what Yoga already consumes.

**No ABI change.** It rides the existing `blazornative_host_event` export — the shape 13.5 found
for `themeChanged`.

### Who owns the state

`Exports.DispatchHostEventCore` gains an arm, `DispatchHostSafeArea(payload)`, which parses, stores
into framework-owned state, and asks the renderer to re-render. `BnSafeArea` reads that state. The
app never sees the event, which is what `reserved` means.

**The rc contract, re-derived rather than trusted.** 14.0's dispatch-arm pin asserts every reserved
name returns **1** with no session mounted, and the 14.1 ROADMAP entry warns the next implementer
to re-derive that rather than assume it. It holds here for an honest reason: the arm **stores the
insets unconditionally**, so a later mount starts with the right values, and returns **1 when there
is no live session to re-render** and **0 when it re-rendered**. The rc reports whether a re-render
happened — exactly what `back` and `navigate` report. The assumption survives because the arm
genuinely shares their shape. **Had it not fit, the correct move would have been to change the pin
and say so, not to contort the arm.**

A malformed payload returns an rc and must never fault the lane.

### The component

`BnSafeArea : BnLayoutItem` — inheriting 13.0's item surface like every other component, so it does
not become the thirteenth component written against `ComponentBase`. It emits a container padded by
the stored insets, and must respect M13's reserved sequence bands (item 1–49, container 50–99,
component-specific 100+, `ChildContent` 200). A collision there produces a **wrong diff silently**,
which is why the band is a rule rather than a convention.

Nesting is handled per decision 3: an inner `BnSafeArea` sees the remaining inset as zero and pads
nothing.

## Testing

**The parity contract is untouched, and that is a design outcome rather than luck.** The declared
tables are `bnLayoutDemoFrames`, `bnScrollDemoFrames`, `bnScrollDemoImageFrames` and
`bnImageDemoBeforeFrames`; the four pages that caused #338 appear in **none** of them, and decision
6 keeps the demo pages that do carry tables unwrapped. Wrapping the capability pages moves **zero**
declared frames.

**Cross-shell testing without a new seam.** Android's and iOS's real insets differ, so a
`BnSafeArea` page could never produce equal tables from real device values. The answer is that the
device test **dispatches `safeAreaChanged` itself** with fixed values before asserting. Both shells
then produce identical frames because the test supplies the numbers, the assertion exercises the
**real wire path** end to end, and the parity contract **extends** rather than breaks. No test-only
override, and no new seam to become an invisibility hole later — the failure mode this milestone has
spent three phases unwinding.

- **Unit (.NET):** the arm's parse and rc contract (0 re-rendered / 1 no session); malformed payload
  returns an rc and does not fault; `BnSafeArea` re-lays-out when insets change; **nested
  `BnSafeArea` pads once, not twice**; each per-edge mode (`off`, `additive`, `maximum`).
- **Integration (both shells):** a new `BnSafeArea` demo page with a declared frame table on both
  sides, asserted after the test dispatches known insets — so `ShellFrameTableDriftTests` compares
  them in the required lane exactly as it does the others.
- **Regression:** the four existing tables must be **unchanged**. If one moves, decision 6 was
  violated — investigate rather than re-baseline.
- **Guards already in force:** 14.0's vocabulary codegen means the name cannot be hand-added to one
  shell, and its dispatch-arm pin means a `reserved` name without a routing arm reds.

## Open Questions

None blocking. The first-frame shift is accepted with a recorded fix shape (decision 7), and
`margin` mode is deliberately omitted (decision 5).

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **Nested `BnSafeArea` double-pads** | Content pushed twice as far; subtle and only visible on notched devices | Decision 3, with a dedicated .NET test. This is the single most likely thing to get wrong, and Flutter's design exists because of it |
| **A demo page with a frame table gets wrapped** | Four declared tables re-baseline, and a real regression hides in the churn | Decision 6, plus a regression assertion that the four existing tables are unchanged |
| **The inset arm breaks 14.0's dispatch-arm pin** | A reserved name that returns 0 with no session reds the pin falsely | Re-derived above: the arm returns 1 with no session because the rc reports whether a re-render happened. Verify rather than assume |
| **Sequence-band collision in the new component** | A wrong diff, silently — M13 named this the severe case | Respect the reserved bands; M13's collision pin is mutation-proven and still in force |
| **Swift and Kotlin inset APIs report at different times** | One shell re-renders on rotation and the other does not | Both report on their existing layout hooks — `viewDidLayoutSubviews` and the Android layout listener — which already fire on rotation and are the twins the repo pairs elsewhere |
| **The template mirror drifts** | `TemplateDriftTests` reds in the required lane | The Android shell change must be applied to both copies in the same commit, as 14.0 and 14.1 both had to |
