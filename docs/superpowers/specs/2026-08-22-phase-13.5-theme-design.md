# Phase 13.5 — Theme system: design and go/no-go

**Milestone:** 13 — Consumer Ergonomics · **Phase:** 13.5
**Surface:** Design (no implementation)
**Date:** 2026-08-22
**Deferred from:** 13.1, which typed the layout lengths and explicitly left
`BackgroundColor` typing to this phase.

---

## 0. What this phase delivers

**A verdict, not a feature.** The milestone scheduled 13.5 as a design phase: decide whether
BlazorNative should ship a theme system before 1.0, and if so, what shape. Nothing here is
implemented. If the verdict is *go*, the implementation is a separate phase with its own plan.

The verdict is **split**, and §6 is the half that says no.

---

## 1. Scope, as agreed

| In | Out |
|---|---|
| OS dark/light **detection** (`themeChanged` host event; Android `uiMode`, iOS `UITraitCollection`) | Material 3 / HIG platform default palettes |
| `BnColor` — typing the colour grammar 13.1 deferred | High-contrast and accessibility variants |
| The disposition of the shipped `BnTheme` record | Typography scale, elevation, ripple, motion |

## 2. Finding — the .NET half already ships

The risk register behind M13 implied theme detection would be expensive because it needs a new
event across a frozen ABI. **It does not, and the .NET receive path needs no new code at all.**

`Exports.DispatchHostEventCore` (`src/BlazorNative.Runtime/Exports.cs:704`) branches on exactly two
reserved names — `back` and `navigate` — and **everything else falls through** to the general
multicast:

```csharp
if (name == BackEventName)     return DispatchHostBack();
if (name == NavigateEventName) return DispatchHostNavigate(payload);

bool faulted = NativeShellBridge.RaiseNativeEvent(new NativeEvent(name, payload));
```

`NativeShellBridge.NativeEvents` is **shipped public API** — line 109 of `PublicAPI.Shipped.txt`, as
`System.Action<BlazorNative.Core.NativeEvent>!`. So an app can already receive an arbitrarily-named
host event today, with no framework change whatsoever.

Two consequences, both load-bearing for the verdict:

1. **`themeChanged` is not an ABI change, and not even a .NET change.** It is the shape `back` and
   `navigate` used, minus the reserved-name branch — those two need a branch precisely *because*
   they hijack the multicast, and `themeChanged` does not.
2. **The entire cost of detection sits in the two shells.** That is a real cost, and the iOS half
   cannot be verified locally, but it is a fraction of what the risk register assumed.

## 3. Finding — the host-event vocabulary is 13.4's bug class, unpinned

This one was not in the brief, and it changes the order of work.

**Host event names are not in `src/wire-vocabulary.json`.** They are hand-written literals, in three
languages, with nothing comparing them:

| Language | Names | Form | Site |
|---|---|---|---|
| C# | `back`, `navigate` | `internal const` | `Exports.cs:652`, `:666` |
| Kotlin | `onResume`, `onPause`, `onDestroy` | **inline literals at the call site** | `MainActivity.kt:360, 365, 375` |
| Swift | `onResume`, `onPause`, `onDestroy` | `static let` constants | `BnAppLifecycle.swift:46-48` |

This is *two copies of one truth, one of them unpinned* — the exact class 13.4 spent a phase closing
for styles, node types and deep links. It is worse here in two specific ways:

- **The .NET side does not know `onResume` exists.** It falls through to the multicast, so there is
  no C# declaration for a drift test to compare a shell literal against. The vocabulary has no
  centre.
- **Kotlin's are inline, Swift's are named.** A typo in one of the three Kotlin call sites produces
  an event that is silently never delivered, and no test in the repo would notice.

**The prerequisite this creates:** adding `themeChanged` as three more hand-written literals would
manufacture a sixth instance of the class 13.4 just closed, inside the very mechanism this phase
depends on. So the host-event vocabulary moves into the manifest **first** — a `hostEvents` section
emitting C#, Kotlin and Swift, adopting the existing five names in the same change. Only then does
`themeChanged` get added.

That is not scope creep; it is the order that avoids knowingly re-opening a closed bug class. It is
also small: the emitters, the byte-comparison test and the manifest's doc conventions all exist.

## 4. Detection — design

**The event.** Shells dispatch `blazornative_host_event("themeChanged", "dark" | "light")`.

**An event alone is insufficient, and this is the design's sharpest constraint.** A component
mounting needs the *current* scheme, not a notification of the next change. If the shells only
report transitions, every app renders its first frame in the wrong palette and corrects on the first
user toggle — which for most users never comes.

So the shells must **seed** the scheme as well as report it. Two candidate seams:

| Seam | Cost | Risk |
|---|---|---|
| **Dispatch `themeChanged` once at boot, before the first mount** | Reuses the one path; no new plumbing | Ordering — it must land after runtime init and before mount, and that window needs locating in both shells |
| Carry the scheme in the boot payload beside `initialRoute` | Ordering guaranteed by construction | A second mechanism for the same fact, and it touches the boot path both shells already treat carefully |

**Recommended: dispatch at boot.** One path, one vocabulary entry, and the seeding and the change
notification cannot drift apart because they *are* the same call. The ordering window is the
implementation phase's first task and its main risk — flagged here rather than discovered there.

**The consumer surface.** A small DI-registered watcher rather than raw multicast filtering:

```csharp
public interface IBnThemeWatcher
{
    BnColorScheme Current { get; }          // seeded at boot, never a guess
    event Action<BnColorScheme> Changed;
}

public enum BnColorScheme { Light, Dark }
```

Apps that want the raw seam keep it — `NativeShellBridge.NativeEvents` is unchanged and still
public. The watcher exists so the common case does not require string-matching an event name.

## 5. `BnColor` — design

13.1 removed the string conversion from `BnLength`, and that absence is what makes `Width="12px"` a
compile error. **That move does not transfer to colours, and the reason matters:** `12px` was CSS
muscle memory the grammar never supported, so rejecting it cost nothing. `#FFEEAA` **is** the
grammar — the shells parse exactly that today. A `BnColor` that refused hex strings would make every
call site more verbose in order to catch a rarer error.

The motivation is nonetheless identical. Colours today are parsed by `parseColorOrNull(...)` with
**log-and-ignore on failure** (`WidgetMapper.kt:1928, 1970`) — the same accepted-then-silently-dropped
posture 13.1 removed for lengths.

**Shape:**

```csharp
public readonly record struct BnColor
{
    public static implicit operator BnColor(string hex);   // throws on malformed
    public static bool TryParse(string? hex, out BnColor result);
}
```

- **The implicit conversion throws.** `BackgroundColor="#GGGGGG"` becomes an immediate, located
  failure instead of a colour that silently does not appear. This is the `Uri` convention: throw on
  the literal path, because a malformed literal is a programmer error at a known call site.
- **`TryParse` covers runtime data.** A server-driven palette must not be able to crash a render, so
  the data path gets the non-throwing form. Recommending only the throwing conversion would be a
  defect; recommending only `TryParse` would make every literal ceremonial.
- **A literal-validating Roslyn analyzer is designed, not built.** 13.1 declined one as "its own
  piece of work" and that judgement holds unchanged. Without it, a bad literal fails at first render
  rather than at build — still a large improvement on failing never.

## 6. The colour-role vocabulary — **no-go before 1.0**

The agreed scope included "BnTheme → colour ROLES (surface, onSurface, …)". **I recommend against
shipping that, and this section is the argument.**

**Role names are a design-system opinion, not a neutral fact.** Material 3 says
`surface`/`onSurface`/`primaryContainer`. Apple's HIG says `systemBackground`/`label`/
`secondaryLabel`. Neither is a superset of the other, and they disagree about how many roles exist
at all. This phase puts **MD3 and HIG compliance explicitly out of scope** (§1) — so prescribing
roles here means inventing a *third* vocabulary, belonging to no platform, matching no designer's
handoff, and **freezing it at 1.0**, where the API baselines make it permanent.

**The gap it would fill is already closed.** An app can build a theme today: `BnTheme` +
`CascadingValue` is device-proven and documented in the state guide 13.3 shipped. What an app
genuinely *cannot* do is learn the OS setting — which is §4, and which is the half this phase says
go to.

**The asymmetry that settles it.** Shipping detection without roles costs an app a dozen lines of
its own record. Shipping the wrong roles costs the framework a permanent public vocabulary that
every consumer must either adopt or work around, and that no future MD3 mapping can be made to fit.
The first mistake is cheap and local; the second is permanent and global.

**What replaces it:** documentation. The state guide gains a worked example of an app-defined theme
record driven by `IBnThemeWatcher`. Apps get the pattern without the framework getting the
vocabulary.

## 7. `BnTheme`'s disposition — remove it

`BnTheme(string Background, string AltBackground)` is shipped public API and is **sample-shaped**:
`AltBackground` exists so a demo can toggle. It is not a theme; it is a two-element palette named
after what the sample does with it.

**Recommendation: delete it from `BlazorNative.Components` and move it into the sample.** If §6
declines to prescribe a *good* role vocabulary, keeping a bad two-name one in the shipped surface is
the worse of both positions. This *reduces* public API before 1.0, which is the right direction, and
M13's decision 1 ("break now, while pre-1.0") already authorises the break.

Consumers lose nothing they cannot restore with one `record` declaration — which is precisely the
pattern §6 says to document.

## 8. Verdict

| Piece | Verdict | Reason |
|---|---|---|
| Host-event vocabulary into the manifest | **GO — prerequisite** | Otherwise this phase manufactures a sixth instance of the class 13.4 closed (§3) |
| `themeChanged` detection + boot seeding | **GO** | Closes a gap apps cannot close themselves; no ABI change, no .NET change (§2, §4) |
| `IBnThemeWatcher` | **GO** | The seam that makes `Current` available at first render |
| `BnColor` + `TryParse` | **GO** | Kills the same silent-drop class 13.1 killed for lengths (§5) |
| Colour-role vocabulary on a framework theme | **NO-GO before 1.0** | Inventing a third design-system vocabulary and freezing it; the gap is already closable by apps (§6) |
| `BnTheme` as shipped | **REMOVE** | Sample-shaped API; keeping it is the worst of both positions (§7) |
| Literal-validating analyzer | **DEFER** | Its own piece of work, per 13.1's standing judgement |

## 9. If go — the shape of the implementation phase

Not a plan; the sequence a plan would have to respect.

1. **`hostEvents` in `wire-vocabulary.json`**, adopting the five existing names. Emitters, Kotlin
   call sites, Swift constants, C# consts. Pinned by the existing byte-comparison.
2. **`themeChanged` added to the manifest**, with no shell emitting it yet.
3. **`BnColor` + `TryParse`**, and `BackgroundColor` retyped. Migration note, as 13.1 had.
4. **Android detection** — `uiMode` at boot and on configuration change.
5. **iOS detection** — `UITraitCollection.userInterfaceStyle` at boot and on trait change. First
   contact with the ordering constraint in §4; no local toolchain, so device-lane dispatch is
   mandatory before this is believed.
6. **`IBnThemeWatcher`** + DI registration.
7. **`BnTheme` removed**, sample updated, state guide gains the app-defined-theme example.
8. **Both device lanes dispatched and green.**

## 10. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **The boot-seeding window does not exist where §4 assumes** | `Current` is unset at first render; the design's value evaporates | It is task 1 of the implementation phase, not a late discovery. If no window exists, fall back to the boot-payload seam (§4) rather than shipping change-only detection |
| **§6 is overruled later and roles are added under time pressure** | The vocabulary lands without the design work that would justify it, and freezes at 1.0 | The no-go is written with its reasoning here, so reversing it means arguing against a record rather than filling a gap |
| **`BnColor`'s throwing conversion turns a dropped colour into a crash** | An app that fed runtime data into a colour now faults at render | `TryParse` ships in the same change and is named in the migration note as the data path |
| **iOS trait observation is written blind** | It compiles, ships, and does nothing on a device | Device-lane dispatch is a DoD line, not a nicety — the pattern that caught 11.4's pump bug |
| **The manifest change touches five live call sites in two shells** | A boot-path regression in a lane that is not per-PR | The names are adopted unchanged; the emitted constants are byte-compared, so any behaviour change is a bug in the adoption, not in the design |

## 11. Out of scope

- **MD3 / HIG platform palettes.** Explicitly excluded (§1), and §6 is why it matters.
- **High contrast, typography, elevation, motion.** Not theme *detection*; each is its own feature.
- **The literal-validating analyzer.** Deferred (§8) with 13.1's reasoning.
- **Theming the shell chrome** (status bar, navigation bar). A capability question, not a colour one.
