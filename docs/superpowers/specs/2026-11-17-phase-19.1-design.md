# Phase 19.1 Design — Re-grade the 1.0 criteria

**Date:** 2026-11-17
**Phase:** 19.1
**Surface:** Docs
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-17

## Goal

Publish an interim, evidence-backed answer to "what blocks 1.0 today". To do that, re-check every row of
`docs/plans/2026-07-22-phase-11.3-one-point-oh-criteria.md` against current `main`, and sweep the
issue tracker for blockers that the July list could not know about. The rest of M19 is then aimed at
the real list.

## Why

The criteria file was last updated on 2026-07-24. Its scoreboard still shows four open blockers: P3,
#209, #210 and #211. The three bugs have since closed, so on paper only P3 is left. But nobody has
checked whether the July evidence still holds, and 98 issues have been filed since then. Phase 19.8
re-grades the file on the final head and makes the 1.0 call. 19.1 is the early pass, so that later
M19 phases and the owner's choices about new blockers rest on the current state, not July's.

## Goals, non-goals, anti-goals

- **Goals.**
  - Every row has a current state and an evidence line dated in M19.
  - The §0 scoreboard is rewritten.
  - Every new blocker candidate is in the file with a proposed class, and the owner has ruled on
    each one.
  - The public docs that quote 1.0 status agree with the new scoreboard.
- **Non-goals.**
  - Fixing any blocker. Fixes belong to later phases, or to a new phase the owner adds.
  - The final re-grade, which is 19.8's.
  - Re-proving Q1 on a device. 19.2 proves the timing marks are silent at `Warn`, and it re-runs
    Q1's paired check as part of that.
  - Grading P3. That is 19.7's job.
- **Anti-goals.**
  - **A scoreboard that can only improve.** The July file says this outright: the count going up is
    the list working.
  - **Evidence that travelled through a document instead of being re-measured.** A July line copied
    forward as "still true" without checking the code is exactly the failure this phase exists to
    catch.
  - **History silently overwritten.** The file records corrections instead of erasing them.

## Constraints

- **The file keeps its path.** `website/docs/api-stability.md:317` links to it by URL, and
  `docs/ios-device-verification-handover.md:169,362` link to it by relative path. Renaming it breaks
  public docs.
- **No test reads the file**, so editing it reds nothing. `README.md` is pinned by
  `ReadmeDriftTests`: it states no counts, and this phase does not add any.
- **Owner rules apply.** No closing keywords: issues are referenced only as `#N`. Ask the owner
  with options. Execution is subagent-driven.

## Approaches

1. **Ledger plus a separate evidence log.** Picked by the owner.
   - The criteria file stays the ledger: new state per row, a dated evidence line, a rewritten §0,
     and a new section for candidates found since July.
   - The working detail goes in a new `docs/plans/2026-11-17-phase-19.1-regrade.md`: for each row,
     what was checked and at which commit; any re-proof that was run; and the full issue-sweep table.
2. **Everything in the criteria file.** Rejected: about 100 lines of mostly "not a candidate" rows
   would bury a ledger whose job is to be checked, not read.
3. **A new dated criteria file.** Rejected: it breaks the public docs link and the handover doc, and
   it splits the history in two.

## Decided with the owner

- **Proof depth for MET rows: re-check, and re-prove only where the cited code changed.** For every
  row:
  - confirm each cited file, line, test, lane or PR still exists and still says what the row claims;
  - run `git log --since=2026-07-24 -- <cited paths>`;
  - when the cited code or mechanism has changed, re-run the row's original proof. For example, A1's
    rename mutation `BnButton.Label` → `BnButton.Text` must still produce RS0016/RS0017 and exit 1,
    and A2's roster pin must still red in both directions.
  - Q1 is re-checked only, with its device re-proof handed to 19.2. The row says so.
- **Owner ruling on candidates.** Each new candidate goes into the file with a proposed class. The
  owner rules on each one at review: the class, and, per the milestone design, whether it becomes a
  new M19 phase (via `add-phase`) or stays listed.

## Approach

**Anchor.** All checks are made against one `main` commit, recorded at the top of the evidence log.
If `main` moves during the phase, the anchor stays put. Rows whose cited files changed after the
anchor are re-checked once more before the scoreboard task.

**Row re-check, one task per section.**

| Section | Rows |
|---|---|
| §1 API | A1–A5, S3, S4 |
| §2 Platform proof | P1–P4 |
| §3 Quality and §3a live bugs | Q1–Q5, #209–#211 |
| §4 Docs | D1–D4 |
| §5 Release | R1–R4 |

For each row, the task records the following in the evidence log:

- what was cited;
- what exists now, with `file:line` at the anchor;
- the `git log` of the cited paths since 2026-07-24;
- whether a re-proof ran, and its result;
- the proposed new state.

Closed issues cited by a row get extra checks: the merged PR is named, and the fix is confirmed
present at the anchor. This covers #209, #210, #211 and #169 (Q4), and #181 and #178 (Q5). A row
whose issue closed becomes MET only when the fix is in the code.

P3 stays open, but its evidence line gains what is now known:

- a contributor's real-iPhone run in September found #338 (no safe-area handling) and #339 (the
  first permission grant deadlocks), both since closed;
- the owner's session is scheduled in 19.7.

D3 is re-measured, because the #173 API-reference work has likely changed its "26 of 88" count.

**Issue sweep.** The sweep covers:

- every issue created on or after 2026-07-24, open and closed (98 at design time);
- every open issue from before then that no row cites (#21, #24, #30 and #216).

Each issue gets one verdict:

- **not a candidate**, for internal CI, test or tooling hygiene that makes no consumer-facing
  promise false;
- **covered by row X**;
- **candidate**, with a proposed class.

The bar is the file's own:

| Proposed class | When |
|---|---|
| **BLOCKER** | The defect falsifies something the project tells consumers in writing (docs, README, xmldoc, a stated contract such as "denial is data"), and no honest caveat can describe it. |
| **DOCUMENTED** | A consumer-visible gap that a specific, named caveat can honestly describe. |

Closed issues are judged by whether the fix is on `main`, not by their state. Likely candidates seen
at design time are #402, #593, #600 and #621. The sweep decides; this list is not a verdict.

**Ledger write.** This is one task, after the re-checks and the sweep:

- update each row's State and Evidence, keeping July's text wherever the state changes, with a dated
  M19 note;
- add a §3b section, "Found since July (Phase 19.1)", for the candidates, laid out like §3a;
- rewrite the §0 scoreboard with counts that come from the rows, not from memory;
- change the status-date line to name Phase 19.1 and the anchor commit.

**Public consistency.** The 1.0-status section of `website/docs/api-stability.md` (around `:300–330`)
and `README.md`'s status paragraph are checked against the new scoreboard. A claim that is now false
is corrected, without adding counts to the README.

**Owner review.** The owner reviews the drafted ledger and rules on each candidate's class and on
whether it becomes a new phase. The rulings are written into the file with the date. Any new phase
is added with `add-phase` in the same PR.

## Tests

This is a docs phase, so no product code changes. What proves it done:

- **Evidence log completeness.** Every row (A1–A5, S3, S4, P1–P4, Q1–Q5, #209–#211, D1–D4, R1–R4) has
  a log entry with an anchor `file:line` or a reason why it has none. Every issue in the sweep set
  has exactly one verdict. The set is re-queried at the end, so issue counts are compared with
  `gh`'s answer, not with this design.
- **Re-proofs** that ran are run on a clean tree from a scratch commit, and the scratch commit is
  then dropped. Each records the command and its red output.
- **Ledger consistency.** Every count in the §0 scoreboard is recounted from the rows.
- **Build.** `dotnet build BlazorNative.sln -c Release` stays green: nothing in `src` changes. When
  `website/` is edited, the docs site build lane must be green on the PR.

## Calls made after the builder check (mine, correct them if wrong)

- **A DOCUMENTED row needs its caveat to be published.** The class means "1.0 may ship with this
  false, provided the README or docs say so in named, specific terms". So for Q4, Q5, D3, R3, R4, S3
  and S4, while the row is still false, the re-check also confirms that the caveat appears where
  consumers read it: README, the docs site or shipped xmldoc. A plan file or tiers doc does not
  count. If the caveat is missing, the row is "caveat missing", and the ledger task either proposes
  the caveat text for the public-consistency step or, when no honest caveat fits, proposes promoting
  the row to a candidate BLOCKER for the owner's ruling. The public-consistency step widens to match.
- **The PR is ready only after the owner's rulings.** The phase finishes with one PR. A blocking
  owner review sits before the PR is marked ready, and the rulings, plus any `add-phase` /
  `insert-phase` edits, land in that same PR. Candidates are never merged as "proposed".
- **Placing a new phase.** A phase the owner adds goes before 19.8, which stays last. It is inserted
  with `insert-phase`, which renumbers 19.8, and the dependency note in MILESTONE.md and ROADMAP.md
  is updated to say what the new phase waits on.
- **Historical device proofs.** P1's (July Android device session) and P2's (simulator lanes) proof
  is re-checked by citing current evidence: the record file still exists, and the lane is green on
  the anchor or its latest run. It is not re-run.

## Open Questions

None for the owner before planning. The candidate rulings are made at review, by design.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A row is marked "still MET" on July's word | A stale claim survives into the 1.0 call | Each row needs a `file:line` at the anchor, or a re-proof. A row with neither is "unverified", not MET. |
| A closed issue's fix was reverted or partial | The scoreboard undercounts | A closed issue counts as fixed only when the fix is located in the code at the anchor. |
| The sweep turns into triage of every issue | The phase balloons | One verdict line per issue. Candidates are classed, not fixed. |
| A mutation re-proof leaves the tree dirty | Docs edits get wiped or swept into a commit | Commit first, check that the tree is clean, then mutate in a scratch commit and drop it. |
| `website/` edits red the docs build | The PR is blocked | Keep website edits to sentences that are now false. Run the site build lane on the PR. |
