# Phase 14.1 Design — The Dispatch Twins

**Date:** 2026-09-21
**Phase:** 14.1
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [14 — Twin Divergence, Closed Mechanically](2026-09-21-milestone-14-design.md)
**Closes:** [#339](https://github.com/MarcelRoozekrans/BlazorNative/issues/339)
**Carries:** M14's central DoD claim — *the semantic sub-shape is closed by a pin, and a NEW
divergence reds.*

## Goal

Give the Apple shell the same two-method dispatch split the Android shell already has, so the
lifecycle caller stops blocking the serial lane; declare that dispatch surface once and pin both
shells to it; and reproduce #339 as a .NET test so the deadlock becomes a required-lane failure
rather than a device-only one.

## The divergence, measured

`dispatchHostEvent` exists in both shells, spelled identically, and blocks in one:

| | Android — `BlazorNativeRuntime.kt` | iOS — `BnRuntime.swift` |
|---|---|---|
| `dispatchEvent` | `:107` async | `:161` async |
| `dispatchEvent` + `onComplete` | `:135` | `:190` |
| `dispatchEventBlocking` (test seam) | `:163` | `:207` |
| `dispatchCore` (private) | `:196` | `:212` |
| **`dispatchEventAndWait`** | `:183` | **absent** |
| `dispatchHostEvent` | `:230` — **fire-and-forget** | `:320` — **blocking** |
| **`dispatchHostEventAndWait`** | `:278` | **absent** |

**The divergence is structural before it is semantic.** Swift is missing *both* `AndWait` methods,
so its single `dispatchHostEvent` does the job of Kotlin's two — which is exactly how a lifecycle
caller ended up on a blocking path. Swift's `sync` body was written for the deep-link/navigate
caller, where Android uses `dispatchHostEventAndWait`, and the lifecycle caller was later pointed
at the same method.

Kotlin's KDoc states the hazard its twin does not: *"Safe to call from any thread EXCEPT the
dispatch lane itself — a call FROM the lane would SELF-DEADLOCK."*

## Spike findings (2026-09-21) — measured, not reasoned

A throwaway spike asked whether the root cause could simply be removed: can
`Exports.DispatchEventCore` stop blocking when a handler goes async? Everything built was
discarded; these are the results.

**1. The deadlock reproduces in a pure .NET unit test.** Setting
`FakeShellHost.AutoCompleteHostCall = false` — the harness's existing *"hold the call open"* flag,
which is exactly the device condition while a permission sheet is up — and dispatching one click
to `BnCameraDemo`'s "Take Photo" handler **hangs indefinitely**. Killed at 150s. No device, no
simulator, no Swift involved.

**2. `Exports.cs:495`'s comment is false, and now provably so.** It reads *"`GetAwaiter().GetResult()`
is the sync contract, not a blocking wait: the InlineDispatcher completed the work before the Task
was handed back."* True for a synchronous handler — `InlineDispatcher.InvokeAsync` runs the work on
the calling thread and returns `Task.CompletedTask`. **False the moment a handler awaits an open
host call**, which is when it matters. Another safety claim with no mechanism behind it.

**3. Returning early on an incomplete Task frees the lane.** With a probe that returns instead of
blocking, the same dispatch returned `rc=0` in **42 ms** with the host call still open.

**4. The suite never produces the condition — by one flag.** `CameraBridgeTests`,
`GeolocationBridgeTests`, `NotificationBridgeTests` and `SecureStorageBridgeTests` all hold calls
open, but they call the bridge **directly**. No test holds a call open *through dispatch*. All 1076
tests pass with the probe applied, because none of them can tell the difference.

**5. So there is a THIRD invisibility seam, and it is the .NET one.** @ceesalberts named two on the
Swift side — `BnAppLifecycle.sinkForTest`'s early return and the camera XCTest's
`suppressSystemCameraPresentForTest`. This is the same fake one layer down, in the language that
actually holds the lane. Four fakes across three languages, each individually reasonable,
together making the defect unreachable everywhere.

**What the spike did NOT settle**, and why the redesign is not in this phase: returning `rc=0`
claims *"handled"* while the handler is still running. **Android's back needs a genuine 0/1 verdict**
and cannot get one from a handler that has not finished — `OnBackInvokedCallback` has no
"I'll tell you later". The dispatch-window guarantee (frames delivered before the export returns)
is broken for async handlers. And nothing observes the handler's eventual completion or fault
beyond a log line. The fix is **viable, not proven**.

## Decisions

1. **Mirror the split; do not redesign the dispatch contract.** Swift gains
   `dispatchHostEventAndWait`; `dispatchHostEvent` becomes fire-and-forget. The blocking body
   survives verbatim under an honest name, and only the caller that should never have blocked
   stops.
2. **The pin is a declared manifest plus a source scan of both shells** — the idiom 14.0 proved.
   The contract is readable in one file rather than inferred from a regex, and when it reds it can
   say which side is wrong.
3. **The pin asserts STRUCTURE and approximates semantics. Say so everywhere.** It compares each
   method's lane-call shape against a declared intent; it does not observe blocking at runtime. A
   genuinely behavioural cross-shell pin would need a JVM test and an XCTest that agree with each
   other — itself an unpinned twin, in the phase about unpinned twins — and has no single-host
   form. 14.0's final review caught this exact overclaim; this phase must not repeat it.
4. **Asymmetry is allowed but must be declared with a reason.** Kotlin's `dispatchEventAndWait` is
   consumed only by `InspectorHost`, a JVM-only dev tool with no iOS counterpart. A naive
   both-shells-must-match pin would force Swift to grow a method with no consumer — manufacturing
   dead code to satisfy a guard. Each manifest entry carries an optional `platforms` with a written
   reason, exactly like `GeneratedSymbolShadowTests.UnconsumedByDesign`.
5. **The invisibility fix is the .NET reproduction, not a Swift proxy.** It reproduces the actual
   bug in the required lane rather than asserting a stand-in for it, and it is the prerequisite any
   future async-dispatch redesign needs in order to prove itself.
6. **Android's suspected exposure is MEASURED, not fixed.** `dispatchHostEventAndWait` does
   `future.get()` and `MainActivity:522` calls it from the main thread inside the back callback,
   while the lane-holding condition (`Exports.DispatchEventCore`) is .NET-side and common to both
   shells. Whatever the measurement returns is recorded; a positive result becomes an **issue**,
   because widening scope mid-phase is how 14.1 stops being early enough to re-scope from.

## Approach

**The Swift split.** `dispatchHostEvent(_:payload:)` becomes `dispatchLane.async` — matching its
own sibling `dispatchEvent`, which already uses `.async` at `:192`, so this is making a method
match the file it lives in rather than introducing a new pattern. `dispatchHostEventAndWait(_:payload:)
-> Int32` takes the current `dispatchLane.sync` body unchanged. `BnAppLifecycle.dispatch` moves to
the former; `BnRuntime`'s two `navigateDispatcher` closures and `BnNotifications.fireNavigate` move
to the latter, because they consume the rc.

**The declared surface.** `src/dispatch-surface.json` declares each method once: `name`,
`semantics` (`fire-and-forget` | `blocking`), optional `platforms` + `reason`. A new test scans
both runtime sources and asserts the declared set matches what each shell carries, and that each
method's lane call matches its declared semantics — Kotlin `execute` vs `submit`/`get`, Swift
`.async` vs `.sync`. It reuses `GeneratedSymbolShadowTests`'s source-scanning machinery
(comment-stripped `CodeLines`, both trees) rather than inventing a parallel one.

**The reproduction.** A .NET test mounts `BnCameraDemo`, sets
`FakeShellHost.AutoCompleteHostCall = false`, dispatches the "Take Photo" click, and asserts
`DispatchEventCore` **does not block**. It must be written so a regression *fails* rather than
hangs — an xUnit timeout, or dispatching on a worker and asserting on a bounded wait. A test that
hangs the suite is not a usable guard, and the spike hung a 150-second run to learn this.

**The Android measurement.** The JVM suite's `HostEventTest` already drives the lane. Determine
whether `dispatchHostEventAndWait` from a non-lane thread deadlocks while the lane is held, record
the result in the phase conclusion either way, and file an issue if positive.

**Ordering.** Fix first, declare second — the declared set will not match until Swift has
`AndWait`, so writing the pin first would red the branch mid-phase for a reason that is not a
defect.

## Tests

- **Unit (.NET):** the differential pin — declared set vs both shells, and lane-call shape vs
  declared semantics. Mutation-proven in **both** directions: flip a declared semantic and it must
  red; add a method to one shell only and it must red.
- **Regression (.NET):** the #339 reproduction. Mutation-proven by reverting the Swift split —
  except the reproduction is .NET-side and shell-independent, so it is proven instead by restoring
  `.GetAwaiter().GetResult()`'s blocking behaviour in a scratch build and confirming the test fails
  rather than hangs.
- **Unit (JVM):** the Android measurement, whichever way it lands.
- **Integration (Swift/XCTest):** existing lifecycle and deep-link suites must pass **unchanged in
  behaviour**. Not one wire byte moves; only which method a caller names.
- **CI:** `ios.yml` dispatched manually on the branch — it does not run on feature-branch pushes,
  and there is no Swift toolchain on the development machine.

## Open Questions

None blocking. The async-dispatch redesign is deliberately deferred with its agenda already
written: the rc contract for a handler that has not finished, Android's back verdict, the
dispatch-window guarantee, and completion/fault observation. It now has a working harness waiting
for it, which is what this phase contributes to it.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **The pin approximates semantics but reads as proving them** | 14.0's overclaim repeated in the phase that should know better | The pin's name, its failure message and this spec all say *structural*. It asserts declared-vs-source agreement, never observed blocking |
| **The reproduction hangs the suite instead of failing it** | A guard that hangs CI is worse than no guard — the spike hung a 150s run proving exactly this | Bounded wait or xUnit timeout, asserted explicitly. Verify the failure mode, not just the pass |
| **Swift is unverifiable locally** | A compile error surfaces late | The 14.0 protocol: static review weighted as the first real check, then a dispatched `ios.yml` run immediately after commit |
| **The pin's regex misreads a refactor** | False red, or worse, false green | Scope patterns to the declared method names; mutation-prove both directions. A pattern that cannot red is the failure mode to hunt |
| **The Android measurement turns positive** | A second live deadlock, mid-phase | File it, do not fix it. Decision 6 exists precisely so this does not consume the phase |
| **Scope drift into the async redesign** | 14.1 stops being early enough to re-scope from, which is why it is sequenced first | The redesign's agenda is written down here and deferred. This phase ships the harness it will need |
