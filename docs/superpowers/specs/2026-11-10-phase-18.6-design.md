# Phase 18.6 Design — Test-suite honesty, part two (#543, #544)

**Date:** 2026-11-10
**Phase:** `18.6`
**Surface:** Infra
**Stage:** phase (one phase, implementation-ready)
**Status:** draft

## Goal

A JVM test stuck on a lost host-call completion fails by name instead of silently using up the 45-minute CI job. Every Android back press that expects a handled back fails in the press's own main-thread turn if that press also finishes the Activity.

## Why

Both issues come from Phase 17.7's mutation runs, and both are tests that hide the regression they exist to catch.

- **#543.** S-mutation "the completer never calls the export" cancelled the `build-test` job at 45 minutes, and the log held no JVM result at all. One stuck test cost every result in the run.
- **#544.** S4, `finish()` after the back dispatch, failed in one run and passed in the next on the same mutation. The back tests check `isFinishing` only after a poll, so a finish is caught only when the destruction beats the poll. `back_at_root_finishes_the_activity` can even pass for the wrong reason.

## How it works today

- `BlazorNativeRuntime.dispatchHostEventAndWait` (`BlazorNativeRuntime.kt:401`) waits on the dispatch lane with an untimed `future.get()`. It is `internal` and test-only (16.2, #346; `DispatchHostEventAndWaitVisibilityTest` pins that).
- `BackNoticeTest.back_hold_probe_holds_the_lane_until_its_camera_call_is_released` calls it on the test thread, while `BackHoldProbe.Hold()` blocks the render thread on a camera call that only the test's releaser thread completes. A lost completion wedges both for the life of the JVM.
- `HostEventTest.kt:344` already shows the bounded form: the blocking back runs on a helper thread and the test `join(2_000)`s it.
- The Gradle `Test` block (`build.gradle.kts:259`) sets no timeout. There is no `junit-platform.properties` and no `@Timeout` in the module. JUnit Jupiter is 6.1.3.
- On Android, `goForwardAndBackToTheRoot` (`BackAndroidTest.kt:348`) and `predictive_back_returns_to_bndemo` (`HostEventAndroidTest.kt:128`) press back and then only poll. `pollUntil` (`Poll.kt`) reports a finished Activity only once it is DESTROYED.
- Four press sites already check `isFinishing`, each written separately: `RecreationAndroidTest.kt:110-113` in the press's turn (17.7's `f01037d9`), and `BackAndroidTest.kt:119`, `:206`, `:253`, `:290` in a later turn.

## Goals

- #543, as the owner decided on 2026-10-24: a **bounded wait** in the test, plus a **per-test timeout** on the Gradle test task.
  - The hold-probe test fails with a message naming the lost release, within a bound, on a lost completion.
  - No single JVM test can hold the step anywhere near 45 minutes. The job log names the test that stuck.
- #544, as the owner decided on 2026-11-10 (shared press helper):
  - One helper presses a handled back and asserts `!isFinishing` in the same main-thread turn.
  - Every press that expects a handled back uses it, so a new back test cannot forget the check.
  - S4 reds all five tests named in #544 at the helper's line, in every run.

## Non-goals

- **Unwedging the probe.** Bounding `BackHoldProbe.Hold()`'s sync-over-async wait changes the scaffolding's contract. #543 lists it as the third option; the owner chose the first two.
- **Changing `pollUntil`.** Making every poll fail on `isFinishing` was offered and not chosen.
- **The production back path.** `dispatchHostEventAndWait` stays as it is: internal, test-only and untimed. The bound lives in the test, as in `HostEventTest`.

## Anti-goals

- A timeout that hides a slow path. The per-test bound sits well above the slowest passing test, measured, not guessed. A test that is merely slow must still pass.
- A check that can pass vacuously. Each new site gets a fresh red under its mutation, per `docs/pin-standard.md`, "Grading a pin: sites and reds".

## Design

### D1. The hold-probe test's bounded wait (#543)

In `back_hold_probe_holds_the_lane_until_its_camera_call_is_released`, run `dispatchHostEventAndWait(BnHostEvent.Back)` on a daemon helper thread that records its rc and return time, and `join` it with a bound, as `HostEventTest.kt:344` does. The releaser fires at 1.5 s, so a bound of 10 s leaves wide margin. If the helper is still alive after the bound, fail with a message that names the cause: the held camera call's completion never reached .NET, so the render thread is still inside `Hold()`. An exception thrown on the helper is carried back and rethrown on the test thread.

The test's existing assertions stay: the back returns after the release, rc 0, and the `released:Cancelled` frame.

Sweep the JVM test module for any other untimed wait on the lane or a host call (`future.get()`, `join()`, `await()` with no bound) and bound it the same way. Today's grep finds only this one. The sweep result goes in the record.

### D2. The Gradle per-test timeout (#543)

In the `tasks.withType<Test>().configureEach` block, set a JUnit Jupiter default timeout through system properties:

- `junit.jupiter.execution.timeout.default`: the per-test bound.
- `junit.jupiter.execution.timeout.thread.mode.default = SEPARATE_THREAD`. A test stuck in a JNA call does not answer an interrupt, so the same-thread mode cannot end it. In the separate-thread mode, JUnit abandons the stuck thread and fails the test by name.

Also set the task's own `timeout` as a backstop below the job's 45 minutes. Once one test wedges the render thread, every later JNA test blocks in `start()` and times out on its own, so per-test bounds alone can still add up past 45 minutes. The backstop ends the step; `testLogging` already prints each `FAILED` line as it happens, so the log names the first stuck test even if Gradle writes no XML.

**Proposed values, to be confirmed by measurement in the plan:** 120 s per test, 25 minutes for the task. The plan's first task measures the slowest passing JVM test and the step's normal duration. The per-test bound must be at least 3× the slowest test, and the task bound must be at least 2× the normal step and under 45 minutes. If the measurement contradicts these numbers, the plan uses the measured ones and records why.

### D3. The shared press helper (#544)

Add `pressHandledBack(scenario)` next to `pollUntil` in `Poll.kt`, shared by the androidTest classes. In one `scenario.onActivity` turn it calls `onBackPressedDispatcher.onBackPressed()` and then asserts `assertFalse(<message>, act.isFinishing)`. The message says the back was enabled and handed to .NET, so a handled back must not also take the platform's default. `finish()` sets `mFinished` synchronously, so a finish on the press path fails deterministically. The only legitimate finish, `BackUnhandled`, arrives on a later main-thread turn.

The test at `BackAndroidTest.kt:193` times the press itself (#346: the press returns at once). The helper therefore returns the press's elapsed milliseconds, measured around `onBackPressed()` only, so that test can use it too.

Use it at every press that expects a handled back:

- `BackAndroidTest`: the helper `goForwardAndBackToTheRoot` (`:354`), `:112`, `:193`, the modal dismissal at `:285`, and the press inside the poll at `:236` if the poll's shape allows it.
- `HostEventAndroidTest.kt:128`.
- `RecreationAndroidTest.kt:110`, replacing its hand-written in-turn check.

The later-turn checks (`:119`, `:206`, `:253`, `:290`, `RecreationAndroidTest.kt:117`) stay. They catch a finish that comes after the press's turn, which the helper cannot see.

The root press, `back_at_root_finishes_the_activity` (`:136`), stays raw: that back is meant to finish. Its vacuity in #544 came from the helper letting a finishing Activity through earlier in the test, which D3 closes.

## Approaches

- **#543** was decided by the owner on 2026-10-24: the bounded wait plus the Gradle per-test timeout. Unwedging the probe was the rejected third option.
- **#544**, decided by the owner on 2026-11-10, from three options:
  - **Shared press helper (chosen).** One helper carries the in-turn check, and every handled-back press uses it. The rule becomes structural, and the four separate checks fold into it.
  - **The issue's two sites only.** The smallest diff, but every future back test must remember the check, and forgetting it is how #544 happened.
  - **Helper plus a `pollUntil` guard.** Catches a finish everywhere, but changes polling for every Android test, including tests that expect a finish. Too broad for this phase.

## Calls made in this design

- The task-level backstop timeout in D2, on top of the per-test bound, because a wedged render thread makes later tests time out one by one.
- The `SEPARATE_THREAD` timeout mode, because a JNA-blocked thread does not answer an interrupt.
- The proposed numbers (120 s, 25 min) are placeholders the plan's measurement confirms or replaces.
- The later-turn `isFinishing` checks stay alongside the helper.
- The helper returns the press's elapsed time so the #346 timing test can use it.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Gradle writes no XML report when the task timeout fires | `ci.yml`'s count step reads nothing | `testLogging` prints each failure as it happens, so the log still names the stuck test. The plan observes what Gradle writes in D4's red and records it. |
| `SEPARATE_THREAD` changes thread-sensitive tests (thread names, ThreadLocals) | Passing tests start to fail | Run the full JVM suite with the setting before the reds. Any test that depends on the test thread gets a per-test override, with the reason recorded. |
| A per-test bound below a slow but healthy test on a cold CI runner | A new flake | Set the bound from measurement, at least 3× the slowest test (D2). |
| S4 still passes one run of five tests | The pin stays timing-dependent | The check is in the press's own turn, which no timing can skip. D4 runs S4 twice to show it. |
