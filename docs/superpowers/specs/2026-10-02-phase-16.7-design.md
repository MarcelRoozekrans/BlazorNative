# Phase 16.7 Design — Make the rc contract true (#455)

**Date:** 2026-10-02
**Phase:** 16.7
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

**Closes:** [#455](https://github.com/MarcelRoozekrans/BlazorNative/issues/455). This phase lifts the
MET NARROWLY verdict on DoD item 7, "#8 is fixed", in the
[16.5 audit](../../plans/2026-10-01-milestone-16-audit.md).

## Goal

If a handler faults after it has begun a host call or a fetch, the shell gets a FaultNotice and
the dispatch returns rc 0. It never gets rc 2. This holds whether the shell answers the call
inside `hostCallBegin` / `fetchBegin` or later, so Android and iOS behave the same. The contract
that states this is the same in its three copies, and a pin keeps it so.

## Background

`NativeShellBridge` begins a host call or a fetch, then awaits a `TaskCompletionSource`. When
the shell completes the call **inside** begin, as Android's geolocation `check`, biometrics
`check` and plain secure-storage arms do (#440), the task is already complete at the `await`.
The handler then runs straight on, and a throw after the await is still in the synchronous part.
The export returns rc 2 and sends no FaultNotice. #455 measured this on `0779982`.

The same handler on iOS, where these calls answer later, yields at the await. Its throw arrives
as a FaultNotice with rc 0. So the outcome depended on the platform, not on what the handler did.

## The first design, and why it was abandoned

The first design for this phase, on the branch `feat/16.7-rc-contract` (kept on origin at
`5847d1d` as reference), forced a yield after begin. It was implemented and reviewed, and the
reviews measured three ways that **any fix that moves the handler's continuation** fails:

- **`Task.Yield()` captures the render thread's context.** The bridge's continuation is then
  posted back to the render thread. App code that blocks the render thread on a host call
  (`.GetAwaiter().GetResult()`) deadlocks, even when the shell answers asynchronously. Before
  this phase, that code finished. Measured: `BackNoticeTest` hung for 30 minutes.
- **`ConfigureAwait(ConfigureAwaitOptions.ForceYielding)` does not capture the context.** The
  bridge then finishes on the pool and can complete before the handler's own `await` checks the
  task. The handler then does not suspend, so the fault is rc 2 again. Measured: the inline facts
  went red in 7 of 15 runs.
- **A mount breaks.** A page whose `OnInitializedAsync` awaits an inline-answered call no longer
  renders synchronously, so `Mount<T>` throws.

A scheduling fix can only post the continuation to the render thread, which deadlocks, or to the
pool, which races. So this phase **classifies the fault instead of moving the continuation**.

## Decisions (owner, 2026-10-02)

- **Change the code, not the words.** Decided 2026-10-01 and recorded in the ROADMAP.
- **Scope: host calls and fetch.** These are the two shell calls a handler awaits through
  `NativeShellBridge`.
- **Classify the fault; do not change scheduling.** This was chosen after the first design's
  measurements above. Two alternatives were rejected:
  - a hand-written `IValueTaskSource` that wraps every public bridge method and changes their
    return types, and still has to be proven against both the deadlock and the race;
  - pausing the phase.
- **The contract's boundary becomes "began a shell call", not "yielded".** A throw between
  starting a call and awaiting it also counts as after the call. That makes the rule
  deterministic, and the same on both platforms.
- **Release: a `BREAKING CHANGE:` footer.** With the pre-major config,
  `bump-minor-pre-major: true`, this ships as 0.18.0. The footer states the 16.1 rc meaning,
  which never got a release note, and the new rule. It says nothing about mounting, because
  mounting is unaffected.
- **A fresh branch, `feat/16.7-classify-fault`, from `origin/main`.** The first design's commits
  carry a BREAKING footer about the mount break, which is false here, and the repo's squash merge
  puts every commit message into the release notes. Only work that still holds is carried over.

## Approach

### 1. Mark the dispatch when a shell call begins

`NativeRenderer`'s `DispatchScope` (`NativeRenderer.cs:~1546`) gains `ShellCallBegun`.

A new internal static hook on `NativeRenderer` marks the scope of the synchronous part that is
running **on the calling thread**:

- it sets `ShellCallBegun = true` on that scope, unless the scope has already captured a fault:
  the mark is ordered, so a fault raised before the first begun call stays rc 2 even when a
  later part of the same synchronous part begins one;
- if no synchronous part is running on that thread, it does nothing;
- it is safe to call from anywhere.

`DispatchSyncPart` already sets and restores `_currentScope` around the synchronous part. The
hook needs a thread-bound view of that same scope, for example a `[ThreadStatic]` set and
restored next to `_currentScope`. It must never use the flowing `AsyncLocal` scope, which would
also mark from continuations.

`NativeShellBridge` calls the hook after the shell accepts the begin, after `BeginHostCall`
and after `BeginFetch` return normally. A begin the shell refuses throws into the handler
before any call is begun, so that fault stays rc 2.
A notice that .NET sends itself (FaultNotice, BackState, BackUnhandled) also goes through the
host-call path, but it is not a shell call the handler began, so it never marks. The exclusion
is structural, not a list of ops: `InvokeHostCallAsync` takes `markDispatch`, true by default,
and `SendNotice`, the one path every notice goes through, passes false. Without that
exclusion, a notice sent during the synchronous part would turn a real synchronous fault into
rc 0.
**The await code is not changed.** Scheduling is exactly as it was before this phase.

### 2. Classify the fault

At the end of `DispatchSyncPart` (`NativeRenderer.cs:~1793-1873`), a fault in the synchronous
part is classified as **`FaultedAfterShellCall`** when the scope's `ShellCallBegun` is set. It
stays plain `Faulted` otherwise. That fault can be captured by the scope or carried by a task
that is already faulted.

`Exports.DispatchEventCore` handles `FaultedAfterShellCall` this way:

- It sends the FaultNotice through the existing late-fault delivery, `DeliverLateFault` /
  `SendFaultNotice`.
- The notice carries the same handler id, event name, exception type and message as a fault
  after a yield. Its flat-JSON args never carry a stack trace or the event payload.
- It returns **rc 0**.

A fault before any shell call still returns rc 2. Whatever logging the synchronous fault already
gets stays as it is.

### 3. The contract

The contract is rewritten identically in three copies, each between `BEGIN rc-contract` and
`END rc-contract` markers:

- `src/BlazorNative.Runtime/Exports.cs`, the dispatch summary at `~:470`;
- `src/BlazorNative.Apple/BnHost/BlazorNativeRuntimeC.h`, at `~:133`;
- `website/docs/guides/threading.md`, at `~:39`.

> rc reports the SYNCHRONOUS part of the handler: 0 = it did not fault, or it faulted only after
> it began a host call or a fetch (it may still be running); 2 = it faulted before beginning one.
> A fault after the handler has begun a host call or a fetch arrives as a FaultNotice host-call
> op, never as an rc, whether the shell answers inside `hostCallBegin` or later. Frames from the
> synchronous part are delivered before the export returns; frames from a continuation are
> delivered later, from the render thread.

The return-code lists in `Exports.cs` and the header are updated to match. `threading.md`'s
plain-terms paragraph states the rule once.

## Tests

All pins follow `docs/pin-standard.md`. Every mutation is run and recorded.

1. **Inline host call, then a throw.** rc 0 and exactly one FaultNotice, carrying the handler
   id, `event`, `type` and `message`. Anchor: the fake completed the call inside begin.
2. **Inline fetch, then a throw.** The same as 1, for fetch.
3. **Begin without await, then a throw.** `var t = Bridge.Check…(); throw …;` gives rc 0 and a
   notice. This pins the "began" boundary.
4. **Notice exclusion.** A handler that sends a .NET notice and then throws still returns rc 2.
5. **Control, no shell call.** `await Task.CompletedTask; throw` gives rc 2 and no notice; the
   absence is checked after the dispatch has settled. The existing synchronous-throw control
   stays.
6. **Regression guard: mount.** A page whose `OnInitializedAsync` awaits an inline-answered call
   mounts synchronously, as it did before this phase.
7. **Regression guard: blocking.** The bounded `BackHoldProbe` pin. With `BackHoldProbe`
   unchanged, blocking the render thread on an asynchronously answered camera call releases when
   the shell answers. It reds within its budget and never hangs.
8. **The copies pin**, over the new text.
9. **JVM, through the NativeAOT dll.** Fact 1's scenario, with the camera call answered inside
   `hostCallBegin`. It asserts the completion rc is 0, and that the fault text starts with the
   held-call fact's prefix and type.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The hook marks from the wrong thread or scope | A fault in another dispatch, or in a continuation, is reclassified | Thread-bound view only, set and restored with `_currentScope`; the `AsyncLocal` mutation row. This does not prevent every misattribution: a continuation of dispatch A that runs inline inside dispatch B's synchronous part, begins a call there and faults marks B, and its fault is captured in B's window. That is the 16.1 window-attribution defect, filed as #464, and is not pinned as correct. What the M4 fact pins is narrower: a call begun on another thread does not mark the dispatch |
| A shell call started on another thread inside the handler, such as in `Task.Run`, is not marked | That fault stays rc 2 | Named in DOES NOT COVER; the contract says "the handler has begun" |
| The reclassified fault skips logging or cleanup the plain Faulted path did | A lost diagnostic | Section 2 keeps the existing synchronous-fault logging; a fact asserts the session survives and the next dispatch works |
| `DeliverLateFault` assumes a pending task | A null dereference or a double notice | Read it first; facts 1–3 assert exactly one notice |
| The squash merge carries an unparseable commit | release-please drops it | commit-parse-check over every commit and the title; confirm the release-please PR after merge |
| `Closes #455` plus another closing keyword | The wrong issue is closed | Grep the body and commits before opening |
