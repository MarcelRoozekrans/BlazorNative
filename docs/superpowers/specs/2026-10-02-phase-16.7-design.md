# Phase 16.7 Design — Make the rc contract true (#455)

**Date:** 2026-10-02
**Phase:** 16.7
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

**Closes:** [#455](https://github.com/MarcelRoozekrans/BlazorNative/issues/455). Lifts the MET
NARROWLY on DoD item 7 ("#8 is fixed") of the
[16.5 audit](../../plans/2026-10-01-milestone-16-audit.md).

## Goal

A fault after a handler's first await on a host call or a fetch reaches the shell as a
FaultNotice and never as an rc. This holds even when the shell completes the call inside
`hostCallBegin` or `fetchBegin`. The rc contract that says so is identical in its three copies,
and a pin keeps it that way.

## Background

`NativeShellBridge` awaits a `TaskCompletionSource` after calling the shell's begin slot: the
host-call path is at `NativeShellBridge.cs:462-486`, and the fetch path at `:318-344`. When the
shell completes the call inside begin, as Android's geolocation `check`, biometrics `check` and
plain secure-storage arms do (#440), the task is already complete at the `await`.

The `await` then does not yield. The handler's throw after it is still part of the synchronous
part, and the export returns rc 2 with no FaultNotice. #455 measured exactly this on `0779982`.
`RunContinuationsAsynchronously` does not help, because it only affects a completion that
happens *after* the await.

## Decisions (owner, 2026-10-02)

- **Change the code, not the words.** This was decided on 2026-10-01 and recorded in the ROADMAP.
- **Scope: host calls and fetch.** Both bridge paths share the inline-completion shape.
  - The contract promises a yield only for awaits on a shell call.
  - It says plainly that awaiting a task the app already completed itself does not yield. That is
    C# semantics, which no runtime can change.
  - Promising that *any* first await yields was rejected. It would need an unconditional hop
    before every handler, which changes the synchronous part of handlers that never await and
    breaks the sync-mount contract that `MountSyncTests` pins.
- **Approach A: yield at the await site.** Two other approaches were rejected:
  - Deferring the completion in `CompleteHostCall` and `CompleteFetch` through a thread-static
    re-entrancy flag. That has more moving parts and changes completion order for every caller.
  - Changing the words instead of the code.
- **Release: a `BREAKING CHANGE:` footer.** The pre-major config, `bump-minor-pre-major: true`,
  makes this 0.18.0. The notes get a "⚠ BREAKING CHANGES" section.
- **The yield is unconditional, and a page that awaits a shell call in `OnInitializedAsync` no
  longer mounts (owner, 2026-10-02, after the final whole-branch review).** The final review
  found that the yield makes such a page fail `Mount<T>` with "requires
  RenderRootComponentAsync to complete synchronously" when the shell answers inside begin. That
  page mounted on Android before 16.7; on iOS it already failed. The owner ACCEPTED this as part
  of the 0.18.0 break, to be documented and pinned rather than worked around. The same review
  found a race in the guarded yield, so the guard was dropped: see §1.

## Approach

### 1. The code

There are two sites in `src/BlazorNative.Runtime/NativeShellBridge.cs`: the host-call await, and
the fetch await. Directly after `BeginHostCall` or `BeginFetch` returns, and before the
cancellation registration and the await, every call does `await Task.Yield();`, with no
condition. The comment at each site says why and names its pins, so it is not an unenforced
safety claim.

**Why unconditional.** The design first guarded the yield with `if (tcs.Task.IsCompleted)`. The
final review found that guard racy: a shell completing the call on another thread between the
check and the await skipped the yield, so the handler's await did not suspend. Yielding on every
call closes that window by construction, and makes an inline-answered call and an
asynchronously answered one behave alike. M3 had measured the unconditional form all-green
before it became the shipped code, and the whole Runtime project was re-run on it: see the
record.

**Where the continuation runs.** On the render thread, `Task.Yield` posts the continuation to the
render dispatcher's queue. The handler resumes as ordinary later work, exactly like a call the
shell answered asynchronously. Its frames are delivered from the render thread, and a fault goes
through the existing late-fault path, `DeliverLateFault`, to a FaultNotice.

**What else changes, and what does not.** A call the shell answers asynchronously now takes one
extra hop through the dispatcher queue before its await; the handler suspends there as it would
have on the pending task, so nothing observable changes for it, which M3 measured. The
cancellation ordering comments stay true: a synchronous completion has already removed the id,
so the registration is a no-op either way.

**The mount consequence.** A root mount, `Mount<T>`, requires the first render to complete
synchronously. A page whose `OnInitializedAsync` awaits a host call or a fetch now always
yields there, so the mount fails, on Android as it already did on iOS. This is the accepted
cost in Decisions, documented in `threading.md` and pinned by
`FaultNoticeTests.APageAwaitingAnInlineCompletedHostCallInOnInitializedAsync_NoLongerMounts`.

### 2. The contract

The contract is rewritten identically in three copies:

- `src/BlazorNative.Runtime/Exports.cs`, in the dispatch summary at `~:470`;
- `src/BlazorNative.Apple/BnHost/BlazorNativeRuntimeC.h`, at `~:133`;
- `website/docs/guides/threading.md`, at `~:39`.

Each copy sits between `BEGIN rc-contract` and `END rc-contract` markers:

> rc reports the SYNCHRONOUS part of the handler: 0 = it did not fault before it first yielded
> (it may still be running); 2 = it faulted before yielding. An await on a host call or a fetch
> always yields, even when the shell completes the call inside `hostCallBegin` or `fetchBegin`,
> so a fault after the first such await arrives later as a FaultNotice host-call op, never as an
> rc. An await on a task the app already completed itself, such as `Task.CompletedTask` or a
> cached result, does not yield: a fault after it is still in the synchronous part, rc 2. Frames
> from the synchronous part are delivered before the export returns; frames from a continuation
> are delivered later, from the render thread.

The return-code list below the contract in `Exports.cs` and in the header is updated to match.
The rc 0 line becomes "did not fault before it first yielded", and the rc 2 line becomes "faulted
before yielding".

`threading.md`'s claim that the copies "can't drift apart" stays. It is now pinned, by item 6 in
the Tests section.

## Tests

All pins follow `docs/pin-standard.md`, and every mutation is run and recorded.

**.NET, in `FaultNoticeTests`, plus `RcContractCopiesTests` for item 6:**

1. **Inline host call, then a throw.** Expect rc 0 and exactly one FaultNotice, op 5, carrying
   the handler id and the exception type. This is #455's probe, committed and inverted.
2. **Inline fetch, then a throw.** Expect rc 0 and one FaultNotice.
3. **Inline host call, no throw.** Expect rc 0, with the handler's result appearing in a frame
   delivered after the export returns, and that frame delivered on the renderer's render thread.
4. **Control, Rule 3.** `await Task.CompletedTask`, then a throw. Expect rc 2 and no FaultNotice.
   This pins the contract's exception sentence.
5. **Anchor, Rule 2.** Facts 1–3 assert that `FakeShellHost` completed the call *inside* begin.
6. **The three copies agree.** Each file must contain exactly one `BEGIN`/`END rc-contract` block.
   The block bodies are compared after normalising comment prefixes and whitespace, and the files
   are read through `BnRepo.Root()`. A mismatch names the file.
7. **The mount consequence.** A page whose `OnInitializedAsync` awaits a host call the fake answers
   inside begin fails `Mount<T>` with the `RenderRootComponentAsync` message. Anchored on the call
   being answered inside begin; its control mounts a page that awaits only `Task.CompletedTask`.

**JVM, `FaultNoticeTest.kt`:** fact 1's scenario through the published NativeAOT DLL, with the
Kotlin test host completing inside `hostCallBegin`. This is the shape Android ships, and it
proves that `Task.Yield` behaves the same under AOT.

**iOS:** no new XCTest. The change is .NET-only, and `BnFaultNoticeTests` already pins the shell
side.

The risk as first written, that only the first frame changes, was wrong | Accepted by the owner on 2026-10-02 as part of the 0.18.0 break. Documented in `threading.md` and in the fix commit's `BREAKING CHANGE:` footer: move such awaits to `OnAfterRenderAsync`, or start the call in `OnInitialized` without awaiting it. Pinned by fact 7. Both device lanes run; a device test that goes red because a mount fails is reported, not papered over |
