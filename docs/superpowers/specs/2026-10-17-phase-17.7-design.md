**Surface:** `Mixed`
**Stage:** phase (one phase, implementation-ready)

- **Milestone:** [M17 — Close the Dispatch Lane's Debt](../../planning/MILESTONE.md)

## Goal

Make DoD item 11 true for every pin M17 added. Make item 5 hold without narrowing, and item 6's "proven on the Android device lane" hold for `retire()`. Then 17.8 can re-audit M17 and close it.

## Non-goals

- New behaviour beyond #537's hop.
- New pins beyond the `retire()` pin, the #537 pin, and reworks of pins that cannot red.
- Changing a pin's assertion to make it easier to red. A rework must make the pin stronger or more honest, never weaker.

## Approach

### 1. Recording a red

Each of the following gets a recorded red in this phase's record, `docs/plans/2026-10-17-phase-17.7-record.md`:

- the 18 pins with no red;
- the 26 pins whose anchor no recorded mutation enters;
- the two overlap anchors.

**What a red is.** A red is a mutation of the **subject code**, or for drift and scan pins of the **planted input**, that makes the pin's own assertion fail. The mutation must not be a test-file edit that deletes the assertion. Each red records:

- the pin;
- the mutation, as a diff or a one-line description with file:line;
- the anchor it enters;
- the command or run id with its `headSha` and attempt;
- the red message, quoted.

**Where each red runs.**

| Pin kind | Route |
|---|---|
| .NET | Locally |
| Pure-Kotlin JVM | Locally |
| JNA, `ci.yml` only | A throwaway draft PR titled `test(17.7): scratch re-red …`, closed with its branch deleted after the run. Several commits are allowed, one mutation per commit and run in turn. |
| Android device | Scratch refs `scratch/17.7-<id>`, dispatched with `android-instrumented.yml`, one run at a time. Delete the ref after the run is verified complete. |

**Batching.** Several mutations may share one run only if the record argues they cannot interfere. A mutation that crashes the process never shares a run (17.6's M4).

**Mutation hygiene,** per [mutations on a dirty tree]:
- commit before mutating;
- mutate in a separate detached worktree;
- `git status --short` must be empty before each mutation and after its restore.

### 2. A pin that will not red

When no subject mutation can fail a pin's assertion, the pin is vacuous or its assertion is unreachable. In that case:

1. **Rework the pin until a real mutation reds it,** then record that red. The rework is a test change in this phase, and the register cell names it.
2. **If no honest rework exists, remove the pin.** Its register cell then says why, and points at what does pin the property.

*Builder's call: the cancellation fact's rc assertion at `FaultNoticeTests.cs:726` is the known instance. #494 and 17.1 named it unenterable. It is NOT one of the 18. It is graded on item 4, where it narrows. Leave it; correct only the MILESTONE text that claims "all #494 anchors redded" (§6).*

### 3. `retire()` wiring (#538 §4, DoD item 6)

17.3's L1 showed that removing `retire()` leaves every device test green, because the .NET unmount already stops the old root rendering. This phase adds a device pin that reds without `retire()`.

**The pin:**
- After a rotation, the **previous** Activity's `BlazorNativeRuntime` instance reports itself retired.
- A test-only accessor reads the retired state. It follows the existing `…ForTest` pattern, as in `WidgetMapper.foreignPatchesForTest`.

**Where it lives.** The pin goes in the reference shell. The template keeps its byte-identical mirror of `MainActivity`'s wiring; the existing mirror guard must stay green.

**Mutations, both on the device lane:**
- remove `retire()` at `MainActivity.kt:470`;
- for the template, show the mirror guard reds when `:483` diverges.

*Builder's call: asserting retired state is weaker than asserting a dropped frame, but L1 showed there is no frame to drop on the tested paths. The state is what `retire()` is for, so the state is what the pin holds.*

### 4. #537: a denied prompt completes on the executor

`onDenied` for `secureSetAuth` and `secureGetWithAuth` is routed through the secure-storage executor, exactly as `afterAuth` routes success, in both copies of `AndroidShellBridge.kt`.

**The pin** takes the after-auth pin's shape, from `AndroidHostCallContractTest.kt:151`: deny the gate on main through `biometricGateHook`, then assert that the completion ran on the secure-storage executor's thread, not on main.

**Mutation:** revert the hop, which must red the pin.

**Biometrics `authenticate`** also completes from the prompt callback, at `:759-764`. It stays as it is, because DoD item 5 names only `check` and the storage paths.

The 17.2 contract comment at `:271-280` says that each handler owns a serial executor and that the outcome arrives through `host_call_complete`. It does not say which thread a prompt's answer completes on. Extend it with one sentence:
- an auth-bound **storage** request completes on its executor, whether the prompt is granted or denied;
- `authenticate` completes from the prompt's own callback, because it does no work after the prompt.

That way the comment claims exactly what the code does.

**Interaction.** This touches the same auth path as #506, the ordering across a prompt. Do not change ordering. If the hop changes observable order, record that as a finding on #506.

## Risks

| Risk | Mitigation |
|---|---|
| A mutation is weakened until it "reds" something irrelevant | The red must fail the pin's own assertion, quoted; the reviewer checks each against the anchor |
| A batched run hides a mutation that would not red alone | Batch only with a written non-interference argument; 17.6's M3 race shows why |
| The `retire()` accessor leaks into the public API | `internal` or `@VisibleForTesting`, as `foreignPatchesForTest` is |
| The #537 hop reorders completions | Record it on #506; do not fix ordering here |
| A dirty-tree mutation wipes work | Use a detached worktree; commit before mutating |
