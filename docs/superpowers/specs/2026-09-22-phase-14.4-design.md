**Date:** 2026-09-22
**Phase:** `14.4`
**Surface:** `Mixed`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M14 — Twin Divergence, Closed Mechanically](../../planning/MILESTONE.md)
**Closes:** the last two M14 DoD items that are not audit — `Debug`/`Verbose` observable on a real
device, and the four documentation landmines — plus [#360][i360], which must land here or M14's
central claim is only conditionally true when 14.5 audits it.

[i17]: https://github.com/MarcelRoozekrans/BlazorNative/issues/17

## Goal

Make the framework's own diagnostics observable on real hardware, make the device slice build in
CI and prove it is the slice we think it is, and make the pin that closes this milestone's central
claim true **unconditionally** rather than for the shapes we happened to test.

## Four workstreams, one phase

They are grouped because they share one property: each is a place where **something claims to be
checked and is not**. That is the same fault M14 exists to close, so they belong together rather
than scattered across a milestone boundary.

| # | workstream | why it is here |
|---|---|---|
| 1 | **Pin hardening** — [#360][i360] | M14's DoD says *"a NEW divergence reds"*. Three reproduced shapes say otherwise |
| 2 | **`Debug`/`Verbose` on a device** | A DoD item, and a measured defect rather than a docs gap |
| 3 | **The device CI lane** | The shell's device slice has never been built in CI at all |
| 4 | **The documentation landmines** | A DoD item; one of them actively misdirects 14.4's own device tester |

**Ordering:** 4 before 3 where they touch the same file, and 1 is independent of everything. Only
one real dependency exists: **workstream 4's handover correction should land before anyone runs a
device checklist**, because it currently instructs the tester to exercise a control this milestone
deleted.

## Workstream 1 — Harden the pin (#360)

Phase 14.3 shipped `src/auth-semantics.json` + `AuthSemanticsDriftTests`. Three reviews each
defeated its central claim with a shape the previous round had not tried, and **each was
reproduced, not argued**. Two remain open plus two smaller ones.

**F1 — the scan is line-local.** `AuthSemanticsDriftTests.cs:218` splits on `\n` and confines every
match to one line, so a wrapped Kotlin token is invisible:

```kotlin
.canAuthenticate(BiometricManager.Authenticators
    .DEVICE_CREDENTIAL)) {
```

passes all three facts green; collapsing it to one line reds immediately. It affects every dotted
Kotlin token — three of eleven vocabulary entries. Swift is immune, because its tokens *begin* with
the dot, so a wrap carries the dot intact. `AndroidShellBridge.kt:896` is already 90 characters, so
a formatter is sufficient to trigger this. **Fix:** match over the whole stripped file text with
whitespace tolerated around the `.`, deriving line numbers from the match offset.

**F2 — the string-literal limit is real.** A URL inside a literal swallows the rest of the line via
its `//`, hiding a live undeclared `.userPresence`. The shells **already contain** `://` in string
literals at `BnDeepLink.swift:113` and `BnCamera.swift:415`; the recorded escape clause — *"neither
shell has one near an authenticator token"* — is a proximity accident, not a property. **Fix:**
strip `//` only when not preceded by `:` on the same line, or track string state.

**F3 — `ignored` promises enforcement it does not have.** The entry says *"if a production caller
ever does, this entry is a lie and should red"*. Making `provisionKey` request device credential
unconditionally leaves the pin **green**, because the ignore key is `file::token` and so excuses
every occurrence in that file. **Fix:** key by `(file, token, line)` — the `Occurrence` identity
already computed — or carry an expected count. Also correct its secondary claim that *"no shipping
caller passes true"*; `AndroidShellBridge.kt:1128` does, and while the substantive point holds, as
written it is falsifiable by one grep.

**F5 — the `$doc` misstates what the test reads.** It says no test reads `kind`; removing `kind`
reds two of three facts. What is true is narrower: the `kind` *value* is unchecked.

**The binding requirement on this workstream is the mutation set, not the fix.** Each of the three
rounds missed its successor's shape for the same structural reason — the mutations exercised
plausible *subject* behaviours and never the pin's own branches. So the fixes must be
mutation-proven against **tokenisation, comment-stripping, suppression, and ignore-matching**
individually, and the new mutations must include a wrapped token, a token after a `://` literal,
and a production widening of an ignored pair.

## Workstream 2 — `Debug` and `Verbose` observable on a device

**This is a measured defect, not a documentation gap.** From the device run:

> `Debug`/`Verbose` could not be observed at all. `BnLog` maps both onto `OSLogType.debug`, which
> the unified log does not capture unless the subsystem is enabled — and **`log config` has no
> `--device` flag**. On macOS 26 `log stream` has lost device support, `devicectl --console`
> carries only fd 1/2, and `OS_ACTIVITY_DT_MODE=YES` mirrors `os_log` to **fd 2** — which
> `BnStderrPump.install()`, the *first* statement in `viewDidLoad`, has already `dup2`'d away.
> Measured: exactly one UIKit line arrives pre-install, then nothing, even at `Verbose`.

Every route is closed, and the last one is closed **by our own code**.

**The fix: skip the pump when `OS_ACTIVITY_DT_MODE` is set.** The pump exists to rescue stderr
*into* the unified log. When a developer explicitly asks for the unified log mirrored *out* to
stderr, the pump is working directly against the thing they asked for. There is precedent for a
conditional skip — the pump already skips under XCTest — so this is a second condition on an
existing seam, not a new mechanism.

It also removes a question that cannot be settled on paper: with the pump installed *and* the
mirror on, `os_log` writes fd 2 → pump reads fd 2 → `BnLog` → `os_log` → writes fd 2. The measured
result was silence rather than a loop, but not creating the cycle is better than reasoning about
why it does not spin.

**`BnStderrPump.swift:34` already documents the install as "⚠ IRREVERSIBLE AND PROCESS-GLOBAL"**,
which is precisely why the decision must be made *before* installing rather than undone after.

**The DoD requires the method be recorded**, so this ships with the working recipe written down —
the environment variable, the `devicectl` invocation, and what a developer should expect to see.
A fix nobody can find is not observability.

## Workstream 3 — The device CI lane

The shape was agreed on [#17][i17] before this phase was planned, and the owner decided on
2026-09-22 that **we build the CI half in-repo** rather than wait for the external contribution.
The human-run signing script stays with @ceesalberts, because it needs an Apple account and
**cannot** live in CI for a public repo — fork PRs cannot read secrets at all.

**A matrix over RID, not a second workflow.** `ios.yml` is one job with `RID: iossimulator-arm64`
as a workflow-level env at `:77`. A matrix with two legs reuses the publish step, the
`IL2072`-is-exactly-4 assert and the `nm -gU` export gate unchanged, parameterising only Yoga's
`-sdk` / `-miphoneos-version-min` flags and the final `xcodebuild` verb. The device leg ends at
`xcodebuild build`, **not `test`** — there is no device to run XCTest on. Its job is *"the device
slice links, and is the slice we think it is"*.

The shared `IL2072 == 4` assert is load-bearing: the device run confirmed the same constant holds
on `ios-arm64`, so one assert across both slices is worth more than two separately-maintained
numbers, and a device-only trimming regression reds.

**The `vtool` / `LC_BUILD_VERSION` gate is the part that carries the value.** `lipo -info` reports
`arm64` for **both** slices and therefore cannot catch a wrong-slice stage. *A device lane that
silently built a simulator slice would be worse than no lane — it would certify the very thing it
exists to check.*

**Required, not advisory — and this needs an owner action outside the repo.** This repo's advisory
lanes have gone stale for many commits at a time, and a green *required* set does not mean the
device lanes ran; that is how a logging-pump bug survived a whole phase, and 14.2 caught the same
trap live. A build-only leg is fast and deterministic, so it can carry required status honestly.
**Marking it required is a branch-protection change in GitHub settings that only the owner can
make.** If it is not made, the lane is advisory in practice regardless of intent — record that
explicitly rather than assuming.

If the matrix fights the existing workflow more than it is worth, a separate `ios-device.yml` is an
accepted fallback; the matrix is a preference.

## Workstream 4 — The documentation landmines

The DoD says four, with `$(AppIdentifierPrefix)` explicitly among them. More than four candidates
exist; the four that cost someone real time are marked **primary**.

| # | landmine | where | why it costs |
|---|---|---|---|
| 1 | **primary** — `$(AppIdentifierPrefix)` must stay **literal** | the A3 keychain-group step of the handover | It expands to different values per team. Substituting a real Team ID yields `-34018` on every keychain call, which reads as a code bug — the device run lost an hour in the wrong layer |
| 2 | **primary** — the handover still describes the **pre-fix** auth behaviour in the present tense | `docs/ios-device-verification-handover.md:171-193` | It tells the tester to *"Get, and choose passcode fallback at the prompt"*. **Phase 14.3 deleted that control.** A 14.4 device tester hunts for a button that no longer exists and may file a false finding. This is review finding **F4** |
| 3 | **primary** — `fd 2 is one-way`, with the consequence the handover omits | the logging section | The documented landmine covers the runtime; it never says the loser is **the developer's console**. Pairs with workstream 2 |
| 4 | **primary** — `simctl openurl` no longer completes unattended | `ios.md` | On iOS 26 it always raises an `Open in "BnHost"?` sheet regardless of foreground app, so the documented recipe hangs |
| 5 | secondary — the export count is claimed as **8**, **9** and **10** | `ROADMAP.md:209` says eight; `ios.yml:25` says NINE; `bridge-extension.md` says 10 | `ios.yml` **asserts the correct 10 names** — verified — so only the prose is wrong, in two places, about a **frozen ABI**. Also unexplained: `Exports.cs` carries 13 `[UnmanagedCallersOnly]` against 10 asserted names; confirm the extra three are deliberate and say so |
| 6 | secondary — `BACKLOG.md:257-258`, `:266-267` are **WASM-era worded** | mentions validating "the `.wasm` binary" and `allow-jit` | There is no `.wasm` and no JIT. Re-word before anyone re-files against it |
| 7 | secondary — there is **no iOS template tree** | `dotnet new` ships an Android shell only | Stated nowhere a template consumer would look |

Items 5-7 are cheap; include them unless one turns out to be a rabbit hole, and say which were cut.

## Tests

- **Unit (.NET):** the hardened pin, mutation-proven against **its own code paths** — tokenisation,
  stripping, suppression, ignore-matching — with at least a wrapped Kotlin token, a token following
  a `://` string literal, and a production widening of an ignored pair. **Each must red.** This is
  the workstream's actual deliverable; the fixes without the mutations repeat the exact mistake
  that produced three rounds of findings.
- **Apple XCTest:** the pump skip, if it can be exercised without a device. `BnStderrPump` already
  carries an injectable sink for driving it without a pipe, so the conditional is likely testable
  even though the `dup2` is not.
- **CI itself is the test for workstream 3** — the device leg must build, and the `vtool` gate must
  be proven by *deliberately staging a simulator slice once* and confirming it reds. A gate never
  observed failing is a gate nobody has tested.
- **Docs:** `npm run build` with `onBrokenAnchors: 'throw'`; counts move together with `ci.yml` and
  `README.md` or `ReadmeDriftTests` reds.
- **No device is required for any of the above.** Workstream 2's *fix* is verifiable in CI; only its
  end-to-end confirmation needs hardware, and that rides the handover checklist.

## Open Questions

- **Does marking the device leg required happen?** It is a branch-protection change only the owner
  can make. The phase ships the lane either way; what changes is whether it can go stale. Record
  the outcome rather than assuming it.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The RID matrix fights `ios.yml`'s existing single-RID assumptions | Workstream 3 balloons and crowds out the rest | The fallback is pre-agreed on #17 — a separate `ios-device.yml`. Take it early rather than fighting; the matrix is a preference, not a requirement |
| The `vtool` gate is written but never observed failing | A gate that certifies rather than checks — the exact failure the lane exists to prevent | Deliberately stage a simulator slice once and confirm it reds. Mandatory, not optional |
| The pin fixes introduce false positives | CI reds on correct code, and the pin gets weakened or disabled under pressure | Measure the live occurrence count before and after, as 14.3's span fix did — it proved 9 occurrences unchanged, which is what made the fix trustworthy |
| Workstream 2's skip hides a real stderr problem | A developer sets the env var and silently loses the pump's rescue path | It is opt-in by an explicit debugging variable, and the recorded recipe says what the trade is |
| Four workstreams is too much for one phase | Partial completion, and a DoD item slips into 14.5 | They are independent. If one stalls, ship the rest and say which was cut — the milestone's own precedent, and 14.4 was always the phase most likely to split |
| The device lanes go stale during this phase | A green required set reads as validation when no device ran | Dispatch both lanes against the **head commit** and compare `headSha`, not conclusion — the 14.2 finding, now twice-applied |
