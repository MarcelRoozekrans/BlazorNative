# Phase 16.1 Design — `The render thread`

**Date:** 2026-09-26
**Phase:** `16.1`
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M16 — Unblock the Dispatch Lane](../../planning/MILESTONE.md)
**Input:** the 16.0 spike conclusion, [`docs/plans/2026-09-26-phase-16.0-spike-conclusion.md`](../../plans/2026-09-26-phase-16.0-spike-conclusion.md).
Its **11 requirements** are this phase's checklist. The conclusion uses the old phase numbers:
its "16.2" means this phase, its "16.3" means 16.2, and its "16.4" means 16.3.
**Reference, never merged:** the spike, `spike/16.0-render-thread` at `9df59f0`.
**Closes:** #345 and #8.

## Goal

Replace `InlineDispatcher` with a .NET-owned render thread, so that:
- an export no longer holds the shell's dispatch lane while a handler awaits the host;
- exactly one thread ever touches the renderer or emits a frame;
- a fault after a handler's first await reaches the shell's `onError`, delivered in the same PR, so
  that no merged state exists in which that fault is only logged;
- shutting down leaves the runtime truly quiet.

## Owner decisions

These were made in the 16.1 brainstorm on 2026-09-26.

1. **One phase, one PR.** The dispatcher and the shells' frame paths land together, because the
   dispatcher alone would put a data race on `main`.
2. **Render-thread exceptions keep today's behaviour and crash.** An exception that escapes posted
   work is re-raised as unhandled, exactly as an `async void` that throws after an await crashes
   today. This is requirement 10.
3. **Quiescence becomes true again.** When shutdown returns, no frame can reach the shell. This is
   requirements 3 and 11.
4. **`ConfigureAwait(false)` follows Blazor's standard rule.** An off-thread `StateHasChanged`
   throws, as in Blazor Server, and the supported fix is `InvokeAsync(StateHasChanged)`. The repo is
   audited for violations. The rule goes on 16.3's app-author page, and an analyzer is filed as a
   follow-up. This is requirement 6.
   - **Why silent marshalling is off the table:** the throw is Blazor's own `Renderer` asserting
     `Dispatcher.CheckAccess()`. The only way to avoid it is a `CheckAccess()` that lies, and that
     lie is 13.2's stack overflow.
5. **Work posted after shutdown completes its `Task` as cancelled.** It is never dropped silently,
   because anything awaiting a dropped `InvokeAsync` would hang forever.
6. **Async fault delivery is folded in from the former 16.2**, so the fault-only-logged window
   never exists on `main`.

## Approach

**1. Truth first.** The first commit corrects the false comment at `Exports.cs:504-506`, as #345
asks, and changes nothing else.

**2. The dispatcher.** `NativeRenderer` gets a per-renderer `RenderThreadDispatcher`:
- one dedicated background thread named `BlazorNative-Render`;
- a single-threaded `SynchronizationContext` installed on that thread;
- an honest `CheckAccess()`;
- `Post` and `Send`, with `Send` running inline when it is already on the render thread.

Every renderer entry point that mutates state is marshalled onto that thread and waits for full
completion when called from any other thread. The spike's list is the starting inventory:
- `Mount`, the root swap and dispose;
- `DispatchUiEventAsync`;
- all of `DispatchHostEventCore`'s arms that touch the renderer: `back`, `navigate`, lifecycle,
  `safeAreaChanged` and the app multicast. The last three were marshalled beyond the spike's brief
  and are now marshalled deliberately. This is requirement 5.

`ReportIfNotTheRenderOwnerThread` becomes a failure under test instead of a log line. Every
thread-identity pin compares against **the renderer under test**, never a process-wide
"last constructed" value. This is requirement 9.

**3. Exports wait for the synchronous part only.**
- An export posts its work and waits until the dispatch has returned its `Task`, not until that
  `Task` completes.
- Completed successfully → rc 0.
- Faulted → rc 2, as today.
- Still running → rc 0, and the `Task` is handed to fault delivery (item 6).
- `Mount` and the swap still wait for full completion, which keeps the sync-mount contract.
- The rc contract, **"rc reports the synchronous part"**, is written once, in
  `BlazorNativeRuntimeC.h` and in `Exports.cs`. Every export's rc table is re-checked against it.

**4. The capture window is scoped to a dispatch.** This is requirement 1, the 16.0 cascade.
- The single `_uiEventDispatchDepth` counter that spans an `await` is replaced by a window that
  opens at dispatch start and closes when **that dispatch's** synchronous part returns.
- `DrainPostDispatchActions` runs at that close. A navigation issued while another handler is
  suspended therefore swaps before its own export returns.
- A fault raised later belongs to the handler that raised it, never to whichever dispatch happens
  to hold the window.

**5. Render-thread exceptions crash, as today.** This is requirement 10.
- An exception escaping posted work goes to an internal `UnhandledExceptionSink`. In production it
  re-raises the exception as unhandled on a fresh thread, so the process terminates as on `main`.
- `Send` propagates the exception to its caller rather than swallowing it in a `finally`.
- Tests replace the sink and assert that it fired.

**6. Async faults reach the shell.** This is #8, folded in.
- `HostCallOp` moves into `src/wire-vocabulary.json`, which today mirrors it by hand in three
  languages: `NativeShellBridge.cs:105`, Kotlin's `HostCallOp` and Swift's `BnHostCallOp`.
  `tools/BlazorNative.WireGen` emits all three copies, like the other names.
- A new op, `FaultNotice`, is added. Its args carry the handler id, the event name, the exception type and the message.
  The stack trace is never included, because it can carry user data.
- When a dispatch `Task` that was still running at rc time later faults, .NET sends a
  `FaultNotice` host call.
- Both shells route `FaultNotice` to their existing `onError` and complete the call as OK.
- An older shell that doesn't know the op takes its unknown-op branch and completes the call with
  Error. On **Android** that branch also calls `onError` (`AndroidShellBridge.kt:280-284`), so the
  fault still reaches it. On **iOS** it does not: the branch only logs through `BnLog.warn`, so the
  fault is logged but never reaches `onError`. Either way the fault is logged, never silent, even
  across a version mismatch. (Corrected in Task 5; the first draft claimed both shells reach
  `onError`.)
- No new export, no new slot: **the ABI is unchanged.**

**7. Quiescence and teardown.** These are requirements 3, 4 and 11.
- Shutdown closes the render thread's queue. Work posted afterwards completes as cancelled
  (decision 5).
- A **callback gate** makes every frame-callback invocation enter a counted region. Shutdown closes
  the gate and waits for callbacks already in flight, then clears the callback pointer. This closes
  the use-after-free window.
- Shutdown then joins the render thread, bounded at 5 s. If a handler never yields, the join times
  out and a warning is logged. The gate still guarantees that **no frame reaches the shell after
  shutdown returns**.
- The Kotlin claims at `BlazorNativeRuntime.kt:330-331` and `NativeBindings.kt:83` are then true,
  and a pin proves it.
- `HostSession.ResetForTests` no longer waits for a render thread while holding `s_lock`.
- Each session's thread is joined on reset, so no thread leaks.

**8. The shells' frame paths.** This is requirement 2.
- Every frame, from a synchronous part or from a continuation, now comes from the render thread.
  Android's `WidgetMapper.pending` therefore has exactly one producer. The iOS frame trampoline is
  audited the same way.
- A Kotlin pin asserts that `WidgetMapper.apply` is always entered on one consistent thread.
- The comment at `Exports.cs:459`, "frames fire only inside host calls", is rewritten to state the
  new contract.

**9. Tests are flipped, never deleted.** This is requirements 7 and 8.
- `DispatchLaneBlockingTests` flips to assert that the export returns while the host call is open.
- The two `RenderThreadWarningTests` flip to assert that the check fails.
- `MountSyncTests`' type assertion becomes a behaviour pin.
- The JVM frame-thread test becomes "frames arrive on one consistent, non-lane thread, serially".
- The JVM #346 pin completes its held call in a `finally` and asserts that the call **returns**,
  never a specific rc. The rc depends on test order in the never-reset JVM session. The back
  verdict itself is pinned in 16.2.
- Every JVM test that holds a host call open completes it in a `finally`.
- **An XCTest twin** of the lane-blocking pin is added, because none exists today.

**10. The `ConfigureAwait(false)` audit.** This is requirement 6.
- Grep every component and library in `samples/`, `templates/` and `src/BlazorNative.*` for
  `ConfigureAwait(false)` that is followed by a render on the same path. Fix each hit with
  `InvokeAsync(StateHasChanged)`, or by removing the `ConfigureAwait`.
- Library-internal `ConfigureAwait(false)`, such as `NativeShellBridge.InvokeHostCallAsync`, is
  correct and stays.
- File the analyzer follow-up as an issue.

## Files / Modules Touched

- **The runtime core**
  - `src/BlazorNative.Renderer/NativeRenderer.cs`: the dispatcher, the entry points and the capture
    window.
  - `src/BlazorNative.Runtime/Exports.cs`, `HostSession.cs` and `NativeShellBridge.cs`: post and
    wait, fault delivery, and shutdown.
- **The ABI header and the wire vocabulary**
  - `src/BlazorNative.Apple/BnHost/BlazorNativeRuntimeC.h`: the rc contract, as documentation only.
  - `src/wire-vocabulary.json` and `tools/BlazorNative.WireGen`: `hostCallOps`, and the generated
    C#, Kotlin and Swift copies.
- **The shells**
  - The Android shell: `AndroidShellBridge.kt` for the `FaultNotice` arm, `BlazorNativeRuntime.kt`
    and `NativeBindings.kt` for the quiescence comments and pin, and `WidgetMapper.kt` for the
    single-producer pin.
  - The iOS shell: `BnRuntime.swift`, and the bridge's `FaultNotice` arm.
  - The template mirrors of each changed shell file, kept byte-identical where a guard requires it.
- **Tests:** the flipped pins listed above, and the new pins listed under Tests.
- **Docs and CI:** `CHANGELOG`, through the commit type, which calls out the rc behaviour change.
  README and `ci.yml` test counts are updated with a history comment.

## Tests

Every new pin conforms to `docs/pin-standard.md` Rules 2–5 and 7, with mutations recorded.

- **.NET:**
  - the render-thread ownership pin;
  - a per-dispatch window pin that reproduces the 16.0 cascade;
  - the sync-mount behaviour pin;
  - 13.2's recursion as a named regression;
  - the exception-sink pin;
  - `InvokeAsync` after shutdown returns a cancelled `Task`;
  - no frame reaches the callback after `Shutdown` returns, even with a handler that never yields;
  - `FaultNotice` is sent for a fault after the first await;
  - `ResetForTests` leaks no thread;
  - the flipped `DispatchLaneBlockingTests` and `RenderThreadWarningTests`.
- **JVM:**
  - `FaultNotice` reaches `onError`;
  - the retired runtime receives no frame;
  - the single-producer frame pin;
  - the flipped frame-thread test;
  - the #346 pin made order-independent.
- **XCTest:** the lane-blocking twin, and `FaultNotice` reaching `onError`.
- **Generated vocabulary:** `HostCallOp` covered by the existing wire-vocabulary codegen pins, with
  `FaultNotice` in all three languages.
- **Device lanes:** Android and iOS dispatched on the PR head, with `headSha` compared.
- **Suite counts:** measured after a clean rebuild, and asserted in `ci.yml` and README.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **The phase is large: 11 requirements plus fault delivery** | A long review loop, and requirements lost between tasks | The plan maps every requirement to a task, and the final review checks the 11-item list line by line |
| **Moving `HostCallOp` to codegen changes a hand-mirrored enum in three languages** | An op renumbered by mistake breaks every capability | The existing numeric values are frozen in the manifest, and a pin asserts they are unchanged from `main` |
| **A handler that never yields stalls shutdown** | Slow teardown | The join is bounded at 5 s, and the callback gate still guarantees quiescence. The stall is logged, and 16.3 measures starvation |
| **The rc behaviour change surprises a third-party shell** | rc 0 read as "handler finished" | The contract lives in the C header, and the changelog calls out the behaviour change |
| **Only a device exposes a threading bug** | Green CI and a hung phone | Both device lanes run, with `headSha` compared. The XCTest twin makes iOS measurable |
| **A new pin passes while checking nothing** | M15's lesson repeats | The pin standard applies, and each pin's mutation is recorded |
