# Phase 13.1 — Type the lengths: design

**Milestone:** 13 — Consumer Ergonomics · **Phase:** 13.1
**Surface:** Refactor
**Date:** 2026-08-20
**Predecessor:** [Phase 13.0 — Extract the item surface](../../plans/2026-08-19-phase-13.0-conclusion.md)
(complete 2026-08-20, PR #287) — 13.1 builds directly on the `BnLayoutItem` /
`BnLayoutContainer` bases it created, and inherits the one collision it deferred here.

---

## 1. The problem, stated as it actually is

Every layout length in the public surface is `string?`. So this compiles, ships, and is
**silently logged-and-ignored** by both shells at runtime:

```razor
<BnView Width="12px" />
```

`12px` is CSS muscle memory and it is not in this framework's grammar. The shells' grammar
is a bare number (points), a number with `%`, or `auto` — no units, ever. The value is
rejected in `YogaLayout.kt`'s `length()` with a `logIgnore`, and the node keeps whatever
width it had. Nothing between the developer's keystroke and a logcat line they will never
read says otherwise.

This is the same *accepted-then-dropped* shape as the visual-style hole that the 2026-08-17
audit of issues #16–#25 found and #263/#266 fixed. That one was four style names silently
discarded; this one is every length on every component.

One further split, inherited rather than designed: `Padding` is `float?` while `Margin` is
`string?`. Same grammar in the shells, two types in .NET, for no reason either type records.

## 2. What this phase does

Introduce two value types — `BnLength` and `BnAutoLength` — and convert every layout length
parameter to them, so that malformed values become **compile errors** instead of runtime log
lines, **while leaving the wire grammar byte-for-byte unchanged**.

Nothing about the wire, the shells, or the ABI moves. The grammar is identical; only *who
builds the string* changes — from the app author's fingers to a type with two ways in.

## 3. Design decisions, and the evidence behind each

### 3.1 Two types, not four — negatives stay shell-side

The shells enforce two independent axes of legality:

| Class | Properties | `auto` legal | negative legal |
|---|---|---|---|
| auto-legal, auto is the default | `Width`, `Height`, `Basis` | ✅ | ❌ |
| plain | `MinWidth`, `MaxWidth`, `MinHeight`, `MaxHeight`, `Padding`, `Gap` | ❌ | ❌ |
| auto-legal, zero is the default | `Margin` | ✅ | ✅ |
| insets | `Top`, `Right`, `Bottom`, `Left` | ❌ | ✅ |

Two types close the **auto** axis completely. The **negative** axis stays where it is today —
enforced in `YogaLayout.kt`'s `length(negative =)` flag and its iOS twin, which reject and
log rather than clamp.

**Decided (owner, 2026-08-20): two types.** Four types (`BnSignedLength`,
`BnSignedAutoLength`) would close the negative axis too, but they double a public type surface
that **freezes at 1.0** and produce four names that are hard to tell apart at a call site. A
negative length is also a different kind of mistake from `12px`: it is a *meaningful value in
the wrong place*, not a typo, and it is rare. The milestone design anticipated this and said to
revisit only "if 13.1 finds it cheap". It is not cheap; it is not taken.

This is a deliberate, recorded limitation, not an oversight: **`Width="-8"` will still
compile** and still be logged-and-ignored by the shells.

### 3.2 `BnAutoLength` composes `BnLength`

```csharp
public enum BnLengthUnit { Points, Percent }

public readonly record struct BnLength(float Value, BnLengthUnit Unit);

public readonly record struct BnAutoLength(BnLength? Length);   // inner null == auto
```

The alternative — two independent structs each carrying `Value`/`Unit` and its own formatter —
puts the wire-format logic in **two** places. "The wire is unchanged" is a Definition-of-Done
line for this milestone, and two copies of a formatter are two ways to drift from it. This repo
already generates the wire vocabulary from a single manifest (`src/wire-vocabulary.json`,
#262) for exactly this reason; duplicating a formatter here would argue against that precedent
in the same codebase.

A third option — one struct with an `IsAuto` flag, legality left to which property it lands on
— was rejected because it makes an illegal state representable: a `BnLength` carrying `IsAuto`
assigned to `MinWidth` would compile, and only the shell would catch it. That is the class of
bug this phase exists to remove.

### 3.3 `BnLength?` — nullable, and `null` means unset

Parameters are declared `BnLength?` / `BnAutoLength?`, not bare structs.

This is the decision most directly informed by this repo's own history. **#178 and #181 were
one bug class:** `default(T)` on a struct bypasses the author's invariant, and it did so
silently — `CaptureOptions` defaults never applying produced a quality-0, visibly posterised
photo on a real device. `DefaultStructTrapSweepTests` exists as a standing guard because of it.

A bare `BnLength` would walk straight back into that trap. `default(BnLength)` is
`Value = 0, Unit = Points` — **a real, legal length of zero**, not "unset". A component whose
`Width` nobody assigned would emit `width=0` and collapse. The failure would be silent, visual,
and platform-agnostic.

`BnLength?` closes it by construction: `default(BnLength?)` is `null`, `null` is unset, and
there is no zero-value that reads as a real length. It also means the migration is mechanical
(`string?` → `BnLength?`) and — more importantly — **the null-reset path is untouched**. That
path is load-bearing: `null` → the shell resets the style, which is what #222 fixed and what
several existing pins assert. Keeping the outer nullability identical means those pins keep
applying unchanged rather than needing to be re-reasoned.

**The double null, said plainly.** `BnAutoLength?` has two nulls with different meanings:

| Value | Meaning | Wire |
|---|---|---|
| `null` (outer) | unset | attribute absent → shell resets |
| `BnAutoLength.Auto` (inner null) | `auto` | `"auto"` |
| `BnAutoLength` wrapping a `BnLength` | a length | `"100"` / `"50%"` |

**And the same argument applies to `BnAutoLength`, where it is sharper.** `default(BnAutoLength)`
is `Length = null`, which by §3.2's encoding reads as **`auto`** — not "unset", and not zero. A
bare `BnAutoLength` field nobody assigned would mean "absorb the free space", which on `Margin`
re-centres the node. That is precisely the shape of #178: a struct's zero-value silently meaning
something the author never chose. It is closed the same way and only that way — the parameters
are `BnAutoLength?`, so `default` is the outer `null` and unset stays unset. A pin asserts both
`default(BnLength?)` and `default(BnAutoLength?)` are `null`, so the guarantee is checked rather
than argued.

This is not an invention. The shells already distinguish these three states — `length()`'s
`autoIsDefault` flag exists *because* `null` and `auto` are different resets, and the comment
above `"margin"` in `YogaLayout.kt` spells out that resetting a removed margin to `auto` would
move the node instead of restoring it. The type mirrors the wire. It still needs a doc comment
saying so, because it is the one genuinely confusing thing in the design.

### 3.4 `BnList<TItem>` stays allowlisted — decided, not deferred

Phase 13.0 discovered that `BnList<TItem>` cannot derive from `BnLayoutItem`: its
`[Parameter, EditorRequired] float Height` collides with the base's `Height`, and Blazor's
`ComponentProperties.CreateWriters` **throws** on the first render of a type with two
parameters matching one name. 13.0 pinned the collision and named 13.1 as the place to
reconcile it.

Reconciled, and the answer is that it stays: `BnList.Height` is fed to
`BnListWindow.Compute(_offset, Height, ItemHeight, Items.Count, Overscan)` as the virtualization
window's divisor. It **must** be a point value. `BnAutoLength` cannot promise one — `auto` and
`50%` are legal in the type and unusable in the arithmetic — and nothing surfaces viewport size
back to .NET, so there is no fallback measurement to recover it.

Rejected alternatives:

- **Rename to `ViewportHeight` and let `BnList` derive.** It would then carry both an inherited
  layout `Height` and a required `ViewportHeight` meaning almost the same thing, and a consumer
  setting both gets a silent conflict between the layout and the arithmetic.
- **Inherit `Height` as `BnAutoLength` and require points at runtime.** This converts a
  compile-time guarantee (`[EditorRequired] float`) into a runtime throw — the exact opposite
  direction to this phase's thesis.

So the allowlist entry's reason is **upgraded from "deferred to 13.1" to settled**, with the
constraint written down. The milestone DoD asks for an allowlist whose entries each carry a
written reason — not for an empty allowlist. `BnList.Width` **is** typed by this phase; only
the two names the collision strands there stay `float`.

## 4. The public surface after this phase

### 4.1 Property mapping

| New type | Properties |
|---|---|
| `BnAutoLength?` | `Width`, `Height`, `Basis`, `Margin` |
| `BnLength?` | `MinWidth`, `MaxWidth`, `MinHeight`, `MaxHeight`, `Top`, `Right`, `Bottom`, `Left`, `Padding`, `Gap` |
| unchanged `float?` | `Grow`, `Shrink` |
| unchanged `string?` | `BackgroundColor` |

`Grow` and `Shrink` stay `float?` deliberately. They are **not lengths** — the shells parse them
through `unitless()`, a different production with no `%`, no `auto` and no units. Typing them as
lengths would let `Grow="50%"` compile into a value the shell then rejects, which is the bug
this phase removes, reintroduced one property over.

`BackgroundColor` stays `string?`. It is a colour, and colour typing is not in this phase's
scope (it belongs with the theme work in 13.4, if that goes ahead).

`Padding` moves `float?` → `BnLength?`. That closes the DoD line *"`Padding` and `Margin` share
one type; the `float?`/`string?` split is gone."* Note they land on **different** types —
`Margin` takes `auto`, `Padding` does not — which is the honest reading of that DoD line: one
shared *grammar*, with the legality difference the shells actually enforce preserved rather than
flattened.

### 4.2 Conversions

```csharp
public static implicit operator BnLength(float points);
public static implicit operator BnLength(double points);
public static BnLength Percent(float value);
```

**The `double` operator is required, not a convenience.** Razor compiles `Width="12.5"` as a
`double` literal, and `double` → `float` is a *narrowing* conversion, so without it every
decimal literal fails with CS1503. This was found by compiling a probe, not by reasoning — see
§6.

There is deliberately **no** implicit conversion from `string`. That absence is the entire
mechanism: it is what makes `Width="12px"` a compile error rather than a runtime log line.

## 5. The wire is unchanged — and the new locale trap

`ToStyleValue()` on both types formats with `CultureInfo.InvariantCulture`, exactly as today's
`ToStyleValue(this float?)` does, and for the reason its comment already gives: *"the shells
parse with a C/Java float parser: a Dutch locale must never put `1,5` on the wire."*

**This phase introduces a way to violate that which does not exist today.** `ItemAttributes` —
the splat that `.razor`-authored components emit through — is
`IReadOnlyDictionary<string, object?>`. Today its values are already strings, so there is
nothing to get wrong. After this phase, putting a `BnLength` **struct** into that dictionary
boxes it, and the renderer stringifies it with `ToString()` — which is culture-sensitive. On a
machine with a comma decimal separator the wire would carry `1,5`, and both shells would reject
it as "not a number, a percentage or `auto`".

The failure is invisible on any developer machine with an English locale and reproducible on a
Dutch one. **13.1 therefore adds a pin that emits the item surface under a comma-decimal culture
and asserts the wire text** — a test that would have been meaningless before this phase and is
load-bearing after it.

Both emitters must call `.ToStyleValue()` explicitly:

- **Mechanism A** (`EmitItemAttributes`, hand-written emitters) — `b.AddAttribute(7, "width", Width.ToStyleValue())`
- **Mechanism B** (`ItemAttributes`, the splat) — the dictionary stores the **formatted string**, never the struct

## 6. What was measured rather than assumed

Everything in this section was established by running something, because the design turns on it.

### 6.1 Razor's literal handling — probed, and it corrected the design

A throwaway Razor project was compiled against a probe struct shaped like `BnLength`:

| Markup | Result |
|---|---|
| `Width="200"` | ✅ compiles (`int` → `float` → `BnLength` → `BnLength?`) |
| `Width="12.5"` | ❌ **CS1503 without a `double` operator** — the probe's finding |
| `Width="@BnLength.Percent(50)"` | ✅ |
| `Height="@BnAutoLength.Auto"` | ✅ |
| `Width="12px"` | ❌ CS1003 |
| `Width="50%"` | ❌ CS1525 |
| `Width="auto"` | ❌ CS0103 |
| `Width="abc"` | ❌ CS0103 |
| `Width="100 px"` | ❌ CS1003 |

The DoD's claim — *"`Width="12px"` is a compile error, not a runtime log line"* — is therefore
**demonstrated, not asserted**, and it needs no analyzer: it falls out of there being no
`string` → `BnLength` conversion.

**The errors are correct but cryptic.** `Width="12px"` reports *"syntax error, ',' expected"*,
which says nothing about lengths. An analyzer could improve the message; it is **not** in this
phase, on the same reasoning as §3.1 — the milestone said revisit only if cheap, and a
diagnostic-quality analyzer is its own piece of work. The migration note carries the error table
above so the mapping from cryptic CS-code to real cause is written down somewhere.

### 6.2 Migration cost across the repo

Measured over `samples/`, `src/`, `templates/`, `tests/`:

| Call-site shape | Count | Effect |
|---|---|---|
| Plain numeric literals (`Height="200"`) | 44 | **compile unchanged** |
| `@`-bound expressions | 76 | expression types change `string` → `BnLength`/`BnAutoLength` — the bulk of the work, mechanical |
| Literal `%` (`Basis="50%"`) | 1 | → `@BnLength.Percent(50)`; the single occurrence is `ItemSurfaceProbe.razor`, added by 13.0 |
| Literal `auto` | 0 | none to migrate |

The feared cost of pure typing — that percentages become verbose — is **one line in one test
file** in this repository. For consumers it is a real change and it goes in the migration note.

## 7. Definition of done for this phase

- [ ] `BnLength` and `BnAutoLength` exist, with the conversions in §4.2 and invariant
      `ToStyleValue()`.
- [ ] Every property in §4.1 carries its new type; `Grow`, `Shrink` and `BackgroundColor` are
      unchanged.
- [ ] `Width="12px"`, `"50%"`, `"auto"`, `"abc"` and `"100 px"` **fail to compile**, pinned by a
      test that compiles them and asserts failure — not by a comment claiming they do.
- [ ] `Width="200"` and `Width="12.5"` still compile.
- [ ] **Frame tables byte-identical** on both shells across the whole sample; no `.kt`, no
      `.swift`, no `wire-vocabulary.json` in the diff.
- [ ] **Locale pin**: emission under a comma-decimal culture puts `1.5`, not `1,5`, on the wire.
- [ ] `DefaultStructTrapSweepTests` covers `BlazorNative.Components` — see §8.
- [ ] `default(BnLength?)` and `default(BnAutoLength?)` are both `null`, pinned — the #178
      guarantee checked rather than argued (§3.3).
- [ ] `BnList`'s allowlist reason reads as settled, with the divisor constraint written down;
      `BnList.Width` is typed.
- [ ] `PublicAPI.Unshipped.txt` updated and read as an API review; migration note written.
- [ ] Both device lanes dispatched and green, with no frame-table edit.

## 8. A gap this phase must close

`DefaultStructTrapSweepTests` — the standing #178/#181 guard — sweeps three assemblies:
`BlazorNative.Core`, `BlazorNative.Runtime`, `BlazorNative.Device`. **`BlazorNative.Components`
is not among them.**

This phase adds two public structs to exactly that assembly. Adding `BlazorNative.Components` to
`ApiAssemblies` is therefore part of 13.1, not a follow-up: shipping new public value types into
the one product assembly the trap-sweep cannot see would be a poor trade for a one-line change.

The sweep flags record structs where every primary-ctor parameter has a default and at least one
default is non-zero. Neither `BnLength` nor `BnAutoLength` has parameter defaults, so neither is
expected to trip it — but the point is that the guard should be *watching* them.

## 9. Out of scope

- **Negative-legality typing or an analyzer** (§3.1) — recorded limitation.
- **A diagnostic-quality analyzer for the cryptic CS errors** (§6.1).
- **Colour typing** for `BackgroundColor` — belongs with 13.4's theme work, if that goes ahead.
- **Any shell change.** If this phase finds itself editing Kotlin or Swift, the design is wrong
  and the phase should stop.
- **Renaming or retyping `BnList.Height` / `ItemHeight`** (§3.4).

## 10. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Culture-sensitive `ToString()` on a boxed struct reaches the wire | Silent on English machines, broken on Dutch ones; both shells reject the value | The §5 locale pin, plus storing formatted strings — never structs — in `ItemAttributes` |
| `default(BnLength)` reads as a real zero length | A never-assigned `Width` collapses a node, silently | `BnLength?` everywhere (§3.3); the §8 sweep extension watches the new types |
| Frame tables move | Severe, possibly on one platform only | Frame tables are the acceptance test, run on both shells across the whole sample |
| The 76 `@`-bound sites hide a semantic change behind a mechanical one | A wrong value ships looking like a type change | Read the `PublicAPI` diff as an API review; the byte-identical frame tables are the backstop |
| Scope creep into an analyzer | Phase slips on its least-certain item | §9 names it out of scope; the migration note carries the error table instead |
