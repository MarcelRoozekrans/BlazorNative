# Phase 18.10 Design — iOS show completes when posted (#444)

**Date:** 2026-11-14
**Phase:** 18.10
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-14

## Goal

An iOS `show` completes `Granted` once its request is handed to `UNUserNotificationCenter`, as Android's does after `nm.notify`. A SpringBoard presentation stall can no longer delay the result or red the iOS lane.

## Why

#444 is the iOS lane's recurring red. With 18.1's instrumentation, run 40642166828 showed SpringBoard taking 11.25 s to deliver `willPresentNotification` to the app. The app answered about 50 ms after delivery. An immediate request's `add` completes only after that exchange, and `BnNotifications.swift:439` completes the host call inside `add`'s completion. So today `Granted` means "presented and answered", and a component we do not own decides when it arrives. Android's `runNotificationAction` (`AndroidShellBridge.kt:784-789`) completes `Granted` right after `postNotification` returns, which means "posted". The owner decided on 2026-11-14 that iOS takes Android's meaning.

## Decisions

| Question | Decision | By |
|---|---|---|
| What does `show`'s `Granted` mean? | Posted: the request is handed to the center. A later `add` error is logged, not returned. | Owner, 2026-11-14 |
| Does `schedule` change too? | No. A scheduled request is not presented, so its `add` never waits on SpringBoard and has never flaked. Its `add` error stays data. | Owner, 2026-11-14 |
| How? | Complete right after `add` is called. | Owner, 2026-11-14 |

## Approaches

1. **Complete right after `add` is called (chosen).** For `show`, `runAction` calls `center.add(request)` and completes `Granted` at once. `add`'s completion keeps its #444 trace and routes an error to the log. It mirrors Android's notify-then-`Granted` line for line.
2. **Complete on `add`'s completion or a 1 s bound, whichever comes first.** Rejected: a timeout is a workaround, and `Granted` would mean "presented" or "posted" depending on timing.
3. **Our own delegate answers `willPresent` at once.** Rejected: the stall is before delivery reaches the app. The app already answers within 50 ms.

## Approach

`BnNotifications.runAction` branches on the action after building the request:

- **`show`:** call `add`, then `complete(requestId, Granted, nil)`. The `add` completion calls `traceAddCompleted` as today. On a non-nil error it reports `"notifications 'show' add failed (request <id>, notification <identifier>)"` with the error through `BnRuntime.shared?.onError`, or `BnLog.error("BnNotifications", …)` when no runtime is booted. This is the same routing `AppleShellBridge.deliverFaultNotice` uses. It never calls `complete` a second time.
- **`schedule`:** unchanged. It completes in `add`'s completion, `Granted` or `Error`.

To pin the error route without a real `add` failure, `BnNotifications` gains a test seam for the add call: a static `addForTest: ((UNNotificationRequest, @escaping (Error?) -> Void) -> Void)?`. When it is nil, production calls the real center. The seam replaces only the call to the center; the completion code it receives is production's.

The 18.1 diagnostics change with the meaning. The `add` trace in production stays, since it now carries the late error and its latency. The test-side daemon probe (`DaemonProbe`, `pollUntilProbing`, the probe half of `diagnose`) comes out of the two show tests, which no longer wait on the daemon. The lane's failure-only `usernotifications.log` step stays; it costs nothing on a green run. (Builder's call: if the probe has no other user, delete it.)

## Tests

- **Held-presentation pin (iOS, real center).** A test delegate is installed on `UNUserNotificationCenter` and holds the `willPresent` completion handler, as run 40624968569 did. A `show` must complete `Granted` within 2 s. The anchor is that `add` has not completed at the moment `Granted` is captured, read from the add trace, so a pin that passes only because presentation was fast is red. Release the hold, and `add` completes: the control that the hold was real. Tear-down releases the hold and clears the delegate even on failure.
- **Late-error pin (iOS, seam).** `addForTest` captures the completion and does not call it. `show` completes `Granted`. The test then calls the captured completion with an `NSError`. The error reaches `onError`, or the `BnLog` path, and the capture hook still holds exactly one status.
- **Schedule unchanged pin.** Through the seam, an `add` that completes with an error makes `schedule` complete `Error`, and one that never completes leaves `schedule` uncompleted. This pins the owner's "show only".
- **Existing show tests** keep their assertions on the built request. Their bound drops from the 10 s probe poll to a plain bound, since `Granted` no longer waits on the daemon.
- **Twin.** Android's `show_posts_a_real_notification_and_cancel_removes_it` is the parity twin. Each header names the other.
- **Reds**, per `docs/pin-standard.md` "Grading a pin": the held-presentation pin reds with `complete` moved back into `add`'s completion. The late-error pin reds with the error route dropped, and with a second `complete` added. The schedule pin reds with `schedule` taking the `show` branch. Every file is edited before mutating, and the final review runs before the reds. Swift does not compile on the Linux host, so reds run on scratch refs through `ios.yml`, with a draft PR opened early.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The delegate hold does not reproduce on the CI simulator, which is unauthorized | The held-presentation pin cannot be built | Run 40624968569 held a delegate's `willPresent` for 15 s on this lane, 3 of 3. If it fails anyway, stop and report, rather than weakening the pin. |
| A test delegate left installed, or a hold never released, poisons later tests | Cascading reds | Release and clear in `tearDown` as well as in the test; reuse the existing `delegate = nil` line. |
| An app relies on `Granted` meaning presented | A silent behaviour change | Android never meant that; the doc comment and the record state the new meaning. |
| #444 recurs on `schedule` | The lane stays flaky | It has never failed there; its `add` does not wait on presentation. Watch it. |
