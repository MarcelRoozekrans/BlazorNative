# Phase 18.4 Design — Recreation during boot (#511), with the cross-bridge hold (#601)

**Date:** 2026-10-31
**Phase:** `18.4`
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)
**Approved:** by the owner, 2026-10-31, including the calls listed under "Calls made in this design".

## Goal

An Android Activity that is recreated while a cold boot is still running shows its own page and works, not a blank or dead screen. This is the M18 DoD item for #511, and a device pin has to prove it.

The phase also fixes #601. A secure-storage request on a key never runs ahead of a pending prompt on that key, even when that prompt was shown by a bridge from an earlier Activity instance. The owner decided this on 2026-10-31: fold #601 into 18.4, with one process-wide owner for the hold.

Both bugs have the same root. Per-Activity objects hold state whose real owner is the process, so a recreation splits it in two.

## Background: how it works today

### The boot (#511)

`MainActivity.onCreate` (`src/BlazorNative.Jni/src/androidMain/kotlin/io/blazornative/shell/MainActivity.kt:238-436`) does the following:

- It builds a new `BlazorNativeRuntime` (`:341`) and a new `AndroidShellBridge` (`:383`).
- It starts a `BlazorNative-Runtime-Boot` thread (`:396`) that calls `runtime.start(...)`, and then sets `booted = true` (`:406`).

`BlazorNativeRuntime.start` (`src/BlazorNative.Jni/src/main/kotlin/io/blazornative/jni/BlazorNativeRuntime.kt:469-545`) runs four steps:

1. `blazornative_init`, which is idempotent.
2. `blazornative_register_frame_callback`. This is process-global, and the last registration wins.
3. `BridgeRegistrar.register()`. The six shell callbacks are process-global too, last one wins.
4. `blazornative_mount`. Since 17.3 (#425), a second mount replaces the root.

The KDoc at `:463-464` says: "Concurrent start() calls (multiple threads) are unguarded — callers must serialize." Nothing serializes them.

`onDestroy` (`:461-491`) calls `runtime.retire()` only `if (booted)` (`:475`). The comment at `:469-474` names the boot case, #511, as not covered.

The hazards when the old boot thread is still before or inside `start()` while the new Activity boots:

- **Frames go to the dead Activity.** The old thread registers its frame callback after the new one. Every later frame then goes to the old runtime's `onFrame`, which feeds the destroyed Activity's mapper. The new Activity stays blank, or frozen on its first mount.
- **The old mount replaces the new root.** The old thread's `blazornative_mount` runs after the new one. The new Activity's views then belong to a disposed root, and taps do nothing.
- **Host calls go to the dead bridge.** The old thread's `BridgeRegistrar.register()` runs after the new one. Secure storage, camera, clipboard and the other host calls then begin on the destroyed Activity's bridge. #511 does not mention this one.
- **Two threads are inside .NET at once.** Both `start()` calls overlap in init, register and mount. That is the concurrent-entry hazard the runtime KDoc warns about, at `:436-445`.
- **The old runtime is never retired.** `booted` was false at its `onDestroy`.

The template copy, `templates/BlazorNative.Templates/content/BlazorNative.App/android/src/androidMain/kotlin/io/blazornative/shell/MainActivity.kt`, must equal the repo's copy, apart from the two divergences `TemplateDriftTests` allows: the `R` import and the fallback component.

### The secure-storage hold (#601)

18.3 (#506) added the hold in `AndroidShellBridge.kt`, and all of it is per bridge instance:

- `secureStorageExecutor` (`:289`).
- `held` (`:302`), the held keys and the requests parked behind each one.
- `pendingPrompts` (`:314`), the prompts that are up.
- `hostActivityDestroyed` (`:319`).

`onHostActivityDestroyed(isChangingConfigurations)` (`:408-419`) does nothing on a configuration change. On any other destroy, it denies every pending prompt of this bridge.

On a configuration change, androidx keeps the prompt alive and answers the **old** bridge's callback. The measurement is in record §1 of `docs/plans/2026-10-31-phase-18.3-record.md`. A same-key request that .NET begins after the recreation goes to the **new** bridge. It finds no hold there and runs at once. This is #506's hazard again, across a recreation: an auth set pending on the old bridge, then a rotation, then a delete on the new bridge, then the late encrypt stores a blob under a deleted key.

The template copy of `AndroidShellBridge.kt` must stay byte-identical. A CI guard checks it.

### iOS

iOS has no counterpart to either bug:

- `HostViewController.viewDidLoad` builds one `BnRuntime` and boots it once (`src/BlazorNative.Apple/BnHost/HostViewController.swift:157-187`).
- iOS does not recreate the root view controller on rotation or on a configuration change, and the shell has one window.
- The iOS secure-storage hold lives in one `BnSecureStorage` per bridge, and one bridge per process.

So iOS gets no code change. The design records this check, and the pin headers name iOS as not affected and say why.

## Goals

1. **The newest Activity owns the session.** After a recreation during boot, the new Activity holds the frame callback, the bridge registration and the root, and the old runtime is retired.
2. **No two `start()` calls are ever inside .NET at once.** This is enforced in `BlazorNativeRuntime`, not stated in a comment.
3. **One hold per process.** A same-key secure-storage request parks behind a pending prompt, whichever bridge showed that prompt. Requests on other keys keep flowing.
4. **A destroy that is not a configuration change denies exactly the prompts whose answer it drops.** Those are its own bridge's prompts, plus the orphans: prompts whose owner bridge's Activity was already destroyed by a configuration change, because androidx moved them into this Activity's fragment (record §1 of 18.3, `docs/plans/2026-10-31-phase-18.3-record.md:75`). It never denies a prompt whose owner's Activity is still alive. The owner decided this on 2026-10-31.
5. **Every claim above is pinned** and graded against `docs/pin-standard.md`, in the section "Grading a pin: sites and reds".

## Non-goals

- **Cancelling a superseded boot partway through.** That is approach B, which was rejected.
- **Skipping a superseded boot that has not entered `start()` yet.** It was considered and dropped. Joining already makes the order correct, the window is a thread start, and the extra branch would need a pin of its own.
- **iOS changes.** See Background.
- **#600** (Biometrics `authenticate` on a stopped Activity) and the flakes #598, #602, #603 and #604. They are noted, not worked.
- **No ABI change.** The 80-byte struct and the 10 exports stay as they are.

## Anti-goals

- **No bound raised to hide a wait.** The new boot's join of the old boot thread is not cut short by a timeout that then boots anyway, because that re-opens concurrent entry. See decision D2.
- **No green pin over a race.** Each ordering pin forces its bad interleaving through a seam, so its mutation reds every run. This is the 18.2 lesson.

## Approaches

The owner chose **A** on 2026-10-31.

- **A. Join the previous boot (chosen).** A process-wide record holds the last boot. A new Activity's boot thread joins the previous boot thread, retires that runtime, and only then calls its own `start()`. `start()` also takes a process-wide lock. The old boot runs to completion into dead views, which is harmless, and the new mount replaces it, as every recreation already does since 17.3.
  - Trades: the rotated cold start waits out the old mount, which takes milliseconds after the shared init.
  - Gains: no partial states, and the order is correct by construction.
- **B. Generation supersede inside the runtime.** A superseded `start()` aborts between steps, and `start()` retires its predecessor itself. It was rejected because it adds partial states between init, register and mount, and it puts a "newest Activity wins" policy into a library that JVM tests and the inspector host also use.
- **C. Process-wide boot lock only.** It was rejected because it stops concurrent entry but not the order: the old boot can take the lock second and mount over the new Activity, which is #511's symptom.

For #601, the owner chose **one process-wide owner** of the executor, `held` and `pendingPrompts`, on 2026-10-31. The two alternatives were rejected:

- Handing the holds over on recreation has its own race.
- Documenting the gap leaves the #506 hazard open.

## Design

### D1. The boot record (MainActivity)

The `MainActivity` companion holds a process-wide `AtomicReference` to the last boot, with the boot thread and its runtime. Call it `Boot`.

- **`onCreate`, on main:** build the boot thread and the `Boot`, then call `val previous = lastBoot.getAndSet(boot)`. Then start the thread. Activities are created on main in creation order, so `previous` is always the immediately older Activity's boot.
- **The boot thread** runs:
  1. `previous?.thread?.join()`.
  2. `previous?.runtime?.retire()`. It is idempotent, so a previous boot that had finished and retired in its own `onDestroy` costs nothing.
  3. `runtime.start(...)`.
  4. The existing `booted = true` and what follows it.
- **`onDestroy`** is unchanged for the booted case, which still retires there. The boot case is now handled by the next boot thread. The "NOT COVERED … #511" comment is replaced by one that says so.
- **An Activity that is finished during boot and never replaced** (back out of the splash) still has its runtime retired, by the next launch's boot in the same process. Until then, the old boot's frames reach a destroyed mapper, which `mapper.destroy()` already makes harmless (`:476-481`).
- **The old boot thread finishing after its Activity died** sets `booted = true` on a dead Activity and posts `requestApplyInsets` to a detached view. Both are harmless. The builder confirms that nothing else after `start()` touches a destroyed Activity unsafely.
- **The template copy** gets the identical change.
- **Two live instances.** The manifest is `singleTop` (`AndroidManifest.xml:47`). A deep link from another task can start a second `MainActivity` while the first is alive, and the new boot then retires the live first Activity's runtime. My call: in scope, and accepted. Since 17.3 the second mount already replaced the first Activity's root, so its UI is dead either way. Retiring the runtime makes that explicit and drops its frames. The first Activity's later `onDestroy` retires again, which is idempotent. The design records it, and no pin is added.

### D2. The join is not bounded

A boot thread that hangs inside `start()` means the native session is broken. Booting a second session on top of it would be concurrent entry. So the join waits.

My call: after 10 s it logs one `BnShellLog.warn` naming the previous boot as still running, then keeps waiting. The log is a name for a hang, not a bound. The builder may choose the logging mechanism, for example `join(10_000)` followed by a warn and a plain `join()`.

### D3. The start lock (BlazorNativeRuntime)

The body of `start()` runs inside `synchronized` on a lock in `BlazorNativeRuntime`'s companion object. The lock is process-wide, because the native session it guards is process-wide.

- **The KDoc changes.** The sentence "Concurrent start() calls … are unguarded — callers must serialize" is replaced by one that says the lock serializes them, and that the order between Activities is the shell's job (D1).
- **Deadlock check:** the frame callback that the mount delivers synchronously never takes this lock (`mapper.apply` only posts, `WidgetMapper.kt:777-791`), and `retire()` does not take it either. The builder confirms that nothing reachable from inside `start()` calls `start()`.
- **A test seam:** an `@VisibleForTesting internal` hook that runs inside the lock, between init and the frame-callback registration. It is `null` in production, and with it the JVM pin holds one `start()` inside the lock.

### D4. The process-wide secure-storage owner (AndroidShellBridge)

`secureStorageExecutor`, `held`, `pendingPrompts` and the `Hold`/`PendingPrompt` types move into `AndroidShellBridge`'s companion object, so every bridge in the process shares them. My call: they stay in the same file, so the byte-identical template guard keeps covering them with no new file to mirror.

- **`PendingPrompt` gains a `shownBy` field**, the bridge that showed the prompt. It is not called `owner`, because `Hold.owner` already means something else.
- **Each bridge records how its Activity died.** `onHostActivityDestroyed(true)` marks the bridge `destroyedByConfigChange`. Today that call returns at once; now it records the mark first, on the shared executor.
- **`onHostActivityDestroyed(false)`** denies every pending prompt whose `shownBy` is this bridge, **or** whose `shownBy` bridge is marked `destroyedByConfigChange`. Those orphans now live in this Activity's fragment, so this destroy drops their answers too. A prompt whose `shownBy` bridge's Activity is still alive is never denied. The owner decided this on 2026-10-31.
  - The case it covers: rotate with a prompt up, then finish the new Activity. A's prompt is denied, and the key is released with `AuthFailed`.
  - `hostActivityDestroyed` stays per bridge, since it gates new prompts on that bridge's Activity.
- **A hold's owner becomes the pair of bridge and request id** (`Hold.owner`, `:296`, checked in `releaseHold`, `:339-346`). My call. In production .NET issues unique ids from one session, but the instrumented tests make up their own ids (`completeHookForTest`, `:825-831`). Two bridges in one process could then collide, and one bridge's release would free another bridge's hold.
- **A parked job** is the closure of the bridge that began it. It completes through that bridge's `completeHostCall`, exactly as today. The builder confirms that completion is keyed by request id process-wide, so a job from the new bridge that drains after a release on the old bridge completes its own call.
- **The other bridge executors** (fetch, location, camera, biometrics) stay per bridge. Only secure storage has cross-request ordering state.
- **Tests share the process.** A hold left behind by one instrumented test would now block the next test, even though that test builds a new bridge. The builder audits `BnSecureAndroidTest`, `ShellBridgeAndroidTest` and `AndroidHostCallContractTest` for a reliance on a fresh hold map. If a reset is needed, it is an `@VisibleForTesting` call that the tests make in `@After` and that asserts the map was empty. It never silently clears a leak.

### D5. Pins

Each pin is graded against "Grading a pin: sites and reds", gets its register cell in `docs/pin-standard.md` in this phase, and has every site red by a recorded mutation.

1. **Instrumented, recreation during boot** (`RecreationAndroidTest` or a sibling class).
   - **The seam:** `@VisibleForTesting`, process-wide, and `null` in production. My call: it runs at the boot thread's entry, **before the join**, and it receives the boot's runtime. The test blocks only the first Activity's runtime, chosen by identity. The new boot passes through the seam unblocked, and then waits in the join.
   - **A failed pin must not hang the lane.** My call: the seam is a latch that the test releases in `@After`, or a `finally`, whatever the outcome. The join stays unbounded in production code, with no test-only exception. A held thread that is released always ends, so every later Activity test's join completes.
   - **Setup:** launch the Activity with the first boot held, and `recreate()`.
   - **Anchors:**
     - The held boot is the first runtime's.
     - While it is held, the new Activity is not booted. That proves the join waits.
   - **Release, then assert positively:**
     - The new Activity shows its page.
     - A tap on it gets a response, which proves the root is live and not disposed.
     - The first runtime is `retiredForTest`.
     - The new runtime is not retired.
     - The new Activity's mapper records no foreign patches (`foreignPatchesForTest`).
   - **Reds:**
     - Removing the join. The new boot then mounts first, and the released old boot mounts over it and takes the callback.
     - Removing the retire of the previous runtime.
2. **JVM, the start lock** (`src/BlazorNative.Jni/src/test`).
   - **Setup:** two runtimes. One `start()` is held at the D3 seam, inside the lock, and a second `start()` begins on another thread.
   - **Assert:** the second does not reach init until the first is released. That needs a probe, for example a second-entry flag set at the seam or a counter on entry to the lock.
   - **Red:** removing `synchronized`.
   - **Native library:** the JVM suite needs the native lib, so the builder checks the known trap with a stale native lib (the `jvm-suite-stale-native-lib` memory).
3. **Instrumented, the cross-bridge hold** (a sibling of the 18.3 secure-storage pins).
   - **Setup:** two `AndroidShellBridge` instances. On bridge A, an auth set whose prompt is held by the gate hook. On bridge B, a delete of the same key.
   - **Assert:**
     - B's delete is parked: the key is held, and B's call has not completed.
     - After A's prompt answers, A's encrypt runs before B's delete, and the key ends deleted.
     - A request on another key, through B, is not blocked.
   - **Red:** a per-bridge hold map, which is today's code.
4. **Instrumented, a destroy denies exactly the answers it drops.**
   - **(a) Own prompts only.**
     - **Setup:** bridges A and B, both alive, each with a pending prompt on a different key. Call `A.onHostActivityDestroyed(false)`.
     - **Assert:** A's prompt is denied (`AuthFailed`), and B's prompt is still pending.
     - **Red:** dropping the `shownBy` filter.
   - **(b) Orphans.**
     - **Setup:** A has a pending prompt. Call `A.onHostActivityDestroyed(true)`, then `B.onHostActivityDestroyed(false)`.
     - **Assert:** A's prompt is denied, and its key is released, so a parked same-key request runs.
     - **Red:** dropping the orphan clause.
   - A real-Activity variant of (b), with a real `recreate()` and then `finish()`, is preferred where the lane allows it. That follows the 18.3 lesson: pin with a real Activity, never only with the gate hook.

All seams are `@VisibleForTesting internal`, `null` or inert in production. Rule 5 headers name iOS as not affected and say why.

## Calls made in this design

- **D2:** the join is unbounded and logs once after 10 s.
- **D4:** the shared state stays in `AndroidShellBridge.kt`'s companion object, not a new file.
- **Dropped:** skipping a superseded boot that has not started yet.
- **iOS:** recorded as not affected, with no change.
- **D4:** a hold's owner is the pair of bridge and request id, and the new prompt field is named `shownBy`.
- **Pin 1:** the seam sits before the join and selects by runtime identity. A latch released in `@After` keeps a failed pin from hanging the lane.
- **D1:** a second live `singleTop` instance retiring the first one's runtime is accepted, with no pin.

**Owner decisions, 2026-10-31:** approach A. #601 is folded in with a process-wide owner. A destroy denies orphaned prompts too.
