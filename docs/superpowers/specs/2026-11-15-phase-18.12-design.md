# Phase 18.12 Design — `#407's relaunch trigger at its cause (#718)`

**Date:** 2026-11-15
**Phase:** `18.12`
**Surface:** `Infra`
**Stage:** phase (one phase, implementation-ready)
**Status:** draft

- **Milestone:** [M18](../../planning/MILESTONE.md), issues #718 and #580
- **Why this phase exists:** the [M18 audit](../../plans/2026-11-15-milestone-18-audit.md) graded DoD item 3 NOT MET. #407's trigger was never found; 18.1 only made the failure name itself.
- **Evidence:** [the 18.1 record §5](../../plans/2026-10-24-phase-18.1-record.md) for #407, and #580's issue body for the iOS cold `LAContext`.

## Goal

The Android lane no longer starts its first test while the APK install's delayed package changes are still arriving, proven by a reproduction that reds without the fix. #580's slow cold `LAContext` start is fixed at its cause, or recorded with evidence of why it cannot be.

## Decisions

| Question | Decision | By |
|---|---|---|
| What counts as "trigger found" for #718 | **Forced and natural.** Force the suspected change while a test runs and observe the same relaunch, one with no "Config changes" line. Also run a bounded natural loop that installs and then starts at once. The forced reproduction becomes the red that the fix greens. | Owner, 2026-11-15 |
| Where the #718 wait lives | **In the test runner.** Before the first test, `BlazorNativeTestRunner` waits for the package manager and the broadcast queues to go quiet after the install, with a ceiling that fails naming the last change. **Plus**, if the reproduction isolates one broadcaster, stop that source before the install, as 18.1 stopped the Play Store. | Owner, 2026-11-15 |
| #580 | **Investigate the cause first.** Run a bounded investigation into why a cold `LAContext` sometimes takes 30 to 51 s. Fix it at the cause if one is found. If not, record why, keep the named failure, and close #580 as accepted with the evidence. | Owner, 2026-11-15 |
| What a forced reproduction must show | **A trace event must force it.** A probe that is not in #407's trace, such as `pm install -r --dont-kill`, only supports the mechanism. The trigger counts as found only if one of these relaunches `MainActivity` in place: one of the trace's own events, which are PermissionController's uid flag update, SdkSandbox's reconcile and GMS `PACKAGE_CHANGED`; or the fresh install's delayed processing itself, fired at install time. A natural recurrence in the loop also counts. If neither happens, the phase stops and reports before fixing. | Owner, 2026-11-15 |
| Bounds | No test bound or timeout is raised. A new wait gets a ceiling, as the settle step's 300 s is. | Owner rule, carried from 18.1 |

## Why

- **The one occurrence.** In run 36124026574, `MainActivity` relaunched between the camera test's echo check and its image poll. The relaunch logged no "Config changes" line. Within about 0.1 s of it, logcat shows three things: PermissionController updating the shell's uid as user sensitive, SdkSandboxManager reconciling `io.blazornative.shell` and then `io.blazornative.shell.test`, and GMS `PACKAGE_CHANGED`. The camera test ran first, 2 s after Gradle installed the APKs at 10:33:04.
- **The gap.** `scripts/android-emulator-settle.sh` runs before `./gradlew connectedAndroidTest`, and that one Gradle step both installs the APKs and starts the instrumentation. So no step waits after the install.
- **The candidate mechanism (to be proven, not assumed).** When a package's `ApplicationInfo` changes in a running process, `ActivityManagerService` calls `scheduleApplicationInfoChanged`. The process then relaunches every one of its activities in place, with no configuration change logged. Overlay changes, split or resource-path updates and some package-state updates take this path. `OverlayManagerService` reacts to package installs asynchronously, so an update that arrives after the app process has started would relaunch the activity exactly like this. The trace fits the mechanism. Nothing yet shows that this mechanism is what happened.
- **DoD item 3** requires each CI flake to be fixed at its cause. A named failure is not a fix.

## Approach

### Part 1: #718, reproduce

1. **Forced reproduction, first.** Write a scratch instrumented test, or reuse the camera composition flow, that starts `MainActivity`, records the activity instance, and then fires one candidate trigger at the shell's package from the test via `UiAutomation.executeShellCommand`. It then checks whether the scenario now holds a different instance, and captures logcat around the event. Run each candidate alone, in this order, stopping at the first that relaunches the activity with no "Config changes" line:
   - an overlay state change that targets the shell, if the image has a suitable overlay, or a `cmd overlay` call that makes `OverlayManagerService` re-evaluate the shell;
   - `pm install -r --dont-kill` of the shell's own APK, which updates `ApplicationInfo` in the running process;
   - a replay of each broadcast in the original trace that the shell can trigger: a permission-flag change on the shell's uid, and an SdkSandbox reconcile, for example by touching the test package.

   The **relaunch signature** has three parts: a new `MainActivity` at PRE_ON_CREATE, no "Config changes" line, and the same process. The candidates split into two groups:
   - **Mechanism probes**, overlay re-evaluation and `install -r --dont-kill`. They show only whether an in-place `ApplicationInfo` relaunch happens on this image, and which signals move when it does. They do not count as the trigger (owner, see Decisions).
   - **Trace events**, the permission-flag change on the shell's uid, the SdkSandbox reconcile, GMS `PACKAGE_CHANGED`, and a fresh install fired while the activity is up. Only one of these, or a natural recurrence, counts as found.

   Run the probes first, because they are cheap and show which signals to watch. Then run each trace event alone. Runs go on scratch refs, one at a time, with `headSha` checked and attempt 1. The scratch test is not merged unless it becomes the pin (see Tests).
2. **Natural loop, bounded.** A scratch lane variant installs the APKs and starts the camera composition test at once, the original timing, and logs the activity lifecycle together with `dumpsys package changes`, `cmd overlay list` and the package broadcasts every second for the first 30 s after the install. It runs **10 times** (my call: about 8 minutes each, one at a time per ref). The loop is evidence, not a gate. A natural recurrence confirms the forced trigger. No recurrence is recorded as such. The loop also measures how long the install's own changes keep arriving after the install, and that number sets the runner's quiet window.
3. **If no candidate forces it,** the phase stops and reports to the owner before any fix is written. The wait condition would have nothing proven to wait on.

### Part 2: #718, fix the wait

4. **`BlazorNativeTestRunner` waits before the first test.** In `onStart`, before `super.onStart()` runs any test, the runner reads signals through `UiAutomation.executeShellCommand` and waits until all of them hold still for a quiet window. Then it runs `am wait-for-broadcast-idle`.
   - The signals are the ones Part 1 showed moving when the found trigger fired. They start from the settle step's two: the `Sequence number` from `dumpsys package changes`, and a hash of `cmd overlay list`.
   - If the trigger moves neither of those, add whatever it does move. The recent broadcast history in `dumpsys activity broadcasts`, filtered to the shell's packages, is an allowed signal.
   - A wait on a signal the trigger is not shown to move is not a fix.
   - **The quiet window** comes from the natural loop's measurement of the post-install tail. It is a quiet gate on a signal, not a test bound, as 18.1's 90 s was.
   - **The ceiling** fails the whole instrumentation run, naming the last change and its time, so a device that never goes quiet fails here and not in some test. The ceiling's value is the builder's call. It is not a test bound.
   - Every read, change and the final wait time are logged under a fixed tag that the lane can grep.
   - A read that returns no sequence number fails at once, as the settle script's does. A failed read never counts as quiet.
   - The window covers the measured post-install tail. A change that arrives later still fails with `RECREATED_WHILE_POLLED`, and the record says how often the natural loop saw one: never, if the window is right.
   - The wait runs for every instrumented run, local and filtered runs included. A filtered run pays the same wait. The design accepts that cost.
5. **Remove a single source, if one is isolated.** If the forced reproduction shows that one broadcaster alone causes the `ApplicationInfo` change, and it can be stopped before the install the way the Play Store was, add that stop to `scripts/android-emulator-settle.sh` with its evidence in the header. The runner wait stays either way, because it covers sources not yet seen.
6. **Comments become true.** The settle script's header and the lane comment in `android-instrumented.yml` currently say the trigger is unproven. Rewrite both to name what the reproduction proved. The 18.1 record keeps its historical text, and the 18.12 record supersedes it.

### Part 3: #580, investigate

7. **Capture a cold start with the daemon's own log.** On the iOS lane, a scratch step collects the simulator's unified log, `xcrun simctl spawn booted log collect` or `log show`. The predicate covers the LocalAuthentication subsystem, `coreauthd`, `biometrickitd` and the test host. The window spans the test process's first `LAContext()` creation. `BnBiometrics.warmUpContext` already times that creation; log its start and end with a unique marker, so the window can be cut out of the log.
8. **Bound:** up to **10 fresh-boot iOS runs** (my call: about 11 minutes each; the tail is about 2 in 10), stopping at the first run with a cold start over 20 s. If none appears in 10 runs, the investigation stops there. #580 is then recorded as not reproduced within the bound, with the timings seen.
9. **Read the slow window.** Find what the daemon or the host waits on during the slow creation: an XPC connection, keychain or SEP simulation setup, a launchd spawn of `coreauthd`, or a lock held by something else.
   - **If a cause is found that the shell or the lane can remove** (for example, a daemon the lane can start, or a dependency it can satisfy, before the test process creates its first context), fix it there. Prove it with the cold-start timing on runs after the fix. Because the tail is rare, the proof is the named mechanism plus runs where it no longer appears. A green run alone proves nothing.
   - **If the cause is outside the repo's reach** (simulator internals), or no cold start was caught, record the evidence in the 18.12 record. Close #580 as accepted, owner decision 2026-11-15. The named failure at `awaitContextWarmUp` stays as it is.

## Tests

- **The forced-trigger proof (the red the fix greens).** A recorded pair of scratch lane runs, the same lane variant with and without the runner wait. A backgrounded `adb` watcher in the scratch step fires the found trigger as soon as Gradle has installed the APKs, so it lands in the window the runner must wait out. It is a scratch pair, not a merged test, because a merged in-process test runs after the wait and cannot land in that window. The merged pins are the wait logic's own.
  - **Without the runner wait:** the camera composition test, or the pin itself, fails with `RECREATED_WHILE_POLLED`.
  - **With the wait:** it passes, and the runner's log shows that it waited on the change.

- **The wait logic's own pins,** instrumented tests in `androidTest`, which moves the Android baseline. They run against a fake shell that returns scripted outputs, each with a subject-side red under RS1:
  - waits while the sequence number changes, and returns only after the quiet window;
  - waits while the overlay hash changes;
  - fails at the ceiling, naming the last change;
  - fails at once when a read has no sequence number, and never counts it as quiet;
  - calls `am wait-for-broadcast-idle` after the quiet window.
- **Regression:** the full Android lane on the feature head, attempt 1 green, with the new baseline. The runner's log line appears and shows a wait. No per-test logcat has a `PACKAGE_CHANGED` line. The 11 deliberate recreations are the only tests with two `MainActivity` instances.
- **#580:** either the post-fix cold-start timings (above), or the recorded evidence of an accepted residual. iOS cannot compile on this Linux host, so any Swift change is proven on the iOS lane.
- **Pin-standard rules apply in full.** Each graded site gets a fresh red at its own line with its own message, one mutation per red. Any written claim that "no subject-side red exists" has at least two concrete subject-side attempts behind it, both recorded.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| No candidate forces the relaunch | No proven trigger; the fix would wait on a guess | Stop and report to the owner (Approach 3); do not ship a wait on an unproven signal |
| The trigger fires from a signal the runner cannot read from the shell uid | The wait misses it | Part 1 logs every signal around the forced trigger; the runner waits on whichever one moves; if none can be read, report it before fixing |
| The runner's wait slows every local run | A slower developer loop | Measure the cost on the lane and record it; the quiet window is set from data, not padded |
| A test bound gets raised by accident while making the lane green | Breaks the owner rule | Plan review checks every timeout diff; the record lists the bounds as unchanged |
| The #580 tail does not show up in 10 runs | No cause found | Record "not reproduced within the bound" with the timings seen, and close #580 as accepted, per the owner's decision |
| The forced-trigger proof exists only as scratch runs | No merged regression test for the trigger itself | The wait logic's own pins are merged; the record carries the red/green pair; the regression for the trigger itself is the lane's attempt-1 green with the runner log |
