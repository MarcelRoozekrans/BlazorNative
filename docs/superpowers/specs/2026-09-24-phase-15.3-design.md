# Phase 15.3 Design — `The first live test: deep-link scheme`

**Date:** 2026-09-24
**Phase:** `15.3`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M15 — A Standard for Pins](../../planning/MILESTONE.md)
**Standard:** [`docs/pin-standard.md`](../../pin-standard.md)
**Issue:** **#296** — deep-link scheme comparison is case-sensitive on Android, case-insensitive on iOS

## Goal

Close **#296** through the mechanism rather than around it: decide which behaviour is correct, give
the scheme **name** one home that every copy is pinned against, observe the divergence **red** on the
lane that runs the Android parser, and only then align the outlier.

## Why this is the milestone's first live test

15.2 defined coverage for the pin defeated five times. 15.3 is the first live divergence to meet the
standard, and the adjacency is deliberate (MILESTONE.md, *Ordering rationale*): if the standard
cannot close a one-word defect cleanly, it is cheap to find out here.

## What scoping measured (2026-09-24, on `origin/main` at `7aab286`)

1. **The divergence is still live, exactly as #296 describes.** `MainActivity.parseDeepLinkRoute`
   compares `data.scheme != DEEP_LINK_SCHEME`. `BnDeepLink.route(from:)` compares
   `url.scheme?.lowercased() == scheme`, and Swift already pins its half with
   `testSchemeMatchingIsCaseInsensitive`. The Kotlin side has no equivalent.
2. **The scheme name has more copies than the phase goal counted, and nothing compares them.** The
   goal names three (the Kotlin constant, `AndroidManifest.xml`, its template mirror). The measured
   set is **six declaration sites plus the vector URLs**:

   | # | Site | Form |
   |---|---|---|
   | 1 | `src/BlazorNative.Jni/src/androidMain/kotlin/io/blazornative/shell/MainActivity.kt` | `const val DEEP_LINK_SCHEME = "…"` |
   | 2 | `templates/…/android/src/androidMain/kotlin/io/blazornative/shell/MainActivity.kt` | same |
   | 3 | `src/BlazorNative.Apple/BnHost/BnDeepLink.swift` | `static let scheme = "…"` |
   | 4 | `src/BlazorNative.Jni/src/androidMain/AndroidManifest.xml` | `<data android:scheme="…" />` |
   | 5 | `templates/…/android/src/androidMain/AndroidManifest.xml` | same |
   | 6 | `src/BlazorNative.Apple/BnHost/Info.plist` | `CFBundleURLSchemes` array |
   | — | `src/deeplink-vectors.json` | the scheme of every `url` |

   The only existing comparison is Swift's `testTheBundleActuallyDeclaresTheScheme`, which checks
   site 6 against site 3 at runtime on the advisory iOS lane. Site 2 follows site 1 only through
   `TemplateMainActivity_EqualsTheRepos_Modulo…`. Sites 4 and 5 are compared with nothing, and the
   template manifest is **not** byte-identical to the shell's (its comment block differs), so no
   mirror guard covers it.
3. **Only one lane can observe the red.** The Kotlin parser is exercised solely by
   `BnDeepLinkVectorTest` (androidTest) on `android-instrumented`. Since #379 that lane runs on every
   PR, but it is **not** a required check. Required: `build-test`, `ios-build`, `android-build`,
   `pr-title`, `footer-check`. A green required set therefore does not show the red happened, so the
   evidence must be that lane's run **on the exact `headSha`** — an advisory lane can go green on an older commit than the one it appears to validate.

## Decisions (owner, 2026-09-24)

1. **Case-insensitive is correct.** RFC 3986 §3.1: schemes are case-insensitive, and producers
   should emit lowercase. iOS is already right and has a test saying so. Making iOS case-sensitive
   would reject URLs iOS already delivers, a user-visible regression on the shell that is correct
   today. Android gains `lowercase()`.
2. **One home plus a pin, not codegen.** The XML manifest and the plist cannot be generated without
   templating them, so codegen would still need the pin for three of six sites. The pin alone
   covers all six.
3. **Reachability is pinned on the emulator, not argued.** #296's counter-argument says the
   intent filter never delivers an uppercase scheme, so the parser fix would be unreachable. That is
   a claim about the platform, and it becomes an instrumented test that asserts what it **measured**.

## Approach

**The home.** `src/deeplink-vectors.json` gains a top-level `"scheme": "blazornative"`. It is the
natural home: the file already owns the deep-link parse rule, and every vector URL is written
against that scheme. WireGen must tolerate the new key. Whether it also emits the value into the
generated tables is a plan-level choice. The pin reads the JSON directly either way, so a generator
bug cannot hide a drift from it.

**`DeepLinkSchemeDriftTests` (.NET, `tests/BlazorNative.Runtime.Tests`).** It reaches the tree
through `BnRepo.Root()` (Rule 6) and extracts one value from each of the six sites with a
site-specific pattern, comments stripped through the shared stripper where the file kind has one.
It asserts:

- **Agreement.** Each site's value equals the home, **ordinally**. Case matters for the
  *declarations*: Android's docs require lowercase filter schemes, because framework matching is
  case-sensitive.
- **The home is lowercase.** RFC 3986's producer rule, and the precondition for the Android filter.
- **Rule 2, the floor.** Every site yields **exactly one** match, and six sites are visited. A
  pattern that stops matching reds on the count; it never passes over nothing.
- **Rule 3, the positive control.** A fixture tree with a planted mismatch (for example, the
  template manifest spelled `blazor-native`) must make the agreement assertion red through the same
  code path the real assertion uses.
- **Rule 5, stated limits.** It pins the **shipped** template, not an app generated from it. A user
  who renames the scheme after `dotnet new` owns all their copies, and `website/docs/shells/android.md`
  already tells them where the copies live. It does not cover a scheme constructed at runtime from
  parts. It does not cover a second `<data android:scheme>` added to another activity; for that
  shape the floor reds, which is a red for the wrong reason and is disclosed as such.
- **Vectors.** Every vector with a non-null route uses the home scheme, compared
  **case-insensitively**, because the #296 row deliberately differs in case.

**The red.** An 8th vector, `BLAZORNATIVE://settings` → `/settings`, is added to the JSON and
regenerated into all three `BnDeepLinkVectors.g.*`. `DeepLinkVectorTests` gains
`TheTable_StillContainsTheSchemeCaseRow`, the analogue of `TheTable_StillContainsTheCaseThatDiverged`,
so losing the row is a red on the required lane and not a quiet diff. This commit is pushed **without
the fix**. The expected result: `android-instrumented` red on the uppercase row, iOS green (it already
lowercases), .NET green.

**Reachability, measured then pinned (instrumented).** Two facts, both against our own package
(`setPackage(context.packageName)`, which package visibility on API 30+ permits):

- **Implicit.** `queryIntentActivities(ACTION_VIEW + BLAZORNATIVE://settings)` shows whether the
  filter resolves an uppercase scheme to `MainActivity`.
- **Explicit.** An intent with the component set bypasses filter matching entirely, so the parser
  is reachable with an uppercase scheme **whatever** the filter does. This is the reason the fix is
  not dead code, and it is stated as something to confirm rather than assumed.

Each assertion is written **after** the measurement is observed on the emulator, never guessed:
never invert an unpinned claim. The result decides how the PR and
CHANGELOG describe the change, as a user-visible fix or as parity hygiene. #296 asked exactly that
question.

**The fix.** `if (data.scheme?.lowercase() != DEEP_LINK_SCHEME) return null` in
`MainActivity.parseDeepLinkRoute`, with a comment citing RFC 3986 and the Swift twin. The template's
`MainActivity.kt` takes the identical edit. The existing template pin reds if it does not, so the
mirror is enforced rather than remembered.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `android-instrumented` does not run, or runs on a later SHA, before C lands | "Red before fixed" goes unevidenced, and the phase's own criterion fails silently | Push B alone and wait for that lane **on B's SHA** before pushing C. Compare `headSha`, not conclusion |
| Site extractors are too loose (match a comment or another attribute) | A pin that agrees with a comment, not the code | Strip comments with the shared stripper; the floor demands exactly one match per site; mutation-prove each extractor |
| The reachability result varies by Android API level | A flaky pin | It asserts on the lane's AVD image, and the test states that API level in its limits. If the result is not stable across runs, record it and keep only the explicit-intent fact |
| WireGen chokes on the new top-level key | Commit A breaks generation | A plan task runs WireGen before and after, with a clean rebuild (`--no-incremental`) |
| Count drift across README and three workflows | `ReadmeDriftTests` red on the required lane | Move all four in the same commit as the tests that change them |
| The template manifest is edited by users and a pin over it feels over-reaching | None for users: the pin runs in this repo only | Stated as a Rule 5 limit |

**No new public API, wire or ABI change:** test files, a JSON manifest, one private Kotlin line and
its template mirror. This is verified in the phase-close diff.
