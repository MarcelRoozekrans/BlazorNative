# Phase 16.2 Design — `Back and navigation off the main thread`

**Date:** 2026-09-27
**Phase:** `16.2`
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M16 — Unblock the Dispatch Lane](../../planning/MILESTONE.md)
**Builds on:** Phase 16.1, the render thread ([PR #428](https://github.com/MarcelRoozekrans/BlazorNative/pull/428)). Its `FaultNotice` op established the .NET-to-shell notice pattern over `hostCallBegin`.
**Closes:** #346.

## Goal

No main thread ever waits on .NET. Android back gets its verdict from a back state that .NET pushes, rather than from a blocking call. Deep-link and notification navigation become fire-and-forget on both shells. The blocking `dispatchHostEventAndWait` leaves the public shell surface.

## Measured starting point

On `main` at `3a9eb62`:
- **Android back blocks the main thread.** `MainActivity.handleBack` (`MainActivity.kt:632-641`) calls `runtime.dispatchHostEventAndWait(BnHostEvent.Back) == 0` from the main thread. It is reached from a platform `OnBackInvokedCallback` registered at `:585-591` on API 33+, and from an `onBackPressed` override at `:602-607`. The callback is registered once and never toggled.
- **Warm deep links block the main thread too.** `onNewIntent` (`:567`) calls the same method for the warm navigate. Its rc is **only logged**.
- **iOS navigation blocks the main thread.** Both navigators, deep link and notifications, call `dispatchHostEventAndWait` from main (`BnRuntime.swift:313-323`). `BnDeepLink` **discards** the rc, and `BnNotifications` stores it **only for a test seam**.
- **`MainActivity` can use AndroidX back.** It is a `FragmentActivity`, so it has a `ComponentActivity` and its `OnBackPressedDispatcher`. `androidx.activity` arrives only transitively, through `androidx.biometric:biometric:1.1.0`. The build has `minSdk` 24 and `targetSdk` 34. The manifest sets `enableOnBackInvokedCallback="true"`.
- **.NET's "can go back" is one slot.** `NativeNavigationManager._previousRoute` (`NativeNavigationManager.cs:140`) is a single slot, and `NavigateBackAsync` returns false when it is null.
- **"Back at root finishes the Activity" is not pinned on a device** (`HostEventAndroidTest.kt:24-27`).
- **iOS has no system back.** `BnHostEvent.back` is unused on iOS.

## Owner decisions (2026-09-27)

1. **Use AndroidX `OnBackPressedCallback`** with `isEnabled` toggled, on every API level. Add `androidx.activity` as an explicit, pinned dependency at a version that drives predictive back.
2. **The visible screen wins the stale window.** The back state is applied on main **in the same batch as the frame that shows the navigation**. If a back still reaches .NET at root, .NET tells the shell to finish, so **a press is never swallowed**.
3. **`dispatchHostEventAndWait` becomes internal and test-only** in both shells, and its public listing goes. `src/dispatch-surface.json` records the change.

## Approach

**1. .NET publishes the back state.**
- `canGoBack` is `_previousRoute != null`.
- Two new ops go into `src/wire-vocabulary.json` `hostCallOps` and are generated for all three languages:
  - **`BackState` = 6**, with args `{"canGoBack":"true"|"false"}`;
  - **`BackUnhandled` = 7**, with no meaningful args.
- `NativeNavigationManager` computes `canGoBack` after every state change: navigate, back, `NotifyMounted`, and session reset. It sends a `BackState` notice **only when the value changes**, and always sends one for a session's first mount.
- The notice is sent from the render thread with the same fire-and-forget delivery as `FaultNotice`: bounded, never throwing into the render thread, and cleaned up.
- **Ordering, which is the heart of decision 2.** The `BackState` notice for a navigation must reach the shell **before** the frames that show the new page. Place the send inside the navigation's synchronous part, before the swap's frames are emitted, and pin the order.
- `DispatchHostBack` at root, where `NavigateBackAsync` returns false, sends `BackUnhandled` and returns rc 1, as it does today.

**2. Android.**
- `onCreate` registers one `OnBackPressedCallback(false)` on `onBackPressedDispatcher`.
- Its `isEnabled` equals `pendingCanGoBack || mapper.hasOpenModal`. It is recomputed **on main**:
  - in `WidgetMapper.applyBatch`, which applies the buffered `BackState` together with the batch;
  - whenever a modal opens or closes.
- `handleOnBackPressed` does one of two things:
  - if a modal is open, it dismisses it, as `requestTopmostModalDismissal` does today;
  - otherwise it calls `runtime.dispatchHostEvent(BnHostEvent.Back)`, fire-and-forget.
- The `BackState` arm only buffers the value, from whatever thread .NET sent it on. The frame producer hands it to the **first batch after the notice that is not removal-only**, and main applies it at the end of that batch's runnable, together with the page. *(Changed in Task 3's fix rounds: a swap is two frames, the old root's removal and then the new page's mount, so the removal-only batch is skipped, or back would change on a blank screen. The mount's batch always exists, even for a page whose first render is empty, which mounts with a lone CommitFrame, so no "apply directly if no batch is pending" fallback is needed; one would apply every value ahead of its page, because the notice always precedes the frames.)*
- The `BackUnhandled` arm posts to main and hands the press to the platform's default back: it disables the callback, re-dispatches through `onBackPressedDispatcher`, then restores `isEnabled` to the mapper's computed state. It does nothing once the activity is finishing or destroyed. *(Changed in Task 3's fix round 1 from `finish()`: on Android 12+ the default back moves a launcher task root to the background rather than finishing it, and a press that reaches .NET at the root should behave exactly like one that never left the shell. The restore keeps the callback from drifting from the mapper, which publishes only on a change.)*
- **Remove** `registerPredictiveBack`, the `backCallback` field and the `onBackPressed` override.
- `onNewIntent`'s warm navigate becomes `dispatchHostEvent`.
- Add `androidx.activity` as an explicit dependency, pinned. Choose the newest version compatible with `compileSdk` 34, and record the choice. Apply the same change to the template's Gradle file and its `MainActivity` mirror. Keep `TemplateMainActivity_EqualsTheRepos_ModuloTheFallbackAndTheImport` green.

**3. iOS.**
- `BnRuntime`'s two `navigateDispatcher`s call `dispatchHostEvent`, fire-and-forget.
- `BnNotifications.lastHostEventRcForTest` loses its rc source. Either make the seam record that the dispatch was issued, or retire it, and say which in the report.
- `AppleShellBridge` gets `BackState` and `BackUnhandled` arms that complete OK and do nothing, because iOS has no system back.

**4. `dispatchHostEventAndWait` becomes internal.**
- Kotlin: `internal`. Swift: `internal`, which is reachable through `@testable import`.
- Update `src/dispatch-surface.json` so the drift pin still covers the method and records it as test-only.
- Update any public doc that lists it, including `docs/` and `website/`.

## Tests

Every new pin conforms to `docs/pin-standard.md` Rules 2–5 and 7, with recorded mutations. **Every notice pin runs in production mode** (`StrictErrors = false`); this is the lesson from 16.1.

- **.NET**
  - The first mount sends `BackState(false)`, and navigating away sends `BackState(true)`.
  - Back to root sends `BackState(false)`.
  - No notice is sent when the value does not change.
  - **Ordering:** the `BackState` notice is recorded before the frame that carries the new page.
  - Back at root sends `BackUnhandled` and returns rc 1.
- **JVM**
  - The shared routing handles ops 6 and 7.
  - `dispatchHostEventAndWait` is not public: a reflection or visibility pin.
- **Android instrumented**, on an emulator:
  - back from a page navigates to its parent;
  - **back at root finishes the Activity**, observed through `ActivityScenario` reaching `DESTROYED`. This is the first on-device pin of that path;
  - **#346's own scenario:** while a handler holds a host call open, a back press returns at once, and the navigation completes once the call is released;
  - navigate, then press back at once: no exit and no swallowed press;
  - with a modal open, back dismisses the modal.
- **XCTest:** the deep-link navigate returns without blocking main, and ops 6 and 7 complete OK.
- **Counts:** measured and asserted in `ci.yml`, `android-instrumented.yml`, `ios.yml` and README, each with a history comment.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **The `androidx.activity` bump moves a transitive dependency that biometric and fragment also use** | A runtime break only a device shows | Pin it explicitly, run the instrumented lane on the PR head, and pin the template's Gradle file to the same version |
| **The ordering between `BackState` and the frame is wrong** | The stale window decision 2 exists to close comes back | A .NET ordering pin, plus the instrumented "navigate then back at once" test |
| **Removing `onBackPressed` changes behaviour below API 33** | Back is ignored on old devices | AndroidX dispatches back on every API level. The instrumented lane runs API 34, so record in the outcome that pre-33 is covered only by AndroidX's own contract |
| **`finish()` on `BackUnhandled` races a navigation** | The app exits after a page was pushed | .NET sends `BackUnhandled` only when back ran at root. A navigation during the race produces a `BackState(true)` in the same frame batch. State the rule and pin the at-root case |
| **Narrowing `dispatchHostEventAndWait` breaks a downstream shell** | A compile error in an app's custom shell | Pre-1.0, and the template never calls it after this phase. The changelog calls it out |
