# Phase 14.3 Design — `Auth semantics`

**Date:** 2026-09-22
**Phase:** `14.3`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M14 — Twin Divergence, Closed Mechanically](../../planning/MILESTONE.md)
**Closes:** [#213][i213] item 1 — the secure-storage ACL mismatch, reported on hardware by
@ceesalberts during the P3 device run.

[i213]: https://github.com/MarcelRoozekrans/BlazorNative/issues/213

## Goal

`requireAuth: true` means **biometry** — one answer, on both shells, enforced by a pin that reds
when a new call site introduces a different one.

## The divergence, stated from the code

M14 classifies twin divergence into two sub-shapes: **vocabulary** (same names, three languages →
closed by codegen) and **semantics** (same name, different behaviour → closed by a differential
pin). #213 item 1 is the second shape, and it is **intra-shell**: the Apple shell disagrees with
itself.

There are **seven live sites** across the two shells that answer "what counts as authentication".
Six say biometry. One does not.

| # | site | kind | token | means |
|---|---|---|---|---|
| 1 | `AndroidShellBridge.kt:949-951` `provisionKey` | gate | `AUTH_BIOMETRIC_STRONG` | biometry |
| 2 | `AndroidShellBridge.kt:896` prompt info | gate | `Authenticators.BIOMETRIC_STRONG` | biometry |
| 3 | `AndroidShellBridge.kt:698` `canAuthenticate` | probe | `Authenticators.BIOMETRIC_STRONG` | biometry |
| 4 | `BnSecureStorage.swift:219` write ACL | gate | `.biometryCurrentSet` | biometry |
| 5 | **`BnSecureStorage.swift:301` read policy** | **gate** | **`.deviceOwnerAuthentication`** | **biometry OR passcode** |
| 6 | `BnBiometrics.swift:167` `evaluatePolicy` | gate | `.deviceOwnerAuthenticationWithBiometrics` | biometry |
| 7 | `BnBiometrics.swift:144` `canEvaluatePolicy` | probe | `.deviceOwnerAuthenticationWithBiometrics` | biometry |

**Site 5 is the outlier**, and the device run proved the OS honours it exactly as written. The
`coreauthd` trace shows what policy 2 builds:

```
ACMRequirement of type:7, state:1, flags:0 ->
    MechanismKofN[4802](k:1)(MechanismPasscode[4799], MechanismPearl[4800])
```

`KofN(k:1)` over `{Passcode, Pearl}` — passcode *or* Face ID — and `securityd` then accepts that
context for the `.biometryCurrentSet` item. So:

> A secret stored under a **biometry-only, current-enrolment-bound** ACL is in practice readable
> with **the device passcode**, and nothing in the API surface, the returned status, or the demo
> echo tells the developer that.

**The consequence is inverted from what #213 predicted.** The issue predicted a spurious
`AuthFailed` after a successful passcode fallback — a usability failure. Hardware showed no such
refusal. What it showed instead is a **weaker gate than the stored ACL declares**, which matters
more: a usability failure is visible, and this is not.

## The decision (owner, 2026-09-22)

**`requireAuth: true` means biometry only.** Align site 5 to the other six.

The milestone left this open as a three-way choice and said to resolve it at phase start. Reading
the code collapsed it, because the split is **6-to-1, not even**: Android means biometry on both
its gate and its probe, the Apple shell's own write ACL means biometry, and `BnBiometrics` means
biometry. Only the storage *read* disagrees — and it is the one that weakens the guarantee.

The two alternatives were both *widenings dressed as consistency*. Adopting passcode-or-biometry as
the contract would require relaxing Apple's ACL to `.userPresence` **and adding
`AUTH_DEVICE_CREDENTIAL` to Android's key spec and prompt** — a four-site change that weakens the
shell which currently gets it right, to match the one that does not. Adding a caller-facing
`BnAuthStrength` parameter would turn a divergence into public API that freezes at 1.0, which is
the opposite of what this milestone is for.

### The lockout trade-off, accepted explicitly

Aligning removes the iOS passcode rescue during **biometric lockout** — the common case, more
likely than "no biometric enrolled". The owner accepted this: **Android already behaves this way**
(`ERROR_LOCKOUT` maps to `AUTH_FAILED`), the secret is never permanently unreachable, because
unlocking the device with the passcode resets biometry, and consistency is the milestone's point.
**No new status value ships** — lockout surfaces as `AuthFailed` on both shells, which is Android's
existing behaviour.

### Device-support floors — checked, not assumed

The change narrows **authenticators**, not device age.

- `.deviceOwnerAuthenticationWithBiometrics` exists since **iOS 8**; this repo targets **iOS 13.0**.
  The `.biometryCurrentSet` ACL already in use needs iOS 11.3, so the read policy is *less*
  restrictive on OS version than the write side already shipping. Nothing regresses on old iOS.
- The policy covers **Touch ID and Face ID** both — `Pearl` in the device log is Face ID's internal
  name, not a restriction. An iPhone SE or 8 keeps working.
- `setUserAuthenticationParameters` is **API 30+** and is already guarded by
  `Build.VERSION_CODES.R`. On **minSdk 24** through 29 the code calls
  `setUserAuthenticationRequired(true)` alone, whose default per-use validity requires a
  fingerprint — device credential was not available for per-use auth before API 30. **Old Android
  is already biometry-only**, so aligning iOS creates no new split.

## Approach

**1 — The behaviour change.** One token, at `BnSecureStorage.swift:301`:
`.deviceOwnerAuthentication` becomes `.deviceOwnerAuthenticationWithBiometrics`. The surrounding
`finishAuthorizedRead` flow, the `inFlightContext` retention, and the simulator affordances
`authLabel` and `authBoundAccounts` are untouched. The file's header comment block, which describes
the read as device-owner authentication, must move with it or it becomes a fresh lie.

**2 — The pin, which is this phase's actual deliverable.** The DoD asks that **a new divergence
red**, not that this one be fixed. `src/auth-semantics.json` declares the seven sites above — each
with `name`, `file`, `language`, a `kind` of `gate` or `probe`, the required `token`, and a
`reason` — behind a `$doc` block explaining why the file exists, in the shape
`src/dispatch-surface.json` established in 14.1. `AuthSemanticsDriftTests` then asserts:

- **Declared-site agreement.** Each site's source still carries its declared token. Reverting
  site 5 reds.
- **Completeness.** Every occurrence, anywhere in either shell's non-test source, of a token from
  the authenticator vocabulary — `.deviceOwnerAuthentication`,
  `.deviceOwnerAuthenticationWithBiometrics`, `.biometryCurrentSet`, `.biometryAny`,
  `.userPresence`, `AUTH_BIOMETRIC_STRONG`, `AUTH_BIOMETRIC_WEAK`, `AUTH_DEVICE_CREDENTIAL`,
  `Authenticators.BIOMETRIC_STRONG`, `Authenticators.BIOMETRIC_WEAK`,
  `Authenticators.DEVICE_CREDENTIAL` — must appear in `sites`, or in `ignored` carrying a written
  reason. **This is the half that makes a NEW divergence red:** a new call site using
  `.userPresence` fails the build instead of quietly becoming an eighth opinion.
- **Anti-vacuity.** The scan asserts it found at least seven tokens. Without this, the completeness
  test passes while scanning nothing the moment its regex stops matching — which is the **known
  open residual** on `EveryDispatchNamedDeclaration_IsDeclaredOrIgnored` from 14.1. Close it here
  rather than reproduce it.

The pin reads **source**, like 14.1's. Say so in the `$doc`: it does not observe an authentication
at runtime, and a genuinely behavioural cross-shell pin would need a JVM test and an XCTest that
agree with each other — an unpinned twin in its own right.

**3 — The read-side contract: already tested, not reachable on a device.** `BnSecureStorage.swift`
`:249-252` states the contract — a plain get of a biometric-bound secret must not hand back the
plaintext.

**Checked before planning any work, and the automated half is already done on both shells:**

- Android — `BnSecureAndroidTest.kt:100-112`,
  `a_plain_get_of_an_auth_bound_item_authfails_the_os_key_binding`, asserting the status **and**
  `assertNull("an AuthFailed get carries no value", outcome.value)`.
- Apple — `BnSecureStorageTests.swift:125-143`,
  `testAnAuthBoundSetAttachesTheAclAndTheShellRefusesAPlainGet`, asserting the status **and**
  `XCTAssertNil(got.value, "an AuthFailed get carries no value")`.

So the DoD's "never exercised" means **never exercised on hardware**, and the reason is narrow and
concrete: `BnSecureDemo.cs` has buttons for Authenticate, Set, Unlock and Delete, but **none for a
plain Get**. Its own header comment at `:23-25` already *describes* the plain-get refusal as part
of the pairing the page exists to show — the page documents a flow it cannot perform.

**The work is therefore the button, not a test.** Do not add a third assertion of what two suites
already assert; add the control that makes the contract reachable by hand on a device, and let it
ride 14.4's checklist.

Two traps that make this bigger than "add a button":

- `BnSecureDemo.cs` is a **hand-written `RenderTreeBuilder`** with explicit sequence numbers in
  bands — Authenticate 10-12, Set 20-22, Unlock 30-32, Delete 40-42. A colliding sequence number
  produces a **wrong diff silently**, with no error. The new button needs its own band.
- The file's comment at `:41-43` records that the shells' render suites select the echo with
  *"first TextView/UILabel that is not a Button"*. A button added in the wrong position moves that
  selector's target and reds both shells' render tests for a reason that looks unrelated.

**4 — A safety claim that nothing enforces.** `BnSecureStorage.swift:206-207` asserts that
`secureSet` returns `Unavailable` when there is no secure hardware or nothing enrolled — that is,
that iOS fails **early**, as Android does at key generation. Nothing pins it, and whether
`SecAccessControlCreateWithFlags` actually fails without enrolment, or succeeds so that `SecItemAdd`
fails later, is exactly what a simulator cannot answer. This is the repo's most-bitten class: an
invariant asserted in a comment. **Establish it or correct the comment.** If it can only be settled
on hardware, say so in the comment and add it to the device checklist, rather than leaving the
claim standing unqualified.

**5 — The migration note.** M14's risk table requires one whichever way the decision went. It states
that `requireAuth: true` now means biometry on both shells, that a passcode no longer unlocks an
auth-bound secret on iOS, and what a consumer relying on that should do. Pre-1.0 is the cheap
window and the surface freezes at 1.0 — that is the argument for making the change now, and it
belongs in the note.

## Tests

- **Unit, .NET:** `AuthSemanticsDriftTests` — declared-site agreement, completeness, anti-vacuity.
  Mutation-prove all three: flip site 5's token, add an undeclared `.userPresence`, and break the
  scan regex. Each must red. A pin that passes under its own mutation is the vacuous-pin class this
  repo has already been bitten by twice.
- **Read-side contract:** **no new test.** Both shells already assert the status *and* the absent
  value — `BnSecureStorageTests.swift:125-143` and `BnSecureAndroidTest.kt:100-112`. Adding a third
  assertion of the same property is duplication, not coverage. What ships is the demo button that
  makes the contract reachable on hardware.
- **Render suites, both shells:** unchanged behaviour but a changed tree — the new demo button must
  not displace the echo selector described at `BnSecureDemo.cs:41-43`, and must not collide with an
  existing sequence band.
- **Regression:** the existing secure-storage and biometrics suites on both shells unchanged in
  count except for the additions above. The token change alters *which* authenticator the OS
  demands; it must not alter any status mapping.
- **Device, manual, folding into 14.4's checklist:** the plain-get button on hardware, and the
  no-enrolment question from item 4.

## Open Questions

None blocking. Both decisions this phase needed — the meaning of `requireAuth`, and whether the
lockout trade-off changes it — were resolved by the owner on 2026-09-22 and are recorded above.

One item is **deliberately deferred, not open**: whether `secureSet` fails early without enrolment
may prove unanswerable off-device. The approach above says what to do in that case — qualify the
comment and add it to the device checklist — so it cannot silently become a blocker.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The simulator cannot enforce a `SecAccessControl`, so the Apple read-side test proves less than it appears to | A green XCTest reads as "the contract holds" when the simulator never enforced anything | The file already documents this and carries simulator affordances for it. The test asserts the *shell's* refusal path and the comment says so; the hardware half rides 14.4's checklist |
| The completeness scan is a regex over source and can silently stop matching | The pin passes while scanning nothing — exactly 14.1's open residual | The anti-vacuity assertion is a **required** part of the deliverable, not a nicety, and is mutation-proven |
| Changing the read policy alters failure modes beyond the intended one | A status mapping shifts and no test notices | The regression bar above: counts unchanged except the named additions, status mappings asserted unchanged |
| An existing consumer relies on passcode fallback | Breaks on upgrade | Pre-1.0 is the cheap window and the explicit reason to do it now. Ships with the migration note |
| The device lanes go stale on a phase that changes shell source | A green required set reads as validation when no device ran | Dispatch both lanes against the **head commit** and compare `headSha`, not just conclusion — the 14.2 finding |
