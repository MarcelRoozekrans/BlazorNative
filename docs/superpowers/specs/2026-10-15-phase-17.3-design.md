# Phase 17.3 Design — `Activity recreation`

**Date:** 2026-10-15
**Phase:** `17.3`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M17 — Close the Dispatch Lane's Debt](../../planning/MILESTONE.md)
**Issue:** #425, with its follow-up comment on navigation history.

## Goal

A recreated Activity never shows a frame from the page it replaced, and Back at its root finishes
instead of navigating to a page from before the recreation.

## What the code actually does, and why the fix changed

The milestone design chose a **session generation**, with `retire()` closing .NET's frame gate as the
fallback. Reading the code showed that premise does not hold:
- **There is one process-global .NET session.** A recreated Activity builds a new
  `BlazorNativeRuntime` and calls `start()`. That re-registers the frame callback, last
  registration wins, and **mounts a second root on the same session**.
  `BlazorNativeRuntime.start`'s KDoc says so: "old instances are never disposed and accumulate
  natively".
- **The stale frames come from the old ROOT, not from an old session.** A handler on the old page
  that is suspended on a host call, a permission sheet for example, resumes after recreation. It
  re-renders, and the frame reaches the **new** Activity's mapper, carrying the old page's node
  ids.
- **`MainActivity` never calls `retire()`.** `onDestroy` only destroys the mapper.

A generation has nothing to tell apart, and it would need a wire change in every shell.
**Owner decision, 2026-10-15: a mount replaces the root.** The milestone DoD and ROADMAP are
updated with this design.

## Approach

1. **A mount replaces the root, in .NET, `HostSession.TryMount`.** When a root is already mounted,
   the mount first unmounts it with `NativeRenderer.Unmount`, as navigation already swaps roots.
   Blazor drops a render request for a disposed component. A late continuation of the old page
   therefore re-renders nothing, and **no stale frame is produced at all**. It also ends the leak
   of one root per rotation. No export, struct field or wire op changes.
2. **Navigation history resets with the root.** A replacing mount clears the navigation
   manager's `_previousRoute`, so Back at the new root is unhandled and finishes the Activity. The
   reset comes **before** the mount's `PublishBackState`, so the shell is told `canGoBack = false`
   before the first frame.
3. **A retired runtime drops frames, in Kotlin, `BlazorNativeRuntime`.** `retire()` sets a flag,
   and the frame callback drops anything it still receives. That closes the window between the old
   Activity's teardown and the new `start()` re-registering the callback, which item 1 cannot
   reach. `RetireLateContinuationTest` pins today's hazard; it is flipped.
4. **The shell retires the old runtime.** `MainActivity.onDestroy` calls `runtime.retire()` after
   its `OnDestroy` event and before `mapper.destroy()`. Both the reference shell and the template
   copy change. `retire()` waits, bounded at 5 s, only for an in-flight synchronous part; since
   16.1 a dispatch returns at its first yield.
5. **iOS** shares the .NET change. It mounts once per app and has no Activity recreation, so its
   behaviour is unchanged: the XCTest lane must stay green, and no Swift change is planned.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Something mounts a second root on purpose, such as a test, a host or a dev tool | It loses its first root | Search every `TryMount` and `Mount<T>` caller. `HostSession.ResetForTests` already starts tests clean. A real multi-root need would surface here |
| Blazor does not drop a render request for a disposed component | Fact 1 reds or throws | Fact 1 is the measurement. If it throws, the throw is caught as a late fault, and the design returns to the owner |
| `retire()` in `onDestroy` blocks main for up to 5 s | An ANR on a slow synchronous handler | A dispatch returns at its first yield since 16.1, so only a slow synchronous part could block, and the slow-handler Warn already flags those. The bound and the risk are recorded |
| Unmounting during a pending dispatch's synchronous part | A fault in the old root's teardown | The unmount runs on the render thread, serialised with dispatches by `OnRenderThread`, as navigation's swap is |
| The template's `MainActivity` diverges from the reference shell | The mirror guard reds | Edit both together |
