# Phase 16.3 Design — `Starvation, measured`

**Date:** 2026-09-27
**Phase:** `16.3`
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M16 — Unblock the Dispatch Lane](../../planning/MILESTONE.md)
**Closes:** #9, a hardening-ledger item that was accepted as debt for 1.0 criterion Q3.

## Goal

Measure what a slow **synchronous** handler still costs now that async handlers free the lane. Make that stall diagnosable with a slow-handler warning, and publish the threading contract for app authors.

## Where #9 stands after 16.1 and 16.2

#9 asked whether one blocked handler starves every later event on the single dispatch lane. The earlier phases have changed the answer:
- **An async handler no longer holds anything.** The export returns when the handler yields (16.1).
- **The main thread never waits on .NET.** Back and navigation are fire-and-forget (16.2).

What remains is a handler whose **synchronous** part is slow. The render thread runs it while the shell's dispatch lane waits for it, so later events queue behind it. That is app code: a heavy computation, or a blocking `.Result` or `.Wait()` inside a handler.

## Owner decision (2026-09-27)

Ship a **slow-handler warning**, plus the measurement and the threading page. Close #9 as fixed by detection plus a documented contract.

## Approach

**1. Measure.** A throwaway harness runs on .NET, directly against `Exports`, with results recorded in the phase record rather than a test. Handlers have synchronous parts of 0, 10, 50, 200 and 1,000 ms, and the harness measures:
- the latency a second event sees, behind a slow first event;
- how long a `back` host event waits for its synchronous part;
- that no main-thread path waits. This is by construction since 16.2; confirm it with the caller scan and the 16.2 device pin, and do not re-measure on a device.

**2. The warning.**
- The render thread already opens and closes a scope around each dispatch's synchronous part (16.1 `DispatchScope`). Time that interval with a `Stopwatch` timestamp.
- When the interval exceeds `SlowHandlerBudget`, log one `BnLog.Warn`. The log names the handler id, the event name and the elapsed milliseconds, and never the payload.
- Warn **once per handler id per session**, then stay quiet for that handler. `BnLog.DefaultLevel` is `Warn` in every build, so this rate limit is what keeps Release quiet.
- `SlowHandlerBudget` is an `internal const`, **100 ms by default**. The measurement may move it, and if it does, the reason is recorded. It is not public API.
- The budget also covers the host-event arms' synchronous parts (`back`, `navigate`, lifecycle, multicast), keyed by event name.

**3. The threading page.** Create `website/docs/guides/threading.md` and link it from the guides index. It covers:
- **The render thread:** what runs where. The shell lane hands work to the render thread, and continuations run on the render thread.
- **Return codes:** rc reports the synchronous part only. Late faults arrive as `FaultNotice`, which reaches `onError` on a thread-pool thread.
- **`InvokeAsync(StateHasChanged)`** instead of `ConfigureAwait(false)` before a render. Link #427.
- **Don't block the render thread:** no `.Result`, `.Wait()` or `GetAwaiter().GetResult()` in a handler. Cite the measurement.
- **The slow-handler warning:** its budget and its once-per-handler rule.
- **Back on Android,** in brief: it never blocks, and the platform default applies at root.

The docs guards already exist (`DocsSamplesDriftTests`, `DocsNameDriftTests` and the CI docs-samples compile), and every code sample on the page must pass them.

**4. #9 is closed after merge,** with an evidence comment: the measurement, the warning and its pins, and the page.

## Tests

Pins follow `docs/pin-standard.md` Rules 2–5 and 7, and run in production mode (`StrictErrors = false`).
- A handler over budget produces exactly one Warn, naming the handler id, the event name and the milliseconds.
- A handler under budget produces none.
- The same handler slow a second time produces no second Warn. A different slow handler produces its own.
- The payload never appears in the Warn: use a payload with a unique marker.
- A slow `back` or lifecycle arm is warned, keyed by event name.
- **Mutations to record:**
  - remove the budget check, so every dispatch warns;
  - remove the once-per-handler set, so the second run warns;
  - include the payload in the message.

Make the slow handler deterministic and cheap: a hook or a test clock, not a real 100 ms sleep that makes the suite slow or flaky. Use a real sleep only where it proves the timer.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Timing tests are flaky on a loaded CI machine | Red CI with no defect | Inject the clock, or make the "slow" case a large multiple of the budget, and never assert near the boundary |
| The warning spams Release logs | Log noise in apps | Once per handler per session, and never the payload |
| The measurement moves the budget | A budget that doesn't match the page | Set the budget from the measurement, record why, and quote the same constant on the page |
| The page drifts from the code | A contract nobody enforces | Use the existing docs guards, name APIs that exist, and link the pins |
