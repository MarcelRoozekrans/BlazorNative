# Phase 16.4 Design — `The lost first tap (#438)`

**Date:** 2026-09-28
**Phase:** `16.4`
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready — a debugging phase: root cause before fix)

**Milestone:** [M16 — Unblock the Dispatch Lane](../../planning/MILESTONE.md). Inserted before the audit
by owner decision on 2026-09-28.
**Fixes:** #438.

## Goal

Find, fix and pin the reason the first tap after a cold boot sometimes never reaches the iOS
biometrics op.

## Measured starting point

- **Failure rate.** `BnBiometricsTests.testAuthenticateBootDeniedIsDataWithinABoundedAwaitNoHang` fails at
  `BnBiometricsTests.swift:229-231` ("Authenticate never reached the evaluation", a 30 s poll on
  `bio.hasInFlightRequestForTest()`).
  - **2 failures in 12 runs.** On the 16.3 branch: 1 in 3 (run 36348165574). On `main` at `1397cf8`: 1 in 9
    (run 36354226421).
  - It is always the same test, and it runs first in its suite, so it is the first tap after the cold
    boot.
- **The strongest lead.** In failing run 36354226421, 16.3's own slow-handler warning logged
  `handler 5 'click' in BlazorNative.SampleApp.BnSecureDemo.AuthenticateAsync held the render thread for 2570 ms`.
  - `AuthenticateAsync` (`BnSecureDemo.cs:137-141`) awaits `Biometrics.AuthenticateAsync(...)`.
  - That reaches `NativeShellBridge.InvokeHostCallAsync` (`NativeShellBridge.cs:~809-812`), which calls
    the Swift `hostCallBegin` **synchronously**.
  - So the 2.5 s synchronous part is spent inside the iOS biometrics begin, and **since 16.1 that
    runs on the .NET render thread**. Before 16.1 it ran on the dispatch lane.
- **Not a clue.** The `unknown op 8` log line in the same run comes from 16.2's deliberate unknown-op
  control test.

## Approach

**1. Evidence before theory.**
- A throwaway branch, `scratch/16.4-diag`, adds temporary logging with thread and timestamp:
  - Swift biometrics `hostCallBegin` entry and exit;
  - every dispatch to main, whether `sync` or `async`;
  - the in-flight flag's set and clear;
  - the invocation of the reply override;
  - .NET `InvokeHostCallAsync` begin, return and complete.
- The iOS lane runs **sequentially** on that branch until a failure is captured. It must be sequential
  because `ios.yml` cancels in-progress runs per ref.
- The branch is deleted afterwards, both remote and local. None of that logging merges.

**2. Is it an M16 regression?**
- The branch `scratch/16.4-pre-m16`, at `8fadff1` (the last commit before #428, which still has
  `InlineDispatcher`), gets 10 sequential iOS runs.
- The measurement started on 2026-09-28.
- The result goes in the record, whichever way it falls.

**3. Hypotheses, each tested against the captured logs:**
- **(a) A blocking hop to main from the render thread.** The biometrics begin blocks on a hop to main
  (for example a `DispatchQueue.main.sync`, or UI or LocalAuthentication work that needs main) while
  main is busy running the test's poll. Before 16.1, the begin ran on the dispatch lane, and that
  lane's relationship to main was the same, so the logs must say what actually changed.
- **(b) A cold-boot ordering race.** The in-flight flag is set and cleared, or never set, before the
  poll can observe it.
- **(c) The tap lands somewhere else.** A 16.2 change routes the first tap to a page or handler the
  test does not expect.

Record each hypothesis as confirmed or refuted, with its evidence.

**4. The fix follows the root cause.**
- No timeout bump.
- No retry.
- No skip.

These are the owner's no-workarounds rule. The fix ships with a **deterministic pin** that
reproduces the defect without luck: an XCTest that forces the interleaving, or a .NET test if the
defect is on the .NET side. The pin is red before the fix and green after, and its mutation is
recorded.

**5. Verification.**
- **The deterministic pin is the proof.**
- 10 sequential iOS runs on the fix branch are recorded as supporting evidence. At a 17% base rate,
  10 clean runs alone would occur about 15% of the time by luck.
- The 16.5 audit re-measures.

## Files / Modules Touched

These are decided by the root cause. Likely candidates:
- `src/BlazorNative.Apple/BnHost/BnBiometrics.swift` and `AppleShellBridge.swift`;
- `src/BlazorNative.Runtime/NativeShellBridge.cs`;
- the Android twin, if the same shape exists there (`BnBiometrics` on Android). Check it, and say so;
- tests: the new deterministic pin;
- record: `docs/plans/2026-09-28-phase-16.4-record.md`, which holds the evidence, the hypotheses and the baseline.

## Tests

- The deterministic pin, following `docs/pin-standard.md` Rules 2–5 and 7.
- Every existing suite stays green. The .NET baseline is 1295, JVM 191, Android 233 and iOS 282.

## Open Questions

None. The root cause, and so the fix, is what this phase exists to find.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The failure won't reproduce with logging on, because the logging changes the timing | No evidence | Keep the logging minimal and asynchronous. If 10 runs capture nothing, widen to the simulator's own `os_log` capture and report back before guessing |
| The root cause predates M16 | M16 inherits someone else's bug | Still fix it here, and record that it predates M16 |
| The fix belongs in Swift that can't be compiled locally | Slow iterations | Iterate on the scratch branch through the lane. The deterministic pin makes each iteration decisive |
| A timing pin is itself flaky | A flaky pin replaces a flaky test | Force the interleaving with seams. No sleeps at the boundary |
