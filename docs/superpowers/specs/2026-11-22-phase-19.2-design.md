# Phase 19.2 Design — Measurement harness

**Date:** 2026-11-22
**Phase:** 19.2
**Surface:** Infra
**Stage:** phase (one phase, implementation-ready)
**Status:** draft

## Goal

Make a repeatable comparison of HEAD against `v0.15.0` on three metrics, on both shells. The metrics are
cold boot, dispatch-lane latency and frame-apply time. Prove on a device lane that the timing marks
print nothing at the default `Warn` and are present at `Verbose`. Phase 19.3 then only has to dispatch
the workflow and write the report.

## Why

M19 must answer whether 1.0 can ship today, and the perf half of that answer needs numbers that old and
new code produce with the same ruler. Nothing in the repo measures boot or latency today. The nearest
thing is `scripts/devloop.ps1`, which polls logcat with a 250 ms stopwatch. The 1.0 criterion Q1
("silent by default") was proven only once, by hand on a phone in July. `BnShellLog.kt` has changed
since then (#523, #691), and 19.1 deferred the device re-proof to this phase. The milestone design
(`docs/superpowers/specs/2026-11-17-milestone-19-design.md`, Decision 2 and "Calls made after the
builder check") fixes the approach: external cold boot plus a small `Verbose`-gated timing seam, a
`workflow_dispatch` workflow, a `v0.15.0` backport branch, and at least 20 runs per side.

## Goals, non-goals, anti-goals

- **Goals.**
  - Timing marks in .NET, the Android shell and the iOS shell, on `main` and on the backport branch, at
    the same semantic points.
  - A `workflow_dispatch` workflow that builds both sides, runs them interleaved in one emulator job
    and one simulator job, and uploads raw samples plus a summary (n, median, IQR per side per
    metric).
  - The Q1 proof, both ways, on the emulator and the simulator, recorded as a re-proof of the
    criteria row.
- **Non-goals.**
  - The report itself, the regression verdicts and #12/#13/#575 (19.3 and 19.4).
  - Any perf fix, and any CI budget gate (Backlog, per the owner's decision).
  - Real-device runs (19.3 for Android, 19.7 for the iPhone). The harness only has to make them
    possible: the same marks, and a script that can collect from a USB device.
- **Anti-goals.**
  - A mark that changes what it measures: its cost inside a measured span must be small and the same
    on both sides.
  - A mark that prints, or costs more than a level check, at `Warn`, which would falsify Q1.
  - A test hook in the shipped shell code. The click driver lives in test sources only (owner,
    2026-11-22).
  - A silent swap of the comparison release if `v0.15.0` will not build.

## Decisions (owner, 2026-11-22)

1. **Cold boot ends at the first Blazor content, not the OS first frame.** Both shells boot .NET off
   the main thread: Android in `MainActivity.kt:424`, iOS on `DispatchQueue.global` in `viewDidLoad`.
   So `am start -W` and `XCTApplicationLaunchMetric` stop at the empty shell layout and miss runtime
   init. Cold boot is measured from the kernel's process start to the end of the first applied
   batch that contains a `CommitFrame`:
   - On Android, the start is `Process.getStartElapsedRealtime()` and the end is
     `SystemClock.elapsedRealtime*` at the end of `applyBatch`, so both ends use the same clock.
     Android also calls `reportFullyDrawn()` at that point, once per process. The system then logs
     its own `Fully drawn … +Nms`, an external second ruler that the workflow records next to the
     mark.
   - On iOS, the start is the process start time from `sysctl` (`kinfo_proc.p_starttime`). The end is
     the wall clock taken at the end of the first `applyBatch` with a commit, so both are wall-clock
     values.
   - `am start -W`'s `TotalTime` is free, so it is recorded as a side column. No UI-test target is
     added on iOS.
2. **The clicks are driven by test classes, not by a shipped hook.** A measurement test class in the
   Android instrumented suite (`src/BlazorNative.Jni/src/androidTest/...`) and one in the iOS hosted
   XCTest suite (`src/BlazorNative.Apple/BnHostTests/`). Each opens a perf page and clicks its real
   widget N times through the shell's own path: `performClick` on the view on Android, and
   `sendActions(for:)` on the `UIControl` on iOS. The normal PR lanes exclude the class, and the
   measurement workflow runs only that class.
3. **The two sides are interleaved in one job.** One dispatch of the workflow, from `main`, with the
   backport ref as an input. The emulator job and the simulator job each alternate HEAD and `v0.15.0`
   run by run, so runner noise hits both sides equally.

## Approaches considered

- **Cold boot.** First Blazor content (picked); OS first frame only, which measures an empty screen and
  needs a new iOS UI-test target; both as two metrics, which adds a third iOS mechanism for a number
  that says little about the framework.
- **Event driver.** Test-harness classes (picked); a self-driving launch mode, which puts a test hook
  into shipped shell code and its template copy; `adb shell input tap`, which is Android-only and
  fragile.
- **Pairing.** Interleaved in one job (picked); one dispatch per ref, which compares different runners
  at different times.

## The marks

Every mark is a timestamp plus a point name and a sequence number. All of a mark's work, including
reading the clock, is behind the existing level gate at `Verbose`. When the gate is closed, a mark is a
single `IsEnabled` check.

| Point | Where (HEAD) | Side |
|---|---|---|
| `boot.start` | process start, read when the shell starts | shell |
| `boot.content` | end of the first `applyBatch` that contains a `CommitFrame` | shell |
| `dispatch.post` | the shell's `onUiEvent` for the click, on the UI thread, before the hop to the dispatch lane | shell |
| `dispatch.enter` | entry of `blazornative_dispatch_event` (`Exports.cs:431`), on the lane thread | .NET |
| `dispatch.handler` | immediately before the renderer invokes `Renderer.DispatchEventAsync` for the event (`NativeRenderer.DispatchSyncPart`, `NativeRenderer.cs:2500`) | .NET |
| `frame.recv` | entry of the shell's frame callback: `FrameCallback.invoke` on Android, `bnFrameTrampoline` / `handleFrame` on iOS | shell |
| `frame.applied` | end of `applyBatch`, after the scroll flush and back-state publish | shell |

The metrics are derived from those points:

- **Cold boot** is `boot.content − boot.start`. A second Android ruler is `Fully drawn`.
- **Dispatch-lane latency** is `dispatch.handler − dispatch.post`, with `dispatch.enter` splitting it
  into the lane-queue part and the in-.NET part.
- **Frame-apply time** is `frame.applied − frame.recv` for the frame the click produced.
- **Click to content**, `frame.applied − dispatch.post`, is reported as an extra, because the marks
  give it for free.

**Points are semantic.** At `v0.15.0` there is no dedicated render thread: that came in Phase 16.1,
after the tag. The backport places each mark at the same event ("the handler is about to start", "the
last patch is applied"), wherever that event lives in the old code. The backport task records the
file:line of each old-side mark.

**Clocks.** A span that crosses the shell/.NET boundary uses one monotonic clock per platform:
- Android: `System.nanoTime()` and .NET `Stopwatch.GetTimestamp()`, both `CLOCK_MONOTONIC` on bionic.
- iOS: `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` in Swift and `Stopwatch` in .NET.

The parser enforces `dispatch.post ≤ dispatch.enter ≤ dispatch.handler` for every sample. A single
violation fails the run, because it means the two sides are not reading the same clock. That check is
the proof of the clock claim, not a comment.

**Emit cost.** The timestamp is taken before any formatting. On both sides the .NET marks go through
one small mark writer, `BnPerfMarks`. It hands the line to a background writer and never writes
synchronously on the measured thread. The same file is copied verbatim to the backport, because
`v0.15.0`'s `BnLog` writes stderr synchronously (`BnLogQueue` came later, in #584). Without this, the
old side would pay a stderr write inside its dispatch span and the new side would not. On the shells,
a mark is one `Log.println`/`os_log` call, the same on both sides.

**Pairing.** The ABI is frozen, so no correlation id crosses it. Pairing instead rests on the
measurement test, which is serial by construction. It clicks once, then waits until the page shows
the new counter value before clicking again. `seq` is a per-point counter per process, and `id` is
the handler id .NET logs on the dispatch points. The parser pairs the k-th `dispatch.post` with the
first `dispatch.enter` and `dispatch.handler` after it that carry the button's `id`. The click's frame
is the first `frame.recv` after `dispatch.handler`, with its `frame.applied`, provided both fall
before the next `dispatch.post`. A click window with no frame, or with more than one, is reported as
a dropped sample. If more than 5% of samples are dropped, the run fails. The perf page has no timers
and no async continuations, so in a clean run there is exactly one frame per click.

**The old lane.** `v0.15.0` already has the single-thread dispatch executor on Android and the serial
dispatch queue on iOS (Phase 3.2). What it lacks is the dedicated render thread. Both sides therefore
get all three dispatch marks. The parser reports the sum and both parts (lane queue, and in .NET)
per side. A shift between the parts that comes from the render-thread change is an architecture
difference, and 19.3's report names it as one.

**Format and transport.** Every mark is one line: `BNPERF <point> seq=<n> t=<ns>`, plus
`id=<handlerId>` on the dispatch points.
- Android shell marks go through `BnShellLog.verbose` with `BnPrivacy.SAFE`, because a REDACTED line
  would hide the numbers.
- .NET marks reach logcat through the stderr pump as `BlazorNative/Perf`, and the unified log through
  `BnStderrPump`.
- iOS shell marks go through `BnLog` at `Verbose`, which maps to os_log `.debug`, category `Perf`. The
  simulator job enables debug persistence for subsystem `io.blazornative` before the run, and reads
  the lines back with `log show --debug`.

## The workflow

**Which page boots.** Every run, cold boot included, mounts `PerfProbe`, so the page is the same on
both sides. That follows the M19 design's "the same page on both sides". Each shell selects it with
its existing launch path:
- On Android, `am start -e io.blazornative.shell.EXTRA_COMPONENT PerfProbe`.
- On iOS, a cold launch through the deep-link route that maps to `PerfProbe`
  (`simctl launch` followed by `openurl`, or `openurl` on a terminated app, whichever resolves at
  launch). The hosted XCTest class starts the runtime with `start(component: "PerfProbe")`, as
  `BnDispatchLaneTests` already does.

The backport's build-only check also confirms that `v0.15.0` has the same launch paths. If the iOS
deep-link route is missing there, a route entry is added on the backport branch, which is
measurement infrastructure. No new launch hook ships on `main`.

**Runtime confound.** HEAD runs on SDK 11 and the backport on SDK 10, as the M19 design intends:
the comparison is the releases as shipped. Whether HEAD's code also needs a .NET 10 run is decided in
19.3, by the rule the M19 design already states, and only when a cold-boot regression appears. The
workflow takes a `head_sdk` input (default: the ref's `global.json`), so 19.3 can run that case
without editing the workflow.

**Landing the workflow.** GitHub dispatches only workflows whose file is on the default branch. While
19.2 is in review, `perf.yml` therefore also carries a `push` trigger limited to this phase's branch.
The final task removes that trigger after the recorded dry run. After merge, the workflow is
dispatch-only, as designed.

`.github/workflows/perf.yml`, on `main`. It has a `workflow_dispatch` trigger only, with these inputs:
- `baseline_ref` (default `perf/v0.15.0-marks`);
- `runs` (default 20, minimum 20);
- `metrics`.

It has no PR trigger, so it never slows a PR.

- **Build jobs.** Each side is built on its own ref with its own `global.json`: HEAD on SDK
  11.0.100, the backport on 10.0.401. The jobs reuse the existing publish, Gradle and XcodeGen steps of
  `android-instrumented.yml` and `ios.yml`. The artifacts are the Android app plus its test APK, and
  the iOS `BnHost` plus its test bundle, for each side.
- **Side-by-side install.** The backport's app id carries a suffix: Android
  `applicationIdSuffix ".v015"`, and a matching iOS bundle-id suffix. Both apps then stay installed,
  and interleaving needs no reinstall between runs. This is a change on the backport branch only.
  The first launch of each app after install is discarded, because on Android it includes dex
  optimisation.
- **Emulator job.** It uses the same emulator setup as `android-instrumented.yml`: API 34, x86_64,
  pixel_6, animations off, plus `scripts/android-emulator-settle.sh`. Then:
  - Cold boot is `runs` launches per side, alternating, each `am force-stop` → `logcat -c` →
    `am start -W -e EXTRA_LOG_LEVEL Verbose …`. Each launch waits for `boot.content` and reads the
    marks, `Fully drawn` and `TotalTime`.
  - Dispatch and frame samples come from `am instrument`, which runs the measurement class for each
    side in alternating blocks: N clicks per block, and enough blocks to reach `runs` samples per side.
- **Simulator job.** The same shape on macOS with `simctl`:
  - Cold boot is `simctl terminate` → `simctl launch --env BN_LOG_LEVEL=5` (or the Info.plist knob
    on the old side, whichever `v0.15.0` honours), waiting for the `boot.content` line in
    `log stream`.
  - Clicks come from `xcodebuild test-without-building -only-testing:` on the measurement class, per
    side, alternating.
- **Q1 proof**, in both device jobs, before the timed runs. For each side:
  - Launch once at the default level, with no extra and no env. Assert zero `BNPERF` lines and zero
    gated `Info`, `Debug` or `Verbose` lines from the BlazorNative tags or subsystem.
  - Launch once at `Verbose`. Assert at least one line of every mark point.

  A failed assertion fails the job.
- **Parser and summary.** A `pwsh` script reads the collected lines, joins them by `seq` and `id`,
  enforces the ordering invariant, and writes:
  - `samples.csv`: side, metric, run, value_ms;
  - `summary.md`: per side per metric, n, median, Q1, Q3, IQR, plus each side's SDK and commit.

  The script does not decide regressions; that is 19.3's rule. The parser has its own fixture tests,
  each mutated to red: a captured log with a known answer, a clock-order violation, and a missing
  point.
- **Real-device mode.** The same collection script takes a device serial, so the owner can run the
  Android phone pass in 19.3 from a laptop. The iPhone pass in 19.7 reuses the `log` collection.
  The contract that 19.3 and 19.7 rely on has two parts, both documented in
  `scripts/perf/README.md`. First, the scripts' parameters. Second, the `samples.csv` columns:
  `side, sdk, commit, metric, part, run, value_ms`. `part` is empty except for the dispatch split.
- **iOS bundle id.** The backport's suffix changes `PRODUCT_BUNDLE_IDENTIFIER` and the test bundle's
  `TEST_HOST` in its `project.yml`. The log filter uses the os_log subsystem `io.blazornative`. That
  name is set in `BnLog.swift`, not derived from the bundle id, so both sides match it exactly.

## The backport branch

`perf/v0.15.0-marks` is cut from tag `v0.15.0` (`0184e1e7`) and pushed. It is never merged and has no
PR. It carries:
- the same marks;
- `BnPerfMarks`;
- the perf page in `samples/BlazorNative.SampleApp`;
- the two measurement test classes;
- the app-id suffix.

The page and test classes are copied from `main` where the old API allows, and adapted only where it
does not; each adaptation is recorded.

**Task 1 is a build-only check**, done before any mark is written. Push the bare branch, dispatch its
own `android-instrumented.yml` and `ios.yml` (both have `workflow_dispatch` at the tag), and record the
run ids:
- If it builds, go on.
- If it does not, pinning an older runner image, Xcode, Gradle or SDK patch on the branch is allowed,
  because that is measurement infrastructure.
- If it still does not build, stop and ask the owner for another release.

## The perf page

The page is `PerfProbe` in `samples/BlazorNative.SampleApp`, registered in `SampleAppPages.cs`. It
has one button whose handler increments a counter and re-renders a block of about 50 labelled rows,
with the counter shown in one of them. So each click produces one frame with a fixed, non-trivial
patch count, and the page is the same on both sides. The exact row count is the builder's call; it
should give a frame-apply time well above the clock resolution.

## Tests

- **Unit, .NET:** `BnPerfMarks` emits nothing and reads no clock below `Verbose`, and emits one
  well-formed line at `Verbose`. The paired control is mutated to red.
- **Unit, JVM and XCTest:** the shell mark helper is silent at `Warn` and emits a SAFE line at
  `Verbose`, again with a paired control.
- **Parser:** the fixture tests above, each shown red by a mutation of its own branch.
- **Device:** the Q1 proof steps in `perf.yml`, both ways on both lanes, and one full dispatch of
  `perf.yml` on the PR head against the backport branch, recorded with its run id.
- **Regression:** the normal PR lanes stay green with the measurement classes excluded, and their
  baseline counts are updated only for tests this phase adds to them.

## Calls made in the design (mine, correct them if wrong)

- **`reportFullyDrawn` ships on `main`**, in the shell and in its template copy. It is the standard
  Android signal and has no effect when no one reads it. It is called once per process, not per
  frame.
- **The marks stay in the product after M19.** They are free at `Warn`, and 19.7's iPhone session
  needs them.
- **App-id suffix on the backport**, instead of reinstalling between runs. You chose interleaving;
  reinstalling every run would make each cold boot a first launch.
- **`pwsh` for the scripts**, matching `scripts/`.
- **Pairing by order in a serial test**, because the frozen ABI cannot carry a correlation id. A
  drop rate above 5% fails the run.
- **`PerfProbe` boots in every run**, cold boot included, through the existing launch paths:
  `EXTRA_COMPONENT` on Android and the deep link on iOS.
- **A temporary branch-limited `push` trigger** on `perf.yml` while the PR is open, removed in the
  last task. Without it the workflow cannot run before it is on `main`.
- **The perf workflow does not judge regressions.** It reports n, median and IQR. The regression
  rule is applied in 19.3's report.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `v0.15.0` does not build on current runners | No comparison | Task 1 is the build-only check; toolchain pins are allowed on the branch; otherwise stop and ask. |
| The shell and .NET clocks differ on a platform | Wrong dispatch numbers | The parser's ordering invariant fails the run on any violation. |
| os_log debug lines are dropped or rate-limited on the simulator | Missing samples on iOS | Enable debug persistence for the subsystem before the run; the parser reports the sample count per point, and a count below `runs` fails the job. |
| A mark's emit cost differs between sides | A false regression | `BnPerfMarks` is identical on both sides and asynchronous; timestamps are taken before formatting. |
| The measurement classes leak into the PR lanes, or their exclusion changes a pinned count | A red or a slower PR lane | Exclude by class; adjust only the counts this phase changes, and record why. |
| The emulator or simulator job runs past the job limit at 20+ runs per side | A partial run | Cold boot and clicks are separate steps with their own timeouts; `runs` and `metrics` are inputs, so a long run can be split. |
| Swift and Kotlin cannot compile on Linux | Late feedback | Open a draft PR after the first shell-mark task, so the macOS and Gradle lanes run early. |
