# Phase 18.5 Design — Slow-handler naming for compiler lambdas (#522)

**Date:** 2026-11-04
**Phase:** `18.5`
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Approved:** pending.

## Goal

A slow-handler warning never names a compiler-generated method. When the app's handler is a
lambda the Razor compiler emitted, the warning names the page that declares it, plus the
position of the call site on that page: the control's type and its frame sequence. This is the
M18 DoD item for #522, decided by the owner on 2026-10-24.

## Background: how it works today

`NativeRenderer` times every UI dispatch's synchronous part. When a dispatch goes over the
budget, `DispatchSubject` calls `HandlerCallSite.Resolve()`, which returns a key, used for
once-per-call-site deduplication, and an owner, which is the name in the warning.
`HandlerCallSite` is recorded at attach time: the tree owner's `Type`, the attribute frame's
`Sequence`, the event name, and the attached delegate.

`Resolve` names the method the delegate runs, `Declaring.Method`. When that method is
framework code and the delegate's target is an `IForwardsUiEvent` wrapper, such as `BnInput`
or `BnCheckbox`, it resolves the app's forwarded delegate instead (17.4, #435).

A compiler lambda then shows up in the warning as its generated name:

- `@bind-Value` on a wrapper forwards a lambda that Razor declares on the page:
  `SlowBindPageA.<BuildRenderTree>b__0_0`.
- An explicit lambda, `OnClick="() => SlowThree(x)"`, that captures a loop variable lives on a
  display class: `SlowHandlerProbe+<>c__DisplayClass0_0.<BuildRenderTree>b__2`.

Two inputs on one page differ only by `b__0_0` against `b__0_1`. That points a developer at
the page but not at the input (#522).

The key is already right. A compiler lambda's method is stable across renders, unique per call
site in source, and shared by every `foreach` item of one call site. Only the name is wrong.

## Goals

- Every warning whose resolved app method is compiler-generated names the declaring page and a
  position on it, and contains no `<…>` compiler name.
- One rule for every compiler lambda, whether bound (`@bind-Value`, `@bind-Value:after`) or
  explicit (`@onclick="() => …"`, `OnClick="() => …"`), reached directly or through a
  forwarding wrapper. Owner decision, 2026-11-04.
- The position is the control's type plus its Razor frame sequence on the page, for example
  `BnInput at sequence 12`. Owner decision, 2026-11-04, chosen over a render-order ordinal,
  which shifts when an `@if` above toggles.
- Grouping is unchanged: two call sites warn twice, and the items of one call site warn once.

## Non-goals

- Naming the `:after` method that sits inside a bind lambda. The renderer cannot see into the
  lambda's body. The position points at the input; the threading page says the `:after`
  method is what runs there.
- Source line numbers. The frame sequence is what the renderer has; the threading page says
  how to map it to the generated `.razor.g.cs`.
- Changing the name of a named app method, `:get`/`:set` included, or of a host-event arm.

## Anti-goals

- No cost on the render path. The position is looked up only when a dispatch is already over
  budget, as the delegate's method is today.
- Naming a diagnostic must never fault the dispatch. Any failure falls back, as `Resolve`'s
  catch already guarantees.
- Never the payload, which can carry user input.

## Design

### D1. When the rule applies

The rule applies when the method `Resolve` would name is app code (not framework, as
`IsFrameworkAssembly` defines it today) and compiler-generated. It covers both paths that name
an app method: the direct path, where the attached delegate is app code, and the forwarded path,
through `IForwardsUiEvent`.

A method counts as compiler-generated when its name starts with `<`, or its declaring type or
any type enclosing it has a name starting with `<`, such as `<>c__DisplayClass0_0` or `<>c`.
Names are used rather than `CompilerGeneratedAttribute`: the existing NativeAOT probe proves
`Method.Name` and `DeclaringType` resolve in the published dll, and attribute metadata is not
guaranteed there.

### D2. The page

The page is the declaring type with every compiler-generated enclosing type stripped. It is the
outermost type that does not start with `<`, walking `DeclaringType` outwards. It is named by
`FullName`, as app methods are today. When a lambda is declared outside a component, such as in
a service or a helper, the same type is named. It gets a position if the walk finds one, and the
type alone otherwise.

### D3. The position

The position is found on the warning path only, on the render thread, after the dispatch scope
has closed, where `DispatchSubject` runs today:

1. `HandlerCallSite` also records the tree owner's component id. It is an `int` copied at attach
   time, with no allocation.
2. Starting at that component, then walking its ancestors through the component-parent map
   (`_tree.TryGetComponentParent`), the renderer reads each component's current frames with
   `GetCurrentRenderTreeFrames`.
3. In each tree it looks for an attribute frame whose value runs the resolved method. The value
   can be a `Delegate`, an `EventCallback`, or an `EventCallback<T>`.
   - An element attribute usually holds the delegate itself, because `RenderTreeBuilder`
     unpacks an `EventCallback` when it adds it.
   - The non-generic `EventCallback` is read through the existing
     `RefAccessors.EventCallbackDelegate`.
   - A component parameter frame holds a boxed `EventCallback<T>` of any T. Its `Delegate`
     field is read by reflection on the boxed value's type, and kept in the NativeAOT build with
     `[DynamicDependency]` on `EventCallback<>`. A per-T `[UnsafeAccessor]` switch was rejected,
     because the walk meets arbitrary T.
   - The JVM probe pins both shapes in the published dll. Any failure to read a value counts as
     no match.

   **It matches by `MethodInfo`, not by delegate identity.** A capturing lambda is a new
   delegate on every render, and the dispatch may already have re-rendered the page.
4. The position is the frame the matching attribute belongs to: the nearest preceding component
   or element frame in the same tree, since attribute frames follow their owner's frame. For a
   component frame that is `BnInput at sequence 12`, and for an element frame `element button at
   sequence 4`, with no angle brackets. The component is named by its short type name, because
   the namespace adds nothing for a framework control. An app component is named by its short
   name too.
5. **The OUTERMOST match on the walk wins**, the one found highest up the ancestor chain. That
   is the frame the lambda's declaring source wrote.
   - When the page passes a lambda to an app component, `<Card OnClick="() => …"/>`, and Card
     forwards it with `<BnButton OnClick="OnClick"/>`, both Card's tree and the page's hold the
     delegate. The first match would report Card's sequence under the page's name, which is
     wrong. The outermost is `Card at sequence N` in the page, which is right.
   - Every `foreach` item of one call site matches at the same sequence in the same tree, so items
     do not change the answer.

Searching ancestors is what makes ChildContent work. A `BnInput` in a `BnView`'s ChildContent
sits in `BnView`'s tree, but with the page's sequence numbers, and its parameter frames hold the
page's lambda. So the walk finds it in `BnView`'s tree, at the page's sequence. The page's own tree holds only
the ChildContent `RenderFragment`, a different method, so it does not match above that, and the
outermost match is still the right one.

### D4. The name and the key

- **Name:** `in {Page}, {Control} at sequence {N}`. With the subject prefix, the warning reads:
  `slow handler: handler 41 'change' in MyApp.Pages.Settings, BnInput at sequence 12 held …`.
- **Fallback:** when no frame matches, the name is `in {Page}` alone, never the compiler name.
  This happens when the component has been disposed during the dispatch, a frame lookup throws,
  or the delegate is held somewhere the walk does not reach.
- **Key:** unchanged, `{Declaring}::{Method}#{EventName}` on the generated method. Grouping
  therefore stays exactly as 16.3 and 17.4 pinned it.

### D5. Pins

In `SlowHandlerWarningTests`, with the real renderer, the real wrappers and Razor-compiled
pages:

- The 17.4 bind facts (`TwoBoundBnInputs_OnTwoPages_…`, `…_OnOnePage_…`,
  `TwoPlainBoundBnInputs_…`) assert the new name: the page, `BnInput at sequence N` with the two
  inputs' distinct sequences, and no `<` anywhere in the warning.
- A capturing explicit lambda in a `foreach` warns once, naming the page and the control's
  sequence, not `<>c__DisplayClass`.
- A bound input inside a `BnView`'s ChildContent names the page and the page's sequence.
- A lambda on a plain element names the element at its sequence.
- A lambda passed through an app component that forwards it to a `BnButton` names the app
  component at the page's sequence, not the inner sequence. This is the outermost-match pin.
- The fallback: a slow handler that hides its own input with an `@if` has no frame left after
  the dispatch, so the warning names the page alone. This is a natural removal, not a test seam.
- `AGetSetBoundBnInput_NamesTheAppsSetMethod` and the named-method facts stay green unchanged.
  That is the control showing named methods are untouched.
- A test-page lambda whose position the renderer has to look up after a re-render: the match by
  method holds when the delegate instance has changed.

In the JVM `SlowHandlerProbeTest` (NativeAOT dll): the capturing-lambda assertion changes from
`<BuildRenderTree>` to the page plus `BnButton at sequence N`, and asserts no `<`. This is the
pin that the names and the frame walk work under NativeAOT.

Every new or changed anchor gets a subject-mutation red, graded per `docs/pin-standard.md`
"Grading a pin: sites and reds". The `SlowHandlerWarningTests` register row's Rule 5 partial,
"tracked as #522", is closed.

### D6. Docs and bookkeeping

- `website/docs/guides/threading.md`: replace the `Page.<BuildRenderTree>b__0_0` paragraph

  `OpenElement(N, …)` in the generated `.razor.g.cs`, which `EmitCompilerGeneratedFiles` writes
  to disk. Also say that with `:after` the slow work is the `:after` method. Remove the "tracked
  as #522" line.
- The record, the register row, the test counts in `ci.yml` and the README if the .NET or JVM
  counts move, then MILESTONE's #522 DoD item, ROADMAP and STATE.

## Constraints

- No ABI change and no public API change: `HandlerCallSite`, `DispatchSubject` and the new
  lookup are internal.
- The template mirror and wire vocabulary are untouched. This is renderer-only C# plus pins and
  docs.
- No Claude signature in any commit or PR. Every commit passes `scripts/commit-parse-check`.

## Left to the builder

- Where the lookup lives (a method on `NativeRenderer` beside `DispatchSubject`, which then
  stops being static), and how the frame walk skips a component's subtree frames.
- Whether a component parameter's value needs unwrapping beyond `EventCallback` and
  `EventCallback<T>`. Measure it on the real `@bind-Value` and `OnClick` output.

## Calls made in this design

- Named by the short type name for the control (D3.4), the full name for the page.
- The fallback names the page alone (D4), rather than keeping the compiler name.
- The key stays on the generated method (D4). That leaves grouping untouched and puts the whole
  change on the warning path.
- Compiler-generated is detected by name (D1), not by attribute, because of NativeAOT.
- Matching is by `MethodInfo` (D3.3), because a capturing lambda is a new delegate each render.
- The outermost match wins (D3.5), so a lambda forwarded through an app component names the
  page's call site. This came from the builder check.
- `EventCallback<T>` is read by reflection plus `[DynamicDependency]`, not by a per-T accessor
  switch (D3.3). This came from the builder check.
- A lambda declared outside a component names its declaring type (D2).
- Element positions read `element button at sequence 4`, with no brackets (D3.4).
- The fallback pin removes the input with an `@if`, with no seam (D5).

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `GetCurrentRenderTreeFrames` throws for a component disposed during the dispatch | Warning dispatch faults | It is inside `Resolve`'s catch-all; the fallback names the page; pin it |
| A parameter's delegate is wrapped in a shape the walk does not unwrap | Fallback name, never a wrong one | Measure the real Razor output first (Left to the builder); pin each shape |
| NativeAOT trims a name or the frame API | Probe red on the JVM lane | The JVM probe pins the published dll |
| Two different frames on the walk run one method | Wrong position | Forwarding through an app component is the real case: the outermost match wins, pinned. Within one tree, one generated method is one source call site; the `foreach` pin checks it |
| Reflection on `EventCallback<T>.Delegate` is trimmed under NativeAOT | Fallback name for component-parameter lambdas | `[DynamicDependency]`; the JVM probe's bind and BnButton shapes red if it is trimmed |
