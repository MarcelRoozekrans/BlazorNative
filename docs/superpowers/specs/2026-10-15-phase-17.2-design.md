# Phase 17.2 Design — `Android host-call contract`

**Date:** 2026-10-15
**Phase:** `17.2`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M17 — Close the Dispatch Lane's Debt](../../planning/MILESTONE.md)
**Issue:** #440. **Precedent:** iOS phase 16.4 (#438), `BnBiometrics.swift` and
`BnSecureStorage.swift`, each with its own serial `workQueue`.

## Goal

The host-call contract says `hostCallBegin` records the request and **returns at once**, and the
outcome arrives later through `host_call_complete`. Android breaks it for two ops. In
`AndroidShellBridge.kt`, `hostCallBegin` calls `handleBiometrics` and `handleSecureStorage`
directly, so all of this runs on the calling thread, which is .NET's render thread:
- `BiometricManager.canAuthenticate`, for the biometrics `check`;
- every AndroidKeyStore operation: provision, init cipher, encrypt, decrypt, `KeyInfo` read, and
  delete with its `commit()`.

Only the prompt itself hops to the main thread. 17.2 moves that work off `hostCallBegin`, as iOS
did in 16.4, so a slow KeyStore never stalls rendering.

## Approach

**Mirror iOS, owner decision 2026-10-15: one serial executor per handler.**

1. **Two single-thread daemon executors** in `AndroidShellBridge`, named after the handlers:
   - `BlazorNative-Biometrics`;
   - `BlazorNative-SecureStorage`.

   They follow the existing `cameraExecutor` and `fetchExecutor` pattern.
2. **`hostCallBegin` returns at once for both ops.** The `BIOMETRICS` and `SECURE_STORAGE` arms
   enqueue `handleBiometrics` and `handleSecureStorage` on their executor, and return. Parsing
   moves with the work, so the begin itself does nothing that can block.
3. **Serial on purpose.** A handler's requests **start** in order: a plain `set` then a `get` from
   one page stay ordered. An auth-bound request frees the executor while its prompt is up, so
   its after-auth work runs when the prompt answers. That was already so when the work ran inline.
   *Corrected after the final review; the question is #506.* And `drainForTest()` is a barrier: it enqueues a latch, waits, and is bounded.
4. **A throw on the executor is data, never a hang.** The enqueued job catches any `Throwable`.
   It reports it to `onError` and completes the request with the op's `ERROR` status.
   - *Builder's call:* if the request had already completed, the second completion gets rc 1,
     which `BridgeHostCallCompleter` already treats as benign. No per-request completed flag is
     added.
5. **The prompt path is unchanged.** `runBiometricGate` already hops to the main thread through
   `activity.runOnUiThread`, and its callback completes the request. Only the work around it
   moves: provisioning, `Cipher.init`, `KeyInfo`, and the decrypt or encrypt after auth. The
   after-auth `doFinal` runs in the prompt callback, on main, today. It moves back onto the
   handler's executor, so no KeyStore work runs on main either. *Builder's call:* this matches
   iOS, where the Keychain work runs on `workQueue` both before and after the prompt.
6. **Out of scope:** geolocation and notifications. Their `check` paths are permission reads,
   which #440 does not name.

**The contract text.** `ShellBridgeHandlers.hostCallBegin`'s KDoc, and the comment block over the
biometrics and secure-storage section, gain the begin contract in iOS's words: record, enqueue,
return, and complete later from the handler's executor.

## Tests

The Android instrumented lane, `android-instrumented.yml`, on scratch refs for the mutations.
- **Test seams**, internal, null or no-op in production, reset in teardown, as iOS does:
  - `completeHookForTest`, which observes `completeHostCall(id, status, payload)` and the thread it
    ran on;
  - `workGateForTest: CountDownLatch?`, which each executor job awaits first, when set;
  - `drainForTest()`, per executor;
  - `jobFaultForTest: (() -> Unit)?`, which each job calls first, so pin 4 can make the job throw.
- **Request ids:** the pins use ids far above any the demo issues, starting at `1_000_000_000L`.
  The real export answers an unknown id with rc 1, and the hook observes the completion before
  that. *Builder's call.*
- **Pins:**
  1. `biometrics_begin_returns_before_the_check_runs`: with the gate closed, `hostCallBegin(check)`
     returns within 1 s and no completion exists. **Anchor:** the gate was reached. Open the gate:
     the completion arrives on `BlazorNative-Biometrics`.
  2. `secure_storage_begin_returns_before_the_keystore_work_runs`: the same, for a plain `set`.
     The completion arrives on `BlazorNative-SecureStorage`.
  3. `secure_storage_keeps_request_order`: a `set` then a `get` of one key, begun back to back with
     no drain between them. The `get` returns the value.
  4. `a_throw_on_the_executor_completes_error_never_a_hang`: a seam makes the job throw. The
     request completes with `SecureStorageStatus.ERROR` within a bounded wait.
  5. `the_after_auth_work_runs_on_the_secure_storage_executor`: through `biometricGateHook`, the
     test approves a `getWithAuth` by calling `gate.succeed()` **from the main thread**, as the real
     prompt's main executor would. It asserts the completion runs on `BlazorNative-SecureStorage`,
     not on main.
     - **A thread-only pin, named:** the hook's `succeed()` passes no `AuthenticationResult`, and
       the emulator's key is per-use auth-bound, so the decrypt throws and the request completes
       `AUTH_FAILED`. The pin proves where the after-auth work runs, not that a real fingerprint
       decrypts, which stays owner-device territory. *Builder's call.*
     - Without the main-thread call, the hook would invoke `onAuthenticated` on the executor
       itself, and the hop-removed mutation would stay green.
- **Mutations**, recorded with their anchors, each on its own scratch ref with `headSha` checked:
  - the old inline call restored in `hostCallBegin`: pins 1 and 2 red;
  - a `newFixedThreadPool(2)` in place of the single thread: pin 3 is at risk, so record whether
    it reds and say so if it is flaky;
  - the throw guard removed: pin 4 red, within its bound;
  - the after-auth hop removed: pin 5 red;
  - each anchor entered once.
- **Lanes:** Android, iOS and CI JVM on the PR head, with `headSha` compared. iOS is unchanged, but
  it is required evidence.

## Open Questions

None. Owner decision, 2026-10-15: mirror iOS, one serial executor each.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A test, or the demo, reads a secure-storage result synchronously after `hostCallBegin` | Flaky or red existing tests | Grep every caller first. Add `drainForTest()` where a test needs the result. The demo is event-driven and already waits for its echo |
| The after-auth hop changes when a prompt callback's completion lands | A completion arrives a little later than before | The test seam observes the completion thread; the denial-is-data tests keep their bounded awaits |
| The template's copy of the file diverges | The mirror guard reds CI | Edit both copies together; the guard is the check |
| Executor threads leak across Activity recreation | Threads pile up | Daemon threads, one per bridge instance, as `cameraExecutor` is today. The bridge's lifetime already owns them. Recreation itself is 17.3 |
