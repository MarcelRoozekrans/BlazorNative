## Approach

**Lane-ordered waves** (owner-chosen over pin-by-pin and over batched device mutations).

1. **Wave 1, local** — groups C, D, E. Each mutation is applied in the working tree, the suite (or
   the named facts) run, the result recorded, and the tree reverted with `git checkout -- .` before
   the next. Cheap, so a vacuous pin surfaces before any device time is spent. The pin fixes below
   land in this wave.
2. **Wave 2, device** — groups A and B. One mutation per scratch ref, refs in parallel, **one run at
   a time per ref**. Before writing a mutation the pin's own code paths are re-read, so the set
   covers its anchors and suppression branches (Rule 7), not only plausible subject behaviours.
3. **Wave 3, write-up** — the record, the register cells, the moved D8/D10 evidence, and the
   ROADMAP goal line.

### Process and evidence

- **Branches.** Work lives on `feat/16.6-prove-pins`. Each device mutation is one commit on its own
  `scratch/16.6-mut-<id>` branch cut from the feat branch's HEAD; a mutation never lands on the feat
  branch. A scratch branch is deleted only after its run's artifact has been read into the record.
- **Validity of a device run.** The run's `headSha` equals the scratch commit, attempt 1, and the
  red test names are read from the JUnit XML or the xcresult artifact, never from the conclusion
  alone. A red that appears only in a test the mutation did not target is not evidence, and the
  record says so (#444 is a known iOS flake).
- **One cause per red.** One mutation per run. A mutation may red several pins; the record lists
  every test it redded, and every test it was expected to red but did not.
- **Vacuity contrasts are their own runs:** remove the anchor, apply the plain mutation, expect
  green.
- **A pin that no plausible mutation reds is a defect fixed in this phase:** record the green
  against the current pin, fix the pin on the feat branch, re-run the same mutation, record the
  red (Rule 7's protocol: reproduce the green first).
- **Every expected red in this spec comes from reading the code.** None has been run yet; each is
  confirmed or corrected by its run, and a surprise is recorded as a surprise.

### Defects found by reading, and what 16.6 does about each

1. **The caller scan has a silent hole.**
   - **What.** An expression-bodied forwarder on its own declaration line,
     `internal fun dispatchHostEventAndWait(e: BnHostEvent) = dispatchHostEventAndWait(e, null)`, is
     suppressed whole by the declaration exclusion at `GeneratedSymbolShadowTests.cs:1123`, so the
     scan stays green.
   - **Fix:** exclude the declaration token, not the line.
   - **Proof:** green on the unfixed scan, red after.
2. **The detector's control reads hand-copied declaration strings.**
   - **What.** `OffendingCallDetector_MatchesACall_AndNotTheDeclaration` feeds copies, not the real
     lines at `BlazorNativeRuntime.kt:358` and `BnRuntime.swift:376`. That is Rule 4 drift.
   - **Fix:** read the real declaration lines through `BnRepo.Root()`, with an anchor that reds when
     a declaration is not found.
3. **`testAFaultNoticeWithNoRuntimeIsStillCompletedOk` makes a promise nothing asserts.**
   - **What.** Its header promises the notice is "logged through BnLog". Deleting that log call is
     expected to stay green.
   - **Fix:** assert the log line through a capture. If no Swift log capture seam exists, the plan
     adds one, test-only.
   - **Proof:** green on the unfixed pin, red after.
4. **`back_at_root_finishes_the_activity` can only go red through its harness.**
   - **What.** Every production mutation that keeps back enabled at the root reds first at the
     harness anchor in `goForwardAndBackToTheRoot` (`:346`).
   - **No code fix.** The pin is not vacuous: the root behaviour is guarded by that anchor, and the
     test-side `ACTION_MAIN` run shows the pin's own assertion can fail. The register cell says
     both.
5. **The shadow detector reads generated lines raw.**
   - **What.** A trailing comment on a generated op line reds the pin.
   - **Disclosed under Rule 5, no fix.** It fails loudly, never silently, and the generator emits no
     such comments.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A device run is cancelled or overwritten by a second run on the same ref | Wrong or missing evidence | One run per ref; check `headSha` and attempt 1 before reading the artifact (sequential-lane rule) |
| #444 or #453 flakes red a test the mutation did not target | A red misattributed to the mutation | Read named test failures from the artifact; an off-target red is recorded as such and the run repeated if it hides the target |
| A .NET mutation does not reach the XCTest because the lane caches the framework | `BnDispatchLaneTests` stays green for the wrong reason | Confirm from the run log that the NativeAOT framework was rebuilt from the scratch commit |
| A pin turns out vacuous on the device | Extra fix rounds, more device runs | Expected by design: green recorded, pin fixed, red recorded, all in this phase |
| An expected red from reading is wrong | A mutation set that misses the pin's branch | Every expectation is confirmed by its run; a miss gets a new mutation, not a weaker cell |
| A local `dotnet test` hangs in `ReferenceFixtureBase` (#454) | A local wave stalls | Run the targeted test classes with `--filter`; #454's fixture is not in the population |
