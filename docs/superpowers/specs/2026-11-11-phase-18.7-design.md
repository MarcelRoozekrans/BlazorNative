# Phase 18.7 Design — Twin divergences (#401, #396)

**Date:** 2026-11-11
**Phase:** `18.7`
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-11

## Goal

Two shell behaviours that differ today become the same on iOS and Android, are documented once, and are held by a behavioural twin pin that goes red on the outlier before the fix.

- **#401:** the stderr pump forwards every line it reads. The managed `BnLog` level is the only gate.
- **#396:** an auth-bound secure-storage `set` on a device with no enrolled biometric returns `Unavailable` on both shells.

## Why

M14 and M15 were built to close twin divergences: the same app call giving a different result per shell. These two are the ones left, and the M18 Definition of Done requires them closed. M18 exists because the owner decided on 2026-10-21 that every acknowledged bug gets fixed.

- **#401.** iOS re-filters pumped stderr lines by the shell's level; Android does not. At an `Error` shell level, iOS drops the Warn-level fallback lines, which carry BCL output and NativeAOT crash text, and Android shows them. A managed `BnLog.Level` raise shows on Android at once and on iOS only after the shell's level is raised too.
- **#396.** Android refuses the auth-bound key without an enrolled biometric and returns `Unavailable`. iOS never checks enrolment, so its result is whatever Apple's keychain does. Apple's source suggests it stores the item and returns `Ok`. Nobody has measured it on a device, and #396 has been blocked on that device run (#17).

## How it works today

### #401

- Both shells parse `[BN|<E/W/I/D/V>|<category>] msg` the same way. An unprefixed or malformed line becomes `(Warn, "native", whole line)`. Kotlin: `BnLogFormat.kt:77`, `:128-150`. Swift: `BnLog.swift:428`, `:466+`.
- Managed `BnLog.Write` drops lines below its level before writing (`src/BlazorNative.Core/BnLog.cs:194-203`, default `Warn`).
- **iOS:** `BnStderrPump.sink` (`BnStderrPump.swift:85-86`) calls `BnLog.write`, which has `guard isEnabled(level)` (`BnLog.swift:251-256`). This is the second gate.
- **Android:** `forward` → `BnShellLog.relay` (`BnStderrLogcatPump.kt:231-232`) → `writeUngated` (`BnShellLog.kt:218-219`). Its comment says the pump is ungated because .NET already applied the level.
- The shell level is resolved at boot on both shells and handed to the runtime as the same ordinal: iOS `BnRuntime.resolveLogLevel()` (`BnRuntime.swift:419-425`, applied at `:252-253`, offset 28 at `:268`); Android `MainActivity.resolveLogLevel()` (`:829`, applied `:315-316`, passed `:452`). The pump is installed before either, so on iOS lines pumped before `:253` are gated at the default `Warn`.
- `website/docs/logging.md:45-47` describes the iOS re-gate as the behaviour. Nothing states Android's.
- The existing pump tests swap the sink (`BnLogTests.swift:166`, `:203`) or check parsing only (`BnStderrPumpTest.kt`, `BnShellLogTest.kt:325-339`). None observes gating.

### #396

- **iOS set:** `secureSet` (`BnSecureStorage.swift:392-428`) builds `SecAccessControlCreateWithFlags(.biometryCurrentSet)` with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. It returns `unavailable` only for a nil access control or `errSecMissingEntitlement`/`errSecNotAvailable` (`mapAddError`, `:596-602`). Secure storage never calls `canEvaluatePolicy`; only biometrics `check` does (`BnBiometrics.swift:308`), behind the test seam `canEvaluatePolicyOverrideForTest` (`:179`).
- **Android set:** `secureSetAuth` → `provisionKey(requireAuth = true)` (`AndroidShellBridge.kt:1017-1029`, `:1258-1281`): `setUserAuthenticationRequired(true)`, and on API 30+ `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`. Key generation throws without an enrolled biometric, and `secureErrorStatus` maps that to `UNAVAILABLE` (`:1326-1329`).
- `src/auth-semantics.json` records "`requireAuth: true` means BIOMETRY" as source-token sites (3 Android, 4 Apple). It never observes an authentication.
- The legend copies say the iOS outcome is unknown: `IMobileBridge.cs:466-472` and `:498-504`, `BnSecureStorage.swift:111-119` and `:386-390`. `ShellBridge.kt:168` and its byte-identical template mirror describe Android's `UNAVAILABLE`.
- The Android instrumented lane runs an API 34 AVD with a lock-screen PIN and no enrolled biometric (18.3 record). `BnSecureAndroidTest.kt` has no test of an auth set returning `UNAVAILABLE`; its auth tests provision with the device-credential test flag. The iOS XCTests check only the constant `unavailable == 3` (`BnSecureStorageTests.swift:84`).

## Goals

- **#401, decided by the owner on 2026-11-11: no second gate.** Both shells forward every pumped line at its parsed level and category, whatever the shell's level. The managed level is the only gate, so a managed `BnLog.Level` raise shows on both shells at once and unprefixed crash/BCL text is never dropped by the shell.
- **#396, the one sensible way:** iOS checks enrolment itself before an auth-bound `set`. With no enrolled biometric, or no biometric hardware, it returns `unavailable` and stores nothing, as Android does. The fix does not depend on Apple's undocumented keychain behaviour, so it no longer waits on #17.
- **Pins, decided by the owner on 2026-11-11: behavioural vectors.**
  - #401: one shared vector file, generated into both shells by WireGen, run through each shell's real pump sink by an XCTest and a JVM test.
  - #396: an XCTest with the enrolment seam forced to "not enrolled", an Android instrumented test on the lane's unenrolled AVD, and a new site in `auth-semantics.json` for the iOS enrolment check.
- Every doc and legend copy states the one behaviour.

## Non-goals

- **A runtime level change reaching the shells.** A managed `BnLog.Level` assignment still does not change the shell's own narration level. Only the pump's second gate goes.
- **An item stored before enrolment was removed.** What a read of an existing auth-bound item returns after the last biometric is removed is not established on either shell. It is out of scope; the docs say so.
- **A passcode fallback for auth-bound items.** `requireAuth: true` keeps meaning biometry (`auth-semantics.json`).
- **Enrolling a fingerprint on the AVD.** API 34 has no shell command for it (18.3 record). The Android pin uses the lane's unenrolled state as it is.
- **The #17 device run.** The checklist item stays as a confirmation run, not a blocker.
- **Lockout parity.** iOS proceeds on `biometryLockout`; Android's behaviour under lockout is unmeasured. Neither shell's docs claim they agree there.

## Anti-goals

- A pin that passes for the wrong reason.
  - The #401 pin must observe after the real sink, not a swapped collector. The current pump tests' collector swap bypasses the gate under test.
  - The Android #396 pin must assert its preconditions first: a secure lock screen and `BiometricManager.canAuthenticate(BIOMETRIC_STRONG) == BIOMETRIC_ERROR_NONE_ENROLLED`. Otherwise `UNAVAILABLE` from "no lock screen" would pass it.
- An ABI change. The 80-byte struct and 10 exports stay; no wire vocabulary changes.
- A comment that claims a safety property nothing pins. Every changed comment that asserts "ungated" or "checks enrolment" names its pin.

## Approaches

Considered for the pins (the owner picked A on 2026-11-11):

- **A. Behavioural vectors (picked).** A shared vector file run through the real code on both shells. It observes behaviour, and it reds iOS before the #401 fix. Cost: a new WireGen emitter for a small vector set.
- **B. Vectors plus a .NET source-token drift test.** The most protection; more surface to maintain for little extra catch.
- **C. Source-token drift only**, as `auth-semantics.json` and `dispatch-surface.json` do. Cheapest, but blind to behaviour: a gate added inside a helper passes it.

For #401's direction the owner chose "no second gate" over "gate on both shells" (drops crash text at an `Error` level and needs two raises) and "gate prefixed lines only" (more rules to document and pin).

For #396 one approach was viable: the iOS check. Making Android return `Ok` is not possible, because the Keystore refuses the key; leaving iOS to Apple's keychain keeps the outcome unknown.

## Design

### D1. iOS pump sink without the second gate (#401)

`BnStderrPump.sink` emits through an ungated entry on `BnLog`, the Swift twin of Kotlin's `writeUngated`: same `emit(level, category, message, privacy)`, no `isEnabled` guard. `BnLog.write` keeps its gate for the `@_cdecl` `BnLogC` shim, which is a different caller. The file header and the sink's doc comment say the pump is ungated because .NET already applied the level, and name the D3 pin.

### D2. The stderr vector file and generator (#401)

`src/stderr-pump-vectors.json` holds cases of `{ shellLevel, line, forwarded, level, category, message }`. The cases cover at least:

- a prefixed `W` line at shell level `Error`: forwarded at Warn (red on iOS today);
- an unprefixed line at shell level `Error`: forwarded at Warn, category `native` (red on iOS today);
- a prefixed `D` line at shell level `Warn`: forwarded at Debug (red on iOS today);
- a prefixed `E` line at shell level `Verbose`: forwarded (green on both; a control).

WireGen emits `BnStderrPumpVectors.g.swift` and `BnStderrPumpVectors.g.kt`, as `DeepLinkVectors.cs` does for `deeplink-vectors.json`. The generated files are never hand-edited.

### D3. The #401 twin pin

One XCTest and one JVM test each loop over every vector. Each sets the shell level, feeds the line through the pump's real production sink, and asserts what reached the log's emit seam: whether a record was written, and its level, category and message. Each test asserts it ran at least one vector, so an empty generated file cannot pass it.

If either log has no seam below the gate, add one at the emit step. The seam must sit after every gate, so it observes what the OS log would receive. On iOS that means a hook recorded immediately before the `os_log` call, with no logic between them (my call). Reading `OSLogStore` back is slower and flaky on the simulator, so it is not used.

**The shell level is really applied (my call).** Each test sets the shell level through the shell's production setter: iOS `BnLog.setLevelFromOrdinal`, Android the `BnShellLog` level the Activity sets. Each vector also writes one shell-narration line below that level through the gated path, and asserts it was dropped. That proves the level took effect. Without it, an "ungated" result could not be told apart from "the level was never set".

Red before D1: the first three vectors fail on iOS and pass on Android. That is the differential red.

### D4. iOS enrolment check (#396)

Before building the access control, `secureSet` with `requireAuth` asks whether biometry can be evaluated. Use `LAPolicy.deviceOwnerAuthenticationWithBiometrics`, the policy the read path evaluates.

- **Where the check lives (my call).** A static helper on `BnBiometrics` creates its own fresh `LAContext`, outside the biometrics instance's lock, work queue and warm-up context. `canEvaluatePolicyOverrideForTest` moves to, or is consulted by, that helper, so the one seam covers both `check` and `secureSet`. `secureSet` already runs off the main thread. The record notes the check's measured cost on the simulator, because of #580's cold `LAContext`.
- `LAError.biometryNotEnrolled` or `.biometryNotAvailable`: return `unavailable` and write nothing.
- `.biometryLockout`: proceed (my call). The condition mirrored from Android is *enrolment*, and a lockout leaves the biometric enrolled. What Android's key generation does under lockout has not been measured, so the docs do not claim lockout parity. It is a non-goal.
- Any other failure: return `unavailable`. The builder records which codes were seen in tests.

A plain `set` (no `requireAuth`) does not call the check.

**Existing iOS tests (my call, plus the owner's 2026-11-11 decision).**
- The ~15 keychain XCTests in `BnSecureStorageTests.swift` that call an auth `set` and expect a store set the override to `(true, nil)` in setup and clear it in teardown. They keep exercising the real keychain path.
- **Owner decision 2026-11-11:** the sample-app XCUITest that taps "Set" on `/secure` (`BnSecureStorageTests.swift:649`, `BnSecureDemo.cs:145`) now expects `Unavailable` on the unenrolled simulator. It becomes an end-to-end pin of D4 through the whole app. The lane does not enrol Face ID.

### D5. The #396 pins

- **iOS XCTest:** with the override returning `(false, LAError(.biometryNotEnrolled))`, an auth `set` returns `unavailable` and a plain `get` of that key returns not-found. A second case with `.biometryNotAvailable` returns `unavailable` too. A control with `(true, nil)` passes the check. Under the simulator keychain it then returns `ok` or the entitlement error the lane already sees; the builder records which.
- **Android instrumented test:** on the lane's AVD, assert the preconditions (`KeyguardManager.isDeviceSecure`, and `canAuthenticate(BIOMETRIC_STRONG) == BIOMETRIC_ERROR_NONE_ENROLLED`), then an auth `set` without the device-credential test flag returns `UNAVAILABLE`, and the key does not exist afterwards.
- **`auth-semantics.json`:** a new Apple site for the enrolment check's policy token, so a change of policy reds the existing drift test.

Red before D4: the iOS XCTest fails. The Android test is green before and after; it is the twin's anchor, and it gets its own red by mutating `provisionKey` to drop `setUserAuthenticationRequired`.

### D6. Docs and legends

- `website/docs/logging.md:45-47`: both shells forward pumped lines ungated; the managed level is the gate. `BnShellLog.kt`'s `writeUngated` comment names the twin pin.
- The status legend copies (`IMobileBridge.cs` ×2, `BnSecureStorage.swift` ×2, `ShellBridge.kt` and its template mirror, kept byte-identical) say: an auth-bound `set` with no enrolled biometric returns `Unavailable` on both shells.
- `docs/ios-device-verification-handover.md:252-261`: the item becomes a confirmation that iOS returns `Unavailable`, no longer an open question.

## Pins and grading

Every new pin is graded against `docs/pin-standard.md`, "Grading a pin: sites and reds":

- Each site gets a fresh red that quotes its message, prefixed `18.7-`.
- Edit every file, comments included, before mutating.
- Each register cell is written in this phase.

Expected reds: the D3 vectors on iOS against the pre-D1 sink; the D3 vectors on Android with a gate added to `relay`; the D5 iOS test against pre-D4 `secureSet`; the D5 Android test with `setUserAuthenticationRequired` removed; and the empty-vector guard.

## Constraints

- No ABI change. No wire vocabulary change.
- Device lanes run only for PRs against `main`, and each lane's `headSha` must match the PR head.
- Test baselines (.NET 1412, JVM 209, Android 271, iOS 296) move by the pins added; `ci.yml` hard-codes the .NET count. If the `auth-semantics.json` drift test counts its sites, the new Apple site moves that count too.
- #396 and #401 are to be closed by the PR. Check the body and commits for closing keywords before opening it.
