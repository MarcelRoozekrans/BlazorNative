# Phase 18.3 Design — Secure-storage per-key ordering (#506)

**Date:** 2026-10-31
**Phase:** `18.3`
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)
**Approved:** by the owner, 2026-10-31, including the calls listed under "Calls made in this design".

## Goal

A secure-storage request on a key never runs ahead of an earlier request on that key that is waiting on a biometric prompt. Requests on other keys keep flowing. The rule is the same on Android and iOS. This is the owner decision of 2026-10-24, "a per-key queue", and the M18 DoD item for #506.

## Background: how it works today

**Android** (`src/BlazorNative.Jni/src/androidMain/kotlin/io/blazornative/shell/AndroidShellBridge.kt`):

- `hostCallBegin` enqueues each secure-storage request on `secureStorageExecutor`, a single-thread executor. This has been the begin contract since 17.2 (#440), and `:271-281` documents it.
- Two actions show a prompt:
  - **auth-bound `set`** (`secureSetAuth`, `:833`): it provisions the key, inits the encrypt cipher, calls `runBiometricGate`, and returns.
  - **`getWithAuth` of an auth-bound key** (`secureGetWithAuth`, `:887`): it inits the decrypt cipher, calls `runBiometricGate`, and returns.
- The executor is free while the prompt is up. The prompt answers on main. `afterAuth` (`:297`) then enqueues the encrypt or decrypt, or the denial's `AuthFailed`, back on the executor, behind everything queued in the meantime.
- **The bug** (#506):
  - auth `set` then `delete`: the delete runs first, and the late encrypt stores a blob under a deleted key, an orphan.
  - auth `set` then plain `set`: the plain set replaces the key, and the late encrypt can overwrite its blob.
  - `getWithAuth` then `delete` or `set` (same shape, milder): the read finishes after the write that followed it.
- The comment at `:277-279` names this as "#506's question". 17.7 (#537) moved the denial completion onto the executor too, so the denial path has the same ordering as success. That is the comment on #506.
- The template copy, `templates/BlazorNative.Templates/content/BlazorNative.App/android/src/androidMain/kotlin/io/blazornative/shell/AndroidShellBridge.kt`, must stay byte-identical. A CI guard checks it.

**iOS** (`src/BlazorNative.Apple/BnHost/BnSecureStorage.swift`):

- `begin` enqueues on `workQueue`, a serial queue (16.4, #438).
- **An auth-bound `set` never prompts on iOS**, the documented iOS asymmetry. `secureSet` runs to its end on `workQueue`. So iOS has **no** set-then-delete hazard.
- **`getWithAuth` of an auth-bound item does suspend.**
  - `secureGetWithAuth` (`:381`) arms the gate and returns.
  - The answer, meaning `finishAuthorizedRead` or the denial, runs wherever the gate answers: LocalAuthentication's reply queue in production, the caller's thread under `authGateHookForTest`. A later `delete` or `set` on the same key can run first.
  - On the simulator the read returns the probed old value. On a real device it reads afresh and sees the later write. So the two platforms disagree, and neither keeps begin order.
- The file header (`:85-88`) already admits that "all Keychain work on workQueue" does not hold for this path.

**Not in scope, noted:**

- **#598** is a one-off timeout in the .NET `SecureStorageBridgeTests` on the Windows runner. It is on the .NET side, which this phase does not touch, and it stays open for a flake sweep.
- **#396**, secure storage on an unenrolled device, is 18.7's.
- **#593** is unrelated: it concerns render batches.

## Owner decisions (this brainstorm, 2026-10-31)

1. **Any request that shows a prompt holds its key, on both shells.** On Android those are the auth-bound `set` and `getWithAuth` of an auth-bound key; on iOS, `getWithAuth` of an auth-bound item. The rule: requests on one key take effect in begin order.
2. **Approach A, park and release on the existing serial queue.**

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| **A. Park and release on the serial queue** | Smallest change to the threading model, and the same shape on both shells. All state lives on the queue thread, so it needs no locks. The begin contract, cross-key order and `drainForTest` stay as they are. | **Chosen by the owner, 2026-10-31.** |
| B. A serial lane per key over a pool | Simpler code, but each pending prompt blocks a thread indefinitely. It replaces the threading model the 17.2 pins and `drainForTest` rely on, and on iOS it means blocking a GCD queue on a semaphore. | Rejected. |
| C. Chain a per-key future | Behaves like A, but the ordering hides in future plumbing, and Swift has no matching primitive, so the shells would diverge in shape. | Rejected. |
| Serialise every request on the prompt | The other option in #506. One slow user blocks every key. | Rejected by the owner, 2026-10-24. |
| Document "await an auth set before touching the key" | No code change, but the bug stays. | Rejected by the owner, 2026-10-24. |

## Approach

**1. The hold (both shells).** Each shell keeps, on its queue thread only, a map from key to a FIFO of parked requests: `held: MutableMap<String, ArrayDeque<…>>` on Android, `[String: [() -> Void]]` on iOS. A key in the map is **held**, even when its FIFO is empty.

- **Start.** When a request starts on the queue, the shell looks up its key first. If the key is held, it appends the request to that key's FIFO and returns. It does not run the request and does not complete it. Otherwise the request runs as today.
- **Take.** A request takes the hold when it reaches its prompt. It puts its key in the map **before** it calls the gate, because Android's no-Activity path calls `onDenied` synchronously, on the executor.
- **No-prompt paths take nothing:** a provisioning failure, a missing key, a plain item on `getWithAuth`, and on iOS an auth `set`.

**2. The release.** The prompt answers on main, or on LocalAuthentication's queue, and the answer is sent to the queue. On Android that is `afterAuth`, already. On iOS the hop is new: see 3. On the queue the after-auth work runs: the encrypt or decrypt, or the denial's `AuthFailed`. Then, **in a `finally`** so that a throw still releases, the shell drains the key's FIFO in order:

- It takes the head and runs it. If the head takes the hold again, because it is itself a prompt request, it stops and leaves the rest parked.
- When the FIFO empties without a new hold, the key leaves the map.

The drain runs inline in the same queue task. Work queued on other keys meanwhile is already behind it and runs next. Cross-key order is not promised, and none is added.

**3. iOS: the gate's answer hops onto `workQueue`.** `BnSecureAuthGate.authenticate` and `deny` send `finishAuthorizedRead`, or the denial, to `workQueue`, so the release, the Keychain read and the hold bookkeeping all run there.

- The file header's "all Keychain work on workQueue does not hold" paragraph becomes true in the positive, and is rewritten to say so.
- The existing iOS tests answer the gate **inside** the hook, which already runs on `workQueue`. Then call `drainForTest()`. A plain `workQueue.async` hop would land after that drain's `sync {}`, and those tests would read a missing completion.
- **Builder's call:** keep those tests passing without weakening their assertions. Either run the answer inline when it already arrives on `workQueue`, using a `DispatchSpecificKey`, or make `drainForTest` drain until quiescent. Record the choice and its reason in the record. A test-only branch in the production path is not allowed, per the 18.2 lesson that a test tap must not change production.

**4. Contracts that stay.**

- `hostCallBegin` still returns before any work runs (#440, pinned by the 17.2 begin pins on Android and the 16.4 begin pins on iOS).
- Requests on one key still start in order, which `secure_storage_keeps_request_order` pins.
- Every request still completes exactly once. A parked request has no completion until it runs.
- After-auth work still runs on the secure-storage executor (17.2 and 17.7 pins).
- `drainForTest` stays a barrier for work that **can** run. Its doc comment says that parked requests do not run until their key's prompt answers.
- The `:271-281` comment's "#506's question" sentence is replaced with the rule.

**5. What a held key costs, and the lost prompt.** A prompt that never answers holds its key indefinitely, and same-key requests wait with it. Today it hangs only its own request. No timeout is added: the DoD bars a bound that hides a slow path.

**Android: verify first, then fix at the source if needed.** This is the owner decision of 2026-10-31.

- Nobody has shown that `BiometricPrompt` always answers when its Activity is destroyed or recreated.
  - `runBiometricGate` completes only from `onAuthenticationSucceeded` and `onAuthenticationError`.
  - Its no-Activity path already denies at once.
- **The first implementation task measures it** on the emulator under a **real** prompt, with no `biometricGateHook`, for each case: recreate the Activity during the prompt (a configuration change) and finish it during the prompt.
  - It records whether each case delivers a callback, which one, and to which callback object.
  - The result goes in the record with its evidence: logcat lines and the test or script used.
- **If any case can lose its answer,** the bridge denies its pending prompts when the Activity that hosts them is destroyed. The denial completes `AuthFailed` through `afterAuth`, which releases the key.
  - The pending prompts are tracked per request id, next to the hold.
  - A real answer that arrives after that denial is ignored, by the owner check in 6.
  - A pin proves the fix: a held key, then the Activity is destroyed, then the parked same-key request completes.
- **If every case answers,** the record holds that evidence, and the class comment cites it in place of an unproven claim. No code is added.
- The 18.4 work on Activity recreation during boot (#511) is next door. This phase keeps to the prompt's own Activity.

**iOS:** `LAContext.evaluatePolicy` calls its reply on cancel, on backgrounding (`systemCancel`) and on lockout. The context is retained in `inFlightContexts` until the request completes, so the reply cannot be lost to deallocation. The record cites this from Apple's documentation. Nothing is measured on iOS.

**6. Hold ownership and the edge paths.** These are my calls, from the builder check.

- **Owner.** A hold belongs to the request id that took it: `held[key] = (owner, fifo)`.
  - Only the owner's after-auth task releases the hold.
  - A second or late answer for a request id that no longer owns the key is ignored, and logged.
  - After running a drained head, the drain stops if the key's owner is now that head, because the head took the hold itself.
- **A throw before the gate is armed.** That covers the throw from `runBiometricGate` itself, from the hook, or from cipher init after the take. The take is undone in a `catch`, and the request completes as it does today, `ERROR` through `runJob`. The parked FIFO is then drained exactly as in a release.
- **Android's `runOnUiThread` lambda** runs after `secureSetAuth` returns. If `BiometricPrompt` construction or `authenticate` throws there, the lambda catches it and calls `onDenied`. That gives an `AuthFailed` through `afterAuth` and a release. Today such a throw is uncaught on main, a pre-existing gap that 18.3 closes because the hold depends on it.
- **The park check** runs in the executor task **before** `runJob`. It parses the key with the same `FlatJson.parse(argsJson)["key"].orEmpty()` that `handleSecureStorage` uses.
  - Malformed JSON or a missing key yields `""`. That is a key like any other: it parks only if `""` is held.
  - The parked unit is the whole `runJob { … }` wrapper, so `testGateForWork` and the `ERROR`-on-throw rule apply when it runs at drain time.
  - On iOS the check is at the top of `run`, after the existing parse.
- **What a parked request sees.** It sees whatever state the holder left.
  - `secureSetAuth` deletes and re-provisions the key before the prompt (`provisionKey`). This is pre-existing, and 18.3 does not change it. So after a denied or failed auth set, the old value is already gone, and a parked `get` returns `NOT_FOUND`.
  - Pin 1 asserts the post-state of the outcome the seam actually yields: blob present and readable after a successful encrypt, absent after a failed one. Either way it asserts no orphan blob and no overwrite by the late work.
- **iOS context retention across the hop.** The hopped closure captures the `LAContext` strongly, as today's gate closure does. `inFlightContexts[requestId]` is cleared by `complete`, which now runs on `workQueue` after the hop. `self` stays `weak`, as today.

## Tests

Each new pin is graded against `docs/pin-standard.md`, "Grading a pin: sites and reds". Every labelled anchor and every claim in a test's name gets a fresh red from a subject mutation, quoting its message. Each pin's register cell is written in this phase.

**Android, instrumented** (`AndroidHostCallContractTest`, the device lane). The `biometricGateHook` seam holds the prompt open by not answering it.

1. **A same-key request cannot overtake an auth set** (DoD pin 1).
   - Begin an auth `set` and hold its gate. Begin a `delete` on the same key, then `drainForTest()`. Anchor: the delete has no completion.
   - Answer the gate. Anchor: the set completes before the delete. Anchor: the key's blob is absent afterwards, so no orphan is left.
   - A **plain `set` variant** ends with the plain value readable. Granting an auth set under the seam may fail its encrypt, since the key needs real auth, and complete `AuthFailed` through `afterAuth`. That still exercises the release, which is the subject. The builder confirms which completion the seam yields, using `setAuthAllowsDeviceCredentialForTest` and `SecureHarness.setPin` as the existing pins do, and the record states it.
2. **Another key is not blocked** (DoD pin 2). With an auth `set` on key A held, a plain `set` and `get` on key B complete. Anchor: B completes while A's gate is still unanswered.
3. **`getWithAuth` holds its key.** With a held `getWithAuth`, a same-key `delete` waits, and the read completes first.
4. **A denied prompt releases the key.** Deny the held auth `set`. Then the parked `delete` completes, on the secure-storage executor.
4a. **A late answer does not release another request's hold.** Request A holds key K and is denied, so the parked auth `set` B takes K. Then A's gate answers again. Anchor: B's parked follower still has no completion.
4b. **The lost-prompt fix**, only if section 5's measurement shows an answer can be lost. With a held key, the Activity is destroyed, and then the parked same-key request completes.

The order "completes before" needs a completion sequence. If the capture in `AndroidHostCallContractTest` keeps no order, add a monotonic index to it. That is a fixture, so the red comes from a subject mutation, never from the fixture.

**Subject mutations the record must run** (RS1 part 1):
- no park at start;
- take the hold after the gate call, not before;
- release only on the success path;
- no `finally` around the release;
- drain the whole FIFO without stopping at a new hold;
- park across all keys instead of one;
- release on any answer, with no owner check;
- no undo of the take on a throw before the gate.

**iOS, XCTest** (`BnSecureStorageTests`, the iOS lane). `authGateHookForTest` holds the gate by keeping it and not answering.

5. **`getWithAuth` holds its key.** Twin of 3: a same-key `delete` waits, and the read completes first, with the value.
6. **Another key is not blocked.** Twin of 2.
7. **A denied gate releases the key.** Twin of 4.
8. **An auth set does not hold**, since it does not prompt on iOS. An auth `set` followed by a `get` completes in order with no gate involved. This pins the asymmetry the design relies on.
9. **The answer runs on `workQueue`.** A gate answered from another thread completes on `workQueue`, read through a `DispatchSpecificKey` or the queue label. This is the positive version of the header's new claim.

Run the same mutation set as on Android, plus "answer not hopped onto `workQueue`".

**Regression:** the existing 17.2 and 17.7 Android pins, the 16.4 iOS begin and retention pins, and the JVM suite, which has no secure-storage executor but shares `ShellBridge.kt`, stay green.

## Calls made in this design (builder's or mine, for the owner to check)

- The drain runs inline in the release task rather than re-enqueueing parked work. Same-key order is identical either way, and inline is simpler.
- The hold is taken before the gate call, so the synchronous no-Activity denial is covered.
- iOS: the answer hops onto `workQueue`. Inline when already on it, or a quiescent drain, is the builder's choice under the constraint in 3.
- No timeout on a held key (see 5). The lost-prompt case is measured first and fixed at its source if real. That is the owner's decision, not mine.
- Unknown actions and any other request with that key park too. The key decides, not the action. A missing key is `""` (see 6).
- A hold has an owner, the request id. Late or duplicate answers are ignored (see 6).
- A throw before the gate is armed undoes the take and drains (see 6).
- The `runOnUiThread` lambda's uncaught throw becomes an `onDenied` (see 6).

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A destroyed Activity loses the prompt's answer | Every later request on that key hangs | Measure it first (section 5). If it is real, deny on destroy and pin it. |
| A path takes the hold but never releases it | Every later request on that key hangs | Release in a `finally`. Pin the denial and throw paths. The "release only on success" and "no `finally`" mutations must red. |
| The iOS hop breaks existing tests that answer inside the hook | False reds, or weakened tests | Handle it per 3. No assertion is relaxed. |
| The seam's "grant" of an auth set fails its encrypt | The pin observes `AuthFailed`, not `OK` | Acceptable: the release is the subject. Record which status the seam yields. |
| The template mirror drifts | CI red | Edit both files in the same commit, and run the mirror guard locally. |
| A green over a race (18.2 lesson) | A vacuous pin | The pins hold the gate open deterministically through the seams, and assert "no completion" after `drainForTest`, not after a sleep. |
| Count drift in lane assertions | CI red | Grep the Android and iOS counts in the first task. |
