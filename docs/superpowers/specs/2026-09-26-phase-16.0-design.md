# Phase 16.0 Design — `The render-thread spike`

**Date:** 2026-09-26
**Phase:** `16.0`
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

**Milestone:** [M16 — Unblock the Dispatch Lane](../../planning/MILESTONE.md) ·
[milestone design](2026-09-26-milestone-16-design.md)

## Goal

Answer one question by measurement:

> **Can a .NET-owned render thread replace `InlineDispatcher` and keep every contract the inline
> dispatcher exists to hold?**

The output is a **go or no-go against criteria written before the spike runs**. A no-go stops M16
and goes to the owner.

## Approach

**The spike is throwaway** (owner decision, 2026-09-26). It lives on `spike/16.0-render-thread`,
which is **never merged**. What merges is a conclusion doc containing:
- the verdict;
- every measurement, with the command that produced it;
- the list of tests whose *assertions*, rather than their behaviour, depend on `InlineDispatcher`.

16.1 then implements the render thread test-first, using the spike only as a reference. This is the
same reason 14.1 threw away its 42 ms early-return probe: a proof of concept is not reviewed code.

**The shape under test** is the one the milestone design chose.
- **The render thread.** The renderer gets a dedicated thread with a single-threaded
  `SynchronizationContext`, and `CheckAccess()` answers honestly.
- **Mount.** The export posts the mount and waits for it to **complete**. This is safe because the
  export thread is never the render thread, and it keeps the sync-mount contract that
  `InlineDispatcher`'s own comment (`NativeRenderer.cs:125-131`) says it exists for.
- **Events.** The export posts the dispatch and waits only until the handler's **synchronous part**
  has run, that is, until `DispatchUiEventAsync` has returned a `Task`, whether or not that `Task`
  is complete. It then returns the rc for that part.
- **Continuations.** A component's `await` captures the render thread's context, so continuations
  resume there. They do so even though `NativeShellBridge.InvokeHostCallAsync` uses
  `ConfigureAwait(false)` internally, because that only affects the bridge's own frame, not the
  caller's.
- **Host events.** The `back` and `navigate` arms of `DispatchHostEventCore` follow the same
  post-and-wait-for-sync pattern as events.

The spike may take any shortcut that does not bias the answer. For example, the fault channel (16.2)
and the `canGoBack` push (16.3) are out of scope, and async faults may simply be logged.

**Criteria, fixed now, before any spike code exists.** **GO** requires all seven:

| # | Criterion | Measured by |
|---|---|---|
| G1 | The full .NET suite passes from a clean rebuild. The **only** permitted failures are tests whose assertion names the type `InlineDispatcher`, and each is listed with a sentence on why it pins a type rather than a behaviour | `dotnet build --no-incremental`, then `dotnet test` |
| G2 | **Sync mount holds.** `MountSyncTests`' behaviours pass unchanged: mount returns an id synchronously, an async `SetParametersAsync` is still rejected with the "synchronously" message, and the parameterless overload works | `MountSyncTests` |
| G3 | **The dispatch window holds.** Frames from a handler's synchronous part are delivered before the export returns, and the navigation window tests pass unchanged | `NavigationTests`, `HostNavigateTests`, `StrictModeTests` |
| G4 | **13.2's recursion does not recur.** Honest `CheckAccess`, and a component `Dispose` → `InvokeAsync` path, pass 10 runs out of 10 with no stack overflow | a spike-local repro of 13.2's case |
| G5 | **#345 is freed, and ownership holds.** In a flipped copy of `DispatchLaneBlockingTests`, `DispatchEventCore` returns within 1 s with the host call still open. Completing the host call runs the continuation on the render thread, and its frame is emitted from the render thread | a spike-local flipped test that asserts thread identity |
| G6 | **The real C ABI agrees.** The JVM suite, 162 tests, passes against the spike's native library, with frames crossing the real callback | `testDebugUnitTest` under JDK 21 |
| G7 | **The devices agree.** `android-instrumented` (228) and `ios` (271) are dispatched on the spike's head, with `headSha` compared, and both are green | the two workflow runs |

**Recorded, not gated.** The spike also records the added cost of the thread hop, as the median and
p95 of 1,000 dispatches before and after. A median increase of more than 1 ms is reported as a
finding for the owner. It does not by itself cause a no-go.

**No-go handling.** When a criterion fails, the spike records:
- what failed;
- the smallest repro;
- whether a fix is conceivable **within 16.1's scope**.

Only a failure with no conceivable fix is a no-go. Any other failure becomes a named 16.1
requirement, and the conclusion says so explicitly. The verdict is never rounded up.

## Tests

The spike runs the **existing** suites as its acceptance bar: .NET 1201, JVM 162, Android 228 and
iOS 271. It adds only spike-local probes for G4, G5 and the timing, and none of those merge. The
merged conclusion cites a command, run ID or SHA for every number.

## Open Questions

None. The criteria are fixed above, and a change to them after the spike has started must be
recorded in the conclusion as a change, with its reason.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **The criteria are bent to fit the result** | A false go carries M16 into a broken 16.1 | The criteria are written in this spec before any code exists, and any change is recorded with its reason |
| **An easy spike hides a hard production case** | A go that 16.1 cannot deliver | G6 and G7 run the real C ABI and real devices, not only the managed suite |
| **The spike quietly becomes 16.1** | Unreviewed proof-of-concept code in production | The spike branch is never merged. 16.1 starts from `main` and works test-first |
| **A partial failure is read as a no-go** | M16 stops for a fixable issue | Only a failure with no conceivable fix is a no-go. Every other failure becomes a named 16.1 requirement |
