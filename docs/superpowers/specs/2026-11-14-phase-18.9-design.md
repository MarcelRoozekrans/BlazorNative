# Phase 18.9 Design — The Windows dispatch bound (#564)

**Date:** 2026-11-14
**Phase:** 18.9
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-14

## Goal

`AShellCallBegunOnAnotherThread_DoesNotMarkTheDispatch_SoAFaultAfterItIsRc2` stops missing its 1 s dispatch bound on the Windows runner. The fix removes the thread pool from the fact's bounded path. The bound stays where it is.

## Why: the cause, as found

**The recurrences.** After 18.1's fix, #564's signature came back twice. Both were Windows `build-test` jobs at attempt 1, on unrelated changes, and both hit the same fact, with no leak into the next fact:

| Run | Date | Ref | Message |
|---|---|---|---|
| 41910675549 | 2026-11-04 | PR #627 | `dispatch_event for handler 8 did not return within 1s`, `FaultNoticeTests.cs:212` |
| 42791875687 | 2026-11-10 | `scratch/18.5-j-q1` | the same |

That is every hit in the 124 failed `build-test` jobs of `ci.yml` runs since 2026-10-26. 18.1's cause, a synchronous `Console.Error` write, does not recur.

**The mechanism.** The handler `pool-begin-then-throw` (`FaultNoticeTests.cs:2493`) begins its host call inside `Task.Run(...)` and blocks the dispatch's synchronous part on `.Wait()`. The render thread is not a pool thread, so `Wait` cannot inline the queued item, and the dispatch waits until a pool worker picks it up. The 1 s `ExportBudget` therefore includes the pool's queue delay.

- xunit 2.9's default "conservative" parallel algorithm runs test bodies on pool workers, at most `ProcessorCount` of them at once. The dumps show `SemaphoreSlim.WaitUntilCountOrTimeoutAsync` under `TestInvoker.CallTestMethod`.
- The pool's minimum is `ProcessorCount` too, which is 4 on the runner.
- This fact holds one worker itself, in `DispatchBounded`'s wait. When three tests in parallel collections are blocked, mostly in render-thread waits, every worker is busy. The item then waits for the pool to inject a thread, about 500 ms or more per thread, and longer on a loaded runner with coverage on.

**Evidence, local, with scratch code that was never committed:**

- **Experiment A.** A scratch fact ran the probe with every pool worker blocked and the maximum left uncapped. It failed with the exact CI message, `dispatch_event for handler 8 did not return within 1s`, in 3 of 3 runs, after 4.4 to 4.9 s. The probe `begin-then-throw`, which needs no pool thread, returned in 0 to 13 ms under the same hold. With a free pool both took 0 to 3 ms.
- **Experiment B.** A sampler in the Runtime.Tests host queued one pool item every 20 ms and timed it, through two full `dotnet test BlazorNative.sln` runs with coverage under `taskset -c 0-3`, which is 4 runs of the Runtime host. The delay exceeded 1 s several times early in the runs, and at about 48 s, which is `PoolStarvationTests`' deliberate hold. Dumps taken at the spikes: 5 workers, 5 running, 0 idle, each running an xunit test body, several blocked in `RenderThreadDispatcher` and `OnRenderThread` waits.

The product is not involved. The dispatch waited on the test's own handler.

## Approaches

| Approach | Trade-off | Verdict |
|---|---|---|
| **The handler begins the call on a dedicated thread** | One file. The fact's claim needs a call begun on another thread that carries the flowing scope, not a pool thread. `Thread.Start` flows the `ExecutionContext`, so the flowing scope arrives as it did under `Task.Run` | **Chosen by the owner, 2026-11-14** |
| Take the test bodies off the pool suite-wide: xunit `parallelAlgorithm: aggressive`, or `ThreadPool.SetMinThreads` in a module initializer | Changes every fact's scheduling, and could hide real pool dependence elsewhere, such as #551's frame-path hop. Closer to a workaround | rejected |
| The dedicated thread, plus a scan pin against `Task.Run(...).Wait()` in test handlers | The pattern has one site, and a text scan is easy to sidestep | rejected |

Raising `ExportBudget` is ruled out by the phase's rule.

## Approach

1. **The handler.** `pool-begin-then-throw` begins `CheckGeolocationPermissionAsync` on a dedicated `Thread` started with `Start`, not `UnsafeStart`, and `Join`s it. The fake answers inside begin, so the join never waits on the shell. Rename what the fact and the probe call it: the label, `PoolBeginThread` and the comment at `FaultNoticeTests.cs:944`. The new names are the builder's call.
2. **A flow anchor.** The handler sets a test-local `AsyncLocal` before it starts the thread, and the thread records what it sees. The fact asserts the value arrived. Without the anchor, a thread that did not flow the context would leave rc 2 for the wrong reason. Under 16.7's M4, which makes the mark follow the flowing scope, the fact must still red at the rc.
3. **A pool-independence pin.** A new fact runs the probe with every pool worker held by `PoolHold`, and asserts that the dispatch returns within `ExportBudget` with rc 2.
   - It runs in the `pool-starvation` collection, which runs alone after the parallel collections. A hold on the whole pool stalls whatever runs at the same time.
   - Its body goes through `OffPool`.
   - Anchor: `PoolHold.EveryWorkerHeld` is true.
   - The hold is released before `TearDown`, and through `DispatchProbe`'s `release` on an overrun.
   - Its red: reverting the handler to `Task.Run(...).Wait()`.
   - Whether it lives in `PoolStarvationTests` or `FaultNoticeTests`, and what has to become `internal` to reach the probe, is the builder's call.
4. **Counts.** The new fact adds one fact on each of two TFMs, so `ci.yml`'s .NET baseline goes from 2824 to 2826. Update the step name and the count comment with it.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The dedicated thread does not carry the flowing scope, so the fact passes vacuously | The thread-bound mark is unpinned | The flow anchor, and 16.7's M4 re-run red |
| Holding the pool stalls the host-session collection's other facts | New flakes | The pin runs in `pool-starvation`, which runs alone |
| Another fact in the suite has the same pool dependence inside a bound | #564 recurs on another fact | Today there is one site; a grep for `Task.Run`, `.Wait()` and `.Result` in the test handlers found no other. The bounded facts and their stacks are checked again in the final review |
