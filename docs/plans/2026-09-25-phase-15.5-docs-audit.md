# Phase 15.5 docs audit — the samples, the names, and every page read against HEAD

The record of phase 15.5's docs work. Task 2 built the fence parser, the compiled-sample build and
`DocsSamplesDriftTests`; Task 3 built `DocsNameDriftTests`; Task 4 read all 20 hand-written pages
against the code and corrected what was false. Every section states the tree it describes; where a
section records an earlier run, it says so.

## Mechanism

- `tools/BlazorNative.DocSamples/DocSampleParser.cs` — the ONE fence parser. `Fences(markdown)`
  finds every fenced code block with a non-empty language; `ParseMarker` reads a
  `bn-sample=<kind>[:<reason>]` token from the fence's info string. `CompiledLanguages` (`razor`,
  `csharp`, `cs`) is the controller ruling (2026-09-25) that scopes the classify-and-compile
  obligation to fences a .NET compiler can actually take.
- `tools/BlazorNative.DocSamples/Program.cs` — the generator. Writes `DocSamples.csproj`
  (`Sdk.Razor`, `net10.0`, `TreatWarningsAsErrors`, ProjectReferences to the shipped packages
  under `src/`, plus `xunit.assert` at the version the repo's test project already uses, read
  from that project at generation time), then one file per compiled-language, non-skip fence under
  `Samples/`, plus the copied `prelude/`. A `statements` fence is wrapped in a method body, with
  any leading `using` directives hoisted above the generated class, so no sample is top-level
  statements and the project is a library, not an executable. A `component:<Name>` fence is
  written as `<Name>.razor`, so another fence can reference it by that name.
- The parser accepts an opening or closing fence indented 0–3 spaces, per CommonMark, and strips
  that indent from the body.
- `tests/BlazorNative.Runtime.Tests/DocsSamplesDriftTests.cs` — the pin. Holds every
  compiled-language fence on a hand-written page to declaring a known kind, holds every `skip` to
  having a reason, floors the compiled-sample count, and holds every narrative page (outside
  `migrating/`) to naming no version.
- `.github/workflows/ci.yml`'s `build-test` job runs the generator then `dotnet build` on the
  result — the step that actually proves the samples compile.

**A design correction found by Step 4, not Step 3:** the first version of the file-stem widening
computed a stem for EVERY path segment, including intermediate directory names, and applied it to
Kotlin/Swift/Objective-C++ files too. Two bugs followed, both caught by the N3 mutation (below)
returning a weaker-than-predicted result on the first attempt:
- `Path.GetFileNameWithoutExtension` on a directory that merely CONTAINS a dot (`BlazorNative.Apple`)
  treats `.Apple` as an extension, silently manufacturing a bare `BlazorNative` resolution — fixed
  by only computing a stem from the true LAST segment of a tracked path, never an intermediate one
  (this is what actually motivated the source-1 namespace-prefix widening above: once the
  accidental path was closed, `BlazorNative` needed a real, honest reason to resolve, and it has
  one);
- stemming `.kt`/`.swift`/`.mm` files gave source 3 silent, undocumented overlap with source 2 —
  `BnStderrPump` was resolving via its own file's stem even with source 2 deleted, which is not
  what "shell declarations" is supposed to mean. `ShellExtensions` now excludes those three
  extensions from stem generation, keeping source 2 and source 3 independently necessary — exactly
  what N3 exists to prove.

## Code questions raised

These look wrong in the code, or in something that is not a docs page, rather than in the docs.
Nothing here was changed, apart from the two comment and XML-doc fixes noted in the Pages table.

1. **`IMobileBridge` replacement is not rejected.** `src/BlazorNative.Runtime/HostSession.cs:381-410`

   does not re-gate. So a managed `BnLog.Level` raise shows on Android and not on iOS — a twin
   divergence of the kind M14 was built to close. `logging.md` now documents the behaviour as it is.
