## 1. Measurements

Task 1, Step 1. Read from the Razor source generator's output under

### BnInput sequences

Each `OpenComponent<BnInput>(N)` is followed by `AddComponentParameter` at N+1 `Placeholder`, N+2
`Value`, N+3 `ValueChanged`. `Placeholder` is a string, so it sits before the callback.

| Page | `OpenComponent<BnInput>(N)` | Placeholder |
|---|---|---|
| `SlowBindPageA` | 0 | `bind-page-a` |
| `SlowBindPageB` | 0 | `bind-page-b` |
| `SlowBindPageTwo` | 0, 5 | `bind-one-a`, `bind-one-b` |
| `SlowBindPageForms` | 0, 5, 10 | `bind-plain-a`, `bind-plain-b` (the third is the get/set input, `bind-get-set`) |

### The `ValueChanged` value

Every one is `EventCallback.Factory.Create<string>(this, CreateInferredEventCallback(this, ...))`, a
boxed `EventCallback<string>` passed through `AddComponentParameter`. Its delegate is the page's own
compiler lambda, declared on the page type itself (no display class), so the generated method sits
directly on the page (`<BuildRenderTree>b__0_N`), as the table below shows.

before the commit.

|---|---|---|
| `change` on a bound `BnInput` | `BnInput.HandleChange` | `SlowBindPageA.<BuildRenderTree>b__0_0` |
| | | `SlowBindPageB.<BuildRenderTree>b__0_0` |
| | | `SlowBindPageTwo.<BuildRenderTree>b__0_0` and `b__0_1` |
| | | `SlowBindPageForms.<BuildRenderTree>b__0_0` and `b__0_1` (plain bind) |

The brief's other sequences hold in `SlowProbe.BuildRenderTree`: the `foreach` item button opens at
11, `other` at 14, the helper button at 89; `ChildPageA` and `ChildPageB` open their button at 2.
Every pin below asserts the measured value, and each one passed green, so none differs from the brief.

The helper's lambda is non-capturing, and the warning names `SlowHandlerWarningTests+SlowHelpers`:
`PageOf` strips the `<>c` the compiler puts it on, as the controller expected. Its receiver is
`SlowProbe` and its target the `<>c` instance, so by Blazor's `RequiresExplicitReceiver` rule the
element attribute keeps the boxed `EventCallback`; `SlowCardPage`'s lambda has the page as both
receiver and target, so BnButton's element attribute holds the raw delegate. Both shapes are read by
`CallbackDelegate`; the two shapes are inferred from that rule, not dumped from the frames.

## 5. Notes

- The `#522` anchors in the three 17.4 bind facts read `Contains($"in {Page}")` with no trailing dot,
  because the fallback is `in {Page}` alone. Task 2 adds the position.
- IL2075, Task 2. `src/BlazorNative.Renderer` does not enable the trim analyzer in its build, so the
  first measure was `dotnet build src/BlazorNative.Renderer -c Release --no-incremental
  -p:EnableTrimAnalyzer=true -p:IsAotCompatible=true`, which reported IL2075 on the unsuppressed
  `value.GetType().GetField("Delegate", …)`. The deciding measure is ILC: `dotnet publish
  samples/BlazorNative.SampleApp -c Release -r linux-x64`. Before `NativeRenderer` called
  `CallbackDelegate`, ILC trimmed it and reported no IL2075. Once wired, it reported one IL2075 at
  `BlazorInterop.cs(91)`, `CallbackDelegate(Object)`. It FIRED, so it is suppressed, exactly that ID,
  on a local function `ReadDelegateField` in the style of the IL2057 suppression in `VerifyAccessors`.
  The justification names the `[DynamicDependency]` and the JVM `SlowHandlerProbeTest` (Task 3). After
  the suppression the publish shows 4 IL2072 and no IL2075.
- The same publishes, before and after Task 2's wiring, also show one IL2070 at `BlazorInterop.cs`
  `PendingQueuedRenderFieldProblem(Type)`, from Phase 18.2. It predates this phase. The `ci.yml` publish
  gate counts IL2072 only, so it passes unseen. Fixed in Task 2's review round, since `BlazorInterop.cs`
  is in this phase's diff: the parameter is annotated
  `[DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.NonPublicFields)]`, with no suppression.
  Every caller passes a `typeof(…)` literal, VerifyAccessors and the 18.2 fact's planted types, so no
  caller needed annotating through. After the fix the analyzer build above reports no trim warning, and
  the linux-x64 publish shows exactly 4 IL2072, no IL2070 and no IL2075.
- Publish gate widening, Task 4. Measured in the log of ci run `42770977305` (headSha `1830108e`, after the
  IL2070 fix): `grep -E 'warning IL'` finds, per publish step, exactly 4 lines `ILC : Trim analysis warning
  IL2072: …` on each of win-x64, linux-bionic-x64 and linux-bionic-arm64, each once, so no duplicates. There is
  no other IL code in those steps. The only fifth hit is the step's own echoed script line, which is not in the
  publish log file the gate reads. The three gates keep the exact-4 IL2072 assertion and add
  `Select-String -Pattern 'warning IL[23]\d{3}'` filtered with `-notmatch 'warning IL2072'`, which fails and
  prints any other IL2xxx or IL3xxx line. Not widened: the ios.yml and android-build publishes, which only
  assert IL2072 as before.
- Publish gate widening, fix round. Measured in the logs of the passing PR-head runs: ios `42772560982`
  (both legs), ci `42772560891` (both ios-build-slice legs, the three build-test publishes and the android-build
  publish) and android-instrumented `42772560984`. Every publish holds only `warning IL2072`, no other IL2xxx
  or IL3xxx code. The same non-IL2072 check (bash `grep -E 'warning IL[23][0-9]{3}' | grep -v 'warning IL2072'`
  with `|| true`) now guards ios.yml, the ci.yml iOS publish and android-instrumented.yml's publish, which was a
  fourth IL2072-only gate. Step names read `… and no other IL warning`. Required checks are job-level contexts
  (`build-test`, `ios-build`, `android-build`, `pr-title`, `footer-check`), so no check references a step name;
