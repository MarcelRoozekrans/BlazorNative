### Task 2: the boot record, `RecreationDuringBootAndroidTest`

Two pins, both through `MainActivity.bootEntryHookForTest`. The hook runs first on the boot
thread, before the join, with the runtime that thread boots. The test holds the first runtime it
sees on a latch and lets every later one pass. `@After` releases the latch, clears the hook and
joins the held thread, bounded at 30 s, whatever the outcome.

  default page with the first boot held, `recreate()`, wait 2 s, release, then assert positively

  with the first boot held, close that Activity, launch the default page, release. The first
  boot's `start()` throws at mount. The mechanism is in §6.

**A leaking mutant poisons the tests that follow it.** Since 18.4 the hold is process-wide and

### The D3 deadlock check

`start()` takes `startLock`, a `private val` in the companion object, and holds it across init,
the hook, the frame-callback registration, `BridgeRegistrar.register()` and the mount. A deadlock
needs code that runs while the lock is held, on this thread or a thread this one waits for, and
takes the lock again. `synchronized` is reentrant on the same thread, so only `start()` from
another thread that the holder waits for can deadlock it. Checked on the fix commit:

- **Nothing reachable from inside `start()` calls `start()`.** The callers of `start(` in the
  main and androidMain source sets are `MainActivity`'s `BlazorNative-Runtime-Boot` thread and
  `PreviewHost`, each a top-level boot. Neither is reachable from a frame callback, a bridge
  callback or the registrar.
- **No frame callback takes the lock or waits on a thread that calls `start()`.** The mount
  delivers its first frame synchronously on .NET's render thread while the `start()` caller waits
  in the export. The callback runs `checkFrameProducer` and `onFrame`.
  - `MainActivity`'s `onFrame` is `mapper.apply`, which buffers and only posts each batch to main,
    `WidgetMapper.kt:777-791`. `onBackState` only buffers, and `onBackUnhandled` posts to main.
  - `PreviewHost`'s `onFrame` is `snapshot::apply`, `PreviewHost.kt:67`, which applies the frame
    to its `TreeSnapshot` synchronously on the render thread. It takes no lock of the runtime's
    and calls nothing that starts a runtime. Its `onError` sets a flag and writes to the sink.
- **`retire()` never takes the lock.** It sets `retired`, shuts the lane down and waits for the
  lane and for callbacks in flight. `shutdown()` calls `retire()` and the native shutdown, without
  the lock. The dispatch lane's `dispatchEvent` paths do not take it either.
- **Main never takes the lock.** `MainActivity` calls `start()` only on its boot thread, so a
  bridge or frame callback during the mount that waits on main does not wait on a thread that
  waits for the lock.

Finding: no path re-enters the lock from another thread while it is held, so the lock cannot
deadlock a boot. The bound the lock adds is the one D2 accepts: a `start()` that hangs inside .NET
holds the lock, and every later `start()` waits for it.

### Task 2: the boot record

- **The mechanism for 1b's replacement Activity: close, then launch.** The first Activity is
  launched with `EXTRA_COMPONENT = "NoSuchComponent"` and its boot held. The test closes its
  scenario, which destroys it during the hold, then launches a second Activity with no extra, so
  it mounts the default page, and releases the first boot after that launch. A `recreate()` was
  not used: the recreated Activity keeps its launch Intent and with it the unknown component,
  since the restored route equals the launch route and so does not pick the page. This is the D1
  case "an Activity that is finished during boot and never replaced", whose runtime the next
  launch's boot retires; the boot record does not tell it apart from a recreation.
- **1b's second anchor, `anchor: the first boot did not fail: its Activity booted`,** is not in
  the plan. It holds the test's premise: the first Activity never set `booted`, which it would
  had its `start()` returned. Its red is a fixture red, a valid component for the first launch.
- **`@After` also joins the held thread,** bounded at 30 s, after it releases the latch and
  clears the hook. A released boot otherwise still runs `start()` while the next test class
  boots, and in the red run it registered its callback after the second Activity's.
- **The boot thread is built unstarted** with `thread(start = false, …)`. The older boot reaches
  it through a local `var previous`, assigned on main by `lastBoot.getAndSet` before
  `bootThread.start()`. `Thread.start` orders that write before the thread's read.
- **D2's warn** is `join(10_000)`, then, if the older thread is still alive, one
  `BnShellLog.warn` at `BnPrivacy.SAFE`, `The previous Activity's boot is still running after
  10 s; this boot waits for it`, then `join()`. `LogPrivacyDriftTests` allows `SAFE` only on a
  message that is one string literal, so the message is not split across lines. No pin covers the warn; it names a hang
  and changes no order.
- **The `retire()` result is not checked,** as in `onDestroy`. It is false when the older
  runtime's dispatch lane did not drain in 5 s; the runtime is marked retired either way, and the
  newer `start()` then proceeds. This is the existing 17.3 behaviour of a rotation, not a new
  case, and no pin covers the timeout.

- **The plan's mutation B3 cannot red anything, so Task 5 argues it in writing instead of
  running it.** B3 moves the join and the retire inside the `try`. That `try` guards this boot's
  own `start()`, and the older boot throws on its own thread, so its failure can never skip code
  on this one. The join keys on the older thread ending, not on its success or on `booted`, so a
  failed older boot is joined and retired either way. B3 is therefore an equivalent mutant, **provided
  that neither `join` nor `retire()` can throw inside the `try`**: a throw from either would be caught
  by the `try` and logged as `Boot failed`, and the new boot would then skip its own `start()`. The
  argument assumes that and was not run; `retire()` is the call that could. The
  Task 2 review corrected the boot-thread comment, which first gave the `try` as the reason.
- **An `InterruptedException` from either `join` would escape the boot thread,** which is
  outside the `try`, and end the process as an uncaught exception. Nothing interrupts the boot
  thread in production: the main and androidMain source sets contain no `interrupt()` call, and
  the thread is reachable only through `lastBoot` and the next boot thread, which only joins it. No catch is added around the join and the retire, and no pin covers this.
- **The rename of 1b makes its red stale.** The red in §2 ran on `045f3274`, under the name
  `a_recreation_after_a_failed_first_boot_still_retires_it`. The rename changes the test file,
  so by the staleness rule that red is not cited for a site; Task 5 re-runs it.

#### The D1 check: the old boot thread after its Activity died

*Corrected by the final review, C1.* The check below covers the older boot thread. It does not cover the
older Activity's own lifecycle events when its runtime is retired while it is alive: `onResume`,
`onPause`, `onDestroy`, the safe-area report and back dispatched on a retired lane and threw. See
"Final review C1" in §2 and the fix wave below.

What the older boot thread does once its Activity is destroyed, read on the fix commit. With the
join, this all runs before the newer boot's `start()`, and the older runtime is then retired.

- **Inside `start()`:**
  - The frame callback and the mount: the mount's first frame reaches the older runtime's
    `onFrame`, `mapper.apply` on the destroyed mapper. It buffers and posts the batch to main,
    where `applyBatchBody` builds views into the detached `widget_root`. `WidgetMapper.destroy()`
    cleared the maps, so this rebuilds a tree that nothing displays and that nothing references
    once the Activity and its runtime are unreachable. That is a transient allocation, not a
    crash. It is the same thing a late frame did to a destroyed mapper before 17.3's retire.
  - The bridge registration: the older bridge is registered until the newer `start()` registers
    its own, a window bounded by the join and the retire. A host call .NET begins in it comes
    from the older page, as in an ordinary rotation, and reaches a bridge whose Activity is
    destroyed. The bridge holds the application context strongly and its Activity only weakly,
    `AndroidShellBridge.kt:94-112`, and 18.3's `hostActivityDestroyed` gates new prompts on it.
    No pin covers a host call in this window; the join keeps it to the older boot's own
    `start()`.
  - `onBackState` buffers in the destroyed mapper; `onBackUnhandled` needs a back dispatched on
    the older runtime, and that Activity never booted, so its boot guard dropped every back.
- **After `start()` returns:**
  - `booted = true` writes a field of the dead Activity. Its `onResume`, `onPause` and
    `onDestroy` have all run, so nothing reads it to dispatch.
  - `runOnUiThread { ViewCompat.requestApplyInsets(widgetRoot) }` posts to main and asks a
    detached view for insets, which does nothing.
  - `lines.forEach { BnShellLog.info(tag, it) }` logs.
- **When `start()` throws,** the catch logs `Boot failed` and the thread ends; nothing else runs.

Finding: nothing after `start()` on the older boot thread touches the destroyed Activity unsafely.
The one cost is the detached tree the older mount's first batch builds, which the design accepts
under approach A: the old boot runs to completion into dead views.

#### The Step 1 audit: tests and the shared hold

#### The fix: where the shared state lives

- **The state is in the companion object, the types are not.** `secureStorageExecutor`, `held`
  and `pendingPrompts` are `private val`s of `AndroidShellBridge`'s companion object, with the
  thread name `BlazorNative-SecureStorage` unchanged. `PromptId`, `Hold` and `PendingPrompt` stay
  private nested classes of `AndroidShellBridge`. A Kotlin nested class has no outer instance, so
  this is the same type either way, and it keeps the instance code naming them unqualified. All
  of it stays in `AndroidShellBridge.kt`, so the byte-identical template guard covers it.
- **The instance methods stay instance methods.** `takeHold`, `releaseHold`, `afterAuth`,
  `holdForPrompt` and `undoHoldForPrompt` run on the shared executor and read the shared maps; each
  builds its `PromptId` from `this` and the request id. `releaseHold` reports a parked job's
  throw through the releasing bridge's `onError`; the job's own `runJob` has already reported it
  through the bridge that began it. The parked job is that `runJob` wrapper, so it does not throw
  into `releaseHold`. Its catch fires only if `runJob`'s own catch block throws, for example
  `completeHostCall` throwing after `onError` has logged. Only in that corner case is a throw
  logged twice, once by each bridge. The catch exists to keep the queue draining. The duplicate
  line is accepted; no product change.
- **`destroyedByConfigChange` is written on the executor.** `onHostActivityDestroyed(true)` queues
  the write and returns. A later final destroy queues its denial on the same serial executor, so
  the denial reads the mark. On a real rotation the old Activity's `onDestroy` runs before the new
  Activity's, so the order holds there too. 4b and 4c pin the orphan clause; the field is also
  `@Volatile`, which the serial executor does not need.
- **The test reset asserts, it does not clear.** `resetHostCallContractForTest()` first clears
  every hook, then reads both maps on the executor through a latch, bounded at 5 s, and throws
  `secure storage: a test left a held key` when either is not empty. `AndroidHostCallContractTest`,
  `FaultNoticeLogAndroidTest` and `SecureHoldAcrossRecreationAndroidTest` call it in `@Before` and
  `@After`, so a leak fails the test that left it, at its `@After`. No pin reds the check itself.

#### The D4 check: a parked job completes its own call

A request parked on a held key is the `runJob` closure of the bridge that began it, built in that
bridge's `hostCallBegin`. When another bridge's release drains it, it runs that closure, so
`handleSecureStorage` runs on the beginning bridge and completes through its `completeHostCall`.
`completeHostCall` sends only the request id and the outcome: `BridgeHostCallCompleter.complete`,
a Kotlin `object`, calls `blazornative_host_call_complete(requestId, …)`, and .NET resolves the
call from `NativeShellBridge.s_pendingHostCalls`, a static `ConcurrentDictionary<long, …>` keyed
by request id, `NativeShellBridge.cs:92`, `:541`. Neither side keys a completion by bridge. Finding:
a job begun on the new bridge that drains after a release on the old bridge completes its own .NET
call. In the tests the completion hook takes the id the same way, and 3a and 4b see the delete
complete under its own id after the other bridge's release.

#### 4c: the real-Activity variant

The lane drives it. The gate hook stands in for the prompt, as in the rest of the class, so the
prompt is not a real androidx prompt, but both destroys are real: `scenario.recreate()` calls
`MainActivity.onDestroy` with `isChangingConfigurations` true, and `moveToState(DESTROYED)`
finishes the recreated Activity, so its `onDestroy` passes false. 4b is kept beside it, since 4b
also pins the order of the denial and the parked delete.
