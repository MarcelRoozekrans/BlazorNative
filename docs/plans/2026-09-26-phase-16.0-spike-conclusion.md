# Phase 16.0 — The render-thread spike: conclusion

**Branch:** `feat/16.0-render-thread-spike` · **Worked:** 2026-09-26

**Spike branch:** `spike/16.0-render-thread`, never merged.
- **BASELINE** `83c47d0cb6b485e1a900918afa9ff3be2329d780`: the probes and timing on the inline dispatcher.

## Verdict

**PROCEED — not a clean GO.** 5 of 7 criteria are met: G2, G3, G4, G5 and G7. **G1 and G6 fail as
written.** No failure was classified as unfixable, so none is a no-go.

The spec sets two rules, and this result sits between them. The first is "**GO** requires all
seven". That is not met, and this document does not claim it. The second is "Only a failure with no
conceivable fix is a no-go. Any other failure becomes a named 16.1 requirement". Every failure under
G1 and G6 has a named root cause and a conceivable fix within 16.1's scope, so M16 proceeds.

The spike answered the question it was built for. A .NET-owned render thread with an honest
`CheckAccess()` does hold the sync-mount contract (G2) and the navigation window tests (G3). It does
not bring back 13.2's recursion (G4). It frees #345: the export returns within 1 s with the host
call still open, and the continuation's frame is emitted on the render thread (G5). The device lanes
are green on the spike's head (G7).

G1 and G6 fail for two reasons.
- **Most of the failures are pins on behaviour that M16's DoD replaces.** They are the #345 and #346
  known-defect pins, 13.2's off-thread-render detector, and the JVM "frames on the dispatch lane"
  contract.
- **One failure exposed a real defect.** The capture window is renderer-wide, so it stays open
  across an async handler's `await`. That defect is 16.1 requirement 1 below.

The ledger's G1 ruling classifies the three G1 behaviour failures as fixable, not as a no-go. They
are "behaviours M16's DoD items 3 and 5 already replace", so they are "fixable-in-16.1 per the
spec's no-go rule". The ruling also records its cost if wrong: "a behaviour the owner wanted kept is
lost". This paragraph is the plain statement that the ruling requires.

## 2. G6: the six JVM failures

All six come from G6 run 2. The failure text is in the spike's `g6-failures.txt`.

| # | Test | Class | Root cause |
|---|---|---|---|
| 1 | `DispatchEventTest.async_dispatchEvent_rerenders_on_the_dispatch_lane` | Intended by the DoD | Frames are now emitted on the .NET render thread, so the frame arrives on `Thread-50`, not `BlazorNative-Dispatch`. JNA attaches the native thread with its default name. DoD item 5 requires this: "Every frame emission and every renderer mutation happens on the render thread". |
| 2 | `HostEventTest.dispatchHostEventAndWait_still_deadlocks_behind_a_held_dispatch_lane` | Intended by the DoD | This is the #346 pin, and it flips. It returns rc 1, which is correct. `NavigateBackAsync` returns false when `_previousRoute` is null, and the test mounts `BnCameraDemo` by name, so the page has no prior route. A temporary managed experiment measured `back rc=1` both with and without the held call. |
| 3 | `InspectorServerTest.end_to_end_tree_dispatch_navigation_sse_and_logs` | Cascade from #2 | See below. |
| 4 | `NavigationTest.settings_click_swaps_root_inside_one_dispatch` | Cascade from #2 | Same |
| 5 | `NavigationTest.back_click_remounts_bndemo_fresh` | Cascade from #2 | Same |
| 6 | `NotificationsTest.navigate_host_event_reroutes_the_live_session` | Cascade from #2 | Same |

**How the cascade happens.**
1. The JVM suite runs every class against **one process-wide .NET session, which is never reset**.
2. The #346 pin completes its held camera call only *after* its `assertFalse`, and not in a
   `finally`.
3. On the spike that assertion fails, so the held call never completes, and the depth counter
   `_uiEventDispatchDepth` stays at 1 for the rest of the run.
4. Every later `SwapRoot` then reaches `RunAfterDispatch` at depth 1. Each swap is **queued and
   never drained**.

**Evidence.**
- `NavigationTest`, `NotificationsTest` and `InspectorServerTest` each pass alone. InspectorServerTest
  ran 2 tests with 0 failures.
- `HostEventTest` and `NavigationTest` run together reproduce the failures. `NavigationTest` shows
  2 of 2 failing, with G6's messages.
- The full suite with #2's `assertFalse` flipped locally gave **162 tests, 1 failure**: test #1. The
  edit was reverted and was never committed.

**No failure is unfixable.** The cascade is a test artefact, but the defect under it is real. A
navigation issued while an unrelated handler is suspended waits for that handler to finish. The
controller ruled that this defect is **a 16.1 requirement, not 16.2**, because it is about
render-thread correctness. See requirement 1.

## 3. Timing: recorded, not gated

The probe `Timing_OneThousandSyncDispatches` times 1,000 synchronous dispatches, and reports the
median and p95 in µs. It ran from a clean rebuild, `dotnet build BlazorNative.sln --no-incremental`,
on each tree.

| | Median µs | p95 µs | Runs |
|---|---|---|---|
| **BASELINE** `83c47d0`, the recorded run | **5** | **13** | This row, plus 3 re-runs: 6/10, 6/7 and 6/7 |
| **SPIKE** `9df59f0`, the final clean-rebuild run | **31** | **39** | This row, plus 4 more runs: 8/27, 8/34, 32/52 and 8/40 |
| **Delta**, recorded run against recorded run | **+26** | **+26** | |

- **Median delta range.** Baseline medians were 5 to 6 µs. Spike medians fell into two groups:
  about 8 µs, and 31 to 32 µs. The median delta is therefore between **+2 µs and +27 µs**.
- **Against the threshold.** The spec's reporting threshold is **1 ms, which is 1,000 µs**. The
  largest measured median delta, 27 µs, is about 37 times smaller. **This is not a finding for the
  owner** under the spec's rule.
- **p95 grew.** Baseline p95 was 7 to 13 µs. Spike p95 was 27 to 52 µs.
- **The two-level median is unexplained.** The implementer suspects `ManualResetEventSlim` spinning
  in one case and a real kernel wait in the other, but did not investigate it. See §6.

## 4. Tests that failed only because their assertion names `InlineDispatcher`

There is exactly one:

- **`MountSyncTests.Renderer_uses_inline_dispatcher_so_mount_chain_completes_synchronously`.** It
  fails at line 87, `Assert.Equal("InlineDispatcher", renderer.Dispatcher.GetType().Name)`. It pins
  the dispatcher's **type**. The contract it names, that the mount chain completes synchronously, is
  held. The other 3 `MountSyncTests` still pin that contract, and they pass (G2).
  - **Caveat:** the next assertion, at line 88, is a behaviour: `CheckAccess()` returns true on the
    calling thread. The spec's shape inverts that behaviour on purpose: "`CheckAccess()` answers
    honestly". Line 87 fails first, so line 88 was never evaluated. 16.1 must replace both lines. See

The spec listed `DispatchEventTests` as naming `InlineDispatcher`. It is not in the failing set.

The other three G1 failures, `DispatchLaneBlockingTests` ×1 and `RenderThreadWarningTests` ×2,
assert **behaviour**. They are not on this list, and that is why G1 is not met.

## 5. 16.1 requirements

Each item is a failure or hazard that the spike measured or traced to code, with its root cause and
the fix it needs.

1. **Scope the capture window to each dispatch's synchronous part.**
   - **Root cause:** `_uiEventDispatchDepth` is a renderer-wide counter. It is decremented in the
     async lambda's `finally`, so it stays at 1 while an async handler is suspended. A second
     dispatch that arrives meanwhile is treated as nested, and `RunAfterDispatch` defers its swap
     until the unrelated handler finishes.
   - **Measured:** `Observe_CaptureWindow_SecondDispatchWhileAsyncHandlerOpen` gave
     `rcBack=0 framesDuringBack=1 depthAfterBack=1 routeAfterBack=/camera`, and after the host call
     completed, `framesSinceBack=3 depth=0 route=/`. The G6 cascade, tests #3–#6, is the same defect.
   - **Case C:** navigate `/` → `/camera`, hold Take Photo, then send back. The result was
     `back rc=0 routeAfter=/camera`, so back reports *handled* while the screen does not change. On
     Android, rc 0 also stops the Activity from finishing. The inline dispatcher deadlocked here, so
     this behaviour is newly observable.
   - **Fix:** close the window when the synchronous part returns, not in the lambda's `finally`.
   - **Test:** a navigation issued while another handler is suspended must swap before its own
     export returns.
   - **Also traced to code, but not measured:** a fault in the second dispatch lands in the shared
     `_uiEventDispatchException` slot and returns rc 0. It then surfaces only as the *first*
     handler's fault. Per-dispatch scoping removes the shared slot. Routing continuation faults is
     16.2's job.
   - Ledger ruling: this is 16.1, not 16.2.
2. **Audit and fix the shells' frame paths.**
   - **Root cause:** frames are now emitted from the .NET render thread. For a synchronous handler
     the frame still arrives while the lane is blocked inside the export. An async continuation's
     frame arrives **outside any export call**, concurrently with the lane. The JNA callback runs on
     a JNA-attached `Thread-N`, as G6 test #1 shows.
   - **The hazard:** Android's `WidgetMapper.pending` list is unsynchronised, and it is now reached
     from the render thread instead of the lane. The iOS frame trampoline must also be audited.
   - **A stale comment:** the `Exports.cs` statement "Frames therefore still fire only inside host
     calls ... containing the 3.0d trampoline hazard" is no longer true.
   - **Fix:** make the JNA and Swift frame callbacks thread-safe. They must hop to their UI thread,
     and frames must stay serial. Correct the `Exports.cs` comment.
3. **Close the `Shutdown` use-after-free window on the frame callback.**
   - **Root cause:** `Shutdown` clears the callback pointer while a render-thread render may be in
     the middle of a callback. Now that frames fire outside host calls, the trampoline can be
     called after it has been cleared.
   - **Fix:** no callback may be in flight when the pointer is cleared. Stop or drain the render
     thread first.
4. **Teardown.** In the spike this had three problems.
   - `HostSession.ResetForTests` waits for the render thread to dispose **while holding `s_lock`**.
     If render-thread work ever needs `s_lock`, for example the first materialisation of the
     `Components` view, that deadlocks. It did not happen in 9 full-suite runs.
   - **Work posted after the render thread shuts down is dropped** with a warning, and `InvokeAsync`
     faults with `ObjectDisposedException`, so a late continuation is lost.
   - **Threads leak.** Each renderer has one thread, and it stops only when the renderer is disposed
     *off* that thread. A renderer disposed on its own render thread, or never disposed, leaks a
     blocked background thread.
   - **Fix:** never wait under a lock during teardown. Choose the post-shutdown policy deliberately,
     and pin it. Tie the thread's lifetime to every dispose path.
5. **The extra host-event arms marshalled beyond the brief.**
   - **Root cause:** with an honest `CheckAccess`, Blazor rejects `StateHasChanged` off the
     dispatcher's thread. The lifecycle multicast (`RaiseNativeEvent`) and the safe-area arm
     (`BnSafeAreaInsets.Report`) have subscribers that call `StateHasChanged`. So the spike ran both
     arms on the render thread **with a full wait**. The brief did not list them. G1 needed them.
   - **Fix:** 16.1 must deliberately marshal every host-event arm, not only `back` and `navigate`,
     and pin each one. It must also decide whether the full wait stays. The DoD says "No main-thread
     caller blocks on .NET".
   - The complete list of entry points the spike marshalled is below this list.
6. **A component that uses `ConfigureAwait(false)` and then re-renders will throw.**
   - **Root cause:** the continuation resumes off the render thread. Blazor then throws
     `InvalidOperationException: The current thread is not associated with the Dispatcher...`. The
     spike observed that exception in the `RenderThreadWarningTests` experiment. On the inline
     dispatcher, the same code worked silently.
   - **The suite does not cover this case.** It is a behaviour change for app authors.
   - **Fix:** document it in 16.1's docs or catch it with an analyzer, and call it out as a
     behaviour change.
7. **Flip or re-pin the tests M16's DoD names. Do not delete any of them.**
   - **`DispatchLaneBlockingTests.AnAsyncHandlerAwaitingAnOpenHostCall_STILL_BlocksTheDispatchLane`**
     is DoD item 3. Invert it, as its own text instructs. G5's probe is that inversion.
   - **The JVM #346 pin, `HostEventTest.dispatchHostEventAndWait_still_deadlocks_...`,** is DoD item
     4. Flip it, and move its held-call completion into a `finally`. See requirement 8.
   - **Both `RenderThreadWarningTests`** are DoD item 5.
     - They fail at lines 165 and 206, where `Assert.Single` finds no report. The honest dispatcher
       turns 13.2's *detect* into Blazor's own *reject*.
     - Un-marshalling `TriggerRootRenderForTests` did not bring the warning back. Blazor threw
       instead. That experiment was reverted.
     - **Fix:** retire the detector, and pin that an off-thread render is rejected or marshalled.
       The DoD's "fails under test instead of only logging" is the target.
   - **The `MountSyncTests` type assertion** is DoD item 6. Replace lines 87–88 with a pin on the
     new contract: `CheckAccess` answers honestly, and mount completes before it returns.
   - **The JVM frame-thread test, `DispatchEventTest.async_dispatchEvent_rerenders_on_the_dispatch_lane`,**
     is DoD item 5. Rewrite it to pin the new contract: frames arrive on one consistent, non-lane
     thread, serially.
8. **Design JVM tests for a shared, never-reset session.**
   - **Root cause:** the whole JVM suite runs against one process-wide .NET session, which is never
     reset. Each managed test gets a fresh renderer from `HostSession.ResetForTests()`, but the JVM
     suite has no equivalent. So one test that leaves a handler suspended poisons every later test.
     The G6 cascade shows this.
   - **Fix:** every JVM test that holds a host call open must complete it in a `finally`. 16.1 must
     either give the JVM suite an isolation mechanism, or design its new pins to leave no suspended
     handler behind.
9. **Keep the `RenderThreadId` probe fix, and use its pattern for every thread-identity pin.**
   - **The defect:** the first full-suite run on the spike failed G5 with `Expected: 105 Actual: 66`.
     Task 2's `RenderThreadId` meant "the most recently constructed renderer's render thread".
     Other test classes build `NativeRenderer`s in parallel, outside the `host-session` collection,
     so the static named another renderer's thread.
   - **The pattern that fixed it:** the static names the **host session** renderer's render thread.
     `HostSession` sets it in `EnsureSession` and clears it in `ResetForTests`. The assertion,
     `Assert.Equal(NativeRenderer.RenderThreadId, frameThreadId)`, stayed as it was.
   - **The rule for 16.1:** a thread-identity pin compares against the renderer under test, never
     a process-wide "last constructed" value. Test parallelism makes the second kind point at the
     wrong renderer.

### The entry points the spike marshalled

Task 3 marshalled these entry points. 16.1 reimplements them test-first from `main`.

- **`NativeRenderer.cs`**
  - `Mount<T>(ParameterView)`, and so `Mount<T>()`, posts and blocks. The "complete synchronously"
    check stays inside, on the render thread.
  - `Unmount(int)` posts and waits.
  - `RunAfterDispatch(Action)` posts and waits, because it reads `_uiEventDispatchDepth`.
  - `TriggerRootRenderForTests(int)` posts and waits.
  - `Dispose(bool)`, called off the render thread, lets Blazor's `CheckAccess()` marshal the
    dispose, then drains the queue and stops the thread. This is 13.2's path, and it is what G4
    exercises.
  - `DispatchUiEventAsync` and `MountAsync` are **unchanged**, because they already use
    `Dispatcher.InvokeAsync`.
  - These are **not marshalled**: the `FrameSink` and `StrictErrors` setters, `Frames` add and
    remove, and `InjectContractViolationForTests`.
- **`HostSession.cs`**
  - `TryMount` does route resolution and `MountRoot` on the render thread, with a full wait.
  - `SwapRoot` makes its `RunAfterDispatch` decision, and performs a depth-0 swap, on the render
    thread with a full wait.
  - `ResetForTests` disposes the session through the `Dispose` path above, with a full wait.
- **`Exports.cs`**
  - `DispatchEventCore` posts, and waits for the synchronous part only. It returns rc 0 if the task
    completed, and rc 2 if it faulted. If the task is incomplete, it returns rc 0 and attaches a
    `ContinueWith` that logs a later fault.
  - `DispatchHostBack` and `DispatchHostNavigate` follow the same pattern.
  - **Beyond the brief:** `RaiseNativeEvent` and `BnSafeAreaInsets.Report` run on the render thread
    with a full wait. See requirement 5.
  - No rc table and no doc comment was changed.

### Carried by later phases

- **16.2 — async faults.** On the spike, a fault after the first `await` is only logged by a
  `ContinueWith` through `BnLog.Error`. The spec allowed that shortcut. It must reach the fault
  channel, and the misattributed second-dispatch fault from requirement 1 must go there too.
- **16.3 — back and navigation.** Case C, the navigate-while-suspended back case, returns rc 0
  while the swap is only queued. 16.3's `canGoBack` push must not report "can go back" on the
  strength of a swap that is only queued. Requirement 1 removes the queueing, and 16.3 must pin
  that the push agrees with it.
- **16.4 — starvation.** The spike did not measure starvation, and #9 is not affected by this
  document.

## 6. What the spike did not test

- **Async fault delivery.** It was out of scope by the spec. Faults after the first `await` were
  logged, not delivered. That is 16.2.
- **The `canGoBack` push.** It was out of scope by the spec. That is 16.3.
- **Starvation.** It was not measured. That is 16.4.
- **Real hardware.** G7 ran on the `android-instrumented` emulator and the iOS simulator, not on a
  phone.
  - The device-side chain main → lane → render thread → main was not provoked by any test. It needs
    a synchronous host callback, such as `TryMount`'s `CurrentRoute` query, that waits on main while
    main is blocked in `dispatchHostEventAndWait`.
  - Nothing concurrent with the lane stressed the frame-path race in requirement 2.
- **The two-level timing median.** Spike medians fell into two groups, about 8 µs and 31–32 µs. The
  cause was not investigated.
- **Criterion changes: none.** G1–G7 are applied as the spec wrote them. See §1.
