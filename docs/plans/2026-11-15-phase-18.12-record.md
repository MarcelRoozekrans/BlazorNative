## 1. Probes

### How the probes ran

- **The probe.** `RelaunchProbeAndroidTest.fires_the_trigger_and_reports_the_instance`, scratch only. It launches `MainActivity` on `BnCameraDemo` with `ActivityScenario`, reads the instance with `currentActivity()` from `Poll.kt`, and reads the trigger id from the instrumentation argument `trigger`. It runs `am wait-for-broadcast-idle` so Gradle's own install is out of the window, watches a 5 s baseline, then fires. After each fire it polls the instance every 250 ms for 10 s. Every line is logged under `BnRelaunchProbe`, ending in `PROBE trigger=<id> relaunched=<bool> pid=<before>/<after>`.
- **The signals,** sampled about once a second from the baseline to the end of the poll, each change logged with its offset from the fire:
  - `seq`: the `Sequence number` from `dumpsys package changes`;
  - `overlay`: an MD5 of `cmd overlay list`;
  - `bcast`: the lines of `dumpsys activity broadcasts history` that name `io.blazornative.shell`, with the ring index stripped.
- **A trigger with several commands** tries them in order and stops at the first that produces the event's own logcat line or a relaunch. Each attempt is logged, so a relaunch is credited to the command before it.
- **Lane-fired triggers.** `scripts/relaunch-probe-lane.sh`, scratch only, runs a background job inside the step script. It waits for the probe's `FIRE` line in logcat, runs the command through `adb shell`, and acknowledges under `BnRelaunchProbeLane`.
- **The lane.** `android-instrumented.yml` on scratch refs: the settle step as on `main`, then the lane script in place of the Gradle call, filtered to the probe class. The baseline assert is skipped on `scratch/` refs, and logcat is uploaded on every run, the `events` buffer included. No bound or timeout was raised.
- **Runs.** One at a time, each on its own `scratch/18.12-probe-<id>` ref made from a clean commit on `d698f435`. Every run below had `headSha` equal to its ref head and was attempt 1. Every ref is deleted.

  In AOSP `android14-release`, `OverlayManagerServiceImpl.onPackageAdded` always adds the new package as a target. `OverlayManagerService.updateTargetPackagesLocked` sends `OVERLAY_CHANGED`, and calls `scheduleApplicationInfoChanged` for the package, only when the package manager's overlay paths for it changed. `ActivityManagerService.scheduleApplicationInfoChanged` changes the global configuration only when the targets include `android`. Otherwise `ActivityTaskManagerService.updateAssetConfiguration` bumps the asset sequence of the target's processes alone. These are source readings; the `overlay-shell` row is the device observation of that path.
- **#407's relaunch is ordered with the install's receivers.** In 36124026574 the old instance went to PAUSED at 10:33:08.956. The shell's user-sensitive update followed at 08.969 and its SdkSandbox reconcile at 08.980; the test package's reconcile came at 09.067; the new instance reached PRE_ON_CREATE at 09.113. No probe run reproduced the delay.

## 2. Natural loop

### How the loop ran

- **The lane.** `android-instrumented.yml` on `scratch/18.12-loop`: the settle step as on `main`, then `scripts/natural-loop-lane.sh`, scratch only, in place of the Gradle call. The script runs `./gradlew --no-daemon installDebug installDebugAndroidTest "-PciSoDir=<temp>/ci-so"`. When Gradle returns, that is second 0. It starts the sampler as a background shell job and, at once, `adb shell am instrument -w -r -e class io.blazornative.shell.BnCameraAndroidTest io.blazornative.shell.test/io.blazornative.shell.BlazorNativeTestRunner` in the foreground. This is the original timing of #407. The baseline assert is skipped on `scratch/` refs, and logcat is uploaded on every run, the `events` buffer included. No bound or timeout was raised.
- **The sampler.** 31 samples, offsets 0 to 30 s from second 0, each taking:
  - `seq`: the `Sequence number` from `dumpsys package changes`;
  - `overlay`: an MD5 of `cmd overlay list`;
  - `bcast`: the lines of `dumpsys activity broadcasts history` that name `io.blazornative.shell`, with the ring index stripped. Every sample's lines are kept, and the analysis compares content, never indices.
- **`pkg-intent`, derived afterwards from the kept `bcast` lines.** Only the `Intent { ... dat=package:io.blazornative.shell... }` header lines. The raw `bcast` signal turned out to be polluted by the instrumentation itself, see below, so this is the install's own package broadcasts alone.
- **Runs.** One at a time, all on `scratch/18.12-loop` at `451e29bf`. Each run's `headSha` equals that head, and each is attempt 1. The ref is deleted.
- **Discarded run, not an infrastructure failure.** The first run, 43761210991 at `f7e6712e`, was cancelled after 39 minutes. My sampler computed its sleep from an `awk` `print` that rounded the epoch to six digits, so it slept for about 50 minutes after sample 0. The camera test itself had passed in 8 s. The fix is `printf "%.3f"`, at `451e29bf`. No sample from that run is used. Replacements for infrastructure failures: 0.
- **What the camera test does by design.** `a_recreation_before_the_image_poll_fails_the_poll_naming_it` calls `scenario.recreate()`, so the first test always has two `MainActivity` instances and one `Schedule relaunch activity`. The logcat alone cannot tell a deliberate recreation from a natural one, since both lack a "Config changes" line, so the per-test count is the discriminator, mapped below.

### Sampler health and load

- **Every sample held a value.** In each of the 10 runs: 31 of 31 samples had a non-empty `seq`, 31 of 31 had an overlay hash that is not the hash of empty output, and 31 of 31 had at least one shell broadcast line. So "none" above is 31 identical readings, not a sampler that returned nothing. A silently failing sampler would have shown an empty `seq` or `d41d8cd9`.
- **The sampler adds load, and it could not have moved the install timing.** Each second it ran three `adb shell` calls, `dumpsys package changes`, `cmd overlay list` and `dumpsys activity broadcasts history`, which take system_server locks briefly. The sample spacing was 1.0 to 1.6 s: the longest gap in any run was 1.6 s, run 43772503784, so a sample sometimes took longer than its second while the camera test ran. But the sampler started at Gradle's return, and the last install-processing line of every run came 0.18 to 0.56 s before the instrumentation start (below), so no install-processing timing was measured under sampler load. What the load could have changed is the camera test's own timing, and so whether a relaunch would have shown. No sampler-free control ran, so that cannot be ruled out; no relaunch was seen with it either.

## 4. The capture

After the second verdict the owner decided "accept, add capture" (2026-11-16). #407's trigger is recorded as not reproduced, and the main Android lane now records its own cause if the relaunch comes back.

**What is captured.** All of it is in the `instrumented-logcat` artifact, which the workflow uploads on every run, green or red (`if: always()`; files that do not exist are ignored).

- `package-sampler.txt`, from `scripts/android-gradle-captured.sh`. The script runs `connectedAndroidTest` and, beside it, a background sampler that reads about once a second from the start of the step until Gradle returns. "Once a second" is a target: an iteration is three bounded reads plus a one-second sleep, so under load it can take several seconds, and the forced runs of §2b showed gaps of 2.2 to 3.3 s. Readers must allow gaps and go by the `utc` field, not the line count. The first line, `T0`, holds the host and device epochs, so the host timestamps can be lined up with logcat. Each sample is one `S` line with:
  - `utc`, the host clock;
  - `seq`, the `Sequence number` line of `dumpsys package changes`;
  - `overlay`, the first 8 hex digits of the MD5 of `cmd overlay list`;
  - `bcast` and `lines`, the MD5 and the count of the `dumpsys activity broadcasts history` lines that name `io.blazornative.shell`, with the ring index stripped.
  The stripped lines themselves follow as `B <n>` lines, so a change in the MD5 can be read.
- `logcat-events.txt`, the `events` buffer, which keeps the `wm_relaunch_resume_activity` changes mask that #407's run lost. The buffer is cleared at the start with `adb logcat -b events -c`.

**Cost and safety.** Every read is bounded by `timeout 5` and guarded with `|| true`. The sampler runs as a background job with stdin, stdout and stderr detached, so an in-flight child cannot hold the runner's pipe open after the kill, is stopped by PID when Gradle returns, and cannot change the step's exit status, which is Gradle's.
