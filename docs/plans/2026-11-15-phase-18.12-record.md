## 1. Probes

### How the probes ran

- **The probe.** `RelaunchProbeAndroidTest.fires_the_trigger_and_reports_the_instance`, scratch only. It launches `MainActivity` on `BnCameraDemo` with `ActivityScenario`, reads the instance with `currentActivity()` from `Poll.kt`, and reads the trigger id from the instrumentation argument `trigger`. It runs `am wait-for-broadcast-idle` so Gradle's own install is out of the window, watches a 5 s baseline, then fires. After each fire it polls the instance every 250 ms for 10 s. Every line is logged under `BnRelaunchProbe`, ending in `PROBE trigger=<id> relaunched=<bool> pid=<before>/<after>`.
- **The signals,** sampled about once a second from the baseline to the end of the poll, each change logged with its offset from the fire:
  - `seq`: the `Sequence number` from `dumpsys package changes`;
  - `overlay`: an MD5 of `cmd overlay list`;
  - `bcast`: the lines of `dumpsys activity broadcasts history` that name `io.blazornative.shell`, with the ring index stripped.
- **A trigger with several commands** tries them in order and stops at the first that produces the event's own logcat line or a relaunch. Each attempt is logged, so a relaunch is credited to the command before it.
- **Lane-fired triggers.** `scripts/relaunch-probe-lane.sh`, scratch only, runs a background job inside the step script. It waits for the probe's `FIRE` line in logcat, runs the command through `adb shell`, and acknowledges under `BnRelaunchProbeLane`.
- **The lane.** `android-instrumented.yml` on scratch refs: the settle step as on `main`, then the lane script in place of the Gradle call, filtered to the probe class. The baseline assert is skipped on `scratch/` refs, and logcat is uploaded on every run, the `events` buffer included. No bound or timeout was raised.
- **Runs.** One at a time, each on its own `scratch/18.12-probe-<id>` ref made from a clean commit on `d698f435`. Every run below had `headSha` equal to its ref head and was attempt 1. Every ref is deleted.

### Other facts for Task 3

- **The install sends `OVERLAY_CHANGED` for the shell.** The first `overlay` run's baseline, before any fire, read these lines from `dumpsys activity broadcasts history`, each beside a `PACKAGE_ADDED` for the same package:

  > #8: act=android.intent.action.OVERLAY_CHANGED dat=package:io.blazornative.shell flg=0x4000010 (has extras)
  >
  > #4: act=android.intent.action.OVERLAY_CHANGED dat=package:io.blazornative.shell.test flg=0x4000010 (has extras)

  In AOSP `android14-release`, `OverlayManagerServiceImpl.onPackageAdded` always adds the new package as a target. `OverlayManagerService.updateTargetPackagesLocked` sends `OVERLAY_CHANGED`, and calls `scheduleApplicationInfoChanged` for the package, only when the package manager's overlay paths for it changed. `ActivityManagerService.scheduleApplicationInfoChanged` changes the global configuration only when the targets include `android`. Otherwise `ActivityTaskManagerService.updateAssetConfiguration` bumps the asset sequence of the target's processes alone. These are source readings; the `overlay-shell` row is the device observation of that path.
- **#407's relaunch is ordered with the install's receivers.** In 36124026574 the old instance went to PAUSED at 10:33:08.956. The shell's user-sensitive update followed at 08.969 and its SdkSandbox reconcile at 08.980; the test package's reconcile came at 09.067; the new instance reached PRE_ON_CREATE at 09.113. Both of those lines come from `PACKAGE_ADDED` receivers in system_server. The install was applied at 10:33:04.069 and 04.261, so that processing arrived about 5 s late, while the process was up. No probe run reproduced the delay.
- **The `bcast` signal in the first `overlay` run moved during the baseline only because the ring index renumbers.** The rerun strips the index. From 43752680667 on, `bcast` moves only when a broadcast about the shell's packages enters the history.
- **The flag word.** #407's Fitness lines carry `flg=0x45000010`, the same as the shell's own `PACKAGE_CHANGED` in the `perm-flags` row. The `gms` row's `pm disable-user` carries `flg=0x5000010`. The flags alone do not name the changed package, since Fitness logs `dat=package:` with it stripped.
