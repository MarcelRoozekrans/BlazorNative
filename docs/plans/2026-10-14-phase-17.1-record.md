## 7. The final review fix wave

A fresh reviewer on the whole branch found no Critical issue and three Important ones, all fixed
here. Their Minors were fixed in the same round, per the owner's rule that review findings are
fixed in the loop.

- **Important 1. A finished dispatch's fault vanished in strict mode.**
  - The no-window path's strict rethrow ran inside B's window and landed in a Task nobody
    observes. There was no rc, no notice and no log, where before 17.1 the fault was B's rc 2.
  - Test first: `AFinishedDispatchsFault_InsideAWindow_IsLoggedInStrictModeToo` went red on the
    unfixed tree, `the finished dispatch's fault vanished in strict mode: nothing logged it,
    nothing reported it.`
  - Fix: inside a window, a finished dispatch's fault is logged with
    `FinishedDispatchFaultLogLabel` and returns, in both modes.
  - R1, removing that branch, reds both Done-rule facts. R2, charging a `Done` owner's fault to the
    window, reds both at their rc.
- **Important 2. The parameter-binding exclusion was unpinned, and its comment was wrong.**
  Removing it left the suite green: a binding fault comes from a render, and a render inside B's
  window runs under B's flow, so the branch was unreachable. It is removed. The comment now says
  why, and that this rests on reading.
- **Important 3.** `Exports.cs`'s rc 2 table said "anything routed to HandleException inside this
  dispatch's window". It now says "raised by its own code or by code that flows no dispatch".
- **Minor 1.** The contract sentence's grammar is fixed in all three copies. It now also states the
  owner's rules for a finished dispatch, logged only, and for code that flows no dispatch, which is
  the window's.
- **Minor 2.** Fact 5 asserts its log line carries `FinishedDispatchFaultLogLabel`, so the fact
  itself tells the no-window path from the late-fault path.
- **Minor 3. A deviation from the design, named.** The Done-rule scenario reports through a
  `ContinueWith` and `ComponentBase.DispatchExceptionAsync`, not through a child's
  `OnInitializedAsync`. The design left that choice to the builder. The fault is A's own code
  either way.
- **Declined to judge, ruled.** A nested dispatch, where B's own fire-and-forget continuation runs
  inline inside a window C opened while B's synchronous part is still open, was not built. It is
  named in the DOES NOT COVER block as resting on reading, and not filed, since it is unverified.

Full suite after the wave: **1323/0**, with Renderer 147, Analyzers 27 and Runtime 1149.
