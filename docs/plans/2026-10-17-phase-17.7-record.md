## 2. #537 — a denied storage prompt completes on its executor

**The fix.** `secureSetAuth` and `secureGetWithAuth` pass `onDenied` through `afterAuth`, the hop
the granted path already used, in both `AndroidShellBridge.kt` copies. The `AuthFailed` completion
of a denied prompt now runs on `BlazorNative-SecureStorage`, not on main. The 17.2 contract comment
gains the sentence from design §4: an auth-bound storage request completes on its executor whether
the prompt is granted or denied, while biometrics' `authenticate` completes from the prompt's own
callback, because it does no work after the prompt. `authenticate` is unchanged.

**The pin.** `AndroidHostCallContractTest.a_denied_storage_prompt_completes_on_the_secure_storage_executor`,
`:204`, with its helpers `denyOnMain`, `:176`, and `assertOnTheExecutor`, `:195`. For an auth-bound
set, then a getWithAuth, it captures the gate through `biometricGateHook`, denies it inside
`runOnMainSync`, and asserts the completion is `AuthFailed`, ran on a thread other than `main`, and
ran on `BlazorNative-SecureStorage`. Anchors: each request reached its prompt, the denial ran on
`main`, a completion arrived.

**Builder's call: a test seam for the set.** On the CI emulator an auth-bound set never reaches its
prompt: its key is provisioned `AUTH_BIOMETRIC_STRONG` only, which needs an enrolled biometric,
17.2 record §4. The new seam `setAuthAllowsDeviceCredentialForTest`, `@VisibleForTesting`,
`internal`, false in production and reset by `resetHostCallContractForTest`, makes the set
provision with the device-credential fallback that `writeAuthBoundSecretForTest` already uses.
The set's prompt and everything after its provisioning are production code. The red-first run below
is the evidence that the set does reach its prompt with the seam.

**Baseline.** The pin adds one instrumented test: the gate in `android-instrumented.yml` moves
245 → 246, and `README.md`'s count table with it, which `ReadmeDriftTests` enforces. The first green
dispatch, 39041834255 on `8cddfb8f`, ran 246 / 0 / 0 and failed only that gate step, still at 245.

## 3. retire() on the device lane

**Why.** M17 DoD item 6 says recreation is proven on the Android device lane by a rotation test.
17.3's mutation L1 removed `MainActivity`'s `retire()` call and every device test stayed green,
because the .NET unmount already stops the old root rendering, so no frame reaches the old runtime
on the tested paths. `retire()` exists to put the old runtime in the retired state, so the pin holds
that state, per design §3.

**The pin.** `RecreationAndroidTest.a_rotation_retires_the_previous_activitys_runtime`, `:150`. It
launches BnDemo, keeps the Activity's runtime, asserts it is not yet retired, rotates with
`scenario.recreate()` and waits for the new boot, then asserts, at `:162`, that the kept runtime
reports itself retired, that the recreated Activity holds a different runtime, and that the new
runtime is not retired. Anchor: the first runtime is not retired before the rotation.

**Test seams,** both `@VisibleForTesting internal`, following `AndroidShellBridge.kt:1794`, and so
unreachable outside the module, and Lint-flagged inside it. That matters for the template: the
generated app's Android project is one module, so `internal` alone would let any Kotlin added there
reach the live runtime. Line numbers are as of fix round 1, which added the annotation import:
- `BlazorNativeRuntime.retiredForTest`, `:171`, reads `retired`;
- `MainActivity.runtimeForTest`, `:192`, reads the private `runtime` field. `RecreationAndroidTest`
  had no way to reach the Activity's runtime; it reached only `mapper`, which is `internal`.

because `TemplateShellSources_AreByteIdenticalToTheRepos` and `TemplateMainActivity_EqualsTheRepos_ModuloTheFallbackAndTheImport`
