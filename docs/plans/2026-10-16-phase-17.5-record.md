## 2. Red

### #454, the bound — `GeneratorRunTests.AChildThatLeavesItsPipeHeld_FailsNamedWithinTheBound_AndLeavesNoProcess`

- **Shape measured first, on Linux.** Under the brief's first stub, `Start-Process` of a sleeper,
  then exit, the stub exited in about 0.4 s. `WaitForExit(5s)` returned true with stdout EOF never
  reached, and the sleeper had been re-parented, with ppid 851, a subreaper. `Kill(entireProcessTree: true)` left it alive.
  `pwsh` on PATH is the dotnet global-tool shim, which starts `dotnet …/pwsh.dll` as a separate
  child. So the pid `Start-Process` returns is the shim's. Controller rulings R1 and R2 followed:
  - R1: a run finishes on exit **and** EOF on both streams, under one deadline.
  - R2: the stub mirrors the dumps. It blocks on EOF from a native child that leaves a sleeper behind.
  - Orphans are accepted as out of a tree kill's reach.
  - The Components fixture is switched too.
- **Inheritance, measured.** `pwsh -File stub.ps1 | cat` did not finish until the sleeper was killed by
  hand. `/proc/<sleeper>/fd/1` was the pipe. The final stub starts the sleeper with
  `Process.Start`, with `UseShellExecute` off and no redirection. The fact's anchor confirms on each run that
  the pipe is held: the launcher exited, and the stub and the sleeper are alive while the run is pending.
- **Red.** `RunBounded` was given the fixture's previous body: `ReadToEnd` on both streams, then
  `WaitForExit()`. The fact waits with an outer 15 s timeout, so the red cannot hang the suite.
  `dotnet test --filter FullyQualifiedName~GeneratorRunTests` gave 1 failed, at 15 s, with the anchor passing:

  > RunBounded did not return within 15 s of the start (00:00:15.0016555): a held pipe hangs it

  The `finally` killed the sleeper, the stub got its EOF, and no process was left.
- **Green.** With the bounded body restored and checked with `cmp`, the fact passed in 5 s.
  The 15 reference-drift facts passed: 8 in `ReferenceDriftTests.cs` and 7 in `ComponentReferenceDriftTests.cs`.

### #454 soak, with the fix in place

- **Setup.** Linux, Debian 13, on the fix commit `b4f4466e`. Twenty sequential full runs of
  `dotnet test --blame-hang --blame-hang-timeout 10m --logger "console;verbosity=normal" -- xUnit.DiagnosticMessages=true`
  from the repo root. Each run was redirected to its own `/tmp/claude-1000/17.5-soak/run-NN.log`.
  The fixtures send one diagnostic line per generation, with the time `RunBounded` took.
- **Result: 20 of 20 runs passed, at 1365/0 each.** That is Analyzers 27, Renderer 147 and Runtime 1191.
  - Every run exited 0, with 16–18 s of wall time.
  - No run hung, aborted or wrote a hang dump.
  - No "did not finish within" failure appeared.
- **Generation time.** 100 generations: 5 packages × 20 runs. Min 1.6 s, median 2.3 s, **max 3.1 s**, which was Runtime.
  The 5-minute bound is about 97 times the slowest generation measured. That leaves room for a cold machine
  or a Windows restore, and a held pipe still becomes a named failure.
- **Node processes: there were none. The soak's count was wrong.** After each run,
  `pgrep -fc "MSBuild.dll.*nodeReuse:true"` reported 2. Those were **self-matches**: the soak loop's own bash
  and its wrapper carry that pattern in their command lines. Re-run alone after the soak, the same `pgrep -fa`
  listed only the calling bash. No MSBuild node with `nodeReuse:true` was seen.
- **Live check, one full run.** `dotnet test --blame-hang --blame-hang-timeout 10m` passed at 1365/0, with every
  `MSBuild.dll` process sampled from `/proc` every 0.1 s.
  - MSBuild writes the launching build's own setting into each worker node's command line, as `/nodeReuse:<value>`.
  - 19 nodes were seen, and all 19 had `nodeReuse:false` and `MSBUILDDISABLENODEREUSE=1` in their environment.
  - 11 were children of `dotnet test`, from the suite's own build.
  - 8 were children of the generator's `dotnet publish`.
- **This host already had node reuse off before the fix.** `~/.bashrc:130` has exported `MSBUILDDISABLENODEREUSE=1`
  since 2026-10-14 11:14. Its comment says idle worker nodes from parallel sessions pushed the VM into swap.
  `~/.claude/settings.json` also sets it in `env`.
  - So on this host the script change was not the variable. The baseline on `f5eff50d` and this soak ran with node reuse
    off either way, and so did any run started from a shell that read `.bashrc` after that time.
  - **The soak is therefore not evidence for the root fix on Linux.** It shows only that the bound and the
    fixtures are stable: 20 of 20, slowest generation 3.1 s.
  - **It also puts the leading suspect in question for the 2026-10-15 Linux hang.** That hang came after the
    `.bashrc` change. Either that run's environment lacked the variable, or node reuse is not the cause on Linux.
    The design says persistent `MSBuild.dll` nodes were running during that hang; their command lines were not recorded.
  - Not resolved here. It goes to the #454 comment and to the controller.
- **What this proves, and what it does not.** Before the fix there was 1 hang in the Linux runs counted on 2026-10-15,
  and 3 hangs in 6 runs on Windows. With the fix there were 0 in 20 on Linux, under a host-wide node-reuse-off
  environment, as above.
  - Windows, where the rate was higher and no such environment is known, is measured only by the lane.
  - What holds whatever the cause: a recurrence is now a named failure within 5 minutes, never a silent hang.
