## 1. The cause, and its evidence

Copied from the design's "Why" section.

**The recurrences.** After 18.1's fix, #564's signature came back twice. Both were Windows `build-test` jobs at attempt 1, on unrelated changes, and both hit the same fact, `AShellCallBegunOnAnotherThread_DoesNotMarkTheDispatch_SoAFaultAfterItIsRc2`, with no leak into the next fact:

| Run | Date | Ref | Message |
|---|---|---|---|
| 41910675549 | 2026-11-04 | PR #627 | `dispatch_event for handler 8 did not return within 1s`, `FaultNoticeTests.cs:212` |
| 42791875687 | 2026-11-10 | `scratch/18.5-j-q1` | the same |

That is every hit in the 124 failed `build-test` jobs of `ci.yml` runs since 2026-10-26. 18.1's cause, a synchronous `Console.Error` write, does not recur.

**The mechanism.** The handler `pool-begin-then-throw` began its host call inside `Task.Run(...)` and blocked the dispatch's synchronous part on `.Wait()`. The render thread is not a pool thread, so `Wait` cannot inline the queued item, and the dispatch waited until a pool worker picked it up. The 1 s `ExportBudget` therefore included the pool's queue delay.

- xunit 2.9's default "conservative" parallel algorithm runs test bodies on pool workers, at most `ProcessorCount` of them at once. The dumps show `SemaphoreSlim.WaitUntilCountOrTimeoutAsync` under `TestInvoker.CallTestMethod`.
- The pool's minimum is `ProcessorCount` too, which is 4 on the runner.
- The fact holds one worker itself, in `DispatchBounded`'s wait. When three tests in parallel collections are blocked, mostly in render-thread waits, every worker is busy. The item then waits for the pool to inject a thread, about 500 ms or more per thread, and longer on a loaded runner with coverage on.

**Evidence, local, with scratch code that was never committed:**

- **Experiment A.** A scratch fact ran the probe with every pool worker blocked and the maximum left uncapped. It failed with the exact CI message, `dispatch_event for handler 8 did not return within 1s`, in 3 of 3 runs, after 4.4 to 4.9 s. The probe `begin-then-throw`, which needs no pool thread, returned in 0 to 13 ms under the same hold. With a free pool both took 0 to 3 ms.
- **Experiment B.** A sampler in the Runtime.Tests host queued one pool item every 20 ms and timed it, through two full `dotnet test BlazorNative.sln` runs with coverage under `taskset -c 0-3`, which is 4 runs of the Runtime host. The delay exceeded 1 s several times early in the runs, and at about 48 s, which is `PoolStarvationTests`' deliberate hold. Dumps taken at the spikes: 5 workers, 5 running, 0 idle, each running an xunit test body, several blocked in `RenderThreadDispatcher` and `OnRenderThread` waits.

The product is not involved. The dispatch waited on the test's own handler.

**The pre-fix red, 18.9-R0.** On `b5128107`, the pin commit, before the handler changed:
`dotnet test tests/BlazorNative.Runtime.Tests -c Release -f net10.0 --no-build --filter "FullyQualifiedName~TheOtherThreadProbe_WithEveryPoolThreadHeld"` failed 1, passed 0, at `ex is null`, with the hold anchor passing first:

> the other-thread probe did not return within its 1 s dispatch bound with every pool worker held, so its synchronous part waits on the thread pool and the Windows runner's busy pool can overrun it (#564): dispatch_event for handler 8 did not return within 1s

The pin then lived in `PoolStarvationTests.cs`; `f0de59fe` moved it, unchanged, to its own file.

## 5. Review fix wave (2026-11-14)

**Finding.** CodeRabbit on PR #710: `FaultNoticeTests.TearDown` promises that each wait is bounded and that every later step runs, but when the dispatch that overran its budget had not returned within `Budget`, it still called `HostSession.ResetForTests()`. That disposes the renderer on the render thread, which the handler most likely blocks, and waits with no bound. The teardown hung, never threw its `TimeoutException`, never reached `NativeShellBridge.ResetForTests()`, and the run hung to the job timeout. Verified by the mutation below.

**Fix.** `bb298477`. `TearDown` now calls `HostSession.AbandonForTests()` when the overrun dispatch did not return, and `ResetForTests()` otherwise, the pattern the `TheBackHoldProbe_…` fact already uses. Its doc comment says so. `Budget`, `StartSession`, `HandlerFor` and `DispatchBounded` became `internal` for the pin.

**Pin.** `TearDownOverrunTests.ADispatchThatOverranAndIsStillRunning_DoesNotHangTearDown_AndTheNextSessionWorks`, in its own file and in the `host-session` collection. Its handler blocks the render thread on a gate only the fact opens; a held host call would not do, because `TearDown` answers every open call itself. The fact runs `TearDown` on a dedicated thread, joined with a bound of `Budget` plus 15 s, so a hang reds with a named message. It then requires a `TimeoutException` naming the overrun dispatch, and a fresh session that mounts. The gate is opened in the finally so the abandoned render thread exits.

**Reds**, on `bb298477`, net10.0, one run each, restored with `git checkout` and a clean tree after each:
