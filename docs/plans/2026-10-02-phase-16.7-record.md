## 4. Tests changed by the behaviour change

The yield made 11 existing tests red, in four demo classes, all with the same cause. Each dispatches a click whose handler awaits a host call that `FakeShellHost` completes inside `hostCallBegin`, then reads `frames[^1]` straight after `Exports.DispatchEventCore` returns. Before 16.7 the inline-completed await did not yield, so the handler ran to the end and rendered its echo during the export. Since 16.7 the continuation renders after the export returns, from the render thread. The contract says exactly that: frames from a continuation are delivered later. So each red is the intended behaviour change, not a regression: every handler still returned rc 0, and every red was `Assert.Single() Failure: The collection did not contain any matching items`, the echo not yet being in `frames[^1]`.

The fix is the same in each: take the frame count before the dispatch, then wait with `ContinuationFrames.WaitFor` for the first later frame that carries the expected patch, and make the original assertion on that frame. `ContinuationFrames` is a new shared helper, `tests/BlazorNative.Runtime.Tests/ContinuationFrames.cs`, with a 10 s budget. The four `MountDemo` frame handlers now add under `lock (frames)`, because the continuation's frame arrives on another thread. The assertions themselves are unchanged; only the frame they read changed.

|---|---|---|
| `BnGeolocationDemoTests.Locate_Granted_EchoesTheFix_NodeIdPinned` | `Assert.Single(frames[^1]…ReplaceTextPatch, p => p.Text.StartsWith(FixPrefix))` | the same `Assert.Single` on the frame `WaitFor` returns for that predicate |

### The JVM twin (Task 5 fix round 1)

The JVM suite was 191/0 before 16.7, per the 16.6 final verification on main, and was cited rather than re-run. With the yield it was red in 5 to 8 tests, varying between runs, in three classes. Each failure message showed a window holding only a `CommitFrame`, so the continuation frame had not arrived when the test read it: the same cause as the .NET table above. Each test took `before = s.frames.size`, dispatched a click on a handler that awaits a host call the test host answers inside `hostCallBegin`, then read `s.frames.subList(before, size)` straight after `dispatchEventBlocking` returned.

The fix is one shared helper, `FrameWait.kt` `awaitReplaceText`. It waits up to 10 s for a window after `before` that holds a single ReplaceText of the expected text on the expected node, which is the predicate each `replaceTextOn` assertion applies, and it requires `before >= 1`, so the mount frame is never in the window. The assertion itself is unchanged and runs on the waited window. The three `boot` helpers now use a synchronized frame list, because the render thread appends to it.
