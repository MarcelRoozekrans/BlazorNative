### Bounds

The rule: per-test at least 3x the slowest test (6.4 s), task at least 2x the step (192 s) and
under 45 minutes. The proposed 120 s per test and 25 minutes for the task satisfy both with a wide
margin (56x and 15x), and a cold runner has room. The measurement does not contradict them, so
they stay: `120 s` per test, `25` minutes for the task.

## 2. The untimed-wait sweep

Task 2. The hold-probe test now runs `dispatchHostEventAndWait(BnHostEvent.Back)` on a daemon
thread named `blocking-back` and joins it for 10 s, failing with the cause named if it is still
alive. A `Throwable` on the helper is rethrown on the test thread as `AssertionError("the
blocking back threw", t)`. The three existing assertions are unchanged.

Sweep of `src/BlazorNative.Jni/src/test` for an untimed wait on the lane or a host call:

| Pattern | Hits | Disposition |
|---|---|---|
| `.join()` with no argument | 1, `HostEventTest.kt:344`, a comment ("never Thread.join() with no timeout") | Not a call. Nothing to do. |
| `.await()` with no argument | 0 | None. Every `CountDownLatch.await` carries a timeout. |
| `Future` / `CompletableFuture` / `.get()` on one | 0 (the `.get()` hits are on `AtomicInteger`, `AtomicReference` and similar, which do not block) | None. |
| `dispatchHostEventAndWait` call sites | 2, `HostEventTest.kt:337` already on a helper thread with `join(2_000)`, and `BackNoticeTest.kt` (the D1 site, now bounded) | `HostEventTest` already follows the pattern. |
| `dispatchHostEventBlocking` | 58 call sites | Not changed. It is the production-shaped blocking path on a lane that is expected to be free, with no host call held open. A wedge there is ended by Task 1's per-test timeout, not a per-site bound. |

The D1 site was the only untimed wait on a held host call, as the design predicted.
