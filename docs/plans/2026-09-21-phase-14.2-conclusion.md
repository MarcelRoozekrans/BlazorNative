# Phase 14.2 — Safe-area insets on both shells: conclusion

**Branch:** `feat/14.2-safe-area-insets` · **Worked:** 2026-09-21
**Verdict:** COMPLETE. `BnSafeArea` ships on both shells, opt-in, present in every snippet a user
would copy (the four capability pages, the `dotnet new` starter page, the new safe-area guide and
the intro example). The four existing declared frame tables are byte-for-byte unchanged; a fifth,
cross-shell `bnSafeAreaDemoFrames` table proves the wire end to end on both the AVD and the iOS
simulator. No ABI change.

---

## 1. What shipped on each shell

**Android (`MainActivity.kt`).** `ViewCompat.setOnApplyWindowInsetsListener(widgetRoot)` reads
`systemBars() or displayCutout()` — cutout matters on its own: it is precisely what made the iPhone's
"Take Photo" button untappable, and Android's Dynamic-Island equivalent is a display cutout, not a
system bar. `reportSafeAreaIfChanged` converts pixels to dp via `resources.displayMetrics.density`
and dispatches the reserved `safeAreaChanged` host event fire-and-forget
(`BlazorNativeRuntime.dispatchHostEvent`, never `…AndWait` — that overload blocks the calling thread,
and this listener fires from a UI callback, which would deadlock the serial dispatch lane against the
main thread per #346).

Android boots the runtime **asynchronously** (`thread(name = "BlazorNative-Runtime-Boot")`), unlike
iOS's synchronous `viewDidLoad` boot, and the first review round caught a defect that difference alone
produced: the first inset callback can arrive *before* `booted` flips true, and because
`onApplyWindowInsetsListener` only re-fires on an actual value **change**, a static-orientation launch
— the common case — would silently never report at all, reproducing #338 on Android behind a green
build. The fix needed both halves together: (1) do not record `lastReportedInsets` when the dispatch
is skipped pre-boot, and (2) call `ViewCompat.requestApplyInsets(widgetRoot)` once `booted` flips true,
forcing the listener to re-fire so the recorded (but undelivered) value gets a second chance. Neither
half alone is sufficient — see the design's own account in the task ledger for the three-interleaving
proof.

**iOS (`HostViewController.swift`).** `reportSafeAreaIfChanged` reads `view.safeAreaInsets` and
dispatches the same reserved event, called **unconditionally at the top of `viewDidLayoutSubviews`,
before** the existing `bounds.size` guard — not inside it. Insets and `bounds.size` are independent
quantities (a status-bar banner growing the top inset is the clearest case that changes insets without
changing bounds), so gating the report on a size change would silently drop exactly the layout passes
this phase exists to catch. `HostViewController` boots synchronously inside `viewDidLoad`, so iOS never
had Android's boot-race class of bug.

**Coverage boundary, recorded rather than papered over.** Neither shell's *reporting* path (the
`WindowInsets` listener / `viewDidLayoutSubviews` hook actually firing on a device) has automated
coverage — `HostViewController` is deliberately inert under XCTest, and the device frame-table tests
(§4) dispatch the event themselves rather than waiting for a real inset to arrive. This was a deliberate
call made in Task 3 and carried forward rather than closed with a new test-only seam: 14.1 spent a whole
phase establishing that test seams become invisibility holes, and inventing one to cover a five-line
reporting method trades a small coverage gap for the exact failure class this milestone is closing. The
reporting path is verified by compilation plus the device lanes; this is a boundary, not silently
missing coverage.

## 2. The per-edge padding prerequisite, and why it was needed

Found while planning, not assumed: `yogaStyles.Box` carried a single `padding`, and
`BnYogaLayout.mm`/`YogaLayout.kt` applied it as `YGEdgeAll` — there was no `paddingTop`. `BnSafeArea`
needs four independently-set values (a notch and a home indicator are never the same size), so it was
**inexpressible on the wire that existed before this phase**. The fix was to add `paddingTop` /
`paddingRight` / `paddingBottom` / `paddingLeft` to `src/wire-vocabulary.json`, regenerate with 14.0's
codegen, and route each edge name to its own `YGEdge*` call in both shells instead of hardcoding
`YGEdgeAll`. This was **inside** the phase, not a separate prerequisite phase, and it leaves the
framework with per-edge padding generally — capability app authors want independently of safe areas.

Three expected failures were captured verbatim as mutation proof rather than treated as bugs to route
around: the codegen byte-compare ("GENERATED FILES ARE STALE") before the `.g.*` files were
regenerated; the routing pin (`YogaLayout.setStyle has no 'when' arm for: paddingBottom, paddingLeft,
paddingRight, paddingTop`) before the shells routed the new names; and a reserved name with no
dispatch arm, before `Exports.cs` grew one. Each is an existing guard catching this phase's own work
before it shipped — the guards did their job.

## 3. The nesting and `maximum` rules, and where they came from

**Nesting must not double-pad — Flutter's rule.** `SafeArea` rewrites the inset data its children
see, so only the outermost instance pads; a nested `BnSafeArea` sees the remaining inset as zero.
Implemented as a scoped `CascadingValue<bool>` around each instance's own `ChildContent` — **not a
static flag**, because a static would wrongly suppress a *second*, unrelated `BnSafeArea` in a
different branch of the tree (two independent screens each wrapped at their own root: both are
legitimately "outermost" in their own branch, and only a cascading value scoped to the render tree,
not the process, gets that right). Mutation-proven: removing the suppression flips the nesting test
from `"0"` padding to `"47"` (the double-pad the rule exists to prevent).

**`maximum` compares against the author's own padding — React Native's rule.** `Off` uses only the
author's own padding for that edge; `Additive` (the default) *sums* the inset with the author's
padding; `Maximum` takes whichever is larger — `Math.max(insets.bottom, 16)`, written once here
instead of by every author. Both directions of `Maximum` are pinned (`MaximumMode_UsesTheAuthorsPadding`,
`MaximumMode_UsesTheInset`) because a naive `MathF.Max` argument swap or a `Math.Min` typo passes
exactly one of the two.

**The Additive default was, until a review finding, entirely unpinned at the frame level.** No test
paired the default mode with non-zero author padding, so "sums" and "replaces" were indistinguishable
to the suite for the mode every app that does not think about it actually takes. A fix round added the
missing test rather than deferring it; the implementation had already summed correctly, so the gap was
evidence of an unpinned property, not a live bug — but the mutation (Additive → inset-alone) flips the
new test from green to red (`Expected: "50" Actual: "34"`), proving it now holds.

Per-edge modes are named `TopEdge`/`RightEdge`/`BottomEdge`/`LeftEdge`, not `Top`/`Right`/`Bottom`/
`Left` — `BnLayoutItem` already declares those names as the CSS-style *position* insets (sequence
14–17), and Blazor's parameter binder throws on a `new`-shadowed parameter of a different type. The
rename is this codebase's own settled answer to that exact collision shape (`BnList`'s
`Height`/`float` vs `BnLayoutItem`'s `Height`/`BnAutoLength?` set the precedent), not a design
preference — see §5 for the design-spec correction this produced.

## 4. The frame-table outcome

**The four existing declared tables are unchanged, verified by measurement, not by omission:**
`bnLayoutDemoFrames` (16 rows), `bnScrollDemoFrames` (17), `bnScrollDemoImageFrames` (1),
`bnImageDemoBeforeFrames` (10) — `ShellFrameTableDriftTests` passes with the same row counts and the
same cell values it asserted before this task began. (A fifth table, `bnImageDemoAfterFrames`, also
exists in the same file and is likewise untouched; it was not named in the task brief's four but is
covered by the same pin.) This is a **regression gate**, not a formality: only the four named
capability pages (`/camera`, `/secure`, `/geolocation`, `/notifications`) were wrapped in
`BnSafeArea`, per decision 6 — the layout, scroll and image demo pages teach layout primitives and
carry the cross-shell parity contract, and were deliberately left untouched.

**The new `bnSafeAreaDemoFrames` table (one row) is cross-shell and dispatch-driven.** A new routed
page, `BnSafeAreaDemo` (`/safearea`, the fourteenth routed page, added to `BnDemo`'s capability menu
immediately before "Camera" so the existing "Camera is the menu's last row" iOS pin needed no edit),
gives its `BnSafeArea` an explicit 300×200 box and a single `Grow="1"` child. Yoga's default
column-stretch then sizes that child to the *entire* padding box — width = 300 − left − right, height
= 200 − top − bottom — so one child's frame is a function of all four edges at once, rather than only
the two a naive "one fixed box" design would prove. Both device suites **dispatch `safeAreaChanged`
themselves** with the same four fixed, distinct, nonzero values (top 47 / right 21 / bottom 34 /
left 13) before reading the laid-out frame — real device insets differ between an AVD and a simulator,
so a table built from whatever the device happens to report could never agree number-for-number, and
the alternative (a test-only override seam) is exactly what three earlier phases in this milestone
spent removing. Android drives the *actual* `OnApplyWindowInsetsListener` via a synthetic
`WindowInsetsCompat` fed through `ViewCompat.dispatchApplyWindowInsets`; iOS — whose `HostViewController`
is deliberately inert under XCTest, like every other class in that suite — calls
`BnRuntime.dispatchHostEventAndWait(.safeAreaChanged, payload:)` directly, the same public method
`HostViewController.reportSafeAreaIfChanged` calls in production. Both reach the identical
`blazornative_host_event` C-ABI entry point; expected value: `(13, 47, 266, 119)` on both shells.

A `.NET`-level test (`BnSafeAreaDemoTests`) pins the wire between the page's explicit dimensions and
the table's numbers directly — it dispatches the same four values via `Exports.DispatchHostEventCore`
and asserts the resulting `paddingTop`/`Right`/`Bottom`/`Left` style patches, catching a page/table
drift before either device lane would.

## 5. The design-spec correction

`docs/superpowers/specs/2026-09-21-phase-14.2-design.md` was written before Task 1 moved per-edge
padding onto `BnLayoutContainer` and before the `TopEdge`/`RightEdge`/`BottomEdge`/`LeftEdge` rename,
so it stated `BnSafeArea : BnLayoutItem` and an unnamed "per-edge modes" object — both wrong against
the shipped code. Corrected in place (marked, not silently rewritten) to `BnSafeArea :
BnLayoutContainer`, with the real parameter names and the collision reasoning that produced them. A
spec that disagrees with the code it specifies is the same defect class this milestone exists to
close, in documentation form — leaving it uncorrected would have shipped that defect into the next
reader who trusts the spec over the source.

## 6. The first-frame limitation

Both shells boot and mount before their first layout pass (`viewDidLoad` / `onCreate`), so neither can
report an inset at mount time — the very first frame renders at zero insets and re-renders once the
real values arrive. This is accepted, not fixed, in this phase; React Native has the identical gap and
documents it identically ("insets are not updated synchronously, so expect a slight delay"). The
recorded fix shape, out of scope here: RN's `initialWindowMetrics` supplies synchronously-available
initial insets at native-module init, which suggests both shells could read the OS's insets
synchronously at boot (before the first render) rather than waiting for the first layout callback —
a follow-up, not a defect this phase silently accepted without a path forward.

## 7. Pages wrapped, and pages deliberately not

**Wrapped:** `/camera` (`BnCameraDemo`), `/secure` (`BnSecureDemo`), `/geolocation`
(`BnGeolocationDemo`), `/notifications` (`BnNotificationsDemo`) — the four pages #338 named; the

**Deliberately not wrapped:** `BnLayoutDemo`, `BnScrollDemo`, `BnImageDemo`/`BnImagePolishDemo` (they
teach layout primitives and carry the parity contract — decision 6); `BnDemo` (the capability-menu
hub, not one of the four named pages); the `website/docs/architecture/layout-and-yoga.md`,
`guides/state.md`, `guides/rest-backends.md`, `migrating/*` code fences (technique illustrations
embedded in unrelated explanatory prose, not whole-page starter examples — wrapping them would be a
non-sequitur mid-explanation of an unrelated concept, the same reasoning decision 6 applies to the
sample's own primitive-teaching pages).

## 8. The JVM count discrepancy — resolved, not papered over

Two earlier implementers reported `./gradlew testDebugUnitTest` at **241 tests**, while `ci.yml`
asserted **162**. Rather than trust either number, the gate's own parse was reproduced exactly:
`ci.yml`'s JVM step globs `build\test-results\testDebugUnitTest\*.xml` specifically (not
`test-results\**\*.xml`) and sums each file's `testsuite` `tests` attribute. Run fresh — the
`testDebugUnitTest` output directory deleted first, then `./gradlew --no-daemon testDebugUnitTest`,
then the exact `Get-ChildItem build\test-results\testDebugUnitTest\*.xml` + XML-sum ci.yml performs —
the result was **25 files, 162 tests, 0 failures**, matching the committed gate exactly. No change to
this number was needed.

The 241 figure is explained by measuring the **release** variant's results too, which happened to
already exist on disk from a separate build: `build\test-results\testReleaseUnitTest\*.xml` sums to
**15 files, 79 tests**. `162 + 79 = 241` exactly. The most likely explanation is that the two
implementers' counting picked up both `testDebugUnitTest` and `testReleaseUnitTest` results together
— either by running the broader `./gradlew test` aggregate task (which builds and tests **both**
variants) rather than `testDebugUnitTest` alone, or by globbing `build/test-results` without scoping
to the `testDebugUnitTest` subdirectory — rather than any Kotlin source actually differing between
what they measured and what the gate measures. **`ci.yml`'s asserted number was already correct**;
Task 6 added one Android instrumented test (`BnSafeAreaAndroidTest`, §4), which lives in the
`androidTest` source set and is not compiled by `testDebugUnitTest` at all, so the JVM gate does not
move by this phase either. Confirmed by re-running the exact gate parse after adding the new
instrumented test: still 162.

## 12. What this phase deliberately did not do

- **Fix the first-frame-at-zero-insets gap.** Accepted with a recorded fix shape (§6), matching
  React Native's own documented behaviour rather than treated as a defect.
- **Add a `margin` mode.** Padding solves #338; a margin mode is non-breaking to add later and
  breaking to remove, so YAGNI applies (design decision 5).
- **Cover the shell-side *reporting* path with a device test.** Deliberately deferred rather than
  papered over with a new test-only seam — see §1's coverage-boundary note.
- **Wrap the layout/scroll/image demo pages, or `BnDemo`.** Decision 6, verified rather than assumed
  (§4's regression gate).
