# Phase 16.3 record — Starvation, measured

**Phase:** 16.3 · **Issue:** #9 · **Spec:** `docs/superpowers/specs/2026-09-27-phase-16.3-design.md`

This record holds the evidence for the slow-handler warning: what a slow synchronous handler costs
the dispatch lane, the budget chosen from that, and the mutations run against the pins.

## 1. The measurement

### What was measured

A throwaway xUnit harness, `StarvationMeasureHarness`, marked `[Trait("Category", "Measure16.3")]`
and **not committed** as a test. Its full source is in the appendix, so the tables can be
regenerated. It ran on .NET directly against `Exports`, with the real `HostSession`
renderer in production mode (`StrictErrors = false`). The mounted probe had two buttons: `slow`,
whose click handler signals that it has started and then `Thread.Sleep`s for N ms, and `fast`,
whose handler does nothing.

For each N in 0, 10, 50, 200 and 1,000 ms, five repetitions of two runs:

- **Dispatch sync time:** the wall time of `Exports.DispatchEventCore` for the slow click, measured
  on its own thread. This is what the shell's dispatch lane waits for.
- **Second event behind it:** once the slow handler has signalled that it started, a second thread
  calls `Exports.DispatchEventCore` for the fast click, and its wall time is measured from the call.
- **Back behind it:** the same, with `Exports.DispatchHostEventCore("back", null)` instead of the
  fast click. The probe is the root page, so the back resolves "not handled" (rc 1). It still runs
  on the render thread, which is what is being measured.

Three warm-up rounds of each call ran first. The tables give the median and the maximum of the five
repetitions.

### The command

Save the appendix as `tests/BlazorNative.Runtime.Tests/StarvationMeasureHarness.cs`, then run:

```
dotnet test tests/BlazorNative.Runtime.Tests --filter "Category=Measure16.3" --logger "console;verbosity=detailed"
```

Run on 2026-09-27 on the development machine: Windows 11 Pro 10.0.26200, .NET 10.0.12, Debug build.

### The results

| Sync part (ms) | Dispatch sync time, median / max (ms) | Second event behind it, median / max (ms) | `back` behind it, median / max (ms) |
|---:|---:|---:|---:|
| 0 | 0.1 / 0.1 | 0.1 / 0.1 | 0.0 / 0.1 |
| 10 | 15.5 / 24.0 | 15.5 / 24.0 | 15.3 / 15.8 |
| 50 | 63.0 / 63.9 | 63.0 / 63.7 | 62.7 / 63.7 |
| 200 | 205.8 / 211.4 | 204.5 / 207.3 | 206.3 / 209.0 |
| 1,000 | 1,004.8 / 1,007.5 | 1,004.7 / 1,007.3 | 1,005.0 / 1,005.7 |

### What the numbers say

- **The cost is one-for-one.** An event posted just behind a slow handler waits for the whole of
  that handler's synchronous part, and nothing more. The second click and the `back` both finish
  within about a millisecond of the slow dispatch itself. There is no amplification and no fixed
  overhead: with a 0 ms handler, every call returns in 0.1 ms.
- **`back` is no exception.** Since 16.2 the shell dispatches back fire-and-forget, so the main
  thread does not wait. But the back's own work still queues behind the slow handler on the render
  thread, and the navigation happens that much later.
- **The small rows are inflated by the Windows timer, not by BlazorNative.** `Thread.Sleep(10)`
  measured 15.5 ms and `Thread.Sleep(50)` 63 ms, which is the 15.6 ms scheduler quantum on this
  host. The 200 ms and 1,000 ms rows, where the quantum is small by comparison, are within 6 ms of
  the requested sleep.

### Main-thread paths

The spec asks that this be confirmed by construction rather than re-measured on a device. The
caller scan on 2026-09-27 found no production main-thread path into a blocking dispatch:

- Kotlin `dispatchEventAndWait` and `dispatchHostEventAndWait` (`BlazorNativeRuntime.kt`) are
  called only from tests and from the desktop JVM inspector (`jvmHost/InspectorHost.kt`), which has
  no Android main thread. `MainActivity` uses the fire-and-forget `dispatchEvent` and
  `dispatchHostEvent`, in the shell and in its template mirror alike.
- Swift `dispatchEventBlocking` and `dispatchHostEventAndWait` (`BnRuntime.swift`) are called only
  from `BnHostTests`. Production uses the async `dispatchEvent` and `dispatchHostEvent`.
- The 16.2 device pins cover back specifically: `BnBackOffMainTests.swift` on iOS and
  `HostEventAndroidTest.kt` on Android.

So a slow synchronous handler stalls the **dispatch lane** and the render thread, and never the UI
thread. The app keeps scrolling and animating; what is late is every event and navigation queued
behind the handler.

## 2. The budget

**`NativeRenderer.SlowHandlerBudget` stays at 100 ms.** The data does not argue for moving it:

- **The cost is linear and one-for-one,** so the budget is simply the delay the next event may
  suffer before the app author is told about it. No overhead has to be subtracted, and there is no
  threshold at which the cost jumps.
- **100 ms is the conventional limit for a response that still feels immediate.** Past it, a tap
  queued behind the handler is visibly late. Android's 5 s input ANR is far too late to be a useful
  diagnostic.
- **A lower budget would sit inside timer noise.** On this host the 15.6 ms quantum turned a
  requested 50 ms into 63 ms. At 100 ms the budget is more than two quanta clear of an ordinary
  50 ms handler, so a warning means a handler really is slow rather than unlucky.
- **Unmeasured, and stated as such:** the synchronous part also includes the re-render, and for a
  navigation the new page's first render. Those were not measured here on a device. A budget much
  below 100 ms risks warning on ordinary page swaps on a slow phone; this is a reason not to go
  lower, not a measurement.

The warning is logged once per handler call site, or per event name for a host-event arm, per
session, and at most `NativeRenderer.SlowHandlerWarningCap` (32) times per session. The next distinct
slow key logs `further slow-handler warnings suppressed` once, and then the warning is silent until
the session resets. `BnLog.DefaultLevel` is `Warn` in every build, so these two rules are what keep
Release logs quiet.

## 3. Where the timing sits

- **UI event dispatches:** `NativeRenderer.DispatchSyncPart`. The clock starts as the dispatch's
  `DispatchScope` opens and stops once it has closed, after the queued navigation swap has drained.
  That is the whole interval `Exports.DispatchEventCore` waits for. Keyed by the handler's
  **owner**: the declaring type and name of the method its delegate runs, plus the event name. The
  delegate is read where the renderer emits the AttachEvent patch, either raw or out of a boxed
  `EventCallback` through an `UnsafeAccessor`, and its method is resolved only once a dispatch is
  over budget. The compiler emits one method per lambda call site, so the key is stable across
  renders and loop items and unique per call site in code.
  - A handler id alone is not stable: Blazor gives a lambda that captures per-render state, such as
    `() => Select(item)`, a new id on every render, so keying by id warned on every click (fix
    round 1).
  - The component whose render tree holds the attribute is not the owner either: `BnButton`
    forwards every app's `OnClick` from its own sequence 100, and a `BnView`'s ChildContent renders
    into BnView's tree with the page's sequence numbers, so a tree-owner key merged every such
    handler in an app into one (fix round 2).
  - When the method is the **framework's**, meaning Blazor's `Microsoft.AspNetCore.Components*`, the
    BCL's `System*` or `BlazorNative.Components`, the owner key is combined with the tree-owner key.
    Every `@bind` of one value type runs Blazor's own binder lambda, so an owner key alone merged
    every such handler in an app into one warning naming Blazor internals (fix round 3). The
    combined key stays per call site and the warning names the component holding it.
  - **Known limit:** a `BlazorNative.Components` wrapper runs its OWN handler for every instance,
    from its own line, so the combined key is the wrapper's and every instance in an app shares
    one warning naming the wrapper. Exactly: BnInput's change, `HandleChange` at sequence 102,
    pinned as a known limit; by the same shape, BnCheckbox, BnPicker, BnSlider and BnSwitch change,
    and BnModal's dismiss click, `HandleDismissRequest`. BnButton, BnImage's `onerror` and BnScroll's
    `onscroll` forward the app's delegate itself and are keyed by the app's method.
  - The tree owner, meaning component type, frame sequence and event, remains the fallback when no
    delegate can be reached or its method does not resolve. A dispatch whose attach was never
    recorded falls back to its handler id.
  - The owner is captured as the scope opens, because the handler's own re-render can dispose its
    id. The map is pruned by each batch's disposed handler ids.
  - **NativeAOT, measured:** `Delegate.Method` resolves in the published win-x64 dll. JVM
    `SlowHandlerProbeTest` drives the sample's `SlowHandlerProbe`, two BnButtons with different
    500 ms handlers, and reads two warnings naming `BlazorNative.SampleApp.SlowHandlerProbe.SlowOne`
    and `.SlowTwo`. With the owner key disabled and the dll republished, the same test reds with
    one warning naming `BlazorNative.Components.BnButton`. The Android and iOS builds use the same
    compiler but were not measured.
- **Host-event arms:** none of `back`, `navigate`, `safeAreaChanged` or the lifecycle multicast
  opens a `DispatchScope`, so each is timed in `Exports.OnRenderThread`, on the render thread,
  around the arm's work. Keyed by event name. The time the post waited in the queue is not counted:
  it belongs to whatever ran ahead of it. Pinned since fix round 1: the back-arm pin records the
  thread of every clock read and requires the render thread.
- **Not timed:** a host event with no session, whose arm runs on the calling thread. There is no
  render thread to starve and no session to key the warning to.

## 4. The pins and their mutations

The pins are `tests/BlazorNative.Runtime.Tests/SlowHandlerWarningTests.cs`, fourteen facts since
fix round 2, in the `host-session` collection, all in production mode, capturing `BnLog` at `BnLog.DefaultLevel`. "Slow"
is a fake clock the handler advances, set per renderer through `NativeRenderer.TimestampForTests`.
Slow cases sit at five times the budget, quick ones at a tenth of it. One fact leaves the clock alone
and really sleeps for 500 ms, to prove the `Stopwatch` path. The JVM `SlowHandlerProbeTest` adds
the NativeAOT half: the owner key, through the published dll.

Each mutation was applied alone, the suite for the class was run, and the mutation was reverted by
reversing the edit before the next one.

| # | Mutation | Result |
|---|---|---|
| 1 | Remove the budget check, so every dispatch warns | **Red:** `AHandlerUnderBudget_LogsNoWarn` |
| 2 | Remove the once-per-key set, so the second run warns | **Red:** `TheSameHandlerSlowTwice_WarnsOnce_AndADifferentSlowHandler_WarnsItsOwn`, `ASlowBackArm_IsWarned_KeyedByEventName_Once`, `ASlowLifecycleArm_IsWarned_KeyedByEventName_AndEachNameWarnsItsOwn` |
| 3 | Include the payload in the message | **Red:** `TheWarn_NeverCarriesThePayload` |
| 4 | Remove the timing call from `DispatchSyncPart` | **Red:** six facts, including `AHandlerUnderBudget_LogsNoWarn` through its clock-read anchor |
| 4b | Mutation 4, with the under-budget pin's clock-read anchor also removed | `AHandlerUnderBudget_LogsNoWarn` goes **green**: the vacuity contrast. Without the anchor, the under-budget pin passes with the timer gone |
| 5 | Remove the timing call from the host-event arms in `Exports` | **Red:** `ASlowBackArm_IsWarned_KeyedByEventName_Once`, `ASlowLifecycleArm_IsWarned_KeyedByEventName_AndEachNameWarnsItsOwn` |

Mutations 1 to 3 are the spec's. Mutations 4, 4b and 5 are the Rule 7 additions: they break the
timing itself rather than the warning's rules, and 4b shows that the anti-vacuity anchor is
load-bearing.

### Fix round 1

Review found that a capturing lambda warned on every click, that nothing capped the warning per
session, and that nothing pinned "queue wait excluded". The fix keys a dispatch by its call site,
caps the warning at 32 per session, and pins the clock's thread. Mutations 1 to 3 were re-run
against the restructured code, then the new ones, each alone and reverted by reversing the edit:

| # | Mutation | Result |
|---|---|---|
| 1 | Remove the budget check | **Red:** `AHandlerUnderBudget_LogsNoWarn` |
| 2 | Remove the once-per-key set | **Red:** five facts, including both capturing-lambda pins and both host-event pins |
| 3 | Include the payload in the message | **Red:** `TheWarn_NeverCarriesThePayload` |
| 6 | Key a dispatch by handler id again | **Red:** `ACapturingLambda_ClickedThreeTimesAcrossReRenders_WarnsOnce` (3 warnings), `TwoCallSites_WarnTwice_AndTwoItemsOfOneCallSite_WarnOnce` |
| 7 | Drop the sequence number from the call-site key | **Red:** `TwoCallSites_WarnTwice_AndTwoItemsOfOneCallSite_WarnOnce`, `TheSameHandlerSlowTwice_WarnsOnce_AndADifferentSlowHandler_WarnsItsOwn` |
| 8 | Remove the cap, both checks | **Red:** `TheCap_Allows32Warnings_ThenOneSuppressionLine_ThenSilence` |
| 8b | Remove only the "silent after suppression" check | **Red:** the same pin; the 34th key logs a second suppression line |
| 9 | Start a host-event arm's clock on the caller, before `InvokeAsync` (the reviewer's mutation B) | **Red:** `ASlowBackArm_IsWarned_KeyedByEventName_Once`, on the clock-thread assertion |

### Fix round 2

Review found that the fix-round-1 key named the tree that holds the attribute, not the handler's
owner, so every BnButton click in an app shared one key. The fix keys by the delegate's method. The
new pins were written after the implementation in this round, so their red was shown by mutation
rather than by a first failing run:

| # | Mutation | Result |
|---|---|---|
| 10 | Key by the tree owner again: skip the delegate's method | **Red:** `TwoBnButtons_WithDifferentSlowHandlers_WarnTwice_NamingTheAppsMethods_NeverBnButton`, `TwoPageTypes_WithSlowButtonsInBnViewChildContent_AtTheSameSequence_WarnTwice` |
| 11 | Stop reading the delegate out of a boxed `EventCallback` | **Red:** `TwoPageTypes_…`, whose handlers are closure lambdas stored as boxed callbacks |
| 10-AOT | Mutation 10 in the published win-x64 dll | **Red:** JVM `SlowHandlerProbeTest`, one warning naming BnButton |

The capturing-lambda pin still warns once under the owner key: the lambda's method is the same on
every render.

### Fix round 3

Review found that the owner key merged every `@bind` of one value type, because each runs
Blazor's binder lambda. The fix combines a framework-declared owner with the tree-owner key. The
pins were written first and ran red before the fix: the `@bind` pin with one warning, the BnInput
known-limit pin on the warning naming `HandleChange`.

| # | Mutation | Result |
|---|---|---|
| 12 | Drop the framework-assembly combine | **Red:** `TwoBindChangeHandlers_OfTheSameType_WarnTwice_NeverNamingBlazorInternals`, `TwoBnInputs_WithDifferentSlowHandlers_StillShareOneWarning_NamingBnInput_KnownLimit` |
| 12b | Combine for every assembly, app code included | **Red:** `TwoBnButtons_…_NeverBnButton`, `TwoPageTypes_…`: the warning names the tree owner instead of the app's method |

`SlowHandlerProbe`'s "Report" now restores the previous `BnLog` sink, because a retired JVM
session never disposes its components.

## Appendix — the measurement harness

The exact source that produced the tables in section 1. It is not part of the suite.

```csharp
using System.Diagnostics;
using BlazorNative.Core;
using BlazorNative.Renderer;
using BlazorNative.Runtime;
using Microsoft.AspNetCore.Components;
using Microsoft.AspNetCore.Components.Rendering;
using Xunit;
using Xunit.Abstractions;

namespace BlazorNative.Runtime.Tests;

// THROWAWAY — Phase 16.3 Task 2 measurement harness. NOT COMMITTED.
[Collection("host-session")]
[Trait("Category", "Measure16.3")]
public sealed class StarvationMeasureHarness(ITestOutputHelper output)
{
    private const string ClickArgs = /*lang=json*/ """{"name":"click"}""";

    [Fact]
    public void Measure()
    {
        FakeShellHost.Reset();
        NativeShellBridge.Register(FakeShellHost.BuildCallbacks());
        HostSession.ResetForTests();
        NativeRenderer renderer = HostSession.EnsureSession();
        renderer.StrictErrors = false;
        var frames = new List<RenderFrame>();
        renderer.Frames += (f, _) => { lock (frames) frames.Add(f); return ValueTask.CompletedTask; };
        var demo = HostSession.ReplaceRegistryEntryForTests("BnDemo", r => r.Mount<SlowProbe>());
        try
        {
            Assert.Equal(0, HostSession.TryMount("BnDemo"));
            int slow = Handler(frames, "slow");
            int fast = Handler(frames, "fast");

            // warm-up
            for (int i = 0; i < 3; i++) { SlowProbe.SleepMs = 0; Exports.DispatchEventCore((ulong)slow, ClickArgs); Exports.DispatchEventCore((ulong)fast, ClickArgs); Exports.DispatchHostEventCore(BnHostEvents.Back, null); }

            output.WriteLine("| sync part (ms) | dispatch sync time: median / max (ms) | second event behind it: median / max (ms) | back behind it: median / max (ms) |");
            output.WriteLine("|---:|---:|---:|---:|");
            foreach (int ms in new[] { 0, 10, 50, 200, 1000 })
            {
                const int reps = 5;
                var own = new List<double>();
                var second = new List<double>();
                var back = new List<double>();
                for (int r = 0; r < reps; r++)
                {
                    foreach (bool useBack in new[] { false, true })
                    {
                        SlowProbe.SleepMs = ms;
                        SlowProbe.Started.Reset();
                        double firstMs = 0;
                        var first = new Thread(() =>
                        {
                            long t0 = Stopwatch.GetTimestamp();
                            Assert.Equal(0, Exports.DispatchEventCore((ulong)slow, ClickArgs));
                            firstMs = Stopwatch.GetElapsedTime(t0).TotalMilliseconds;
                        });
                        first.Start();
                        Assert.True(SlowProbe.Started.Wait(TimeSpan.FromSeconds(10)));
                        double behindMs = 0;
                        var behind = new Thread(() =>
                        {
                            long t0 = Stopwatch.GetTimestamp();
                            if (useBack)
                                Exports.DispatchHostEventCore(BnHostEvents.Back, null);
                            else
                                Assert.Equal(0, Exports.DispatchEventCore((ulong)fast, ClickArgs));
                            behindMs = Stopwatch.GetElapsedTime(t0).TotalMilliseconds;
                        });
                        behind.Start();
                        first.Join();
                        behind.Join();
                        own.Add(firstMs);
                        (useBack ? back : second).Add(behindMs);
                    }
                }
                output.WriteLine($"| {ms} | {Med(own):0.0} / {own.Max():0.0} | {Med(second):0.0} / {second.Max():0.0} | {Med(back):0.0} / {back.Max():0.0} |");
            }
        }
        finally
        {
            SlowProbe.SleepMs = 0;
            HostSession.ReplaceRegistryEntryForTests("BnDemo", demo);
            HostSession.ResetForTests();
            NativeShellBridge.ResetForTests();
        }
    }

    private static double Med(List<double> xs) { var s = xs.OrderBy(x => x).ToList(); return s[s.Count / 2]; }

    private static int Handler(List<RenderFrame> frames, string label)
    {
        List<RenderFrame> all; lock (frames) all = frames.ToList();
        foreach (var f in all)
        {
            var text = f.Patches.OfType<ReplaceTextPatch>().FirstOrDefault(p => p.Text == label);
            if (text is null) continue;
            int button = f.Patches.OfType<CreateNodePatch>().Single(p => p.NodeId == text.NodeId).ParentId!.Value;
            return f.Patches.OfType<AttachEventPatch>().Single(p => p.NodeId == button && p.EventName == "click").HandlerId;
        }
        throw new InvalidOperationException(label);
    }

    private sealed class SlowProbe : ComponentBase
    {
        public static volatile int SleepMs;
        public static readonly ManualResetEventSlim Started = new(false);

        private void Slow() { Started.Set(); if (SleepMs > 0) Thread.Sleep(SleepMs); }
        private void Fast() { }

        protected override void BuildRenderTree(RenderTreeBuilder b)
        {
            b.OpenElement(0, "button");
            b.AddAttribute(1, "onclick", EventCallback.Factory.Create(this, Slow));
            b.AddContent(2, "slow");
            b.CloseElement();
            b.OpenElement(3, "button");
            b.AddAttribute(4, "onclick", EventCallback.Factory.Create(this, Fast));
            b.AddContent(5, "fast");
            b.CloseElement();
        }
    }
}
```
