# Phase 13.2 — The dispatcher's honest answer: conclusion

**Branch:** `feat/13.2-dispatcher-honest-answer` · **Worked:** 2026-08-21
**Verdict:** COMPLETE, with the phase's premise **overturned by measurement**. The goal —
*"measure what breaks when `CheckAccess()` stops returning an unconditional `true`, then ship the
guard the evidence supports"* — is met. The evidence supported a different guard than anyone
expected.

---

## 1. The finding, first, because it is the phase

**`InlineDispatcher.CheckAccess() => true` is not a lie left lying around. It is load-bearing.**

The spike made it honest — capture the constructing thread, compare — and the **test host process
died with a stack overflow**, reproducibly, 3 runs of 3. Not a test failure. A process kill.

The loop, captured from a live stack rather than reasoned about:

```
Renderer.Dispose()
  → CheckAccess()                              false
  → Dispatcher.InvokeAsync(() => Dispose())    marshal to "the right thread"
  → InlineDispatcher.InvokeAsync runs it INLINE, on the same thread
  → Renderer.Dispose()  →  CheckAccess()       false
  → …until the stack ends
```

**Blazor calls `CheckAccess()` to decide whether to MARSHAL, not merely to assert.** That is the
insight the phase turned on, and nothing in the codebase said it. An inline dispatcher runs work on
the *calling* thread and therefore has nowhere to marshal to — so it **must** claim every thread is
the right one. The two are a matched pair.

Making `CheckAccess()` honest therefore requires giving `InvokeAsync` a real queue and a real owner
thread. That breaks the **sync-mount contract**: the C-ABI mount path requires the first render to
complete synchronously inside the native callback window (`Exports.cs`, pinned by `MountSyncTests`).
The dispatcher's own comment has said this since Phase 2.4 — what nobody had done was connect it to
`CheckAccess()`.

**The door is closed until the dispatcher itself changes, and the dispatcher cannot change while the
C ABI is what it is.**

### What the milestone predicted, and what it got right

The M13 risk register predicted casualties in **#9** (dispatch-lane starvation) and **#213 item 2**
(a parked async fault off a pool thread), and named the fallback: *"Debug-only warning is the
documented fallback."*

It found #213's territory exactly — both crashing tests are `AsyncFramesFaultTests`, the
parked-fault pair — and it landed on the fallback. But the *mechanism* was not the predicted one.
The prediction was "currently-working async paths become exceptions". The reality is that the change
is **structurally impossible**, for a reason that has nothing to do with async faults: it is
infinite recursion in Blazor's marshalling protocol.

That distinction matters for anyone who reads this later and thinks the guard could be tightened
into an assertion "once the async faults are cleaned up". It cannot. The async faults were never the
obstacle.

## 2. What shipped

`NativeRenderer.ReportIfNotTheRenderOwnerThread()`, called at the top of `UpdateDisplayAsync` — the
one place every render batch passes through.

| | |
|---|---|
| **Detects** | a render batch driven from a thread other than the one that drove the first batch |
| **Reports** | `BnLog.Warn` under `StrictErrors`, `BnLog.Debug` otherwise |
| **Throws** | **never** — not even under `StrictErrors` |
| **Costs** | one `Environment.CurrentManagedThreadId` and one `Interlocked.CompareExchange` per batch |

**Why "owner" is the first batch's thread, not the constructing thread.** Construction can happen
anywhere — a DI container on any thread. What the sync-mount contract actually cares about is the
thread that drives renders inside the native callback window, and the first batch is the earliest
honest observation of it.

**Why it never throws.** `StrictErrors` elsewhere means "surface rather than swallow", and it may
rethrow. Not here. A throw would be a behaviour change on a path that works today, in the exact area
the spike had just proved is delicate. This detects; it does not prevent.

**Why the gate is `StrictErrors` and not `[Conditional("DEBUG")]`.** A `Conditional` check compiles
away at *library* build time, and consumers take a Release-built package — so it would have been
invisible to every consumer and could only ever have caught this repo's own regressions.
`StrictErrors` ships, every test harness enables it, and a consumer can opt in on a real device.
Reporting at `Debug` when it is off means a consumer running ordinary trace logging (#237's posture)
sees it without having to discover the flag first.

## 3. Standing pins

| Pin | What it refuses | Mutation that reds it |
|---|---|---|
| `ARenderFromANonOwnerThread_WarnsUnderStrictErrors_AndNamesBothThreads` | The condition going unreported, or a report that does not name both threads | Remove the check |
| `WithoutStrictErrors_TheSameConditionReportsAtDebugLevel` | The level collapsing to one setting | Always `Warn` |
| `TheOrdinarySingleThreadedPath_IsSilent` | The guard firing on every batch | Drop `owner == current` |

Each is proven against a **different** mutation. The third is the one that matters most: a guard
that fires on every batch is noise, and noise looks like coverage while providing none — the
failure class 13.1 recorded after finding two tests that passed while checking nothing.

.NET test count **1051 → 1054**.

## 4. A defect this phase created and fixed, worth recording

The first full-suite run came back with **two failures in `Renderer.Tests`** that had nothing to do
with the renderer.

`BnLog.Level` and `BnLog.Sink` are **process-wide statics**, and xUnit runs test *classes* in
parallel. The new test's capture helper installed a sink for the duration — which meant it was
installed for every class running beside it, including `StrictModeTests` and
`DevHostBridgeEventTests`, which assert on log output. The capture **swallowed their lines**.

`Runtime.Tests`' `BnLogTests` had already documented this hazard and solved it with
`[Collection("host-session")]`. The fix is the same shape — a `bnlog-global` collection — plus a
sink that **forwards to whatever was previously installed**, so a capture can never swallow even if
ordering slips.

**Also recorded because the conclusion should be honest about its own process:** that same run took
**50 minutes** for `Runtime.Tests` against a ~25-second baseline, and the first diagnosis was that
the new guard caused it. That was wrong. Re-measured on an idle machine, `Runtime.Tests` runs in
**23 seconds** with the guard in place, and the guard fires fewer than 50 times across the suite.
The 50 minutes was contention from ~48 leftover `dotnet`/`testhost` processes from earlier runs. The
wrong diagnosis cost two instrumented measurement rounds; the right one took one clean run.

## 5. What 13.2 deliberately did not do

- **Make `CheckAccess()` honest.** Measured as impossible without replacing the dispatcher (§1).
- **Throw on the condition.** Detection only, for the reason in §2.
- **Change the dispatcher, the sync-mount contract, or the C ABI.** All three are what make the
  honest answer unavailable; none is in this phase's scope.
- **Resolve #9 (dispatch-lane starvation).** Still open, still accepted debt. This phase touched its
  neighbourhood and did not address it: a single-lane starvation problem is about *scheduling*, not
  about which thread a batch arrives on.
- **Close #213 item 2.** Already fixed and pinned by `AsyncFramesFaultTests`; this phase used those
  tests as its measurement instrument, nothing more.
