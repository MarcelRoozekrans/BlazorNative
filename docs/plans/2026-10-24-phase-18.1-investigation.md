## #551: `ShutdownQuiescenceTests` positive control sees no frame for 10 s (Windows ci)

### Evidence

- **Four hits, not three.** They are 39098620055, 39544377750, 39750959240 and also **39763174153**, which is
  #563's branch `feat/17.10-reaudit` at `c8e77254`. That hit is not yet on the issue.
- **Always the same fact.** It is `APendingHandler_EndsCancelled_WhenItsCallCompletesAfterShutdown_PositiveControl`,
  never its twin `NoFrameReachesTheCallback_AfterShutdownReturns_PositiveControl`, which runs the same
  `RunHeldCall(shutdown: false)`.
- **Always early in the run, and 12–16 s long.** It failed at xUnit 20.28 s, 21.44 s, 17.78 s and 29.52 s,
  taking 16 s, 15 s, 12 s and 14 s. Each fact therefore started about 4–15 s into the Runtime assembly.
  12–16 s is the 10 s `WaitUntil` plus the `finally`'s `Task.WaitAll`, which returned within about 2–6 s. So
  **the handler did complete. Everything after `CompleteHostCall` was late, not lost.**
- **Locally, four cores with coverage.** On `taskset -c 0-3`, this fact is the first `RunHeldCall` in the
  class's execution order and runs about 1–2 s into the suite. It takes 130–520 ms. Its twin, later in the run,
  takes 13 ms. On one core it runs about 13–58 s in, after the start-up burst, and takes 20 ms.
- **Instrumented locally** (scratch only; it timed `CompleteHostCall` → the first `CountFrame`, and a pool
  probe queued just before it):

  ```
  P complete->frame=35.0  poolProbe=34.1  pending=4 threads=7 busy=5
  P complete->frame=560.2 poolProbe=558.8 pending=1 threads=6 busy=5
  P complete->frame=637.3 poolProbe=636.3 pending=5 threads=6 busy=5
  P complete->frame=312.2 poolProbe=311.0 pending=4 threads=6 busy=5
  (the twin, later: complete->frame=0.1 poolProbe=0.0)
  ```

  **The frame latency equals the pool's queueing latency, to the millisecond.**
- **A heap dump at the stall** (`pool-stacks.txt`) shows six workers, all running and none idle. They are:
  1. vstest `TcpClientExtensions.MessageLoopAsync`, in `Socket.Poll`, for the whole run.
  2. xunit `VsTestRunner.RunTestsInAssembly`, in `WaitOne`, for the whole run.
  3. `HttpReferenceFixture` → `ReferenceFixtureBase..ctor` → `BoundedScript.RunBounded` →
     `Process.WaitForExit`. A class fixture runs `generate-reference.ps1` synchronously on a pool thread;
     `ReferenceDriftTests.cs:55`, bound 5 min. Five such fixtures run one after another through the first
     ~15 s.
  4. `GeneratorRunTests` → `Task.Run(() => BoundedScript.RunBounded(...))` → `Process.WaitForExit`. It holds a
     pool thread for up to its 15 s bound; `GeneratorRunTests.cs:67/150/199`. Two of its three facts run to the
     bound by design.
  5. Another test running.
  6. The positive control's own xUnit thread. xUnit 2.9 runs test bodies on pool threads; this one sits in
     `WaitUntil`'s `Thread.Sleep` loop.

### Cause

**Likely, with the mechanism confirmed.** The frame path crosses the thread pool once.
`NativeShellBridge.CompleteHostCall` → `tcs.TrySetResult`. The TCS is `RunContinuationsAsynchronously`
(`NativeShellBridge.cs:471`) and the await is `ConfigureAwait(false)` (`:504`), so `InvokeHostCallAsync`
resumes on a pool thread. Only after that is `TakePhotoAsync`'s continuation posted to the render thread. The
test process starves its own pool in the first ~15 s:

- the two permanent infrastructure blockers;
- pwsh process waits held synchronously on pool threads, in `ReferenceFixtureBase` and `GeneratorRunTests`;
- test bodies that sleep-poll on pool threads.

The pool's starvation injection adds roughly one thread per 0.5 s, and only when no progress is made, so a
queued continuation waits.

On the Windows runner every blocker is worse. Each pwsh start-up and `dotnet tool restore` takes seconds.
Three test hosts share 4 vCPUs. And, see #564, pool threads also block in `Console.Error` writes when vstest's
stderr pipe is full: the #564 dump has a pool thread blocked on the console lock in
`Exports.DeliverLateFault`. Locally this gave 35–640 ms. On CI it reached more than 10 s.

The 10 s magnitude was not reproduced on Linux. That part rests on the same mechanism with Windows-scale
blockers.

The collection is **not** the cause. `ShutdownQuiescenceTests.cs:62` and `FaultNoticeTests.cs:57` are both
`[Collection("host-session")]`, like every class that touches `HostSession`, `NativeShellBridge` or
`FakeShellHost`. There is no `xunit.runner.json` and no `CollectionBehavior`. The uncollected files that
mention the bridge only call its pure static JSON helpers. Teardown races were ruled out by the timing, and
request-id theft was ruled out as well. A stolen `LastHostCallRequestId` would leave the camera call pending,
so the `finally`'s `WaitAll` would add another 10 s, making the fact at least 20 s, not 12–16 s.

### Fix at the cause

Stop the test process from holding pool workers in synchronous waits:

- `BoundedScript.RunBounded` runs off the pool: a dedicated thread, or an async `WaitForExitAsync` plus
  async EOF waits.
- `ReferenceFixtureBase` and `ComponentReferenceFixture` become `IAsyncLifetime`, or start their script on a
  dedicated thread.
- `GeneratorRunTests` uses `TaskCreationOptions.LongRunning` or a `Thread` instead of `Task.Run`.

That removes the blockers the dump names. The #564 fix removes the console-lock blockers.

**Optional product follow-up (owner decision; file it, do not fold it in).** The bridge could stop hopping
through the pool. If it does not `ConfigureAwait(false)` on the host-call TCS, a completion posts straight to
the captured render-thread context. Then a resumed handler's frame no longer depends on pool health on
devices either.

### Pin and proof

- **Pin on the property:** `RunBounded` throws when it is called on a pool thread
  (`Assert.False(Thread.CurrentThread.IsThreadPoolThread)`). Mutation: restore `Task.Run` in
  `GeneratorRunTests` and the pin goes red.
- **Deterministic reproduction of the dependency, local on Linux:** occupy every pool worker with blocking
  waits on a gate. For example, cap the pool with `ThreadPool.SetMaxThreads` and queue `gate.Wait()` items.
  Then run `RunHeldCall(false)`. It goes red every time, and goes green on release. This shows the positive
  control fails exactly by pool starvation.
- **Measured proof of the fix, local:** run the full suite with coverage on `taskset -c 0-3`, N=20 times,
  logging the pool-probe latency at the positive control. Before the fix it is 35–640 ms; after, it should be
  about 0.
- **Final proof:** Windows ci, N green runs. The probe line in the log would show latency on the real runner.

### Local reproduction attempts

- The two classes alone, 15 runs: all green.
- Full suite with coverage on 4 cores, 6 runs, then 1 core, 3 runs: all green. The latency was measured as
  above.

## #564: a `FaultNoticeTests` dispatch misses its 1 s bound and leaks a notice (Windows ci)

### Evidence

- **Run 39764450069.** `AChildsBegunCall_DuringTheReRender_MarksTheDispatch_SoALaterRenderFaultIsRc0` failed
  `[991 ms]`: "dispatch_event for handler 15 did not return within 1s" (`FaultNoticeTests.cs:145`, from
  `:1380`). Next, `AFaultNoticeCarriesNoPayloadField` saw two notices: request 193 for handler 15, then its
  own request 194 for handler 2. That fact took only 72 ms. So **the "hung" dispatch finished about 1.0–1.07 s
  after it started. It was slow, not hung.**
- **Locally every FaultNotice dispatch takes 1–2.5 ms.** That was 102 dispatches over 3 full runs; the slowest
  was 2.5 ms.
- **The test host's stderr is a pipe to `vstest.console`.** `/proc/<testhost>/fd/2 -> pipe`, and its parent is
  vstest.console. A meter (scratch only) measured about 57 KB in 195 lines over a run, about 55 KB of it in the
  ~5 s window where the FaultNotice and late-fault classes run. On Linux the pipe holds 64 KB, so it never
  blocks. A Windows anonymous pipe made by `Process` with default size is about 4 KB, and blocks the writer
  until the reader drains it. That size is likely but not verified on the runner.
- **Reproduced locally with the exact CI signature.** `tools/squeeze.sh` runs the unmodified suite. It shrinks
  the test host's stderr pipe to 4 KiB with `F_SETPIPE_SZ` and pauses `vstest.console` with
  `SIGSTOP`/`SIGCONT` in 1.5 s bursts, emulating a lagging reader. **3 of 7 runs failed** (0 of 19 normal runs
  did):

  ```
  ACallBegunByAnInlineContinuation_DoesNotMarkTheWindow   dispatch_event for handler 6 did not return within 1s
  AChildsBegunCall_..._SoALaterRenderFaultIsRc0           Assert.Single() Failure: ... (190 handler 2), (192 handler 15)
  ABackNoticeDotNetSends_..._(back-unhandled-then-throw)  dispatch_event for handler 10 did not return within 1s
  ```

  The second line is the leak: the stuck fact's notice landed in the next fact.
- **Dump at the stall** (`disp-stacks.txt`):
  - the render thread is in `Interop.Sys.Write` ← `ConsolePal.Write` ← `StreamWriter.Flush` ←
    `SyncTextWriter.WriteLine` ← `BnLog.Write` ← `BnLog.Error` ← `NativeRenderer.HandleException` ←
    `Renderer.HandleExceptionViaErrorBoundary`;
  - the dispatch thread is in `DispatchEventCore`'s `GetResult()`, waiting for it;
  - a pool thread is in `Monitor.Enter` on the same `SyncTextWriter` from `Exports.DeliverLateFault`'s
    `BnLog.Error`.

### Cause

**Confirmed.** `BnLog.Write` (`BnLog.cs:169-173`) writes synchronously to `Console.Error` when no `Sink` is
set. Production never sets one: the shells pump stderr. `FaultNoticeTests` sets none either. The render thread
logs inside the dispatch's synchronous part (`NativeRenderer.HandleException` → `BnLog.Error`), and the
dispatch lane logs too (`Exports.cs:573/584`). So when the stderr pipe is full, the export blocks until the
reader drains it.

On the Windows runner the pipe is small and vstest.console drains it late under load. One fault burst then
stalls a dispatch past `ExportBudget`.

The same coupling exists on devices. There the stderr pump in each shell is the reader, and the render thread
can block behind it. Device pipes hold 16–64 KB, so it is rarer.

**The leak is a separate harness bug, also confirmed.** `DispatchProbe` (`FaultNoticeTests.cs:1362-1382`)
calls `DispatchBounded` before it returns `(pending, previous)`. Each caller's `try { … } finally {
TearDown(pending, previous); }` therefore starts only after a successful return (`:777-795`, `:806-819`, and
every other `DispatchProbe` caller). When `DispatchBounded` throws, nothing tears down:

- `Exports.PendingDispatchObserver` stays pointed at the dead fact's lambda;
- the session and the held calls stay alive.

The next fact's `StartSession` runs `FakeShellHost.Reset()` (which clears `HostCallLog`), then `Register`, then
`HostSession.ResetForTests()`. That reset's `renderer.Dispose()` waits, with no bound, for the stuck sync part.
Then the old dispatch returns `FaultedAfterShellCall` and `Task.Run(SendFaultNotice)` (`Exports.cs:585`) sends
its notice into the new registration and log.

### Fix at the cause

1. **Never block the caller in `BnLog` (owner decision: a Core behaviour change).** The default sink hands
   the line to a bounded queue drained by one background writer thread. On overflow it drops lines and counts
   them in a later "N lines dropped" line. It flushes at `blazornative_shutdown` and process exit.
   - This keeps the line format and the level gate.
   - It changes timing only: a line is no longer on stderr when `BnLog.Error` returns. Some tests may read
     stderr synchronously; check the `BnLogTests` and `TraceLoggingTests` sink pins.
   - The test-only alternative, a non-blocking sink for the test assembly, would hide a property production
     shares, so it is not recommended as the fix.
2. **Fix the harness leak in this change (in scope).** `DispatchProbe` tears down its own state when
   `DispatchBounded` throws: catch, `TearDown(pending, previous)`, rethrow. Better, every fact gets its pending
   list and previous observer before anything can throw, for example through a small disposable scope.
   Optionally, `StartSession` could assert that no `PendingDispatchObserver` from another fact is still
   installed, which names the leak instead of failing the next fact.

### Pin and proof

All of these are deterministic and local on Linux.

- **Cause pin.** `Console.SetError` to a writer whose `WriteLine` blocks on a gate. Dispatch the
  `child-begin-then-sibling-throw` handler. Assert that `DispatchBounded` returns within `ExportBudget`, then
  release the gate. Today it is red every time. With the non-blocking sink it is green.
  - Mutation: make the writer thread synchronous again and the pin goes red.
  - Restore `Console.Error` in a `finally`.
  - The pin needs `host-session`, because `Console` is process-global.
- **Leak pin.** Make one dispatch exceed the budget deterministically: a handler that waits on a gate in its
  synchronous part. Let `DispatchBounded` throw, release the gate, then run a normal fact. Assert that its
  `Notices()` holds only its own notice and that `PendingDispatchObserver` was restored. Red today.
- **Regression proof.** `tools/squeeze.sh` × N (≥10): 3 of 7 red today, expected 0 of N after.
- **Then Windows ci, N green runs.**

**Do not raise `ExportBudget`.** The dispatch's own work is about 2 ms. The bound caught a real blocking I/O
on the render thread.

## #453: iOS cold `LAContext()` exceeds the biometrics boot test's 30 s wait

### Evidence

From the scan of the last 40 failed `ios.yml` runs (`iosf/summary.txt`):

| Run | Date | Cold `LAContext` | Outcome |
|---|---|---|---|
| 37151841884 | 2026-10-03 | **41476 ms** | `testAuthenticateBootDeniedIsDataWithinABoundedAwaitNoHang` failed, "no reply armed … the request IS recorded" |
| 38464775031 | 2026-10-13 | **32088 ms** | same failure |
| 38620165907 | 2026-10-14 | **40889 ms** | same failure |
| 38500427251 | 2026-10-14 | 26304 ms | passed, 3.7 s inside the wait |
| 38541337756, 38955912185 | 10-14, 10-16 | 7237 ms, 5875 ms | passed |

In 12 sampled green runs, the boot tests ran about 7–16 s after "All tests started" and passed in 0.5–1 s.

### Cause

**Confirmed.** The first `LAContext()` in the process is created on `BnBiometrics.workQueue`
(`BnBiometrics.swift:252-288`). The reply is armed only after it (`awaitArmedReply`,
`BnBiometricsTests.swift:397-424`). So the first tap waits for the cold LocalAuthentication start. That start
reached 41 s, and it comes early: `ios.yml:486-495` lets `xcodebuild test` boot the simulator itself and
starts testing right away, with no `simctl boot` and no `bootstatus` wait. The biometrics suite runs within
seconds of boot.

Since the issue was filed, #453 has gone from a margin to a real red three times.

### Fix at the cause

These are the issue's two options; the choice is the owner's. The evidence favours the first.

- **(a) Warm at shell boot.** `BnBiometrics` enqueues one `makeContext()` on `workQueue` when it is created
  at runtime boot. It records completion with a `contextWarmForTest` signal or flag. Production gains: the
  first real prompt no longer pays the cold start once the app has been up for a while. The boot tests then
  wait for "warm done" as their own named step before tapping. The cold start is environmental and stays
  bounded by the step, but the failure names it and it no longer sits in the tap's 30 s.
- **(b) Settle the simulator in the lane.** `xcrun simctl boot $udid && xcrun simctl bootstatus $udid -b`
  before `xcodebuild test`. This is unverified as a cure, because coreauthd may still start lazily. Use it
  alongside (a).

### Pin and proof

- **Order pin, deterministic in the hosted XCTest.** Use the existing `contextFactoryForTest` seam to block the
  warm-up. Assert that runtime boot enqueued exactly one creation before any tap, and that the tap's
  evaluation reuses the warm queue. This works like `testHostCallBeginReturnsWhileContextCreationIsBlocked`.
- **Proof on the iOS lane only.** Run N≥10 fresh-boot runs and count `slow LAContext creation` warnings
  against the tap-to-armed latency. Today about 2–3 in 10 log a cold start above 5 s, and 3 of the last ~40
  failed runs failed on it.
- There is no local proof: Linux has no simulator.

## #444: iOS `BnNotificationsTests` show never completes Granted

### Evidence

- **Four hits.** Three from September are on the issue: 36382233615, 36174446962 and 36118597927. A fourth is
  **39793915268 on 2026-10-22**, not on the issue.
- **Two failures in the same run, twice.** In 36118597927 and 39793915268, `testShowGrantRoundTripsThroughTheRealHostCallComplete`
  also failed right after, at lines 296–299 and 297/299.
- **It is bimodal.** In 12 sampled green runs both show tests pass in 0.03–0.22 s. Failures take 10.05–10.1 s,
  the full `pollUntil`. Nothing lands in between, so **a completion is lost or held, not slow**.
- **The test just before it never fails.** `testScheduleBuildsATimeIntervalRequestFromWhen` passes in 0.05 s.
  It uses the same id `"7"` with a 1 h trigger.
- **Every show uses id 7.** That includes the demo's (`BnNotificationsDemo.cs:48 DemoId = 7`).
- **Timing.** The notifications suite started 30–75 s after "All tests started" in the failing runs, about
  the same as in green runs.
- **The logs say nothing more.** There are no UserNotifications log lines in the job output.

### Cause

**Unknown.** The show path is `runAction` → `UNUserNotificationCenter.current().add(request) { error in
complete(...) }` (`BnNotifications.swift:344-359`), and the completion is the only route to the capture.
Unverified candidates:

1. `add` of an immediate, nil-trigger request whose identifier `"7"` matches a request just added by schedule
   and removed asynchronously by `setUp`'s `clearCentre()` (`:400-404`). The XPC calls to usernotificationsd
   are asynchronous, and the request is replaced while it is still being removed.
2. usernotificationsd or SpringBoard stalled shortly after boot. An immediate request needs presentation; a
   scheduled one does not. The second show failing in the same run fits a stall that lasts more than 20 s.
3. A completion that arrives but is not Granted. Line 151 asserts
   `capturedStatuses() == [granted]`, so `[error]` or `[granted, granted]` would read as "never completed".

### What would find it

A scratch-branch diagnostic run on the iOS lane, like the #438 treatment:

1. Make the assertion print the captured statuses.
2. Timestamp the `add` call and its completion.
3. At 5 s with no completion, probe the daemon: time `getNotificationSettings` and
   `getPendingNotificationRequests`. A reply means only this request is lost; none means the daemon is stalled.
4. On failure, collect `xcrun simctl spawn booted log show --last 3m --predicate 'subsystem BEGINSWITH
   "com.apple.UserNotifications"'` as an artifact.
5. A/B the id: show with a unique id, such as 8, versus 7 after schedule.

Loop `BnNotificationsTests` with `-test-iterations 30` on a freshly booted simulator; the hit rate is low. No
fix should be written before this. No retry and no longer poll.

## #407: Android `BnCameraAndroidTest` photo never loads into BnImage within 15 s

### Evidence

Run 36124026574 (2026-09-25, pre-16.1). This is from the `instrumented-test-results` per-test logcat for
`take_photo_composes_a_captured_file_into_a_measured_bnimage`.

**The timeline:**

- 10:33:06.1: the test starts. `MainActivity@2baecf1` is RESUMED at 06.99.
- 08.96 → 09.03: `@2baecf1` goes PAUSED → STOPPED → **DESTROYED** while the test is running.
- 09.11 → 09.26: a **new** `MainActivity@7c0b1fa` goes from PRE_ON_CREATE to RESUMED.
  ActivityScenario logs "lifecycle changed event received but ignored … last known transition was DESTROYED".
- 24.48: the test fails at `BnCameraAndroidTest.kt:254`, the image poll. The echo poll at `:237` had already
  passed, before the relaunch.
- `app_time_stats: … max=14231ms count=4`: after the relaunch nothing changed on screen.

**What was happening on the emulator:**

- Heavy post-boot package churn: the full logcat counts per-minute package-change lines of 79, 296, 146, 99,
  83, 23 and 7 from 10:31 to 10:37.
- `PACKAGE_CHANGED pkg=com.google.android.gms` at 08.80.
- `SdkSandboxManager … reconcilation for io.blazornative.shell` at 08.98, then for `io.blazornative.shell.test`
  at 09.07.
- Several apps logged "Scheduling killing of process to refresh configuration".
- Earlier global config changes `80000000` (assets paths) and `20000400`.

The image is `google_apis` API 34 (`android-instrumented.yml:239-242`). The manifest declares no
`configChanges` (`AndroidManifest.xml:45-64`), and assets-path changes cannot be declared anyway.

**Other tests in that run.** The only other tests with two MainActivity instances are the ones that recreate
on purpose: `pending_permission_request_survives_activity_recreation`, and BnImage's second mount.

**No recurrence seen.** The JUnit XML of the last 20 failed `android-instrumented` runs shows no camera
failure. Those runs are mostly mutation re-reds.

### Cause

**Confirmed for this occurrence.** The emulator's post-boot package updates (GMS) change asset paths about two
minutes after boot. That relaunched MainActivity in the middle of the test. Since 17.3 (#425) a recreated
shell re-mounts its page fresh. Before 17.3, it re-mounted without the old root's state. Either way, the
demo's `_src` is component state, so the new BnImage never gets the photo, and the test waits 15 s on a page
that will not change.

Neither Coil nor the media scanner is involved: the load was never requested on the new page.

### Fix at the cause

1. **Settle the emulator in the lane before `connectedAndroidTest`.** Wait until the package manager is
   quiescent, meaning no package-change broadcasts for N seconds. Or use an image without Play updates, such as
   the `default` target, if the suite needs no GMS. Check that before switching. Or disable auto-updates and
   run `cmd package bg-dexopt-job` first. Choosing among these is a lane decision.
2. **Make the harness name a recreation.** `CameraHarness.pollTrue` fails "activity recreated mid-test" when
   the scenario's activity instance changes. `PollAndroidTest.a_poll_on_a_destroyed_activity_fails_naming_it`
   shows such a helper exists; reuse it. This makes any future hit self-diagnosing. It is not the fix.

### Pin and proof

- **Deterministic harness pin, on the Android lane.** Call `scenario.recreate()` between the tap and the image
  poll. The camera test must fail naming the recreation, not "Coil did not load".
- **Proof of the lane fix.** The logcat of N lane runs shows no package-change lines after the settle gate,
  and no foreign MainActivity instance inside a test. A grep for two PRE_ON_CREATE hashes per test logcat can
  be part of the lane.
- Android lane only. There is no local proof without an emulator.

## Appendix A: `squeeze.sh`, the #564 reproduction

```bash
#!/bin/bash
# usage: squeeze.sh <scratch> ; runs one suite with the testhost's stderr pipe shrunk to 4 KiB and
# vstest.console paused in bursts, to emulate a Windows anonymous pipe with a lagging reader.
S=$1; cd $S/inv; export PATH=$HOME/.dotnet/tools:$HOME/.dotnet:$PATH
rm -f $S/f181/disp.log $S/f181/dump2.done $S/f181/disp.dmp $S/f181/stderr-meter.log
taskset -c 0-3 dotnet test tests/BlazorNative.Runtime.Tests -c Release --no-build --nologo -v q --settings coverage.runsettings --results-directory $S/f181/sq --logger "trx;LogFileName=sq.trx" > $S/f181/sq.log 2>&1 &
for k in $(seq 1 80); do th=$(ps -eo pid,args | grep "[t]esthost.dll" | awk '{print $1}' | head -1); [ -n "$th" ] && break; sleep 0.25; done
vc=$(ps -o ppid= -p $th | tr -d ' ')
echo "testhost=$th vstest=$vc"
python3 -I -c "
import fcntl,os,sys
fd=os.open('/proc/$th/fd/2', os.O_WRONLY)
print('old', fcntl.fcntl(fd, 1032)); fcntl.fcntl(fd, 1031, 4096); print('new', fcntl.fcntl(fd, 1032))
"
end=$((SECONDS+45))
while [ $SECONDS -lt $end ] && kill -0 $th 2>/dev/null; do kill -STOP $vc; sleep 1.5; kill -CONT $vc; sleep 0.3; done
kill -CONT $vc 2>/dev/null
wait
grep -E "Passed!|Failed!|\[FAIL\]|did not return|Assert.Single" $S/f181/sq.log | head
```
