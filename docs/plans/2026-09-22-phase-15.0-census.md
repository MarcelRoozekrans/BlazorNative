# Phase 15.0 — the pin census

**Every caller of `BnRepo.Root()`, measured against `docs/pin-standard.md`.**

Milestone 15 exists because roughly two dozen drift pins accumulated with no shared standard, each
written to catch the bug in front of its author. Task 1 made the population enumerable, Task 2 gave
it one door, Task 3 wrote the rules. This is the measurement.

Its job is to size phase 15.1. A census that flatters the population plans the wrong phase; so does
one that condemns it. Every verdict below names the file, the assertion, and the reason, so a reader
can disagree with a specific judgement rather than with a mood.

---

## 2. Callers are not pins — the classification, drawn per file

Rule 6 closes with a warning this census had to act on: *"Reaching the tree does not by itself make a
test a pin. The caller list is a complete population, not a finished classification — judge per
file."* It then names two files as examples of tree-readers that are not pins.

**I read both and disagree with both, in different directions.** The disagreements are recorded here
in full, because a classification error propagates straight into 15.1's scope.

### 2.1 `TextCollapseParityDriftTests` is a pin, not golden support

The standard files it under "reads the checkout in support of golden assertions rather than to
compare two copies of one truth". It does not read the checkout in support of anything. It reads
`WidgetMapper.kt`'s `when (p.nodeType)` factory, composes it with a declared SDK inheritance table,
derives the Android shell's text-bearing node types from that, then derives the same set
*behaviourally* from `BnTestTree` by mounting a probe per node type — and asserts the two sets are
equal. That is two copies of one truth, compared. Its own header says so:

> *the fix ... did so by introducing a SECOND hard-coded list ... with nothing holding it to the
> Android shell's real behaviour ... This pin is what makes the new list a measurement instead of a
> claim.*

It is assessed as a pin below, and it scores well.

### 2.2 `BnImageDemoTests` is half a pin, and the checkout reads are the pin half

The standard's framing has this one backwards. The file's five golden and arithmetic facts never
touch the tree — they assert on `RenderFrame` patches and on `BnImageDemo`'s own constants. Every
`BnRepo.Root()` call in the file funnels through one helper, `ShellSource`, and that helper has
exactly two callers:

- `TheAndroidFixtureServer_ServesExactlyBnImageDemosNaturalPixelSizes`
- `TheIosFixtureServer_ServesExactlyBnImageDemosNaturalPixelSizes`

Those two hold **three transcriptions of four integers** — `BnImageDemo`'s constants,
`ImageFixtureServer.kt`, `BnImageFixtureServer.swift` — to one value. The file states the stakes
itself: each device suite asserts against its own fixture's decoded size, so both stay green while
measuring different images, and the phase's entire parity claim quietly becomes false.

So the checkout reads are not in support of the golden. They are the one genuine cross-shell pin in
the file. **Assessed split:** the two fixture-server facts as a pin, the other five as exempt.

### 2.3 The resulting classification

| Classification | Count | Files |
|---|---|---|
| Pin | 26 | everything except the split below |
| Mixed — pin facts plus non-pin facts | 1 | `BnImageDemoTests` — 2 pin facts, 5 exempt facts |
| Not a pin at all | **0** | — |

Every one of the 27 callers reaches the tree to compare two copies of one truth, to hold a checkout
fact against a derived one, or to enforce a property of the tree itself. The caller list and the pin
list turned out to coincide more closely than Rule 6 anticipated. That is a finding about the
standard's examples, not a licence to stop judging per file next time.

## 4. The two aggregate answers

These are the numbers 15.1 is planned against, so both are stated with the counting method attached.

### 4.1 Positive controls — the gap is real, and it is narrower than the standard expects

Rule 3 says positive controls are *"the one most existing pins fail"*. **Measured, that is not what
the population looks like.** The counting method matters, so here it is: a file has a positive
control if it contains at least one assertion requiring a detector to still hit a known fixed point.
Rule 3 lists three admissible forms and this census honours all three — a known-matching subject, a
known-mismatching subject the detector must reject, and a structural assertion about the parse. It
also honours Rule 3's own worked concession that a **positive-match pin is controlled by
construction**: *"`DeepLinkSeedDriftTests` is a positive-match pin by construction: it asserts a
match exists rather than that none does, so its detector is exercised on every run."*

| Measure | Count |
|---|---|
| Files with **no** positive control anywhere | **1** — `PinPopulationTests` |
| Files carrying **at least one uncontrolled detector** | **8** |
| **Individual detectors with no positive control** | **9** |

The nine, each named with the rewording that would send it green:

| # | File | Detector | Reword it and… |
|---|---|---|---|
| 1 | `PinPopulationTests` | `BypassMarkers` — `"BlazorNative.sln"`, `"AppContext.BaseDirectory"` | no offenders, forever. Nothing requires either marker to be found anywhere. |
| 2 | `ShellStyleTableDriftTests` | `ParseNameTable`'s `"([^"]+)"` extractor, **over-match direction** | a style name that coincides with a Yoga *value* keyword reads as a dispatch arm. Live, §5.1. |
| 3 | `ComponentReferenceDriftTests` | the nine banned prose patterns | published repo-speak passes. This file already carries the scar, §5.3. |
| 4 | `DispatchSurfaceDriftTests` | `DispatchNamedDeclaration` | zero declarations found, completeness guard green over nothing. Also has no floor, §5.2. |
| 5 | `GeneratedSymbolShadowTests` | the shadow declaration regex | a hand-written twin stops being seen; `#279` reopens silently. |
| 6 | `GeneratedSymbolShadowTests` | `\b{seam}\s*\(` for the two host-event seams | a production bypass call stops being seen. |
| 7 | `IosSliceMatrixDriftTests` | `^\s{4}(if\|continue-on-error):` | a conditioned matrix leg passes. One clause of an otherwise strongly controlled fact. |
| 8 | `PackagePurityTests` | `AppShapedTypeName` — `(Demo$)\|(Probe$)\|(^SpikeRazor)` | the *next* demo page parked in a shipped assembly passes. The 16-type roster still bites; the net does not. |
| 9 | `ReleaseWorkflowPinTests` | `VersionOverride` — `[-/]p:(Version\|PackageVersion)\s*=` | a version override in the release path passes. §5.5, and it is mislabelled. |

**Every one of the nine is an absence assertion.** That is the pattern, and it is the single most
useful thing this census found: *the population's positive-control gap is exactly its
absence-assertion surface.* A pin that asserts a match exists is controlled for free. A pin that
asserts nothing matches needs a fixed point bolted on, and nine such pins do not have one.

This reshapes 15.1. It is not "add a detector to most of twenty-seven pins". It is **nine named
detectors, each needing one fixed-point assertion**, and the fixed point is usually already sitting
in the tree — `ConsoleErrorDriftTests`, `NSLogDriftTests` and `AndroidLogDriftTests` each solved this
exact problem for the exact same assertion shape, and their solutions are copyable.

one fact, not one file.

| Severity | Count | Instances |

| **No anti-vacuity property at all** | **1 fact** | `DispatchSurfaceDriftTests.EveryDispatchNamedDeclaration_IsDeclaredOrIgnored` |
| Floor present but on the **wrong side** of the comparison | **3 facts** | all three facts of `ShellStyleTableDriftTests` |
| Floored | the remaining **109** | — |

The population holds **118** `[Fact]` and `[Theory]` methods in total: 4 with a floor problem,

**No file in the population lacks a floor entirely.** `DispatchSurfaceDriftTests`' other two facts

residual already recorded at the close of 14.1 — **still open on this branch, unchanged**.

## 5. The seven gaps, argued

### 5.1 `ShellStyleTableDriftTests` — the floor is on the wrong set, and the over-match is live

Two findings, and the second is the one to act on.

**The floor guards the wrong side.** All three facts have the shape:

```csharp
var routed = NativeRenderer.YogaStyleAttributes;
var dispatched = ParseNameTable(KotlinYogaLayout, KotlinSetStyleBody);
var missing = routed.Except(dispatched).ToList();
```

`ParseNameTable` ends with `Assert.NotEmpty(names)` — so `dispatched`, the set being *subtracted*,
is floored. `routed`, the set being *iterated*, is not. `NativeRenderer.YogaStyleAttributes` and
`VisualStyleAttributes` are built from `src/wire-vocabulary.json`; if either came back empty,
`routed.Except(dispatched)` is empty and all three facts go green over nothing.
`WireVocabularyCodegenTests.TheRenderersStyleSets_AreTheManifests` would catch the collapse
elsewhere — but that is cross-coverage, not this pin's own floor, and Rule 2 is about the assertion
shape in front of you.

**The extractor over-matches, demonstrably, today.** `ParseNameTable` collects *every* quoted string
in the function body. Extracted from `YogaLayout.setStyle` right now, alongside the real arm names,
are: `"center"`, `"flex-start"`, `"flex-end"`, `"row"`, `"row-reverse"`, `"column"`,
`"column-reverse"`, `"nowrap"`, `"absolute"`, `"relative"`, and two multi-line log message strings.
None of those is a dispatch arm; all of them are in `dispatched`.

The consequence is a false green with a concrete shape: Yoga's *value* vocabulary overlaps its
*property* vocabulary, so a style name added to the manifest that collides with a value keyword —
`gap`, `row`, `column`, `wrap`, `center` are all live candidates — would be reported as dispatched on
the strength of a `flexDirection` value literal, with no arm written. That is precisely the failure
this pin exists to catch, reachable through the pin itself.

Rule 5's test settles how seriously to take it: *"A limit that can only cost you a red is a footnote.
A limit that can hand you a green is a defect, whether or not it is written down."* This one hands
you a green, and it is not written down — the doc comment discloses that the pin proves the arm is
*written* rather than *reached*, which is a different and smaller limit.

Rule 3's second form is the fix shape: **a known-mismatching subject the detector must still reject.**

### 5.2 `DispatchSurfaceDriftTests` — the 14.1 residual, unchanged

`EveryDispatchNamedDeclaration_IsDeclaredOrIgnored` iterates
`DispatchNamedDeclarations(source)`, which is `Regex.Matches(...).Select(...).Distinct()`. If the
regex stops matching — a reformat putting a newline between the method name and its paren would do
it — the loop runs zero times and the fact passes while scanning nothing. Its two siblings in the
same file are floored; this one is not, and it has no fixed point either.

Partial mitigation, recorded so 15.1 does not over-scope: `EveryDeclaredMethod_ExistsInEveryShellItClaims`
asserts `Assert.Equal(wantKotlin, Regex.IsMatch(kotlin, $@"\bfun\s+{name}\s*\("))` over at least four
declared methods, and that cousin pattern would red under most of the same reformats. The hole is
real but narrower than it reads.

The fix is one assertion and the file's own header names the principle it violates: *"A method this
pin cannot classify ... reds loudly naming the method, rather than passing vacuously. That is the
exact failure mode #339 exposed in the first place: a pin that goes quiet on what it cannot see."*

### 5.3 `ComponentReferenceDriftTests` — a detector with a recorded scar and no control

`PublishedDocs_SpeakToConsumers_NotToTheRepo` is well floored: `members.Count > 50`,
`published.Count > 50`, and a named fixed point proving the shipped XML loaded
(`P:BlazorNative.Components.BnLayoutItem.BackgroundColor`). Those control the *walk*.

The nine banned patterns control nothing. They are asserted absent, and nothing anywhere requires any
of them to still match a real string. The file records the exact failure this invites, in its own
comment:

> *NO trailing `\b`, and that is not sloppiness — it is a correction. The phrase in the shipped XML
> was "the BnDemo goldens stay byte-identical", and `/\bgolden\b/` does NOT match "goldens" ... The
> mutation caught 3 of 4 patterns and this was the miss.*

A detector that failed to match its subject, found by mutation, in this file, on this assertion. The
scar is attached; the control is not.

Everything else in the file conforms, including a genuinely measured floor
(`parameters.Count > 60`, measured at 74 with the reasoning for the number written out).

### 5.4 `GeneratedSymbolShadowTests` — excellent floors, two uncontrolled absence detectors

`GeneratedSymbolFloor = 14` is a model floor: measured, itemised as 5 Swift plus 6 Kotlin plus 3 C,
asserted inside the one helper both pins iterate, with an explicit note that a silent parse failure
would green *both*. `EveryGeneratedSymbol_IsConsumed_OrAllowlistedWithAReason` is positive-match and
therefore controlled.

Two detectors are not:

- **the shadow declaration regex.** The pin asserts no hand-written declaration of a generated symbol
  exists outside a forwarding window. Nothing asserts the declaration regex still matches a known
  declaration — and the natural fixed point exists in the tree already, since
  `BnFrameAdapter.swift`'s `static let nodeTypes = BnWireVocabulary.nodeTypes` must be *matched as a
  declaration and then exempted by the forwarding window*. Nothing asserts either half fired. That is
  also a Rule 7 concern: the suppression branch is the forwarding window, and no assertion proves
  anything ever enters it.
- **the host-event seam call pattern.** `NoProductionShellSource_CallsTheHostEventSeamsDirectly`
  floors the walk (`sources.Length > 0`) but nothing requires `\bdispatchHostEventUnchecked\s*\(` to
  still match anywhere. The seam's legitimate call sites are in test source sets the pin excludes
  by design, so the fixed point would have to be built rather than borrowed.

### 5.5 `ReleaseWorkflowPinTests` — one fact controlled, one mislabelled

`TheNugetApiKey_IsReferencedExactlyOnce_AndOnlyInReleasePleaseYml` is among the best-controlled
assertions in the population: `total == 1` means a reworded `NugetApiKeyReference` yields zero
matches and **reds**. An exact-count structural assertion is Rule 3's third form, exactly.

`TheReleaseWorkflow_NeverOverridesTheVersion` is not, and it says it is. The assertion labelled
**"THE POSITIVE CONTROL, first"** is:

```csharp
Assert.True(source.Contains("dotnet nuget push", StringComparison.Ordinal), …);
```

That proves the *subject* is still the release path. It proves nothing about the `VersionOverride`
regex, which is the detector. Measured against Rule 3's definition — *a fixed point that the detector
is required to hit* — it is a Rule 4 subject-moved guard wearing Rule 3's name.

**This mislabel is why it is called out rather than folded into the list.** A 15.1 sweep that greps
for the phrase "positive control" to find what is already covered will score this file as done. It is
not. Whatever mechanism 15.1 uses to find the nine detectors in §4.1 must read the assertion, not
the comment above it.

### 5.6 `PinPopulationTests` — no control, and its own limit is not where the standard says it is

Two findings on the mechanism that makes the population enumerable at all.

**No positive control, and the natural fixed point is excluded by name.** The pin asserts an empty
offender list. Nothing requires either `BypassMarkers` entry to be found anywhere — so a mistyped
marker, or a `CommentStrippedSource` change that strips too aggressively, leaves it green forever.
The standard is candid about the floor's scope: *"including its author's own floor of 100 — proves
only the walk."*

The sharp part is where the obvious fixed point went. `tests/Shared/BnRepo.cs` contains **both**
markers in live code — it is the one permitted implementation of the walk — and it is one of the two
files the pin skips by name. **The one file guaranteed to hold the detector's subject is the one file
the detector never reads.** That is not an argument for removing the exclusion; `BnRepo.cs` must stay
exempt from the offender check. It is an argument that the exemption and the control are two
different jobs, and only one of them was done — which is `NSLogDriftTests`' whole design, in reverse:
*"The exempt test bundle is the fixed point that proves the detector detects."*

**Rule 5's disclosure is not at the pin.** Rule 5 states the limit and then asserts where it lives:
*"That is written down where the pin is, with a worked demonstration, rather than inferred."*
Grepping `PinPopulationTests.cs` for `adversarial`, `concatenat`, `determined`, `limit`, `does not
cover` and `cannot see` returns **nothing**. The file's header covers the definition of a pin, why
the scan runs over stripped code, and the two by-name exclusions. The accidental-versus-determined
boundary and the string-concatenation bypass are disclosed only in `docs/pin-standard.md`. The
standard's claim about its own sibling is false on this branch. Cheap to fix; worth fixing, because
Rule 5 is specifically about a reader finding the limit where they find the guard.

### 5.7 `BnSafeAreaCoverageTests` — a disclosed limit that fails green

The smallest gap in the list, included because Rule 5's test is about direction rather than size.

The pin greps five named files for the literal `"BnSafeArea"`. Its floor is structural and sound — a
literal five-row `TheoryData`, each row asserting `File.Exists` before the content check — and the
assertion is positive-match, so the detector is controlled. It discloses its limit honestly:

> *It cannot tell an active wrap from a wrap sitting inside a `@* comment *@` — that is a real, small
> gap.*

But trace the direction. Delete the wrap and the file stops containing the string: **red**, correct.
Comment the wrap out and the file still contains the string: **green**, while the page renders under
the notch — which is `#338` restored. Rule 5: *"A limit that can only cost you a red is a footnote. A
limit that can hand you a green is a defect, whether or not it is written down."*

Eight sibling pins route their scans through `CommentStrippedSource` for exactly this reason. This
one does not — and cannot directly, since the shared stripper handles C#, Kotlin and Swift comments,
not Razor's `@* *@`. That makes it a small piece of real work rather than a one-line reuse, and
sizing it that way is the point of saying so here.

## 6. Things that are not verdicts

### 6.1 The enforcement blind spot, named as the brief asks

`PinPopulationTests` excludes two files **by name, never by pattern**:

```csharp
if (name == "BnRepo.cs" || name == "PinPopulationTests.cs") continue;
```

Both exclusions are correct and neither should be removed. `BnRepo.cs` is the one permitted
implementation of the walk; `PinPopulationTests.cs` is where the markers are declared, and nothing
can scan for a string it is forbidden to contain.

**The blind spot is what follows from them: a bypass written inside either file is invisible to
enforcement.** Concretely, and in rising order of plausibility:

1. A test class declared *inside* `PinPopulationTests.cs` could walk to `BlazorNative.sln` by hand and
   never be seen. Implausible, but it is the exclusion read literally.
2. **`BnRepo.cs` could grow a second walk.** This is the one that matters. `BnRepo.Root()` and
   `BnRepo.TestBinaryDirectory()` already coexist there — deliberately, and the second one's doc
   comment explains that routing `PackagePurityTests`' legitimate `AppContext.BaseDirectory` use
   through the helper is what kept the marker list at its original width. A third method, added the
   same way, with a slightly different sentinel or a slightly different climb, would be **two copies
   of one truth inside the file whose entire purpose is that there be one** — Rule 8's
   twin-divergence precondition, sitting inside the mechanism built to prevent it, in the one
   location no scan reads.

Nothing currently guards that. `BnRepo.cs` is 51 lines and reviewed by eye. 15.1 should decide
whether that is sufficient and write the answer down either way; the census's job is to make sure
nobody discovers the exclusion by surprise.

### 6.2 What "conforms" does and does not claim

It claims the file satisfies Rules 2 through 6 as far as reading the source can establish. It does
**not** claim Rule 7 — *its mutations must exercise the pin's own code paths* — which is a property of
work that was done, not of code that can be read. Several files record their mutation history
(`PackageVersionPinTests`' Gate B, `ComponentReferenceDriftTests`' four-pattern mutation,
`ReleaseWorkflowPinTests`' first-run red on a YAML comment). Many do not. **No Rule 7 column appears
in the scorecard because this census cannot honestly fill one in**, and a column of guesses would be
worse than its absence. If 15.1 wants Rule 7 coverage measured, that is a separate exercise with a
test runner attached.

### 6.3 One needs-mutation sub-finding

**`PackagePurityTests.ResolveAssemblyPath` — a possible stale-build-output channel.**

When an assembly is not beside the test binary, the pin resolves it from the checkout:
`src/<name>/bin/<config>/<tfm>/<name>.dll`. That is whatever was last built there, and it can be
arbitrarily old. `File.Exists` reds when the file is *absent*; nothing reds when it is *stale*.

The failure shape, if it is reachable: a demo page added to `BlazorNative.Analyzers` today would not
appear in a dll built last month, so `TheMovedRoster_IsAbsentFromEveryShippedAssembly` and
`NoAppShapedTypeName_InAnyShippedAssembly` would pass over old metadata. Whether it is reachable
depends on CI's build ordering and on whether `build-test` guarantees a fresh build of the Analyzers
project before the suite runs — **runtime state this census cannot evaluate by reading**, which is
exactly the condition the brief says to mark rather than guess at.

Marked `needs-mutation`. The experiment is cheap: build, edit a type name in the Analyzers source,
run the suite without rebuilding that project, and see whether the pin notices.

### 6.4 Three smaller observations, recorded so they are not rediscovered

- **`AnalyzerHelpLinkDriftTests`' heading floor is not measured.** `anchors.Count > 5` runs against
  a page with 9 headings outside code fences. It clears at 67% of its subject, and Rule 2's corollary
  asks for *a measured floor with stated headroom*. It is not theatre the way `>= 20` against 131
  was, and the fact's main assertion is positive-match and therefore controlled — but the number came
  from nowhere in particular, and the corollary exists because such numbers get argued down.
- **`RouteTableDriftTests` carries an explicit negative control** and almost nothing else in the
  population does. `TheDuplicateRouteFixture_IsOtherwiseValid` exists solely so the
  duplicate-refusal test cannot be satisfied by `Extract` throwing on every input. It is Rule 3's
  second form, built deliberately, and it is the pattern §5.1 needs.
- **`WireVocabularyCodegenTests` has the population's best malformed-input coverage** — three
  distinct bad manifests, each asserting a specific message substring, which is a mutation set
  committed as tests. It is the closest thing in the repo to Rule 7 discharged in-tree, and it is
  worth copying rather than admiring.
