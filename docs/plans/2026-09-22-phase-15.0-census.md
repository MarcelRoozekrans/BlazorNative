# Phase 15.0 — the pin census

**Every caller of `BnRepo.Root()`, measured against `docs/pin-standard.md`.**

Milestone 15 exists because roughly two dozen drift pins accumulated with no shared standard, each
written to catch the bug in front of its author. Task 1 made the population enumerable, Task 2 gave
it one door, Task 3 wrote the rules. This is the measurement.

Its job is to size phase 15.1. A census that flatters the population plans the wrong phase; so does
one that condemns it. Every verdict below names the file, the fact, the assertion, and the reason,
so a reader can disagree with a specific judgement rather than with a mood.

---

## 0. The unit of classification is the fact, not the file

**Read this before the tables, because every number below is counted per fact.**

Rule 6 states the principle and `BnImageDemoTests` is its proof: five of that file's seven facts
never touch the checkout, and exactly two do. A single verdict on that file would be a lie in one
direction or the other.

So:

- **The population is enumerated by file** — `grep -rl "BnRepo.Root()"` is what makes it
  mechanically enumerable at all, and a helper called from a fixture puts the whole file on the
  list. That is Rule 6 working as designed.
- **The population is judged by fact.** A file appears in the scorecard as one row when all of its
  facts agree, and as several rows when they do not.
- **A single-verdict file is one whose facts agree** — it is not a file that was judged in bulk.

Two kinds of disagreement turned up, and they are different:

| Kind | Meaning | Count |
|---|---|---|
| **Mixed by kind** | the file holds both tree-reading facts and facts that never touch the checkout | **5 files** |
| **Mixed by verdict** | every fact reads the tree, but their verdicts differ | **3 files** |
| Single verdict | all facts agree | 19 files |

**8 of 27 files are mixed.** That is a minority, which is why the per-fact pass is a correction
rather than a re-census: nineteen files keep the verdict and the single row they already had.

## 2. Which facts are pins

### 2.1 The test applied

Rule 1: *a pin is a test that reads the repository tree at runtime and asserts on its contents.*
Applied per fact, that excludes three shapes that appear inside population files:

- **facts asserting over build output.** Reading `BlazorNative.Components.xml` from
  `Path.GetDirectoryName(assembly.Location)`, or type names off a `.dll`, is not reading the
  repository tree. Rule 6 draws this line itself when it explains why `BnRepo.TestBinaryDirectory()`
  exists: *"`PackagePurityTests` genuinely needed its own build output rather than the repo tree"* —
  a different job, named separately, on purpose.
- **facts asserting over in-process state.** A baseline held against `SampleAppPages.All` is a
  content pin, but it is not a *tree* pin.
- **facts over a fixture the test writes itself.** A temp file created, fed to a parser, and deleted
  is a unit test of the parser.

A fact stays a pin when the checkout read is load-bearing even though it is mediated. The reference
fixtures run `scripts/generate-reference.ps1` **from the checkout** precisely so the pin cannot drift
from the lane — the file says a pin that re-implemented publish and generate *"could pass forever
while the lane pointed at bin/"*. The tree read is the point, so those facts are pins.

### 2.2 Two corrections to Rule 6's examples, now folded into the standard

Recorded here because they are what produced the per-fact unit.

**`TextCollapseParityDriftTests` is a pin, not golden support.** All four of its facts read
`WidgetMapper.kt` or `BnWidgetMapper.swift` and hold them against a behaviourally-derived harness
set. Its own header: *"This pin is what makes the new list a measurement instead of a claim."*

**`BnImageDemoTests` is half a pin, and the checkout reads are the pin half.** Its golden and
arithmetic facts never touch the tree. Every `BnRepo.Root()` call funnels through one helper,
`ShellSource`, whose only two callers hold **three transcriptions of four integers** —
`BnImageDemo`'s constants, `ImageFixtureServer.kt`, `BnImageFixtureServer.swift` — to one value.

## 4. The two aggregate answers

Both are stated with the counting method attached, because both are what 15.1 is planned against.

### 4.1 Positive controls — the gap is real, narrower than the standard expects, and one shape

Rule 3 says positive controls are *"the one most existing pins fail"*. **Measured, that is not what
the population looks like.** A fact has a positive control if it contains an assertion requiring a
detector to still hit a known fixed point. Rule 3 lists three admissible forms and this census
honours all three, plus Rule 3's own concession that a **positive-match pin is controlled by
construction**: *"`DeepLinkSeedDriftTests` is a positive-match pin by construction: it asserts a
match exists rather than that none does, so its detector is exercised on every run."*

| Measure | Count |
|---|---|
| Files with **no** positive control anywhere | **1** — `PinPopulationTests` |
| **Uncontrolled detectors, total** | **9** |
| …**sitting in a pin fact** | **7**, across **6** files |
| …sitting in a non-pin fact in a population file | **2** |

All nine, with the rewording that would send each one green:

| # | File · fact | Detector | Reword it and… | In a pin fact? |
|---|---|---|---|---|
| 1 | `PinPopulationTests` · the one fact | `BypassMarkers` | no offenders, forever. Nothing requires either marker to be found anywhere. | **yes** |
| 2 | `ShellStyleTableDriftTests` · all 3 | the quoted-name extractor, **over-match direction** | a style name coinciding with a Yoga *value* keyword reads as a dispatch arm. Live, §5.1. | **yes** |
| 3 | `DispatchSurfaceDriftTests` · `EveryDispatchNamedDeclaration…` | `DispatchNamedDeclaration` | zero declarations found, completeness guard green over nothing. §5.2. | **yes** |
| 4 | `GeneratedSymbolShadowTests` · `NoGeneratedSymbol_IsShadowed…` | the shadow declaration regex | a hand-written twin stops being seen; `#279` reopens silently. | **yes** |
| 5 | `GeneratedSymbolShadowTests` · `NoProductionShellSource…` | the seam call-site pattern | a production bypass call stops being seen. | **yes** |
| 6 | `IosSliceMatrixDriftTests` · the one fact | the job-level `if` / `continue-on-error` pattern | a conditioned matrix leg passes. One clause of an otherwise strongly controlled fact. | **yes** |
| 7 | `ReleaseWorkflowPinTests` · `TheReleaseWorkflow_NeverOverrides…` | `VersionOverride` | a version override in the release path passes. §5.5, and it is mislabelled. | **yes** |
| 8 | `ComponentReferenceDriftTests` · `PublishedDocs_SpeakToConsumers…` | the nine banned prose patterns | published repo-speak passes. The file carries the scar, §5.3. | no |
| 9 | `PackagePurityTests` · `NoAppShapedTypeName…` | `AppShapedTypeName` | the *next* demo page parked in a shipped assembly passes. | no |

**Every one of the nine is an absence assertion.** That is the finding: *the population's
positive-control gap is exactly its absence-assertion surface.* A pin that asserts a match exists is
controlled for free. A pin that asserts nothing matches needs a fixed point bolted on, and nine such
assertions do not have one.

**All nine are worth closing** — the last two are not pins, but an uncontrolled detector is a
liability regardless of which population it sits in, and both live in files 15.1 will already have
open. What the classification buys is that 15.1 knows which two are outside the pin standard's
remit and should not be scoped as drift-pin work.

This reshapes the phase. It is not "add a detector to most of twenty-seven pins". It is **nine
fixed-point assertions**, six of them copyable from `ConsoleErrorDriftTests`, `NSLogDriftTests` and
`AndroidLogDriftTests`, which solved this exact problem for this exact assertion shape.

### 4.2 Anti-vacuity — four facts, and the "nothing at all" claim was too strong

**This number moved, and the per-fact pass is what moved it.** See §8.

| Severity | Facts | Instances |
|---|---|---|
| **Can pass while scanning nothing** | **4** | 3 in `ShellStyleTableDriftTests`, 1 in `DispatchSurfaceDriftTests` |
| …executing **no** anti-vacuity assertion at all | **0** | — |
| Floored on the set they iterate | 98 | the rest of the pin facts |

All four have the same shape, and it is not "no floor" — it is **a floor on the wrong side of the
comparison**:

- `ShellStyleTableDriftTests` floors `dispatched`, the set being *subtracted*, and leaves `routed`,
  the set being *iterated*, unfloored.
- `DispatchSurfaceDriftTests.EveryDispatchNamedDeclaration_IsDeclaredOrIgnored` calls `Surface()`,
  which does assert `methods.Count >= 4` — so an anti-vacuity assertion genuinely executes inside
  that fact. It guards the **manifest**, not the **scan**. The scanned set, the `dispatch`-prefixed
  declarations in the two runtime sources, has no floor, so the `foreach` can run zero times with
  the assertion above it satisfied.

The actionable finding is unchanged: four facts can go green over nothing, and the fix is a floor on
the iterated set. Only the label moved, and it moved toward a sharper description of the defect.

## 5. The gaps, argued

### 5.1 `ShellStyleTableDriftTests` — the floor is on the wrong set, and the over-match is live

All three facts, same two findings. The second is the one to act on.

**The floor guards the wrong side.** Every fact has the shape:

```csharp
var routed = NativeRenderer.YogaStyleAttributes;
var dispatched = ParseNameTable(KotlinYogaLayout, KotlinSetStyleBody);
var missing = routed.Except(dispatched).ToList();
```

`ParseNameTable` ends with `Assert.NotEmpty(names)`, so the *subtracted* set is floored. `routed`,
the *iterated* set, is not. `NativeRenderer.YogaStyleAttributes` and `VisualStyleAttributes` are
built from `src/wire-vocabulary.json`; if either came back empty, `routed.Except(dispatched)` is
empty and all three facts go green over nothing.
`WireVocabularyCodegenTests.TheRenderersStyleSets_AreTheManifests` would catch the collapse
elsewhere — but that is cross-coverage, not this pin's own floor, and Rule 2 is about the assertion
shape in front of you.

**The extractor over-matches, demonstrably, today.** `ParseNameTable` collects *every* quoted string
in the function body. Extracted from `YogaLayout.setStyle` right now, alongside the real arm names,
are `"center"`, `"flex-start"`, `"flex-end"`, `"row"`, `"row-reverse"`, `"column"`,
`"column-reverse"`, `"nowrap"`, `"absolute"`, `"relative"` and two multi-line log message strings.
None is a dispatch arm; all are in `dispatched`.

The consequence has a concrete shape. Yoga's *value* vocabulary overlaps its *property* vocabulary,
so a manifest name colliding with a value keyword — `gap`, `row`, `column`, `wrap`, `center` are all
live candidates — would read as dispatched on the strength of a `flexDirection` value literal, with
no arm written. That is precisely the failure this pin exists to catch, reachable through the pin
itself.

Rule 5 settles how seriously to take it: *"A limit that can only cost you a red is a footnote. A
limit that can hand you a green is a defect, whether or not it is written down."* This one hands you
a green, and it is not written down — the doc comment discloses a different and smaller limit, that
the pin proves the arm is *written* rather than *reached*.

Rule 3's second form is the fix shape: **a known-mismatching subject the detector must still
reject.** `RouteTableDriftTests.TheDuplicateRouteFixture_IsOtherwiseValid` is the worked example
already in the tree.

### 5.2 `DispatchSurfaceDriftTests` — one fact of three, the 14.1 residual, unchanged

`EveryDispatchNamedDeclaration_IsDeclaredOrIgnored` iterates `DispatchNamedDeclarations(source)`,
which is a `Regex.Matches` projection. If the regex stops matching — a reformat putting a newline
between the method name and its paren would do it — the loop runs zero times and the fact passes
while scanning nothing. The `Surface()` floor it inherits guards the manifest, not the scan; see
§4.2.

Its two siblings conform and keep their verdict. **This is a mixed-by-verdict file: two facts good,
one bare.**

Partial mitigation, recorded so 15.1 does not over-scope:
`EveryDeclaredMethod_ExistsInEveryShellItClaims` asserts a per-method `Regex.IsMatch` equality over
at least four declared methods, and that cousin pattern would red under most of the same reformats.
The hole is real but narrower than it reads.

The file's own header names the principle the bare fact violates: *"A method this pin cannot
classify ... reds loudly naming the method, rather than passing vacuously. That is the exact failure
mode #339 exposed in the first place: a pin that goes quiet on what it cannot see."*

### 5.3 The two uncontrolled detectors that turned out not to be in pins

**`ComponentReferenceDriftTests` is no longer a gap, and the reason is structural rather than
exculpatory.** Its two generated-reference facts — the ones whose checkout read is load-bearing —
are well floored and controlled by named fixed points: `BnView`, `BnText` and `BnButton` must be
among the reflected components, and the generated page set is compared both directions. They
conform.

The uncontrolled detector is the nine banned prose patterns in
`PublishedDocs_SpeakToConsumers_NotToTheRepo`, which reads the XML beside the **test binary** and
never touches the checkout. That fact is well floored for what it is — `members.Count > 50`,
`published.Count > 50`, and a named fixed point proving the XML loaded — but the nine patterns
control nothing. The file records the exact failure this invites, in its own comment:

> *NO trailing `\b`, and that is not sloppiness — it is a correction. The phrase in the shipped XML
> was "the BnDemo goldens stay byte-identical", and `/\bgolden\b/` does NOT match "goldens" ... The
> mutation caught 3 of 4 patterns and this was the miss.*

A detector that failed to match its subject, found by mutation, on this assertion. The scar is
attached; the control is not. **Still worth fixing — just not as drift-pin work.**

**`PackagePurityTests` is likewise clean on its pin half.** Its three shipped-set facts —
`TheShippedSet_IsExactlyTheSrcCsprojs`, `TheConsumerSmokeScript_PacksExactlyTheShippedSet`,
`TheConsumerSmokeProject_ReferencesExactlyTheShippedSet` — read the checkout, compare sets both
directions against an enumeration of `src/`, and floor every parse. They conform with no
sub-finding. The uncontrolled `AppShapedTypeName` pattern net lives in
`NoAppShapedTypeName_InAnyShippedAssembly`, a PE-metadata fact.

### 5.4 `GeneratedSymbolShadowTests` — excellent floors, two uncontrolled absence detectors

`GeneratedSymbolFloor = 14` is a model floor: measured, itemised as 5 Swift plus 6 Kotlin plus 3 C,
asserted inside the one helper both shadow pins iterate, with an explicit note that a silent parse
failure would green *both*.

`EveryGeneratedSymbol_IsConsumed_OrAllowlistedWithAReason` is positive-match and therefore
controlled — it **conforms**, and keeps that verdict. The other two do not:

- **`NoGeneratedSymbol_IsShadowedByAHandWrittenDeclaration`.** Nothing asserts the declaration regex
  still matches a known declaration — and the fixed point exists in the tree already, since
  `BnFrameAdapter.swift`'s forwarding declaration of `nodeTypes` must be *matched as a declaration
  and then exempted by the forwarding window*. Nothing asserts either half fired. That is also a
  Rule 7 concern: the forwarding window is the suppression branch, and no assertion proves anything
  ever enters it.
- **`NoProductionShellSource_CallsTheHostEventSeamsDirectly`.** Floors the walk
  (`sources.Length > 0`) but nothing requires the seam call-site pattern to still match anywhere.
  The seam's legitimate call sites are in test source sets the pin excludes by design, so the fixed
  point would have to be built rather than borrowed.

### 5.5 `ReleaseWorkflowPinTests` — one fact controlled, one mislabelled

`TheNugetApiKey_IsReferencedExactlyOnce_AndOnlyInReleasePleaseYml` is among the best-controlled
assertions in the population: `total == 1` means a reworded `NugetApiKeyReference` yields zero
matches and **reds**. An exact-count structural assertion is Rule 3's third form, exactly. It
**conforms**.

`TheReleaseWorkflow_NeverOverridesTheVersion` does not, and it says it does. The assertion labelled
**"THE POSITIVE CONTROL, first"** is:

```csharp
Assert.True(source.Contains("dotnet nuget push", StringComparison.Ordinal), …);
```

That proves the *subject* is still the release path. It proves nothing about the `VersionOverride`
regex, which is the detector. Measured against Rule 3's definition — *a fixed point the detector is
required to hit* — it is a Rule 4 subject-moved guard wearing Rule 3's name.

**This mislabel is why it is called out rather than folded into the list.** A 15.1 sweep that greps
for the phrase "positive control" to find what is already covered will score this fact as done. It
is not. Whatever mechanism 15.1 uses to find the other detectors must read the assertion, not the
comment above it.

### 5.6 `PinPopulationTests` — no control, and its own limit is not where the standard says it is

Two findings on the mechanism that makes the population enumerable at all.

**No positive control, and the natural fixed point is excluded by name.** The pin asserts an empty
offender list. Nothing requires either `BypassMarkers` entry to be found anywhere — so a mistyped
marker, or a `CommentStrippedSource` change that strips too aggressively, leaves it green forever.
The standard is candid about the floor's scope: *"including its author's own floor of 100 — proves
only the walk."*

The sharp part is where the obvious fixed point went. `tests/Shared/BnRepo.cs` contains **both**
markers in live code — it is the one permitted implementation of the walk — and it is one of the two
files the pin skips by name. **The one file guaranteed to hold the detector's subject is the one
file the detector never reads.** That is not an argument for removing the exclusion; `BnRepo.cs`
must stay exempt from the offender check. It is an argument that the exemption and the control are
two different jobs, and only one was done — which is `NSLogDriftTests`' whole design, in reverse:
*"The exempt test bundle is the fixed point that proves the detector detects."*

**Rule 5's disclosure is not at the pin.** Rule 5 states the limit and asserts where it lives: *"That
is written down where the pin is, with a worked demonstration, rather than inferred."* Grepping
`PinPopulationTests.cs` for `adversarial`, `concatenat`, `determined`, `limit`, `does not cover` and
`cannot see` returns **nothing**. The file's header covers the definition of a pin, why the scan runs
over stripped code, and the two by-name exclusions. The accidental-versus-determined boundary and
the string-concatenation bypass are disclosed only in `docs/pin-standard.md`. Cheap to fix; worth
fixing, because Rule 5 is specifically about a reader finding the limit where they find the guard.

### 5.7 `BnSafeAreaCoverageTests` — a disclosed limit that fails green

The smallest gap, included because Rule 5's test is about direction rather than size.

The pin greps five named files for the literal `"BnSafeArea"`. Its floor is structural and sound — a
literal five-row `TheoryData`, each row asserting `File.Exists` before the content check — and the
assertion is positive-match, so the detector is controlled. It discloses its limit honestly:

> *It cannot tell an active wrap from a wrap sitting inside a `@* comment *@` — that is a real, small
> gap.*

But trace the direction. Delete the wrap and the file stops containing the string: **red**, correct.
Comment the wrap out and the file still contains the string: **green**, while the page renders under
the notch — which is `#338` restored. Rule 5: *"A limit that can only cost you a red is a footnote.
A limit that can hand you a green is a defect, whether or not it is written down."*

Eight sibling pins route their scans through `CommentStrippedSource` for exactly this reason. This
one does not — and cannot directly, since the shared stripper handles C#, Kotlin and Swift comments,
not Razor's `@* *@`. That makes it a small piece of real work rather than a one-line reuse, and
sizing it that way is the point of saying so.

## 6. Things that are not verdicts

### 6.1 The enforcement blind spot

`PinPopulationTests` excludes two files **by name, never by pattern**:

```csharp
if (name == "BnRepo.cs" || name == "PinPopulationTests.cs") continue;
```

Both exclusions are correct and neither should be removed. `BnRepo.cs` is the one permitted
implementation of the walk; `PinPopulationTests.cs` is where the markers are declared, and nothing
can scan for a string it is forbidden to contain.

**The blind spot is what follows: a bypass written inside either file is invisible to enforcement.**
In rising order of plausibility:

1. A test class declared *inside* `PinPopulationTests.cs` could walk to the solution file by hand
   and never be seen. Implausible, but it is the exclusion read literally.
2. **`BnRepo.cs` could grow a second walk.** This is the one that matters. `BnRepo.Root()` and
   `BnRepo.TestBinaryDirectory()` already coexist there — deliberately, and the second one's doc
   comment explains that routing `PackagePurityTests`' legitimate base-directory use through the
   helper is what kept the marker list at its original width. A third method added the same way,
   with a slightly different sentinel or climb, would be **two copies of one truth inside the file
   whose entire purpose is that there be one** — Rule 8's twin-divergence precondition, sitting
   inside the mechanism built to prevent it, in the one location no scan reads.

Nothing currently guards that. `BnRepo.cs` is 51 lines and reviewed by eye. 15.1 should decide
whether that is sufficient and write the answer down either way; the census's job is to make sure
nobody discovers the exclusion by surprise.

### 6.2 What "conforms" does and does not claim

It claims the fact satisfies Rules 2 through 6 as far as reading the source can establish. It does
**not** claim Rule 7 — *its mutations must exercise the pin's own code paths* — which is a property
of work performed, not of code that can be read. Several files record their mutation history
(`PackageVersionPinTests`' Gate B, `ComponentReferenceDriftTests`' four-pattern mutation,
`ReleaseWorkflowPinTests`' first-run red on a YAML comment). Many do not. **No Rule 7 column appears
because this census cannot honestly fill one in**, and a column of guesses would be worse than its
absence. If 15.1 wants Rule 7 measured, that is a separate exercise with a test runner attached.

### 6.3 One needs-mutation sub-finding, and it sits in a non-pin fact

**`PackagePurityTests.ResolveAssemblyPath` — a possible stale-build-output channel.**

When an assembly is not beside the test binary, the pin resolves it from the checkout's own build
output directory. That is whatever was last built there, and it can be arbitrarily old.
`File.Exists` reds when the file is *absent*; nothing reds when it is *stale*.

If reachable: a demo page added to `BlazorNative.Analyzers` today would not appear in a dll built
last month, so `TheMovedRoster_IsAbsentFromEveryShippedAssembly` and
`NoAppShapedTypeName_InAnyShippedAssembly` would pass over old metadata. Whether it is reachable
depends on CI build ordering and on whether `build-test` guarantees a fresh build of the Analyzers
project — **runtime state this census cannot evaluate by reading**, which is the condition the brief
says to mark rather than guess at.

**Both affected facts are the PE-metadata ones, so this lands outside the pin population.** The
file's three pin facts do not call `TypeNamesOf` at all. Marked `needs-mutation` regardless; the
experiment is cheap: build, edit a type name in the Analyzers source, run the suite without
rebuilding that project, see whether the pin notices.

### 6.4 Three smaller observations

- **`AnalyzerHelpLinkDriftTests`' heading floor is not measured.** `anchors.Count > 5` runs against a
  page with 9 headings outside code fences. It clears at 67% of its subject, and Rule 2's corollary
  asks for *a measured floor with stated headroom*. Not theatre the way `>= 20` against 131 was, and
  the fact's main assertion is positive-match and therefore controlled — but the number came from
  nowhere in particular, and the corollary exists because such numbers get argued down.
- **The population's two best negative controls both sit in non-pin facts.**
  `RouteTableDriftTests.TheDuplicateRouteFixture_IsOtherwiseValid` exists solely so the
  duplicate-refusal test cannot be satisfied by the extractor throwing on every input, and
  `WireVocabularyCodegenTests`' two malformed-manifest facts drive the validator over three bad
  shapes asserting specific message substrings. Both are Rule 3's second form, built deliberately,
  and both are the pattern §5.1 needs — **so the model for the hardest fix in 15.1 is already in the
  tree, just outside the pin population.**
- **`WireVocabularyCodegenTests`' nine pin facts are controlled on their own**, independently of
  those two: exact ordered host-event list, exact reserved list, byte comparisons behind measured
  floors, `Contains` assertions on emitted enum text. Reclassifying the validator pair costs the
  file nothing.
