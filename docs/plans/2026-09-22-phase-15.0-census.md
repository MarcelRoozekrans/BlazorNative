# Phase 15.0 — the pin census

**Every caller of `BnRepo.Root()`, measured against `docs/pin-standard.md`.**

Milestone 15 exists because roughly two dozen drift pins accumulated with no shared standard, each
written to catch the bug in front of its author. Task 1 made the population enumerable, Task 2 gave
it one door, Task 3 wrote the rules. This is the measurement.

Its job is to size phase 15.1. A census that flatters the population plans the wrong phase; so does
one that condemns it. Every verdict below names the file, the fact, the assertion, and the reason,
so a reader can disagree with a specific judgement rather than with a mood.

---

## 0. The unit of classification is the fact, not the file

**Read this before the tables, because every number below is counted per fact.**

Rule 6 states the principle and `BnImageDemoTests` is its proof: five of that file's seven facts
never touch the checkout, and exactly two do. A single verdict on that file would be a lie in one
direction or the other.

So:

- **The population is enumerated by file** — `grep -rl "BnRepo.Root()"` is what makes it
  mechanically enumerable at all, and a helper called from a fixture puts the whole file on the
  list. That is Rule 6 working as designed. **Since 15.2 the key to run is
  `grep -rlE "BnRepo\.Root\(\)|ShellSourceScan\."`** — see the widening note in §1; the
  original spelling now loses a pin.
- **The population is judged by fact.** A file appears in the scorecard as one row when all of its
  facts agree, and as several rows when they do not.
- **A single-verdict file is one whose facts agree** — it is not a file that was judged in bulk.

Two kinds of disagreement turned up, and they are different:

| Kind | Meaning | Count |
|---|---|---|
| **Mixed by kind** | the file holds both tree-reading facts and facts that never touch the checkout | **5 files** |
| **Mixed by verdict** | every fact reads the tree, but their verdicts differ | **3 files** |
| Single verdict | all facts agree | 19 files |

**8 of 27 files are mixed.** That is a minority, which is why the per-fact pass is a correction
rather than a re-census: nineteen files keep the verdict and the single row they already had.

## 2. Which facts are pins

### 2.1 The test applied

Rule 1: *a pin is a test that reads the repository tree at runtime and asserts on its contents.*
Applied per fact, that excludes three shapes that appear inside population files:

- **facts asserting over build output.** Reading `BlazorNative.Components.xml` from
  `Path.GetDirectoryName(assembly.Location)`, or type names off a `.dll`, is not reading the
  repository tree. Rule 6 draws this line itself when it explains why `BnRepo.TestBinaryDirectory()`
  exists: *"`PackagePurityTests` genuinely needed its own build output rather than the repo tree"* —
  a different job, named separately, on purpose.
- **facts asserting over in-process state.** A baseline held against `SampleAppPages.All` is a
  content pin, but it is not a *tree* pin.
- **facts over a fixture the test writes itself.** A temp file created, fed to a parser, and deleted
  is a unit test of the parser.

A fact stays a pin when the checkout read is load-bearing even though it is mediated. The reference
fixtures run `scripts/generate-reference.ps1` **from the checkout** precisely so the pin cannot drift
from the lane — the file says a pin that re-implemented publish and generate *"could pass forever
while the lane pointed at bin/"*. The tree read is the point, so those facts are pins.

### 2.2 Two corrections to Rule 6's examples, now folded into the standard

Recorded here because they are what produced the per-fact unit.

**`TextCollapseParityDriftTests` is a pin, not golden support.** All four of its facts read
`WidgetMapper.kt` or `BnWidgetMapper.swift` and hold them against a behaviourally-derived harness
set. Its own header: *"This pin is what makes the new list a measurement instead of a claim."*

**`BnImageDemoTests` is half a pin, and the checkout reads are the pin half.** Its golden and
arithmetic facts never touch the tree. Every `BnRepo.Root()` call funnels through one helper,
`ShellSource`, whose only two callers hold **three transcriptions of four integers** —
`BnImageDemo`'s constants, `ImageFixtureServer.kt`, `BnImageFixtureServer.swift` — to one value.

### 5.1 `ShellStyleTableDriftTests` — the floor was on the wrong set, and the over-match was live · **CLOSED by 15.1 task 1**

**The floor guards the wrong side.** Every fact has the shape:

`ParseNameTable` ends with `Assert.NotEmpty(names)`, so the *subtracted* set is floored. `routed`,

limit that can hand you a green is a defect, whether or not it is written down."* This one hands you
a green, and it is not written down — the doc comment discloses a different and smaller limit, that
the pin proves the arm is *written* rather than *reached*.

reject.** `RouteTableDriftTests.TheDuplicateRouteFixture_IsOtherwiseValid` is the worked example

`@* … *@` is a different grammar from `//` and `/* … */`, so a Razor stripper is not a second copy

survive is the HOME.** The next pin that needs to read a `.razor` file will look for comment

So the Razor grammar lives in `CommentStrippedSource` — as `StripRazor`, a **sibling entry point**,
not a `razor:` flag on `Strip`. A flag would thread through `Lines` and `NumberedCodeLines`, would

shared hot path is the precise mechanism by which a helper change leaves the aggregate suite count
correct while moving what one pin sees. `Strip`'s body was not edited at all, so the eight callers
are unchanged by construction; their suites were re-run individually anyway.

`StripRazor` composes: Razor comments first, then `Strip`, because a `.razor` file is a mixed
grammar and a `@code` block carries the C# forms. Three limits remain and each is labelled with its
direction at the pin: an `@if` branch that never executes and an HTML comment both **fail green**,
and — the widest of the three, inherited from the original design rather than from the stripper —
**mentioning is not wrapping**. A name match cannot prove the component is an ANCESTOR of the
page's content. Closing that means mounting each page and asserting on the frame, which is a
different and much larger pin.

## 6. Things that are not verdicts

### 6.1 The enforcement blind spot

`PinPopulationTests` excludes two files **by name, never by pattern**:

```csharp
if (name == "BnRepo.cs" || name == "PinPopulationTests.cs") continue;
```

Both exclusions are correct and neither should be removed. `BnRepo.cs` is the one permitted
implementation of the walk; `PinPopulationTests.cs` is where the markers are declared, and nothing
can scan for a string it is forbidden to contain.

**The blind spot is what follows: a bypass written inside either file is invisible to enforcement.**
In rising order of plausibility:

1. A test class declared *inside* `PinPopulationTests.cs` could walk to the solution file by hand
   and never be seen. Implausible, but it is the exclusion read literally.
2. **`BnRepo.cs` could grow a second walk.** This is the one that matters. `BnRepo.Root()` and
   `BnRepo.TestBinaryDirectory()` already coexist there — deliberately, and the second one's doc
   comment explains that routing `PackagePurityTests`' legitimate base-directory use through the
   helper is what kept the marker list at its original width. A third method added the same way,
   with a slightly different sentinel or climb, would be **two copies of one truth inside the file
   whose entire purpose is that there be one** — Rule 8's twin-divergence precondition, sitting
   inside the mechanism built to prevent it, in the one location no scan reads.

Nothing currently guards that. `BnRepo.cs` is 51 lines and reviewed by eye. 15.1 should decide
whether that is sufficient and write the answer down either way; the census's job is to make sure
nobody discovers the exclusion by surprise.

#### The decision — 15.1 task 5: **no dedicated guard**, and the reasoning rather than the verdict

**First, what does NOT answer this section, because the near-miss is instructive.** 15.1 task 3 gave
`PinPopulationTests` a positive control,
`TheBypassMarkers_AreStillFoundInBnRepo_TheOnePermittedHomeOfTheWalk`, and it reads as though it
covers this. It does not, and it points the wrong way: it asserts each declared marker is still
**found** in `BnRepo.cs`, so a third walk added there — spelling the sentinel a third time — makes
that control **more** satisfied, never less. Scoring it as coverage would be §5.5's mislabel trap in
a new dress: a control judged by its neighbourhood instead of by its assertion. The pin's own
header already files this correctly, as limit 3, in the group labelled *these fail green*.

**The decision is therefore taken here, and it is no.** Two mechanisms were considered and both were
priced against the specific hazard above — *`BnRepo.cs` grows a third method holding a second copy
of the walk* — rather than against the section's general unease.

**Candidate 1 — an exact-occurrence count, the `TheNugetApiKey_IsReferencedExactlyOnce` shape.**
That is Rule 3's third form and the obvious thing to copy. Measured on the stripped source of
`BnRepo.cs` as it stands: `BlazorNative.sln` occurs **twice** — in `Root()`'s `File.Exists` and
again inside `Root()`'s own throw message — and `AppContext.BaseDirectory` occurs **twice**, in
`Root()` and in `TestBinaryDirectory()`. So the constants would be 2 and 2, and **one of the four
occurrences is an error-message sentence.** Rewording that sentence reds the guard for a reason
nobody can connect to a second walk, which is the failure mode §5.5 already refused a prose anchor
over, and which Rule 2's corollary names in as many words: a guard that moves for irrelevant
reasons gets argued down rather than investigated.

**And it would be pointed away from the hazard.** §6.1's item 2 is a third method *with a slightly
different sentinel or climb*. A walk built on `global.json`, on `.git`, or on a fixed parent count
adds **no** occurrence of either marker and leaves the count at 2 and 2. So the count guard reds on
the harmless edit and stays green on the named one — Rule 5's forbidden direction, under a name
claiming coverage.

**Candidate 2 — a member roster: assert `BnRepo` declares exactly `Root` and `TestBinaryDirectory`.**
This one does red on a third method whatever sentinel it uses, it is about fifteen lines, and it is
the *inventory rather than judgement* shape `docs/pin-standard.md` endorses when it says what
replaces mechanical Rule 2 enforcement. It is the stronger candidate and it is still declined, for
one structural reason: **the hazard is a walk, not a member.** `Root()`'s own body could grow a
second climb — a fallback for a missing sentinel, say — with the member list untouched, and the
roster would be green over exactly the divergence it was bought to catch. A guard that covers the
easy half of a hazard, under a name that reads as covering the hazard, is the shape this milestone
exists to stop shipping.

**What is relied on instead, stated so it can be disagreed with.** Two walks inside `BnRepo.cs` are
a Rule 8 problem — two copies of one truth — and **not** a Rule 6 problem: both would still be
members of the one shared helper, so every caller stays enumerable and no pin becomes invisible.
That bounds the damage to the divergence class itself, in one 51-line file, in one class, with the
copies adjacent. That is the *best* case for the ordinary review that has caught every twin
divergence in this repo so far, and the exact opposite of the 24-copies-across-24-files state the
consolidation was built to end.

**This is a judgement about cost, and Rule 5 applies to it.** It is conditioned on an observable
fact — `BnRepo.cs` holds two members and one walk — so **the trigger to revisit it is that file
growing a third member.** If that happens, re-read this section before adding the member, not after.

**One thing this decision does not license.** *Neither* exclusion may be widened. The stripper's
move into `tests/Shared` beside `BnRepo.cs` during this phase was deliberately **not** taken as a
reason to exclude it — living in that directory is not the qualification, doing the walk is — and
the pin's header says so. Every by-name exclusion is a blind spot that can never be read again.

### 6.3 One needs-mutation sub-finding, and it sits in a non-pin fact

**`PackagePurityTests.ResolveAssemblyPath` — a possible stale-build-output channel.**

When an assembly is not beside the test binary, the pin resolves it from the checkout's own build
output directory. That is whatever was last built there, and it can be arbitrarily old.
`File.Exists` reds when the file is *absent*; nothing reds when it is *stale*.

If reachable: a demo page added to `BlazorNative.Analyzers` today would not appear in a dll built
last month, so `TheMovedRoster_IsAbsentFromEveryShippedAssembly` and
`NoAppShapedTypeName_InAnyShippedAssembly` would pass over old metadata. Whether it is reachable
depends on CI build ordering and on whether `build-test` guarantees a fresh build of the Analyzers
project — **runtime state this census cannot evaluate by reading**, which is the condition the brief
says to mark rather than guess at.

**Both affected facts are the PE-metadata ones, so this lands outside the pin population.** The
file's three pin facts do not call `TypeNamesOf` at all. Marked `needs-mutation` regardless; the
experiment is cheap: build, edit a type name in the Analyzers source, run the suite without
rebuilding that project, see whether the pin notices.

#### The experiment — 15.1 task 5. **Run, not argued. The channel is real and is not reachable.**

This section said the question was decidable by experiment rather than by reading, so it was run
rather than reasoned about, and what follows is what happened rather than what was expected.

**The commands, so the next reader can repeat them.**

```bash
# 0. a clean solution build — also the suite run, so the checkout build output is current
dotnet test BlazorNative.sln

# 1. plant an app-shaped type in BlazorNative.Analyzers, the ONE shipped assembly
#    that is not copied into the test output directory
cat > src/BlazorNative.Analyzers/ZzStaleChannelExperiment.cs <<'EOF'
namespace BlazorNative.Analyzers;
internal sealed class StaleChannelProbe { public static int Value => 1; }
EOF

# 2. run the purity facts the ORDINARY way, from the test project alone
dotnet test tests/BlazorNative.Runtime.Tests/BlazorNative.Runtime.Tests.csproj \
  --filter "FullyQualifiedName~PackagePurityTests"

# 3. delete the source again, leaving the dll still holding the probe, and
#    suppress the build
rm src/BlazorNative.Analyzers/ZzStaleChannelExperiment.cs
dotnet test tests/BlazorNative.Runtime.Tests/BlazorNative.Runtime.Tests.csproj --no-build \
  --filter "FullyQualifiedName~PackagePurityTests.NoAppShapedTypeName_InAnyShippedAssembly"

# 4. restore
dotnet build src/BlazorNative.Analyzers/BlazorNative.Analyzers.csproj
```

**Step 2 — the pin NOTICED, and the build log says why.** The run printed
`BlazorNative.Analyzers -> src\BlazorNative.Analyzers\bin\Debug\netstandard2.0\BlazorNative.Analyzers.dll`,
the dll's timestamp moved, and `NoAppShapedTypeName_InAnyShippedAssembly` went **red**: *"caught an
app-shaped type in a shipped assembly: StaleChannelProbe in BlazorNative.Analyzers"*. Six of the
file's seven facts passed; the one that should red, red.

**The mechanism, which is the part worth keeping.** Every `src/*` csproj carries

```xml
<ProjectReference Include="..\BlazorNative.Analyzers\BlazorNative.Analyzers.csproj"
                  OutputItemType="Analyzer" ReferenceOutputAssembly="false" />
```

and `BlazorNative.Runtime.Tests` references `BlazorNative.Core`, so the Analyzers project is in the
**test project's own build graph** even though its dll never lands in the test output directory.
`ReferenceOutputAssembly="false"` is what keeps it out of that directory — which is *why* it is the
one shipped assembly that goes down `ResolveAssemblyPath`'s checkout fallback in the first place —
while the reference carrying that flag is what keeps it built. The same line causes the fallback
and forecloses the staleness.

**Step 3 — the stale read IS reachable, and was observed.** With the source deleted and the build
suppressed, the fact still red naming `StaleChannelProbe`, and the dll's timestamp was unchanged
from step 2. The scan read PE metadata for a type the checkout no longer declares.

**Note the direction, because it is the opposite of the one this section feared.** A deleted type
read out of a stale dll is a false **red**. The mirror — a type *added* since the last build, absent
from the old metadata — is the false **green** §6.3 predicted, and it follows from the identical
read. So the hazard is real; the question was only ever whether anything reaches it.

**Two conditions must hold together, and in this repo they do not.** The run must suppress the
build, **and** the Analyzers source must have changed since the last build of that configuration.
CI does carry the first: `ci.yml`'s `.NET tests` step runs
`dotnet test BlazorNative.sln -c Release --no-build`. What closes it is the step immediately above,
`dotnet build BlazorNative.sln -c Release`, which builds every project in the solution including
this one, in the same configuration `ResolveAssemblyPath` will go on to select — it reads
Debug-or-Release off the test binary's own path rather than guessing.

**Verdict: `needs-mutation` → resolved, and the sub-finding is NOT a defect.** No change to the pin
and none proposed. The honest remainder is a disclosure rather than a hole: nothing in
`PackagePurityTests` *states* that two of its facts are only as fresh as the last build of
`BlazorNative.Analyzers`. That costs nothing today because no path reaches it, and it is recorded
here so that a future change to CI's build ordering, or to the analyzer reference's
`ReferenceOutputAssembly` flag, is understood as changing this answer.

assertion is a fixed point it must still hit.** One lesson, four worked examples already in the
tree, nine places to apply it.

## 9. What this census cannot see — the enumeration key has a hole

**Read this alongside §1, because it is a limit on that section's completeness rather than a
footnote to it.** Rule 5 applies to a census as much as to a pin.

**The population is enumerated by a grep for the tree-reading helpers — `BnRepo.Root()` since
15.0, widened in 15.2 to also match `ShellSourceScan.` — so the population is *tree-readers*.**
That is what makes it mechanically enumerable at all, and Rule 6 says so plainly. But "reads the
repository tree" is Rule 1's definition of a pin, and **Rule 2's subject is larger than Rule 1's
definition**:

> *Vacuity is a property of the assertion shape, not of the input. An assertion of the form* for
> every X, assert Y *passes trivially when there are no X — and it does not matter whether X came
> from a regex over source, a directory walk, a manifest parse, or an in-memory collection.*

**A test that compares two in-memory collections never calls `BnRepo.Root()`.** It can hold two
copies of one truth, red when they diverge, carry every property this document measures — and be
invisible to the key. The enumeration is not merely incomplete in the way any sample is; it is
**blind in exactly the direction a vacuous-capable pin sits.**

§1 already names the live instance and treats it as an example the standard reasons *about*. That
framing was too comfortable, and this section is the correction:

**`RouteMenuDriftTests` is the demonstration, not the exception.** It asserts
*every routed page, except two exemptions, has a menu row* over an in-memory page list. The standard
cites it in Rule 2 precisely because it would pass over an empty list. So the one test the standard
uses to prove that vacuity is independent of file access is also the one test **no mechanism this
milestone built can see**:

| Mechanism | Sees `RouteMenuDriftTests`? | Why not |
|---|---|---|
| `BnRepo.Root()` call graph — the population key | **no** | it never reaches the checkout |
| `PinPopulationTests` — Rule 6 enforcement | **no** | it scans for tests that reach the tree *without* the helper; one that never reaches the tree is correct by that rule |
| This census | **no** | its scope is §1's caller list |
| Any future guard keyed on the helper | **no** | same key, same hole |

**What it means for 15.1.** Two things, and they are separable:

1. **The number `102 pin facts` is a count of tree-reading pin facts.** Every verdict in §3 stands;
   none of them is disturbed. But the denominator is not "every pin in the repo" and should not be
   quoted as one. How many non-tree pins exist is **unmeasured** — `RouteMenuDriftTests` is the one
   this census happened to walk past, and Rule 1's four-for-four scar is the reason to assume it is
   not alone.
2. **A second enumeration would need a different key**, and no cheap one is known. Tree-reading is
   decidable by a call-graph grep; *compares two copies of one truth* is not — it is the same
   binding problem that sank mechanical Rule 2 enforcement in `docs/pin-standard.md`, arriving from
   the other side. **15.1 should decide and record whether the Rule 6 population is the population
   it wants**, and if the answer is no, what the second key is. Recording the decision matters more
   than the outcome: an undisclosed hole in an enumeration is how a census becomes folklore.

   > **STILL OPEN at the close of 15.1, and recorded as open rather than answered.** That phase
   > closed the census's two named decisions, §6.1 and §6.3, and all nine gap facts. It did **not**
   > take this one — no task scoped it and none of the nine gaps required it — so the Rule 6
   > population is still the population by default rather than by choice. Recording that is the
   > point of this section: the hole is disclosed, it is unchanged, and nothing in 15.1 narrowed it.
   >
   > **Its home is 15.4**, ruled by `docs/superpowers/specs/2026-09-23-phase-15.1-design.md` before
   > 15.1 began: the wrong second key reintroduces the name-based enumeration M15 spent a phase
   > removing, so the decision must not be rushed inside a fix phase. **#375** is its live instance
   > — a vacuous-capable pin over two in-memory collections, invisible to the current key.

   > **DECIDED in 15.4 (owner, 2026-09-24): a hand-kept register.** The Rule 6 population stays
   > *tree-readers*. Pins over in-memory collections are listed by hand in `docs/pin-standard.md`,
   > directly under Rule 6, and Rule 6 now says both that its population is tree-readers and what the
   > register costs: it grows only when someone remembers it. A `[Pin]` attribute was rejected as
   > declared-not-derived. `RouteMenuDriftTests` is the register's first row and gained per-fact floors
   > in the same phase, which closes #375. **The counts in §1 and §3 remain counts of tree-readers**,
   > as this section always said. The register is not added to them.

**No verdict changes because of this section.** Its job is to make sure nobody plans against §1's
counts believing them to be exhaustive over pins, when they are exhaustive over *tree-readers*.
