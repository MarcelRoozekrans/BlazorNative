## 1. The thesis, and whether it held

Six issues came out of a fresh review of 0.10.0. **Four of them were one bug class** — *two copies of
one truth, one of them unpinned* — the same shape as the visual-style hole (#263/#266) and the
wire-vocabulary drift (#262). So the Definition of Done was written as **"a NEW instance of the shape
reds"**, not "these four are patched".

It held, with one caveat stated at the outset and worth repeating: **one class did not mean one fix.**
The copies lived in three different places and each admitted a different mechanism. A single
universal guard would have been blunt enough to need constant allowlisting and would have closed none
of the three properly.

| Instance | Where the twin lived | Mechanism |
|---|---|---|
| **#279** | a Swift literal shadowing a generated symbol | consume the generated value; pin that no generated symbol is shadowed |
| **#278 / #282** | two hand-written parsers, Kotlin ↔ Swift | a generated shared vector table asserted by three suites |
| **#280 / #281** | the harness weaker than the device | pin the node-type maps **equal**; model both shells; dispose on throw |

## 2. #280's stated bug does not exist

The issue says an unmapped node type "passes the harness and aborts rc 2 on device". **It cannot.**
`NativeRenderer.MapElementToNodeType` ends in a catch-all returning `view`, so an unknown element is
coerced *upstream* of both the harness and the encoder. Measured, not argued: a `marquee` element
projects as `view`.

The issue reasoned from two true facts — `BnTestTree.Apply` accepts any string, `MapNodeType` throws
— across a coercion that sits above both. A good-faith review error of the kind only measurement
catches.

The briefed fix was unavailable too: `BlazorNative.Testing` has **no reference to
`BlazorNative.Runtime`**, so reaching `FrameEncoder` needed a new edge in the *shipped package
dependency graph* — not an `InternalsVisibleTo` — plus a second internal type.

**What replaced it is stronger in one direction.** Pinning the two node-type maps **equal** catches
something the briefed gate never could: a dropped `MapElementToNodeType` arm silently reclassifies a
component as `view`, and an encoder-in-the-harness gate would have stayed green.

## 3. Both parity bugs were latent, and that is the argument

Every route declared today is single-segment, so the two deep-link parsers agreed on everything
shipped. #279's two lists matched exactly — nine names, same order. **Neither bug was reachable by
any current test, which is why neither was caught**, and why the answer had to be a guard rather than
four careful patches.

The vector table also found a divergence nobody had reported: a bare `blazornative://` returned null
on Android where iOS returns the root route. The table is the specification, so it found what the
issue had not.

## 4. Standing guards, and the mutation that proves each

Every guard was mutation-proven. Two proofs are worth reading twice.

## 5. What the process caught that the plan did not

Recorded because the plan was wrong in ways worth remembering. All five were defects in the plan or
its briefs, found by implementers or reviewers rather than by their author.

- **The flagship pin could never have gone green.** Its pattern flagged any declaration of a
  generated symbol's name — including the correct forwarding form, and including the plan's own
  prescribed fix. The pre-flight scan looked straight at that pair and verified the *red* state was
  intended without asking whether a *green* state was reachable.
- **The plan's Task 6 command could not run the test at all.** `testDebugUnitTest` reads `src/test`;
  the file is in `src/androidTest`. So the JVM count does **not** move and the *instrumented* one
  does. Following the plan would have rebased 161 and **redded a required lane**. The plan was
  corrected in place, because it is committed and outlives the session that wrote it.
- **The brief authorised two files where a third was mandatory.** `TemplateDriftTests` holds the
  template's `MainActivity.kt` byte-identical to the repo's on a required check; leaving it would
  have redded `build-test` *and* shipped #278 to every generated app.
- **#282 was broader than described.** Not merely unmapped routes dropped: iOS took the default
  bridge and nothing on the boot path ever replaced it, so even a *mapped* cold deep link left the
  router reporting the root route.
- **A silent-degradation channel inside the phase's own flagship guard.** `GeneratedSymbols()` was
  the one scan with no anti-vacuity floor: had its pattern stopped matching, both pins would have
  passed over an empty set. The same review found the pin blind to a third generated file
  (`BnWireVocabulary.g.h`), which made a DoD line **false while the pin reported green**.

## 6. Known limitations, stated rather than discovered

- **Scheme case-sensitivity** ([#296](https://github.com/MarcelRoozekrans/BlazorNative/issues/296)).
  iOS lowercases; Kotlin compares directly. Deferred because Android's intent filter is itself
  case-sensitive against a lowercase manifest value, so the URL never reaches the parser — and the
  residual is asymmetric in the harmless direction: iOS can accept an extra URL, never produce a
  wrong route. Written down *because* a reachability argument is the kind that turns out wrong.
- **`FrameEncoder` has two throw sites; this phase pinned one**
  ([#297](https://github.com/MarcelRoozekrans/BlazorNative/issues/297)). Nothing enumerates
  `RenderPatch` subclasses against the patch-kind switch. #261 added `ScrollToPatch` exactly that
  way, so this is a routine change away from being live.
- **The Android vector suite runs on the instrumented lane**, which is dispatch/nightly rather than
  per-PR. Mitigated: the *required* .NET lane pins the vector **table**, so a gutted table reds on
  every PR even though the parser assertion does not.
- **The #282 seed pin asserts the shape of the call, not runtime behaviour.** `viewDidLoad` returns
  early under XCTest, so the branch is unreachable from the hosted bundle. Weaker than an integration
  test, stronger than a comment — and the test's own header says so.
- **The symbol-count floor is a total, not per-file.** Today it equals the exact count, so any single
  loss reds. Once the manifest gains a vocabulary, one language's pattern could break entirely and
  the total still clear. Not live; parked deliberately rather than spending a second fix wave, and
  recorded here so it is a decision rather than an oversight.
- **The iOS half of the text-collapse pin is declared, not derived.** Parsing `makeView` was declined
  as more likely to encode a wrong answer *with the confidence of a measurement* than to help.

## 7. What 13.4 deliberately did not do

- **Close #280 as written.** Its scenario is unreachable (§2); the issue is re-scoped rather than
  ticked.
- **Add a package-graph edge** from `BlazorNative.Testing` to `BlazorNative.Runtime`.
- **Fix pre-existing documentation it walked past.** `BnSwitch`'s XML doc names a widget the shell
  does not build ([#298](https://github.com/MarcelRoozekrans/BlazorNative/issues/298)) — filed, not
  fixed, because opportunistic one-at-a-time doc fixes are the pattern #291 exists to replace.
- **Take #283's other six items.** 0 fixed here, 7 split out with a written disposition. The phase
  closes the class; it is not "fix everything the review found".
