# Phase 14.1 — The dispatch twins: conclusion

**Branch:** `feat/14.1-dispatch-twins` · **Worked:** 2026-09-21
**Verdict:** COMPLETE. `dispatchHostEvent` existed in both shells, spelled identically, and blocked
in one — Swift's lifecycle caller shared a queue with the dispatch lane instead of getting its own,
freezing the app on a real device whenever a permission sheet appeared (#339). The Swift trigger is
fixed and pinned to a declared dispatch surface. The **shared .NET root cause underneath it is not
fixed** — deliberately, per the plan's own instruction — and is now two filed, harness-provable
issues instead of one device-only mystery.

---

## 1. The spike's four findings (why a fix is not obvious)

Before this phase, a throwaway spike asked whether `Exports.DispatchEventCore`'s
`GetAwaiter().GetResult()` could simply be replaced with an early return. It measured, not reasoned:

- An early return that claims "handled" while an async handler is still running **does** free the
  lane — **rc=0 in 42ms**, call still open.
- The whole suite (1076 tests, pre-phase baseline) passed with that probe applied, because nothing
  else exercised the path.
- Returning early is not safe, for four reasons that have to be answered together, not one at a
  time:
  1. **The rc contract.** `blazornative_dispatch_event` returns 0/1/2/3 meaning "the handler ran;
     here is the outcome." An early return changes that to "accepted." Every shell routes non-zero
     rc to `onError`.
  2. **Android's back is a hard blocker.** `OnBackInvokedCallback` must decide *synchronously*
     whether to finish the Activity, on rc 0 vs 1. There is no "I will tell you later" in that API.
  3. **The dispatch-window guarantee** — swap frames delivered before the export returns — breaks
     for async handlers.
  4. **Completion and faults.** Nothing observes the handler's eventual outcome once the export has
     returned.
- Phase 13.2 hit the adjacent wall from a different direction: an honest `InlineDispatcher` needs a
  real queue, which breaks the sync-mount contract `MountSyncTests` pins.

This phase's task brief carried the finding forward as a constraint: **do not touch
`Exports.DispatchEventCore`.** Step 7 verifies a zero diff on `Exports.cs` against `main` (see §6).

## 2. What the reproduction proves, and does not

`tests/BlazorNative.Runtime.Tests/DispatchLaneBlockingTests.cs` turns the spike's device-only
deadlock into a local, bounded ten-second test (it never returns early — the pin's whole point is
that the wait runs out rather than the dispatch returning):

- Mounts `BnCameraDemo`, holds its "Take Photo" host call open (`FakeShellHost.AutoCompleteHostCall
  = false` — the unanswered-permission-sheet condition), then dispatches the click on a worker
  thread and waits a bounded 10s.
- **Re-run at the start of this task, it still failed** — exactly as the brief predicted. Task 2
  fixed Swift's *lifecycle* caller, not the shared .NET path this test exercises, so the fix could
  not have made it pass.

Per the brief's Step 1 branch, the test was **converted to pin the defect rather than "fixed"**:
renamed `AnAsyncHandlerAwaitingAnOpenHostCall_STILL_BlocksTheDispatchLane`, its assertion inverted
(`Assert.False(returned.Wait(Budget), …)`), and its header rewritten to say plainly that it pins a
KNOWN DEFECT left in place on purpose, naming the follow-up (#345) and stating that a fix should
**flip the assertion, not delete the test**.

**What this proves:** the .NET-side root cause is real, reproducible without a device, and now has
a permanent, honest, green regression harness. **What it does NOT prove:** that the defect is fixed,
that Swift's or Kotlin's fix "solved" it, or that the two shells behave identically under this
condition — only that they *say* the same thing (14.0's final review caught exactly this overclaim
one phase ago; this conclusion does not repeat it).

## 3. The Android measurement (Step 3)

`dispatchHostEventAndWait` (`BlazorNativeRuntime.kt`) does an untimed `future.get()` against the
single `BlazorNative-Dispatch` lane (a single-thread `ExecutorService`). `MainActivity.handleBack`
(line 522, the `OnBackInvokedCallback`/predictive-back path) calls it from the main thread.

A new JVM test, `HostEventTest.dispatchHostEventAndWait_still_deadlocks_behind_a_held_dispatch_lane`,
measured whether Android's own entry point is exposed to the same lane-serialization hazard:

1. Mount `BnCameraDemo`, dispatch "Take Photo" fire-and-forget (`dispatchEvent`) against a host
   whose `hostCallBegin` records the request and never completes it — the JVM/Android twin of the
   .NET test's `FakeShellHost.AutoCompleteHostCall = false`.
2. From a second thread, call `dispatchHostEventAndWait(BnHostEvent.Back)` — the exact call
   `MainActivity:522` makes.
3. Join that thread with a bounded 10s timeout (never unbounded, per Task 1's rule that a hanging
   measurement is worse than no measurement).

**Result: it deadlocks.** The probe thread did not return within 10s. The lane is a single worker
thread; the held "Take Photo" dispatch already occupies it, so the queued "back" `Callable` cannot
even start until the stuck call finishes — which, in this test, is never, until the test itself
completes it during cleanup (see below). This is the same root cause as #345, reached through
Android's own production call site rather than the .NET test harness.

This is filed as its own issue, **#346**, rather than folded into #345 — Android's back path carries
its own hard constraint (`OnBackInvokedCallback` needs a synchronous verdict) that #345's write-up
already identifies as one of the four open questions a fix must answer.

The JVM test pins this the same way the .NET test does: it asserts the probe thread is **still not
back**, passing on today's broken behaviour, written to flip (not delete) once #346/#345 land a fix.
**A cleanup step, run only after the measurement, completes the held host call explicitly** — the
blocked native call sits on the ONE process-global .NET session every JVM test class in the same
run shares (not a per-instance resource), so leaving it open would corrupt every test class that
runs after this one in the same JVM. Confirmed empirically: before the cleanup was added, three
unrelated suites (`NavigationTest`, `NotificationsTest`, `InspectorServerTest`) failed when the
measurement test ran ahead of them; with the cleanup, the full 162-test suite is green.

## 7. What 14.1 deliberately did not do

- **Fix `Exports.DispatchEventCore`.** Measured as unsafe without answering four open questions
  (§1); tracked as #345.
- **Fix Android's `dispatchHostEventAndWait` deadlock.** Measured, not fixed; tracked as #346.
- **Claim the two shells behave identically under the held-lane condition.** The dispatch-surface
  guard (Task 3, `DispatchSurfaceDriftTests`) proves the two shells *say* the same thing — the
  method names and shapes match. It does not and cannot prove they behave identically; #345 and
  #346 exist precisely because the underlying behaviour (deadlock under an open host call) is
  shared, not because it was verified equal.
- **Widen scope because the Android measurement came back positive (deadlocked).** Filed as its own
  issue per the brief's explicit instruction, not fixed here.
