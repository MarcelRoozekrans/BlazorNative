### The fix

- **The cause**, as the investigation found it: `BnLog`'s default sink wrote each line to `Console.Error` on the caller's thread. On the Windows runner a full stderr pipe blocked the render thread inside `NativeRenderer.HandleException`'s `BnLog.Error`, in the middle of a dispatch.
- **The sink.** `BnLog.Write` still formats the line on the caller's thread, so the level gate and the redaction are decided there, unchanged. It then hands the line to `BnLogQueue` (`src/BlazorNative.Core/BnLogQueue.cs`).
  - The queue is bounded at 1024 lines. One background thread, `BlazorNative-LogDrain`, writes each line with one `WriteLine`, so line atomicity holds.
  - The drain thread is started with `UnsafeStart`, so it captures no `ExecutionContext`. With `Start` it kept the first logger's AsyncLocals for the life of the process. On a device the first logger is usually the render thread inside a dispatch, so it kept that dispatch's `DispatchScope` and the renderer that `s_mountGeneration` holds.
  - When the queue is full, the line is dropped and counted. The count is reported in one `[BN|W|BnLog] N lines dropped: the log queue was full` line, either just before the next line that fits, or, when the drain empties the queue with drops still counted, by the drain itself, to the writer of the line it just wrote. So a burst followed by nothing is still reported.
  - **The drop line is always Warn, and never gated by `BnLog.Level`. This is deliberate.** Warn is the level for "something was dropped", and at a threshold of Error the lost lines may be errors. `BnLog.Level`'s remarks state the exception.
  - Each entry keeps the writer that was `Console.Error` when the line was logged.
  - A custom `BnLog.Sink` is still called synchronously on the logging thread; only the built-in writer is queued.
  - `BnLog.Flush(TimeSpan)` is `internal`. Core grants `BlazorNative.Runtime` InternalsVisibleTo for it, so the public API is unchanged. **Ruling:** this is a deliberate exception to Core's stated policy, a public, honestly-named seam over an InternalsVisibleTo web. `Flush` is a member app code has no reason to call. `BnSafeAreaInsets.Current`'s remarks name the exception since the final review's m1, and `Report` stays public.
- **Rule: every level stays asynchronous, Error included.** A synchronous write or flush on any level is #564 again: the blocking call was an Error on the render thread. `BnLog.Sink`'s remarks state the rule.
- **The accepted trade-off: lines lost at a hard kill.** A process the OS kills, as it can kill an app on Android or iOS, loses whatever the queue still holds. That backlog is normally empty, because the drain is idle whenever stderr is draining, and the shells' in-process pumps already lose what they had not forwarded. The queue drains, each time bounded by 500 ms, at three exits:
  - `blazornative_shutdown`, in a `finally` after `HostSession.Shutdown`, because a NativeAOT library may never see `ProcessExit`;
  - `AppDomain.ProcessExit`;
  - `AppDomain.UnhandledException`.

  Task 7's device lanes are to confirm whether `ProcessExit` fires under NativeAOT on each device. No path flushes synchronously on its own.
- **The tests that read stderr back.** There are seven such sites: `BnLogTests.TheDefaultSink_WritesTheFormattedLineToStderr`, both `RegistrationTests` stderr facts, the `CaptureStderr` helpers in `DispatchEventTests` and `HostEventTests`, `HostNavigateTests.Navigate_HostCallbackFault_Returns2` and `NavigationTests.RouteChanged_ThrowingSubscriber_StrictMode_StillContained_AndLogged`.
  - Each calls `BnLog.Flush` before it reads the capture, and asserts that the flush drained, with "the BnLog queue did not drain within 10 s, so the captured stderr is incomplete".
  - Their own assertions are unchanged.
  - `RegistrationTests`' `DoesNotContain` fact can therefore not pass because the line has not arrived yet.
- **The harness.**
  - `DispatchProbe` and `DispatchTwo` tear down on every exit path: a `catch` calls `TearDown` and rethrows.
  - `DispatchBounded` records a worker that overran its budget, and stops disposing that worker's event under it.
  - `TearDown` takes an optional `release` that frees what the fact holds open.
  - When the last dispatch overran, `TearDown` joins its worker, bounded by `Budget`. Then, always, it waits for every late FaultNotice send to complete, bounded by `Budget`.
  - The sends are exact. `Exports` hands the `Task.Run(SendFaultNotice)` task of a FaultedAfterShellCall dispatch to `Exports.LateFaultNoticeObserver`, an internal test tap that is null in production, like `PendingDispatchObserver`.
  - `FaultNoticeTests.StartSession` installs a tap that records each send, and never removes it, so a send from an earlier fact that is still in flight is recorded too.
  - A completed send has begun its host call, because `SendNotice` begins it synchronously. The pool-drain heuristic is gone.
- **Coverage.** Round 1's first drain loop, with the trailing-drop report inlined, came out of coverlet.collector 10.1.0's IL instrumentation as an invalid program. Under `coverage.runsettings`, which `ci.yml` uses, the test host crashed with `InvalidProgramException` at `BnLogQueue.Drain`, and squeeze aborted 7 of 7 runs. A Debug run without coverage was unaffected. `2f1f0c39` moves the loop body into `DrainOne`, so `Drain` is `while (true) DrainOne();`, and the behaviour is unchanged. `BnLogTests` then passed 3 of 3 under coverage, and squeeze 7 of 7. The code comment at `Drain` records why.
  - **Tracked as #574.** By owner decision, the coverlet bug is tracked as a repo issue, with an upstream report to follow.
  - **The trigger, measured in a standalone repro under the session scratchpad:**
    - a Release build with coverlet.collector 10.1.0;
    - a loop that never returns;
    - an `if` directly before a `try/finally`, which a `lock` is.
  - The pre-18.1 `Drain` was already `while (true)` and did not crash, so the loop alone is not the trigger. Why the combination breaks is a hypothesis, stated in #574.
  - No coverlet.collector newer than 10.1.0 exists on nuget.org as of 2026-10-25, prerelease included.
  - The workaround hides nothing in the product. Re-inlining the body crashes the coverage run again.
  - The real fix is to bump coverlet once upstream fixes the bug.
- No bound or timeout was raised, and the ABI is unchanged.

**`GatedWriter`.** `tests/BlazorNative.Runtime.Tests/GatedWriter.cs` stands in for a stderr pipe whose reader lags: every write blocks until the test opens it.

**The leak pin** forces its leak with no timing luck.
- Its handler, `gated-begin-then-throw`, begins a call and then waits on a gate inside the synchronous part.
- A late reader opens the gate only once the next fact's `StartSession` has cleared the host-call log.
- When nothing tore the overrun fact down, the stuck notice therefore always lands in the next fact.

**The slow-notice pin** forces the narrower half: a send still in flight when its fact ends.
- Its `release` puts a gate on `FakeShellHost`'s FaultNotice begin before it frees the handler.
- That gate opens only when `WaitForNoticeSends` reports that it is about to wait on at least one live send, or else when the next fact's `FakeShellHost.Reset` opens it after clearing the log.
- So a TearDown that does not wait for the send leaks the notice into the next fact every time.

### The invariant

The brief offered two invariants for the starvation pin: (a) the test suite's own blocking waits never run on the pool, or (b) the frame path does not depend on a free pool thread.

**(b) is false today, and (a) is the one this phase pins.** The frame path crosses the pool, by the product's current design. This phase changes no product code, so (b) cannot be pinned. The cause is the test process holding its own pool threads, so the fix keeps the suite's blocking waits off the pool. The starvation pin then accepts either outcome. Either the frame arrives under a held pool, which is (b), or the positive control fails naming thread-pool starvation and reports that the frame arrived once the pool was released.

**The hop is avoidable, but not by one line.** The investigation names one hop, at `NativeShellBridge.cs:471` and `:504`. Instrumented in the scratch worktree, there are two:

1. `:504` awaits the `RunContinuationsAsynchronously` TCS with `ConfigureAwait(false)`, so `InvokeHostCallAsync` resumes on a pool thread.
2. `CapturePhotoAsync`, at `:981`, awaits `InvokeHostCallAsync` with `ConfigureAwait(false)` too. With `:504` changed, the inner method completes on the render thread. The runtime does not inline a `ConfigureAwait(false)` continuation while a `SynchronizationContext` is current, so it queues `CapturePhotoAsync`'s continuation to the pool.

| Experiment, scratch only | Starvation pin, with an extra `Assert.True(ex is null)` |
|---|---|
| E1: `:504` without `ConfigureAwait(false)` | Still starved. The instrumented `:504` continuation ran on `BlazorNative-Render`, but `BnCameraDemo`'s continuation ran 2 s later, after the release |
| E2: `:504` and `:981` without `ConfigureAwait(false)` | The frame arrived under the hold, in 3 of 3 runs, 0.6 s per fact |

Making the frame path pool-free is a product behaviour change across every façade method, so it is not folded in. **Filed as #575**, for an owner decision, with three options and a proposal.

### The fix

- **`BoundedScript.RunBounded` refuses a thread-pool thread.** It throws `InvalidOperationException`, naming the rule and #551, before it starts the script. The new `RunBoundedAsync` runs it on a dedicated thread.
- **`OffPool`** is a new test helper. It runs a body with `TaskCreationOptions.LongRunning`, which gives it its own thread outside the pool. `RunBoundedAsync` uses it.
- **The reference fixtures are `IAsyncLifetime`.** `ReferenceFixtureBase`, behind the four package fixtures, and `ComponentReferenceFixture` await the generation in `InitializeAsync`. Their constructors used to hold a pool thread for each whole generation, five fixtures one after another in the first ~15 s.
- **`GeneratorRunTests`** awaits `RunBoundedAsync` instead of `Task.Run(() => RunBounded(…))`, at `:67`, `:150` and `:199`. The edit keeps every line in place, so the register's cited lines in that file do not move.
- **The positive controls run off the pool.** `NoFrameReachesTheCallback_AfterShutdownReturns_PositiveControl` and `APendingHandler_EndsCancelled_WhenItsCallCompletesAfterShutdown_PositiveControl` sleep-poll for the pool-hopped completion, which made them holder 6 in the investigation's dump. Both now return `OffPool.Run`'s Task.
- **The positive control names starvation.** `RunHeldCall` queues a `PoolProbe` just before `CompleteHostCall`. When no frame comes and the probe has not run either, the message at `ShutdownQuiescenceTests.cs:270`, `:282` since `ebb5085f`, names thread-pool starvation and #551 instead of BnCameraDemo. It then waits up to `Budget` again and says whether the frame arrived once the pool was released. Otherwise it keeps its old message, with the probe's delay added. It logs `completion->frame` and the probe delay to the test output.
- No bound or timeout was raised. The starvation pin's 2 s frame wait is new and its own. Product code and the ABI are unchanged.

  - It enqueues one context creation on `workQueue` and returns, so boot never waits for it.
  - `workQueue` is the serial queue that arms every request. A request that arrives during the warm-up queues behind it and reuses the warm process; it cannot start a second cold creation alongside it.
  - The creation goes through `BnLAContextTiming`, so a slow cold start still logs its warning.
  - The context is dropped once made.
  - `contextFactoryForTest` is read when the warm-up is enqueued, not when it runs. A warm-up that is still queued when a later test installs a factory cannot call that factory.
  - When the creation returns, `contextWarm` is set; `contextIsWarmForTest()` reads it. No production code waits on it.
- **The boot tests.** Both wait for `contextIsWarmForTest()` as a named step, `awaitContextWarmUp`, before they tap. A warm-up that is still running after 30 s fails there, with "the LAContext warm-up the shell starts at boot did not finish within 30.0 s: a cold LocalAuthentication start (#453), not a biometrics regression". The tap's 30 s wait for the armed reply is unchanged.
- **The lane.** A new step in `ios.yml`, after the simulator is selected, boots the same udid that `xcodebuild test`'s `-destination` names, with `xcrun simctl boot`. It accepts a device that is already booted, then blocks on `xcrun simctl bootstatus <udid> -b` and logs how long that took. Before this, `xcodebuild test` booted the device itself and started testing at once. **Corrected in fix round 1:** the runs below show that this step does not fix #453. It is kept for its own reasons, which its comment now states.
- **No iOS template copy exists.** `templates/BlazorNative.Templates` ships only the Android shell, so there is no second copy to keep identical and no mirror guard applies. The brief's "both copies" has nothing to act on.
- No bound or timeout was raised, and the ABI is unchanged. The named step's 30 s is a new wait of its own. It moves a cold start out of the tap's wait into a step that names it, as design §3 decided.
