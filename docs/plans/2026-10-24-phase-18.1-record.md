## 2. #564

**Commits:** `037388dc` adds the three pins, red. `feb2539f` is the fix, and adds the drop-count pin. `d0b2188d` makes the leak pin's late reader stand down once the gate is open. Every red and run below was taken on `d0b2188d` unless it says otherwise.

### The fix

- **The cause**, as the investigation found it: `BnLog`'s default sink wrote each line to `Console.Error` on the caller's thread. On the Windows runner a full stderr pipe blocked the render thread inside `NativeRenderer.HandleException`'s `BnLog.Error`, in the middle of a dispatch.
- **The sink.** `BnLog.Write` still formats the line on the caller's thread, so the level gate and the redaction are decided there, unchanged. It then hands the line to `BnLogQueue` (`src/BlazorNative.Core/BnLogQueue.cs`).
  - The queue is bounded at 1024 lines. One background thread, `BlazorNative-LogDrain`, writes each line with one `WriteLine`, so line atomicity holds.
  - When the queue is full, the line is dropped and counted. The next line that fits carries the count, and the drain writes `[BN|W|BnLog] N lines dropped: the log queue was full` just before it. The drop line uses `FormatLine`, so the shells' pumps map it like any other line.
  - Each entry keeps the writer that was `Console.Error` when the line was logged.
  - A custom `BnLog.Sink` is still called synchronously on the logging thread; only the built-in writer is queued.
  - `BnLog.Flush(TimeSpan)` is `internal`, so the public API is unchanged.
- **Which paths drain synchronously.** Nothing logs and then flushes on its own path. The default queue drains at `AppDomain.ProcessExit` and at `AppDomain.UnhandledException`, each bounded by 500 ms, best effort. A process the OS kills, as it can kill an app on Android or iOS, raises neither event. Lines still queued at that moment are lost. Before the fix they could at best have been sitting in the pipe's buffer.
- **The tests that read stderr back.** There are seven such sites: `BnLogTests.TheDefaultSink_WritesTheFormattedLineToStderr`, both `RegistrationTests` stderr facts, the `CaptureStderr` helpers in `DispatchEventTests` and `HostEventTests`, `HostNavigateTests.Navigate_HostCallbackFault_Returns2` and `NavigationTests.RouteChanged_ThrowingSubscriber_StrictMode_StillContained_AndLogged`. Each now calls `BnLog.Flush` before it reads the capture. Their assertions are unchanged. `RegistrationTests`' `DoesNotContain` fact flushes too, so it does not pass because the line has not arrived yet.
- **The harness.**
  - `DispatchProbe` and `DispatchTwo` now tear down on every exit path: a `catch` calls `TearDown` and rethrows.
  - `DispatchBounded` records a worker that overran its budget, and stops disposing that worker's event under it.
  - `TearDown` takes an optional `release` that frees what the fact holds open. When the last dispatch overran, `TearDown` first joins its worker, bounded by `Budget`. Then it waits until the pool has taken every queued item, bounded by `ExportBudget`, so that the dispatch's late `Task.Run(SendFaultNotice)` has begun before the fact is reset.
- No bound or timeout was raised, and the ABI is unchanged.

`GatedWriter` (`tests/BlazorNative.Runtime.Tests/GatedWriter.cs`) stands in for a stderr pipe whose reader lags: every write blocks until the test opens it. The leak pin forces its leak with no timing luck. Its handler, `gated-begin-then-throw`, begins a call and then waits on a gate inside the synchronous part. A late reader opens the gate only once the next fact's `StartSession` has cleared the host-call log. When nothing tore the overrun fact down, the stuck dispatch's notice therefore always lands in the next fact.

**RS1 filing.** M1 to M4, A1 to A4 and L2 change product code, so they are item 1. M5, M6 and L1 change the harness, and the harness is the leak pin's subject: the #564 leak lives only there, in `DispatchProbe`, `TearDown` and `DispatchBounded`, and the fix changed exactly that code. So they are item 1, the helper the pin exists for. If a grader files them as item 3, this is the argument it needs. No product-side change can make `DispatchProbe` skip its teardown or `TearDown` skip the observer. L2 is a product-side red for the second anchor, and no product change can stop a gated handler from overrunning. Each of the three reds its own site with its own message.

**Survived, and disclosed: M7.** M7 removes `TearDown`'s wait for an overrun dispatch: the join and the pool drain. The leak pin stays green in 5 of 5 runs. With the teardown in place, the gate opens at the start of `TearDown`. The dispatch's late notice then has to lose a race of a few microseconds against the rest of `TearDown` and the next fact's `StartSession`, and the pin cannot force that race. So the wait closes a real but narrow window, and no pin holds it.
