# Phase 16.4 record — The lost first tap

**Phase:** 16.4 · **Issue:** #438 · **Spec:** `docs/superpowers/specs/2026-09-28-phase-16.4-design.md`

This record holds the evidence for why `BnBiometricsTests.testAuthenticateBootDeniedIsDataWithinABoundedAwaitNoHang`
fails intermittently on the iOS simulator lane: the rates, the diagnostic log excerpts, the verdict on
each of the spec's hypotheses, and the root cause. The fix is Task 3 and is not recorded here.

## 1. The failure has two signatures, not one

The issue describes one failure, the in-flight poll at `BnBiometricsTests.swift:229-231`. The lane's
history shows two different assertions failing in the same test:

| Signature | Assertion | What the test saw |
|---|---|---|
| **S1** | `:231` "Authenticate never reached the evaluation" | the in-flight flag was not set within the 30 s poll |
| **S2** | `:237` "a cancelled auth never reached the echo" | the flag was seen, but the op never completed |

They have different root causes (section 5), and both are needed to explain the observed rate.

## 5. Hypotheses

### (a) A blocking hop to main from the render thread — **REFUTED**

- The begin path makes no synchronous hop to main. `AppleShellBridge.hostCallBegin` →
  `BnBiometrics.begin` → `authenticate` contains no `DispatchQueue.main` call. The only main hop on the
  path is `BnWidgetMapper.apply`'s `DispatchQueue.main.async` for the frame, and it is async.
- While the render thread sat inside `LAContext()`, main answered an async probe in 0.1–0.5 ms
  (every run) and in 1.2 ms from the watchdog one second into a 1.7 s `LAContext()` (run
  36383549035). Main was never busy: the test's poll loop logs any `RunLoop.run` iteration over
  250 ms, and none fired in any run.
- The "what changed in 16.1" question has a plain answer: nothing that matters here. The same test
  failed with the same S1 signature before M16 (run 36045241846, `9f965af`), and first taps of
  24–44 s passed before M16. Before #428 the same `LAContext()` ran on the dispatch lane, which is
  equally invisible to the test's poll.

### (b) A cold-boot ordering race — **CONFIRMED, in a different shape than the spec guessed**

Not "the flag is set and cleared before the poll sees it". The flag is set **before the test's reply
seam has been captured**, and the test uses the flag as its "safe to reply now" signal:

- `BnBiometrics.authenticate` sets `inFlightRequestId`, releases the lock, and only then calls
  `evaluatePolicyReplyOverrideForTest`, which is where the test's closure stores `pendingReply`.
- The test polls `hasInFlightRequestForTest()` on main, and on `true` calls
  `pendingReply?(false, LAError(.userCancel))`. `pendingReply` is a captured `var`, written on the
  render thread and read on main with no synchronisation.
- If main reads between the flag and the capture, `pendingReply` is still `nil`, the optional call
  does nothing, and nothing will ever complete the host call. The echo poll then times out: S2.
- Logged directly in run 36382752535: `inFlight=true replyCaptured=false` at t=513015.9, between
  `reply override INVOKE` (513015.2) and `RETURNED` (513016.1).
- The race is in the test seam's protocol, not in production: production has no reply seam, and
  `LAContext.evaluatePolicy` delivers its reply itself. The shape has existed since the test was
  written, in both the pre-M16 lane and the post-M16 render thread.

### (c) The tap lands somewhere else — **REFUTED**

The tap is `h=5 'click'`. It reaches `BnSecureDemo.AuthenticateAsync` (`AuthenticateAsync handler
ENTER`), which begins `op=Biometrics` (`op=2` on the Swift side), and the in-flight flag is set on the
test's own `runtime.bridge.biometrics`. This happened in all three runs and in both signatures. The
slow-handler line in both historical failures names the same handler.

## 6. Root cause

**S2 (confirmed by logs).** `BnBiometrics.authenticate` publishes the in-flight flag, which the boot
tests treat as "the reply seam is armed", before it invokes `evaluatePolicyReplyOverrideForTest`. So
main can see `true` while the test's `pendingReply` is still `nil`, and the test's reply becomes a
silent no-op that leaves the host call pending forever. It happens only when main's poll reads inside
that window. The diagnostic logging widened the window to about 1 ms, and in production code it is a
few instructions. That is why it is rare, and why it was caught on the first diagnostic run.

**S1 (strongly indicated, not captured over 30 s under logging).** The first `LAContext()` in the
process is a cold, synchronous cost of 0.5–1.7 s in the three runs logged, against 2.6–4.7 ms warm. It
runs on whatever thread calls `hostCallBegin`, and the flag is set only after it. The first boot test
is the first `LAContext()` in the process. In every logged cold sample, `LAContext()` was 95–99% of
the handler's synchronous part (525 of 531 ms, 909 of 956 ms, 1667 of 2039 ms). S1's failing run
logged a 33381 ms synchronous part, and the flag cannot be set until it ends, so the 30 s poll lost.
What was not captured is an `LAContext()` over 30 s with the watchdog running. The attribution of the
33 s to `LAContext()` rests on that proportion and on there being no other cold work on the path,
not on a direct log.

Neither cause is an M16 regression. Both were present before #428, and the pre-M16 failure and long
passes show it.

## 7. Notes for the fix (Task 3)

- **S2:** the test needs a completion-safe "armed" signal. It must be published only after the seam
  holds the reply, or else the reply must be read under the same synchronisation that published it.
  `testAuthenticateBootRoundTrips…` has the identical shape and the identical race.
- **S1:** the only way to bound the first tap is to get the cold `LAContext()` off the path the test
  waits on, and off the render thread in production, where it now blocks rendering for the cold
  duration. A timeout bump is excluded by the owner's no-workarounds rule, and would not bound a 30 s+
  cold call anyway. A deterministic pin can use a seam that blocks the context factory.
- **Android twin.** `AndroidShellBridge.runBiometricGate` has neither shape. Under test,
  `biometricGateHook` receives the gate directly, with nothing published before it. In production,
  the `BiometricPrompt` is built inside `activity.runOnUiThread`, asynchronously, so no platform
  object is constructed on the calling thread.
- **Unexplained in run 36354226421 (S2):** the test took 52.5 s, but the logged sync part (2.6 s)
  plus the 10 s echo poll account for about 13 s. That run had no diagnostics, so the other ~40 s cannot
  be attributed. It does not change the verdict: its failing assertion is S2's.
