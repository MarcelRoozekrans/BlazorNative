## 1. Does a prompt answer when its Activity is destroyed?

**VERDICT: can-be-lost**

On the lane's API 34 emulator every case answered, measured below. The answer is still not
guaranteed. androidx 1.1.0 hands the answer to the client through a `LiveData` observer that only
fires while the `BiometricFragment` is started. On API 34 the answer gets there in time only
because SystemUI's cancel reaches the app before the fragment's `ON_STOP`, and that is a
cross-process race. On API 24 to 28, inside our `minSdk = 24`, the cancel is *issued from*
`onStop`, so after a `finish()` it can never get there. Task 3 therefore takes the deny-on-destroy
branch, and it must skip a destroy that is a configuration change, see (a).

### How our prompt is wired

`runBiometricGate` (`AndroidShellBridge.kt:948`) builds one `BiometricPrompt` per request at
`:968`, with the `(FragmentActivity, Executor, AuthenticationCallback)` constructor. Its executor is
`ContextCompat.getMainExecutor(appContext)` (`:969`), and its callback is an anonymous object
that captures that request's `onAuthenticated` and `onDenied`. Nobody builds a second prompt for
the request, on recreation or otherwise.

### Source findings: androidx.biometric 1.1.0

Read from `biometric-1.1.0-sources.jar` (dl.google.com maven, sha256
`a34841717766cd97c36f708763ead26c79a9721129ffd87c57c99fea10a8f9e0`). The Gradle cache holds
only the AAR, with no sources.

- **The callback lives in the Activity-scoped ViewModel.** `BiometricPrompt.init`
  (`BiometricPrompt.java:899-913`) stores the executor and callback in `BiometricViewModel`
  (`setClientExecutor`/`setClientCallback`, `BiometricViewModel.java:273-287`), obtained from
  `new ViewModelProvider(activity)` (`BiometricPrompt.java:1025-1029`). Only the two **Fragment**
  constructors add `ResetCallbackObserver` (`:804`, `:886`), which clears the callback on
  `ON_DESTROY` (`:721-734`). Our FragmentActivity constructor (`:828-846`) adds none, so the callback
  is never reset on our path. `BiometricViewModel` has no `onCleared` override, so clearing it
  does not cancel the authentication either.
- **The prompt is a headless `BiometricFragment`** in the Activity's FragmentManager, added
  under tag `androidx.biometric.BiometricFragment` (`BiometricPrompt.java:218`, `:1067-1086`). It is
  destroyed with the Activity and restored on recreation. `MainActivity` passes
  `savedInstanceState` to `super.onCreate` (`MainActivity.kt:239`) and declares no
  `configChanges` in the manifest.
- **The answer path.** The framework callback is `AuthenticationCallbackProvider`, cached in the
  ViewModel. Its listener `CallbackListener` (`BiometricViewModel.java:64-116`) holds the ViewModel
  **weakly** and, if `isAwaitingResult()`, writes the result to a `LiveData`:
  `onSuccess` at `:78-90` and `onError` at `:93-101`. `updateValue` (`:646-651`) uses `setValue`
  on main and `postValue` elsewhere. The fragment observes those LiveDatas with **itself** as
  lifecycle owner in `connectViewModel` (`BiometricFragment.java:261`, result at `:269`, error at
  `:282`). Only then does `sendSuccessToClient` (`:896-910`) or `sendErrorToClient` (`:921-939`)
  post to `mViewModel.getClientExecutor()` and call `mViewModel.getClientCallback()`. A
  lifecycle-bound LiveData observer is active only while its owner is at least STARTED, and it is
  removed at DESTROYED. That is androidx.lifecycle semantics, not read in this jar. So an answer
  that lands after the fragment's `ON_STOP` waits for a restart. If the fragment is destroyed
  first, it is dropped.
- **onStop.** `BiometricFragment.onStop` (`:239-246`) cancels the authentication
  (`CANCELED_FROM_INTERNAL`) only below API 29, and only if the Activity is not changing
  configurations (`isChangingConfigurations`, `:1038-1041`). On API 29+ the fragment never cancels
  on its own.
- **No re-show.** `showPromptForAuthentication` is guarded by `isPromptShowing()` (`:412-425`), a
  ViewModel field that survives recreation. androidx never calls `authenticate` again on its own.
- **FingerprintDialogFragment** is used only below API 28, or for crypto on listed devices
  (`isUsingFingerprintDialog`, `BiometricFragment.java:995`). Its `onCancel` (`:240-243`) sets
  `fingerprintDialogCancelPending`, which the fragment's observer turns into a
  `CANCELED_FROM_USER` error. That observer is again bound to the fragment's lifecycle, so the same
  rule applies.

### Per case: which callback object receives the answer

| case | measured on API 34 (lane) | from source, API 24–28 | callback object |
|---|---|---|---|
| (a) configuration change, `recreate()` | the prompt **stays up** across the recreation, with no cancel within 10 s; the answer then arrives as `onAuthenticationSucceeded` | `onStop` skips the cancel while changing configurations (`:243`), so the prompt survives as on API 34 | **the original** per-request callback built at `:968`, held in the retained ViewModel and delivered through the **new** fragment instance |
| (b) `finish()` | `onAuthenticationError(10 = ERROR_CANCELED)` about 140 ms later: SystemUI's `AuthController` evicts the client on the task-stack change | the cancel is issued from `onStop` (`:239-246`), after the fragment's `ON_STOP`, so the error reaches an inactive observer that is then destroyed: **lost** | the original callback, when it arrives |
| (c) background, HOME | `onAuthenticationError(10)` about 40 ms later (`AuthController: Close BP, reason :homekey`) | cancelled in `onStop`; the error waits in the LiveData until the Activity restarts; if the Activity is destroyed first: **lost** | the original callback, when it arrives |

In (b) and (c) on API 34, the error reaches the client only because it arrives before the
fragment's `ON_STOP`. After `ON_STOP` the observer is inactive, as above. The emulator wins that
race by a wide margin: about 10 ms from SystemUI's dismissal to our callback. No API guarantees it,
and an OEM SystemUI that does not evict on a task-stack change would leave the prompt up past the
Activity's destruction. A later answer from that prompt then reaches a ViewModel with no observer
left.

**For Task 3:** case (a) is the one androidx keeps alive. The original callback still receives
the real answer after the recreation, so deny-on-destroy must not fire when
`isChangingConfigurations()` is true. In (b) and (c), API 34 usually delivers the real
`ERROR_CANCELED` first. The deny then finds nothing pending, or loses to that answer, and the
owner check in spec section 6 ignores whichever comes second.

### Deviations from the plan's test list, accepted by the controller

- **`completionNow(id)`, not `completionFor(id, 0)`.** `completionFor`'s loop is
  `while (now < deadline)`, so a zero timeout never looks and always returns null: every
  "has no completion" anchor written that way would be vacuous. `completionNow` reads the list once.
- **The denial pin has a "delete waits" anchor** before the deny. Without it the pin passes pre-fix,
  since the delete completes at once and still completes `OK` on the executor.
- **The throw pin is reshaped.** As planned, the throw happens in the same executor task as the
  take, so no request can park before the undo, and the pin passes pre-fix. Instead A holds the
  key, auth set B and the delete park, and the second gate call, B's when it is drained, throws.
  That covers spec §6's undo with a parked follower, and a drained head that throws.

### What the seam's after-auth work yields

The hook's `succeed()` passes no `AuthenticationResult`, so an auth set's encrypt runs on the
un-unlocked cipher. Each pin logs the status under tag `BN-18.3`. In the green run every
seam-granted after-auth task completed status 2, `AUTH_FAILED`, on `BlazorNative-SecureStorage`:
the auth set in `delete_waits`, `plain_set_waits` and both sets of `second_prompt`, and the
getWithAuth in `getWithAuth_delete`. So the release ran through afterAuth's catch path, which is
the subject, and the ordering and post-state assertions hold for that status.

The orphan-blob assertion in `a_same_key_delete_waits…`, `an orphan blob survived the delete`,
is therefore **partial**: the encrypt fails, no blob is ever written, and it cannot red under the
seam. It stays, named partial; Task 6 grades it.

For the same reason the plain-set pin's two `the late auth work overwrote the plain set` assertions,

## 6. Deviations and calls

- **Biometrics' `authenticate` prompt is not denied on destroy.** It holds no key, so a lost answer
  hangs only its own request, as before 18.3: no regression, and #506 is about held keys. Denying
  it would need a second pending registry on the biometrics executor and a change to its
  completion path, which completes from the prompt's own callback since 17.2. A gate that
  **starts** after the destroy is denied, biometrics included, through the shared gate check below.
  The in-flight case is a pre-existing gap outside #506, handed to the controller to file.
- **A late answer does no work.** The brief allowed the completer's benign rc 1 on a second
  completion. That is not enough for a late **success** on an auth set: its encrypt would write a
  blob after the delete parked behind the denial had run. So `afterAuth` runs its work only if it
  removes the request's pending entry; a later answer for the same request logs and does nothing.
  It still calls `releaseHold`, so the owner check stays the only guard against releasing another
  request's hold, and the "no owner check" mutation still reds
  `a_late_answer_does_not_release_another_requests_hold`. That pin's second answer no longer
  produces a second completion; its assertions are unchanged.
- **After the destroy, a gate denies at once.** The denial drains the parked requests. An auth
  request among them would otherwise reach a prompt on the destroyed Activity, where androidx drops
  it silently because the FragmentManager's state is saved, and hold its key forever: the very hang
  this task fixes. The bridge's Activity never comes back, since a new Activity builds a new bridge.
  So `hostActivityDestroyed` makes `runBiometricGate` deny, before the hook as well, because the
  hook stands in for the prompt. It is checked again on main, for a gate posted before the destroy
  that reaches main after it. The second pin covers the first check. The main-thread check also
  denies when the gate's own Activity is destroyed or finishing, by controller ruling; see the
  follow-up in §2.
- **Not pinned, with the reason:** `MainActivity.onDestroy`'s call to `onHostActivityDestroyed`,
  and `cancelAuthentication` on a real prompt. The destroy pins call the entry point directly with
  a hook-held gate. A real prompt needs a lock-screen credential typed into SystemUI, which only the
  Task 1 probe did, by hand-scripted `input text`. The test file's DOES NOT COVER list names both.
- **Review minor 2 is a literal, not the id.** `LogPrivacyDriftTests` allows `BnPrivacy.SAFE` only
  on a single string literal with no `$`, so the ignored-release warn cannot keep `$requestId`. It
  now reads `secure storage: ignored a release by a request that does not hold its key`, SAFE, and
  shows in logcat. The new ignored-answer warn follows the same rule.
