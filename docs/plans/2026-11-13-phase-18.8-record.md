**The identity.** `NtQueryInformationFile` `FileInternalInformation` on a duplicate of the
handle. Run 43464630350's calibration, a pipe from `CreatePipe` in the watcher:

```
idle read end: id=0x00000000000001FF end=server serverPid=2996 clientPid=2996 … status=ok
idle write end: id=0x00000000000001FF end=client serverPid=2996 clientPid=2996 … status=ok
read end with a pending read: timeout after 3000 ms
write end with a pending read: id=0x00000000000001FF end=client … writeQuota=0 … status=ok
```

Both ends report one id, so the id names the pipe, not the end. A read end with a pending
synchronous read cannot answer: the query waits on its file object. In a stall the reader's end
always has a read pending, so the watcher takes the id from the **write end** the reader handed
out: the stdout and stderr handles of the reader's child, read from the child's PEB while the
child lives. It keeps only a pipe whose `GetNamedPipeServerProcessId` is the reader, which is
a pipe the reader created. A holder is a process other than the reader that has a handle
with that id. The handle-table `Object` pointers are the cross-check: no file object reported two
ids in any run.

### Loop

Task 2 added `scripts/scratch-530/loop-530.ps1`, `iter-runner.ps1` and the job `experiment` in `scratch-530.yml`. The job needs `selftest`, mirrors `ci.yml` build-test from the toolchain steps through the Release build, and runs the loop with 20 iterations and 10 warm.

Each iteration's test step runs in a child `pwsh -File iter-runner.ps1`, started without redirection so it inherits the loop step's stdout and stderr, as `ci.yml`'s step does. The body is `ci.yml` line 2405 character for character, so `2>&1 | Tee-Object -FilePath $log` writes the iteration's log. The stripped arm's runner adds `--filter "FullyQualifiedName!~GeneratorRunTests"`. The watcher is rooted at that child. The loop waits 15 minutes for the child in the scratch run; the suite's own bound is 5 minutes, so a real stall shows inside it. On expiry the loop writes `outer-stall.txt`, stops the child and the descendants it can reach through parent links by PID, and counts the iteration as a stall. A holder whose parent chain has exited is not reachable that way: `outer-stall.txt` lists the watcher-tracked processes still alive from its `stall-<n>` tree.csv files, those directories are the full record, and the reset stops the holders by their recorded StartTime. The descendant walk ignores a parent link whose child predates its parent. A holder from `holders.csv` is stopped only when the process under that PID started at the StartTime that the same stall's `tree.csv` recorded.
