## §0 Harness

The harness lives only on scratch refs and is never merged into `feat/18.8-pipe-holder`.

**Files, on the scratch refs only:**

| File | Role |
|---|---|
| `scripts/scratch-530/watch-holder.ps1` | The watcher. Polls the process tree under `-RootPid`, fires on trigger A, a generator `pwsh` with no living child for 30 s, or trigger B, a descendant that outlives its generator `pwsh` by 30 s and shares a pipe with the `pwsh`'s parent. It matches holders by kernel pipe identity. Each firing writes `stall-<n>/` and a line in `stalls.csv`. |
| `scripts/scratch-530/plant-holder.ps1` | The planted holder for the self-test. `-Mode Parent` reads a native child's output; `-Mode Holder` is that child: it opens an inheritable handle to the pipe root, starts an inheriting silent sleeper, `pwsh -Command Start-Sleep`, and exits after `-HolderLingerSeconds`. Self-test run 1 used a `ping` sleeper. |
| `.github/workflows/scratch-530.yml` | Triggers on `push` to `scratch/530-**`, `windows-latest`. Job `selftest` here; Task 2 adds job `experiment`. |

### Self-test after the amendment: the planted holder named by kernel pipe identity

The owner amended D2 on 2026-11-13: match by the pipe's kernel identity. Runs on
`scratch/530-selftest` after the amendment, each `headSha` equal to the ref head at the time:

| Run | headSha | Result | What it showed |

| 43463883911 | `564ec4b434cf8fb4eb06ea8a50777b8c79809899` | failure | Calibration on a pipe of the watcher's own: both ends of a `CreatePipe` pipe report one id; a query on a read end with a pending read blocks. |
| 43464630350 | `7144ffd6c97da7041ce3912a7f0e54bf417b1b9b` | **success** | The sleeper named by the id of the parent's output pipe. |

`Handle.zip` SHA256 `279AAF8ECCB6F79147F4DCC6BA091FB895C4CB8B199A0DD186A4C76BC519D2CD`, Handle 5.0,
in every run.

**The identity.** `NtQueryInformationFile` `FileInternalInformation` on a duplicate of the
handle. Run 43464630350's calibration, a pipe from `CreatePipe` in the watcher:

```
idle read end: id=0x00000000000001FF end=server serverPid=2996 clientPid=2996 … status=ok
idle write end: id=0x00000000000001FF end=client serverPid=2996 clientPid=2996 … status=ok
read end with a pending read: timeout after 3000 ms
write end with a pending read: id=0x00000000000001FF end=client … writeQuota=0 … status=ok
```

Both ends report one id, so the id names the pipe, not the end. A read end with a pending
synchronous read cannot answer: the query waits on its file object. In a stall the reader's end
always has a read pending, so the watcher takes the id from the **write end** the reader handed
out: the stdout and stderr handles of the reader's child, read from the child's PEB while the
child lives. It keeps only a pipe whose `GetNamedPipeServerProcessId` is the reader, which is
a pipe the reader created. A holder is a process other than the reader that has a handle
with that id. The handle-table `Object` pointers are the cross-check: no file object reported two
ids in any run.

**The planted holder as named,** run 43464630350, trigger A on parent `pwsh` 1036, `stall-1`:

- The parent's read ends `0x6E8` and `0x858` timed out: they are its pending reads.
- `output-pipes.csv`: the holder `pwsh` 912's stdout handle `0x854`, client end, object
  `0xFFFFE78A1C48A9A0`, id `0x0000000000000200`, server pid 1036, the parent.
- `holders.csv` line for the sleeper, `MatchedBy` `OutputPipeId`:

```
"0x0000000000000200","7992","""C:\Program Files\PowerShell\7\pwsh.EXE"" -NoProfile -Command ""Start-Sleep -Seconds 600""","912","pwsh.exe","descendant","0x854","0xFFFFE78A1C48A9A0","client","OutputPipeId","True"
```

- `tree.csv` chain: `7992 pwsh.exe <- 912 pwsh.exe, dead <- 1036 pwsh.exe`.
- `env-7992.txt`, read from the sleeper's PEB, holds `BN530_PLANTED=planted-by-selftest`, set
  by the job above the parent, and `MSBUILDDISABLENODEREUSE` is absent.
- Trigger B fired once for the holder `pwsh` 912, 30 s after it exited, and named the same
  sleeper by the same id.

`holders.csv` also lists the sleeper's other matches with `OutputPipe` `False`: pipe handles
it inherited from the parent through the holder, matched by id or object. They are not the
output pipe, and the record reads only `OutputPipe` `True` rows as the holder.

### Fix round 1: the root, short-lived children and abandoned queries

The task review found three gaps, all fixed on `scratch/530-selftest`:

- **The pipe root matched everything.** `\Device\NamedPipe\` answers id `0x0` with no pipe
  end, and every `pwsh` holds it. Now only rows with a pipe end and a non-zero id take part.
- **A holder whose native child was never seen alive went unnamed.** A second rule now needs no
  probe of the child, `CreatedByAnchor`: a client end of a pipe that `GetNamedPipeServerProcessId`
  says the reader created, with an id that none of the reader's answering handles has. Every
  process in the handle scan is a candidate, tracked or not.
- **An abandoned query kept its duplicate open,** so the watcher itself could hold a pipe end.
  Now the duplicate is closed on abandonment, and each later call checks first.

Run 43467609868, headSha `2043791cee2960242cbc86ae3bcb3a69fb1a94b6`, **success**, two variants:

| Variant | Sleeper named by | Tracked | Pipe id |
|---|---|---|---|
| linger 10, the holder `pwsh` seen and probed | `OutputPipeId+CreatedByAnchor`, triggers A and B | True | `0x00000000000001F9` |
| linger 0, the holder `pwsh` never seen | `CreatedByAnchor`, trigger A | False | `0x0000000000000201` |

In both, the sleeper's planted root handle answered id `0x0` and matched nothing. Each
`trigger.txt` reports `object cross-check conflicts: 0`. The calibration shows an abandoned
query on a pending read, with its duplicate closed, and the read still completing:

```

after the abandoned query: write True, pending read completed True, bytes read 1
```

**Fix round 2,** run 43468790484, headSha `0d15792c92114c2266c4c31a73b39fb1c6d59660`,

the running count, 15 after the first firing and 30 after the second.

### Loop

Task 2 added `scripts/scratch-530/loop-530.ps1`, `iter-runner.ps1` and the job `experiment` in `scratch-530.yml`. The job needs `selftest`, mirrors `ci.yml` build-test from the toolchain steps through the Release build, and runs the loop with 20 iterations and 10 warm.

Each iteration's test step runs in a child `pwsh -File iter-runner.ps1`, started without redirection so it inherits the loop step's stdout and stderr, as `ci.yml`'s step does. The body is `ci.yml` line 2405 character for character, so `2>&1 | Tee-Object -FilePath $log` writes the iteration's log. The stripped arm's runner adds `--filter "FullyQualifiedName!~GeneratorRunTests"`. The watcher is rooted at that child. The loop waits 15 minutes for the child in the scratch run; the suite's own bound is 5 minutes, so a real stall shows inside it. On expiry the loop writes `outer-stall.txt`, stops the child and the descendants it can reach through parent links by PID, and counts the iteration as a stall. A holder whose parent chain has exited is not reachable that way: `outer-stall.txt` lists the watcher-tracked processes still alive from its `stall-<n>` tree.csv files, those directories are the full record, and the reset stops the holders by their recorded StartTime. The descendant walk ignores a parent link whose child predates its parent. A holder from `holders.csv` is stopped only when the process under that PID started at the StartTime that the same stall's `tree.csv` recorded.
