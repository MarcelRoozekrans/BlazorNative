### F1: `:811`

`:811` is a conjunction, `ChildThrowSeq > SiblingBeginSeq && SiblingBeginSeq > 0`. It has two halves:
- **the order half:** the begin came before the fault;
- **the throw-reached half:** the sibling threw at all.

This fact has no separate throw-reached anchor, while its mirror has one, at `:782`. So `:811` is the
only check that the throw happened. RS1 grades the site, not one half of it.

**The site's red is X1, a subject red.** The renderer refuses to create a component after the running
synchronous part has begun a shell call. `BeginOnInitChild` still begins its call, so `:809` passes.
`ThrowAfterSiblingBeganChild` is never created, so `ChildThrowSeq` stays 0, and `:811` reds with its
own message. The first pass missed X1, and the review found it. It is a synthesized bug shape, of the
same kind as B6 and B7.

**What the subject can and cannot do on this path.** Only fixture code writes the two counters: the
first line of `BeginOnInitChild.OnInitialized`, `:1357`, and of
`ThrowAfterSiblingBeganChild.OnInitialized`, `:1345`. Blazor's diff calls each child's
`OnInitialized` in the order of the parent's render tree, which is the fixture's `BuildRenderTree`,
`:1298` and `:1300`. Blazor is not the subject. The subject runs at three points on this path:
- **`NativeRenderer.CreateComponentState`, `:1823`,** runs for each child before Blazor sets its
  parameters.
  - **It can stop a stamp.** It can refuse to create a child, so that child's stamp is never
    written. Refusing the second child is X1, which reds `:811`. Refusing the first child stops the
    begin, which reds `:809` first.
  - **It cannot reverse the order.** The second child does not exist yet when the first child's
    `OnInitialized` runs.
- **`NativeShellBridge`'s begin and `NativeRenderer.NoteShellCallBegun`, `:1635`,** run after
  `SiblingBeginSeq` is stamped.
  - **They can stop the call.** That is B1, which reds `:809` first.
  - **They cannot move either stamp.**
- **`NativeRenderer.HandleException`, `:606`,** runs after `ChildThrowSeq` is stamped, so it can
  change neither.

So a subject mutation can stop a stamp from being written, and X1 does so at `:811`. It cannot
reverse the order. The order half alone has no subject red, and the review agreed with that.

**The order half, corroborated by B4.** These attempts kept both stamps and left the order intact.
Each was one mutation, run with the filter `FaultNoticeTests.AChildsBegunCall`, except B1:
- **B1, the bridge begins nothing.** This reds `:809` first: the begin anchor fails and `:811` is
  never reached.
- **The mark is a no-op,** `NativeRenderer.cs:1642`: `scope.ShellCallBegun = true;` → `{ }`. `:809`
  and `:811` pass. The fact reds at `:814`: `rc was 2: the child's begun call marks the dispatch, so
  the later render fault is a FaultNotice with rc 0, not the dispatch's rc 2.`
- **The window captures no fault,** `NativeRenderer.cs:636`: `scope.Fault ??= exception;` →
  `_ = exception;`. `:809` and `:811` pass. The fact reds at `:816`: `no FaultNotice for the render
  fault after the begun call.`

B4 swaps the fixture's two children. The begin still happens, so `:809` passes, and `:811` reds
with its own message, naming both stamps in the reverse order. A subject red exists for the site, so
under RS1 B4 is corroboration and counts for nothing. It is kept because it is the only run that
enters the order half.

**The order half is not vacuous.** The same swap, with `:811`-`:813` commented out, reds at `:814`
instead: `rc was 2: the child's begun call marks the dispatch, …`. That message blames the product's
mark, but the mark is correct: the fault simply came first, which
`AFaultBeforeASiblingBeginsAShellCall_…` pins as rc 2. So without `:811`, a fixture that drifted into
the other order would report a product bug that does not exist. `:811` is what names the real cause.
This contrast deleted an assertion in scratch, so it is not a red. It only shows that the order half
is load-bearing.

The design's example for `:702` was to make the fallback key by the tree owner instead of the call
site. It was run first: `NativeRenderer.cs:1767-1768`, the framework branch's

two framework methods attached at one call site. So this mutation is equivalent for every input the
class builds, and it is not a red. B8 changes the owner that the line names, and that reds `:702`.
