### Pins, on `perf/v0.15.0-marks` only

1. `1970ffdb`: five csproj files declared `Microsoft.AspNetCore.Components` and `Microsoft.AspNetCore.Components.Web` at the floating `10.0.1*`. That now resolves to 10.0.15, while `Microsoft.Extensions.DependencyInjection` is pinned to 10.0.12 in Runtime, which raises NU1605 as an error (package downgrade). Fix: replace `10.0.1*` with `10.0.12` in the SampleApp, Runtime.Tests, Components, Renderer and template csproj files. This hides nothing. The published BlazorNative.Renderer 0.15.0 nuspec on nuget.org lists Microsoft.AspNetCore.Components and Microsoft.AspNetCore.Components.Web at exactly 10.0.12, so the pin restores the shipped version.
2. `d8a24b17`: `src/BlazorNative.Apple/project.yml` declared Kingfisher as `from: 8.12.0`, which now resolves to 8.16.0. That version has a minimum deployment target of iOS 15, while the shell targets iOS 13, so `BnImageLoader.swift:80` failed to compile. Fix: `exactVersion: 8.12.0`. The tag had no lock file, so 8.12.0 is the declared floor. The 8.x that v0.15.0 actually built against is unknown, and any later 8.x it used was still iOS 13 compatible.

Neither pin touches the 19.2 branch. The `perf/v0.15.0-marks` branch has no PR and must not be merged.

### Launch paths at v0.15.0

Android (`src/BlazorNative.Jni/src/androidMain/kotlin/io/blazornative/shell/MainActivity.kt`):

- `EXTRA_COMPONENT = "io.blazornative.shell.EXTRA_COMPONENT"` is declared at line 73 and read at line 322 with `intent.getStringExtra(EXTRA_COMPONENT)`. It wins over a deep-link route, which wins over `routes["/"]`, which wins over the fallback `"BnDemo"`.
- The string is passed to `runtime.start(componentName = ...)`, then to the `blazornative_mount` export, then to `HostSession.TryMount(name)` in `src/BlazorNative.Runtime/HostSession.cs:210`. That method looks the name up in the component registry, which is derived from `PageManifest` (the pages the app registers with `RegisterPages`). An unknown name returns rc 1.
- So any registered page is launchable by name, and `PerfProbe` needs no route entry in `MainActivity.kt`. It only has to be registered as a page. The generated `res/raw/blazornative_routes.json` (loaded by `loadDeepLinkRoutes`, line 659) is only for route-based deep links, so a probe launched by `EXTRA_COMPONENT` does not need a route there.
- Log level: `EXTRA_LOG_LEVEL = "io.blazornative.shell.EXTRA_LOG_LEVEL"` exists (line 96), read at line 702. It outranks the manifest meta-data `io.blazornative.logLevel` (line 120). Values are `BnLogLevel` names.

iOS (`src/BlazorNative.Apple/BnHost/`):

- `BnDeepLink.swift:43` defines `BnDeepLink`; the scheme is `blazornative` (line 54). A cold launch stashes the route, and `HostViewController.swift` resolves the launch component at :183-185 as `BnDeepLink.shared.resolvedLaunchComponent() ?? runtime.bridge.notifications.resolvedLaunchComponent() ?? "BnDemo"`.
- `resolvedLaunchComponent()` (`BnDeepLink.swift:139`) looks the route up in a fixed, hand-written map, `static let routeComponents` (line 64, entries at :65-66), which at the tag holds only `/notifications` and `/geolocation`. An unmapped route falls back to `BnDemo`.
- So `PerfProbe` does need an entry on the branch: either `"/perfprobe": "PerfProbe"` in `routeComponents`, or a different launch route into `runtime.start(component:)`. The `.NET` side mounts by registered name just as on Android.
- Log level: the `BN_LOG_LEVEL` environment variable (`BnRuntime.swift:385`, `resolveLogLevel`), for example `xcrun simctl launch --console --env`; it outranks the Info.plist string `io.blazornative.logLevel`. There is no `EXTRA_LOG_LEVEL` analogue on iOS beyond that.
