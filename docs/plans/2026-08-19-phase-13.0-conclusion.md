# Phase 13.0 — Extract the item surface: conclusion

**Branch:** `refactor/13.0-item-surface` · **Closed:** 2026-08-19
**Verdict:** COMPLETE. Source-compatible, binary-breaking. Release gate green.

---

## 1. What the phase did

Seventeen layout parameters were copy-pasted across eight components and **absent
from four more**. A `BnText` could not take a margin; a `BnButton` could take
nothing at all. There was no mechanism that would ever have raised the question —
the surface was a convention, and conventions do not red.

After 13.0 the item surface is declared **exactly once**, on `BnLayoutItem`:

| | |
|---|---|
| **Item surface (17)** on `BnLayoutItem` | `BackgroundColor`, `Margin`, `AlignSelf`, `Grow`, `Shrink`, `Basis`, `Width`, `Height`, `MinWidth`, `MaxWidth`, `MinHeight`, `MaxHeight`, `Position`, `Top`, `Right`, `Bottom`, `Left` |
| **Container surface (5)** on `BnLayoutContainer : BnLayoutItem` | `Padding`, `Justify`, `Align`, `Wrap`, `Gap` |

Eleven concrete components now derive from one of the two bases
(`BnActivityIndicator`, `BnButton`, `BnCheckbox`, `BnImage`, `BnInput`,
`BnPicker`, `BnScroll`, `BnSlider`, `BnSwitch`, `BnText` from `BnLayoutItem`;
`BnView` from `BnLayoutContainer`, with `BnFlexPreset` — and through it `BnRow`
and `BnColumn` — abstract over it).

Four of them **never had the surface before** and were granted it here: `BnText`,
`BnButton`, `BnInput`, `BnActivityIndicator` (pinned by
`LayoutSurfacePinTests.NewlyGranted_HasTheFullItemSurface`).

**Lengths are unchanged.** Every length is still a string in the shells' grammar.
Typing them is Phase 13.1 and is deliberately not here — see §4, the `BnList`
allowlist entry, which is the collision 13.1 has to reconcile.

## 2. The TWO emission mechanisms, and why one would not have sufficed

`@inherits` de-duplicates the **declarations**. It does nothing about the
**emission** — the seventeen `AddAttribute` calls that put the values on the wire.
Those needed a shared helper too, and there is no single helper that both kinds of
component can call.

### Mechanism A — `EmitItemAttributes(RenderTreeBuilder b)`, sequence 1–17

Used by every **hand-written** emitter: `BnActivityIndicator`, `BnButton`,
`BnImage`, `BnInput`, `BnScroll`, `BnText`, `BnView`. These own their
`BuildRenderTree`, so they can call a protected method at a known point and it can
assign exact sequence numbers. The bands are normative — item 1–17, container
50–99, the component's own attributes 100+, `ChildContent` 200 — because a
sequence collision **does not throw**; it produces a wrong diff, silently.
`LayoutSurfaceSequenceBandTests` (13 tests) is the pin.

Wrappers that render another `BnLayoutItem` rather than an element use the
component-parameter twin, `ForwardItemParameters` / `ForwardContainerParameters`
(`BnFlexPreset`).

### Mechanism B — `@attributes="ItemAttributes"`, one shared sequence number

Used by the four `.razor` controls: `BnCheckbox`, `BnPicker`, `BnSlider`,
`BnSwitch`.

**A single mechanism was not available, and the reason is structural, not stylistic.**
A component written as markup does not own its `BuildRenderTree` — the Razor
compiler generates it and assigns *every* sequence number. There is no point in
that generated method at which `EmitItemAttributes(b)` could be invoked. The
helper is literally unreachable from a `.razor` file. The first draft of the plan
said "replace the attribute block with the helper" for these four; it would not
have compiled, and reading `BnCheckbox.razor` is what surfaced it.

So the four splat a dictionary instead. All seventeen attributes then share **one**
sequence number rather than spanning 1–17. That is still correct, and not by luck:
repeated sequence numbers inside a run of attributes make the diff match **by name**
instead of by position, so a value that changes updates and a value that goes null
still emits its reset. `BnFormControlTests`' four
`*_DroppingAnItemAttribute_EmitsExactlyItsReset` tests exist precisely to pin that
removal path, which a "does it render?" test never reaches.

**The mechanism was chosen by measurement, not preference.** The splat costs a
`Dictionary` allocation per render, which is why the numbered form remains the
default wherever it is reachable. The splat is the exception the `.razor` shape
forces, and it is the one documented exception in the sequence-band pin.

### The trap worth carrying forward: the element path and the component path treat null oppositely

- `ItemAttributes` and `EmitItemAttributes` target an **element**. Null means
  *absent*: `ItemAttributes` filters nulls out of the dictionary, and
  `AddAttribute(int, string, object?)` refuses to append a null-valued attribute
  anyway.
- `ForwardItemParameters` targets a **component**. Null is **passed through** as a
  real parameter value, because that is what "the author did not set it" has to
  mean when the receiving component will apply its own default.

Both spellings mean "unset" and they are implemented oppositely. The filter in
`ItemAttributes` is therefore **defensive, not load-bearing, and that was measured
rather than assumed**: deleting it changes no frame today and the whole suite
stays green (mutation-tested). It is kept because the "null is not appended" rule
is *element-only* — splat the same dictionary onto a component and a null would
land as a real parameter and overwrite a default. Filtering at the source makes
the dictionary mean "the attributes the author set" at both destinations instead
of only one.

A second, quieter asymmetry between the two: `EmitItemAttributes` writes the
**wire string** (`AlignSelf.ToStyleValue()`, `"alignSelf"`), while
`ForwardItemParameters` forwards the **typed CLR value** under the C# property
name (`nameof(AlignSelf)`, the `FlexAlign?` itself) — because the receiver is a
component that will do its own conversion. Those forwarded names are matched as
strings at runtime by `AddComponentParameter`, so a rename that updated the
declaration and missed a forward would fail at runtime, not at compile time.
`nameof` plus `ForwardedParameterNameTests` is what closes that.

There is no `ItemParameterSplat`. The plan proposed one; the forwarding path
needed a `RenderTreeBuilder` method rather than a dictionary, and
`ForwardItemParameters` is what shipped.

## 3. Frames did not move, and that is the phase's core claim

Granting the surface to a component that never had it **cannot** move a frame,
because a null item attribute is not appended to an element at all. "Unset"
reaches the wire as "absent". The shell frame tables
(`BnDemoFrameTables.swift`, `BnLayoutDemoAndroidTest.kt`, and the
`ShellFrameTableDriftTests` that mirror them) are byte-identical across the phase
and were not edited.

No Kotlin, no Swift, and no `src/wire-vocabulary.json` changed. The wire
vocabulary is unchanged: the same seventeen style names, in the same grammar.

The style multiset was pinned **before** any component moved
(`PatchEquivalenceTests.ItemSurface_EmitsEveryParameter_AsAStableMultiset`, written
in Task 1 against a probe page that sets all seventeen), so it captures truth
rather than the refactor's own output. Measured before and after:

```
17 (nodeId, property) -> value pairs, identical:
  backgroundColor=#ff0000  margin=8       alignSelf=center  flexGrow=1
  flexShrink=0             flexBasis=50%  width=100         height=200
  minWidth=10              maxWidth=300   minHeight=20      maxHeight=400
  position=absolute        top=1          right=2           bottom=3   left=4
```

Order within the frame is not asserted, and deliberately: the refactor renumbers
sequences, and Yoga does not care what order styles arrive in. But "unaffected"
had to be measured rather than asserted, which is what the multiset projection is.

## 4. The allowlist: two entries, both discovered while migrating

`LayoutSurfacePinTests.AllowedNonLayoutComponents` is an **exception ledger**, not
a suppression list. Every entry carries its reason in writing, so the day a
thirteenth component is added, a false-by-omission surface has to be *argued*.
That is exactly how `BnText` went months with three parameters: nothing forced
the question.

The plan guessed **three** exceptions. Two survived contact.

### `BnList<TItem>` — a type collision Blazor throws on

Its `[Parameter, EditorRequired] float Height` is required to be a number (the
virtualization window arithmetic needs one), while `BnLayoutItem.Height` is the
`string?` length grammar. Same name, two types.

This is not a style objection — it is a **runtime throw**. Blazor's
`ComponentProperties.CreateWriters` collects base *and* new-shadowed properties
(only `override` pairs dedupe) and throws `InvalidOperationException` — *"declares
more than one parameter matching the name 'height'"* — on the first render of a
type that tried it. Pinned by
`BnList_CannotTakeTheItemBase_BecauseItsHeightIsNarrowedToFloat`, with
`BnList_KeepsExactlyTheTwoItemNamesTheCollisionStrandsThere` guarding the two item
names the collision strands there.

Renaming or retyping either `Height` was forbidden this phase. **Reconciling the
collision is Phase 13.1's job** — that is the phase that types the lengths, and it
is the natural place for it.

### `BnModal` — the node accepts no styles at any layer

The modal node cannot carry layout styles at all. Both shells **diagnose and
ignore** every `SetStyle` on it (Android `WidgetMapper.kt`'s `"modal"` arm; iOS
`BnWidgetMapper.swift`'s equivalent guard), and `"modal"` is deliberately absent
from `measuredNodeTypes` on both sides. Its wire node is a 0-sized, shell-fixed
anchor that no author-set style can reach a pixel through.

Inheriting the surface would advertise sixteen parameters that compile, offer
IntelliSense, and silently do nothing at every layer — **the exact
accepted-then-silently-dropped defect class this phase exists to eliminate**.
Pinned by `BnModalTests.MountedWithFullDeclaredSurfaceSet_ModalNodeStillCarriesZeroStyles`
and `BnModal_DoesNotTakeTheItemSurface_TheModalNodeAcceptsNoStyles`.

`BnModal` was granted the surface in commit `1413cc9` and then **removed from it**
in `5286bb2` — the migration is what found the shell guards.

### The third guess that was wrong: `BnActivityIndicator`

The plan expected `BnActivityIndicator` to be a fixed-size shell primitive and
therefore a third exception. It was investigated (Task 8 Step 1) and **it is not
one**: it is a **measured Yoga leaf**, exactly like `image` / `checkbox` /
`switch` / `slider` / `picker`. Both shells' widget mappers put
`activityindicator` in the *same* unified node-creation path as every other
widget, with a measure function attached **by node type** and no special-cased
fixed size outside Yoga. So it correctly gained the surface.

Its intrinsic size is unchanged: leave `Width`/`Height` null and it measures
itself as before; set them and the box is definite — the same declared-vs-intrinsic
choice `BnImage` documents. It still has **no control parameters**, which remains
the design (decision 5: "no props, no new wire surface"), and the reflective
no-control-parameters pin still guards that. The only rename in the phase is on
this component: `DeclaresNoParameters_TheSurfaceIsPresenceItself` →
`DeclaresNoOwnParameters_ButInheritsTheFullItemSurface`.

## 5. Consumer migration note

> **Source-compatible, binary-breaking. Recompile against the next release. No
> source edits are required** (one narrow doc-comment caveat below).

Every parameter a consumer could bind before, they can bind now, by the same name
and with the same type. Nothing was removed from the *surface*; 146 property
declarations moved from eight component types onto two shared bases. That is
invisible to C# source and to Razor markup: `<BnView Margin="8" />` binds
identically before and after.

It is **binary**-breaking because a compiled assembly references
`BnView.set_Margin` on `BnView`, and that member now lives on
`BnLayoutContainer`. An app that links an old binary against the new package gets
a `MissingMethodException`, not a compile error. The remedy is a recompile and
nothing else.

**Evidence:** not one *binding* changed anywhere in the repo.
`samples/BlazorNative.SampleApp`, the project template and `samples/ConsumerSmoke`
all use the surface heavily, and **no markup and no C# that sets a parameter was
edited**. ConsumerSmoke is the load-bearing case: it builds and runs against the
packed `.nupkg`s rather than project references, so it is a real consumer, and its
green run is what the claim rests on.

### The one exception, and it is worth stating precisely

Exactly one file in the repo needed an edit, and it is **not** a usage:

```diff
- /// <inheritdoc cref="BnView.Padding"/>
+ /// <inheritdoc cref="BlazorNative.Components.BnLayoutContainer.Padding"/>
```

(`samples/BlazorNative.SampleApp/BnThemedPanel.razor`.)

`Padding` is still bindable on `BnView` and still means the same thing — but it is
no longer **declared** there, so a `cref` naming `BnView.Padding` no longer
resolves. That is `CS1574`, which this repo escalates to an error.

So the honest migration note has a footnote: **a consumer whose own XML docs point
a `cref` or `<inheritdoc>` at one of the 22 names on its OLD declaring type will
get a CS1574**, and only then. Retarget the `cref` at `BnLayoutItem` or
`BnLayoutContainer`. This affects doc comments only — never a binding, never a
call, never markup — and only projects that treat CS1574 as an error. The
BlazorNative-shaped app that does not document its own wrappers with crefs into
the component library, which is nearly all of them, needs nothing.

Four components gain parameters they never had (`BnText`, `BnButton`, `BnInput`,
`BnActivityIndicator`). That is purely additive: unset parameters emit nothing.

`BnList<TItem>` keeps its `float Height` unchanged; consumers of it see no
difference at all.

## 7. Closing verification

| Check | Result |
|---|---|
| API baseline review (`PublicAPI.Unshipped.txt` vs `main`) | **CLEAN** — 292 `*REMOVED*` lines = 146 properties × 2 accessors, across 8 types; every one matched name-and-type by a base declaration; zero names outside the 17 item + 5 container lists; no type, method or field removed. Entries left **unshipped** (they promote at release, not here). |
| `dotnet test BlazorNative.sln -c Release` | 993 passed / 0 skipped / 0 failed |
| `cd website && npm run build` | **green**, with `onBrokenAnchors: 'throw'` enforced |
| `pwsh scripts/consumer-smoke.ps1` | **PASS** — eight packages packed warning-free at 0.10.0, purity clean, mount + `RegisterPages` from packages alone |

One real defect the anchor check caught, fixed here: the class-level `<remarks>`
on `BnLayoutItem` used `<see cref>` for `EmitItemAttributes` and `ItemAttributes`.
Both are **protected**, and the reference generator runs xmldoc2md with
`--member-accessibility-level public` on purpose (the `protected` default would
document `ComponentBase`'s web-hosting members on every page of a framework that
renders to native widgets). No heading is emitted for them, so the crefs rendered
as links to anchors that do not exist and `npm run build` failed. They are now
`<c>`, with a header comment on the file explaining why restoring the crefs reds
the *site* build and nothing local will tell you.

The anti-vacuity floor in `ComponentReferenceDriftTests.EveryParameter_CarriesADocComment`
was re-measured and rebased: the real `DeclaredOnly` `[Parameter]` count is now
**74** (it was 196 before the consolidation, and the floor had been loosened to
`> 50` mid-phase as a placeholder). It is now `> 60` — just under the measurement,
so a collapse still reds.

## 8. What 13.0 deliberately did not do

- **Type the lengths.** Every length is still `string?`. That is Phase 13.1, and
  it is the phase that must also resolve the `BnList.Height` collision.
- **Ship the baseline.** `PublicAPI.Unshipped.txt` stays unshipped; promotion to
  `PublicAPI.Shipped.txt` happens at release.
- **Touch the shells.** No `.kt`, `.swift`, `.mm`, or `wire-vocabulary.json`.
